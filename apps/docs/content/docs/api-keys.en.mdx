---
title: "API key"
description: The kinds of API key and their scopes, and how to issue and revoke them with a web login
---

An API key is a Bearer token for calling the `/v1` session API. Send it with every request as `Authorization: Bearer <key>`. What a key can do is decided by its scope. Management APIs such as agents, members, and keys cannot be called with a key (403); they are called only with the web login cookie.

## scope

| scope | What it does |
| --- | --- |
| `sessions:read` | Read sessions, turns, events, usage, and receipts |
| `sessions:write` | Create sessions, send messages, and request pushes |
| `sessions:control` | interrupt, pause, resume, close, terminate, and change the profile |
| `sessions:approve` | Answer permission requests and questions, approve or reject push requests, open PRs and comment on them |
| `sessions:recover` | Recovery decisions. Not included in `write` or `control` |

A request without the scope gets 403 `FORBIDDEN` before the body is read. Issue `sessions:approve` only to people.

## Kinds

| Kind | Issued by | How it behaves |
| --- | --- | --- |
| Personal key (`personal`) | Any member, their own only | Acts as the person who created it. Its scopes are the intersection of the key's scopes and the scopes that person's current role allows. If that person is deactivated, 401 |
| Agent key (`agent` + `agent_id`) | owner, admin, and that agent's administrator | Acts as the key itself, not as a person. Creates and sees only sessions created from that agent's release. It keeps working after the person who issued it leaves. It cannot have `sessions:approve`, so it cannot approve requests or answer questions |

There is no key without an agent, that is, no key that reaches the whole workspace. Sending `kind: "agent"` without `agent_id` gets 400 `BAD_REQUEST`.

A key can carry a `name` (1 to 64 characters after trimming, not required) so you can tell it apart in the list. Without one it is `null`.

Organization admin keys, owned by the organization and tied to no person (for automation such as Terraform, CI or SCIM), do not exist yet. The web console's API key screen shows their place as "Coming soon", to owners and admins only.

## Issue a key

Issue it in the web console, or call `POST /v1/api-keys` with the web login cookie. The example below uses the `WEB` header from [Create](/agents/create#log-in). The secret (`secret`) appears only once, in this response. Keep it in a variable and do not print it.

```bash
issued=$(curl -sS "$API/v1/api-keys" "${WEB[@]}" \
  -d '{"kind": "personal", "name": "laptop", "scopes": ["sessions:read", "sessions:write"]}')
MY_KEY=$(echo "$issued" | jq -r .secret)
KEY_ID=$(echo "$issued" | jq -r .key.id)
echo "$issued" | jq '{kind: .key.kind, name: .key.name, scopes: .key.scopes, receipt: (.receipt_id != null)}'
curl -sS -w '\n' "$API/v1" -H "Authorization: Bearer $MY_KEY"
```

```text
{
  "kind": "personal",
  "name": "laptop",
  "scopes": [
    "sessions:read",
    "sessions:write"
  ],
  "receipt": true
}
{"status":"ok","owner_id":"…"}
```

Requesting a scope beyond the issuer's own scopes returns 403 `SCOPE_NOT_GRANTABLE`.

## List and revoke

The list shows only your own personal keys and the keys of the agents you manage. Secrets are not shown.

`last_used_at` is when the key last authenticated a request. It is recorded at most once a minute per key, and a use made while another request is writing a session with the same key is skipped and recorded on the next use, so it can lag by more than a minute. `null` means no use has been recorded since last-use recording began, not that the key was never used. `created_by_user` is the issuer's id and current display name. The name stays after the issuer leaves the workspace or their account is disabled. It is `null` on a key with no recorded issuer (one made with the operator CLI).

```bash
curl -sS "$API/v1/api-keys" "${WEB[@]}" | jq -c --arg id "$KEY_ID" '.items[] | select(.id == $id) | {kind, name, scopes, revoked_at, used: (.last_used_at != null), issuer: .created_by_user.display_name}'
curl -sS -X DELETE "$API/v1/api-keys/$KEY_ID" "${WEB[@]}" | jq '{receipt: (.receipt_id != null)}'
curl -sS -o /dev/null -w '%{http_code}\n' "$API/v1" -H "Authorization: Bearer $MY_KEY"
```

```text
{"kind":"personal","name":"laptop","scopes":["sessions:read","sessions:write"],"revoked_at":null,"used":true,"issuer":"…"}
{
  "receipt": true
}
401
```

A revoked key gets 401 from the next request. Revoking a key that is already revoked changes nothing and returns `receipt_id: null`.

## Operator CLI

An operator can issue a key directly on the server. On the local stack it is `scripts/local.sh key` ([Quickstart](/getting-started/quickstart#get-an-api-key)). This path does not go through the permission checks above.

```sh
scripts/local.sh key <owner> --scopes sessions:read,sessions:write
scripts/local.sh key --workspace <workspace-id> --personal <user-id> --scopes sessions:read,sessions:write
```

A key made for `<owner>` uses that name as its owner. `--workspace` goes only with `--personal`: the key is that member's personal key and acts as them. `--workspace` without `--personal`, or a workspace id in place of `<owner>`, is refused. No key reaches the whole workspace. Issue agent keys in the web console or with `POST /v1/api-keys`.
