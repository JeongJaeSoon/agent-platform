---
title: "Kubernetes の設置"
description: 公開された Helm chart で Kubernetes に Werft を設置し、/readyz 200 まで確認する
---

公開された Helm chart で Kubernetes に Werft を設置します。リポジトリの checkout は不要で、chart 1つに3つのイメージの digest と worker runtime が入っています。このページだけに従えば、`/readyz` が 200 を返すところまで進めます。Linux サーバー1台に Docker Compose で設置する場合は [単一サーバーの設置](/run-server/self-hosting/single-server) を読んでください。

<Callout type="warn">
最初のリリース `v0.1.0` が公開され、chart `0.1.0`(appVersion `v0.1.0`)も一緒に公開されました。リリースを設置するには `VERSION` を `0.1.0` にします(chart のバージョンは `v` を除いたタグです)。`VERSION` だけを変えれば下のコマンドは同じです。ただし kind で最初から最後まで確認したのは、`v0.1.0` と同じ commit の chart `0.1.0-main-<12>` で、chart `0.1.0` でこの手順を実行してはいません。`0.1.0-main-<12>` はリリースではありません。
</Callout>

## 必要なもの

| 項目 | 要件 |
| --- | --- |
| クラスター | Kubernetes。NetworkPolicy を強制する CNI が必要。強制しないと worker の分離がない |
| ツール | `helm` 3、`kubectl`、`curl` |
| PostgreSQL | 16。クラスターの中から届くアドレス |
| S3 互換オブジェクトストア | bucket 1つ。既定の保護モード `locked` は versioning、Object Lock、既定の暗号化 SSE-S3(`AES256`)が有効な bucket を要求する。そうでないと API は起動を拒否する |
| ネットワーク | クラスターが `ghcr.io` から chart とイメージを取得できる。パッケージはログイン不要 |

chart は PostgreSQL、オブジェクトストア、Secret の値を作りません。worker Pod も作りません。scheduler がセッションごとに作ります。公開イメージは `linux/amd64` と `linux/arm64` を含む index なので、ノードは自分のアーキテクチャを取得します。

### workspace のストレージと上限

単一サーバーでは XFS `prjquota` が workspace の容量と inode を制限します([ディスクの準備](/run-server/self-hosting/single-server))。Kubernetes にはその条件がなく、上限の仕組みが違います。表は2つの経路を同じ項目で並べたものです。

| 項目 | 単一サーバー | Kubernetes |
| --- | --- | --- |
| 保存場所 | セッションごとに Docker `local` volume。Docker データルートの XFS 上 | セッションごとに PVC が1つ(`werft-ws-<installationId>-<sessionId>`)で、worker の `/workspace` に mount する。`ReadWriteOnce`、`Filesystem`。`/tmp` と HOME はメモリの emptyDir で、hostPath は使わない |
| 容量の上限 | `EXECUTION_WORKSPACE_QUOTA_MB`、既定 4096MiB(最小 1024) | PVC の `requests.storage`、helm の `worker.workspace.quotaMb`、既定 4096MiB(最小 1024)。実際に強制されるかは StorageClass 次第 |
| inode の上限 | `EXECUTION_WORKSPACE_QUOTA_INODES`、既定 1,000,000 | **ない。** Werft も chart も設定しない。ファイルシステムの既定に従う(ext4 は作るときに数が決まる) |
| 強制する主体 | XFS `prjquota`(カーネル)。scheduler の preflight が確認 | kubelet と CSI ドライバー。Werft はサイズを要求するだけで、使用量は読まない。確認する preflight もない |
| 超えたとき | worker の書き込みが `ENOSPC`。上限を設定できなければ scheduler は起動しない | StorageClass がサイズを強制すれば `ENOSPC`。強制しなければ上限がないのと同じ。PVC の外のノードディスク(主にログ)は `worker.ephemeralStorageMb`(既定 1024MiB、requests=limits)を超えると kubelet が Pod を evict する |
| 運用者が決める値 | Docker データルートのファイルシステムとサイズ、2つの上限 | `worker.storageClass`(空ならクラスターの既定)、`worker.workspace.quotaMb`、`worker.ephemeralStorageMb`、worker ノードのファイルシステムのサイズ |
| 確認コマンド | `findmnt -no FSTYPE,OPTIONS -T "$(docker info -f '{{.DockerRootDir}}')"`、`xfs_quota -x -c 'report -p'` | 下記 |

```bash
kubectl get storageclass
kubectl -n werft get pvc -l app.kubernetes.io/part-of=werft,werft.installation=<installationId> \
  -o custom-columns=NAME:.metadata.name,REQUEST:.spec.resources.requests.storage,CAPACITY:.status.capacity.storage
kubectl -n werft exec <worker-pod> -- df -h /workspace
kubectl -n werft exec <worker-pod> -- df -i /workspace
```

`kubectl get storageclass` で、使う StorageClass の provisioner がサイズを強制する volume を作るか確認します(例: EBS gp3 は要求したサイズがそのままブロックデバイスの大きさになる)。PVC 一覧の `REQUEST` は Werft が要求した値、`CAPACITY` はプロビジョナーが作ったサイズです。`df -h` の合計はファイルシステムのオーバーヘッドでどちらとも違うことがあるので、一致するかどうかで判定しません。確認するのは、`CAPACITY` が `REQUEST` 以上であることと、同じ StorageClass の試験用 PVC に `REQUEST` より多く書き込んだとき `ENOSPC` になることです。`df -i` で inode の合計が見えます。これらのコマンドはクラスターで実行していません(**未検証**)。値はコード(`specs.ts`、`config.ts`)と chart から読みました。

- **PVC は必須です。** worker Pod が使う workspace の volume は PVC だけで(`specs.ts`)、emptyDir や hostPath に切り替える設定はありません。セッションの PVC は Pod とは別に生き続けるので、Pod が入れ替わっても同じ名前の PVC に再び接続します。scheduler がセッションごとに Pod と PVC を作ります。
- **StorageClass がサイズをハードに強制するかどうかを、Werft は見ません。** コードは `requests.storage` を要求し、その値を `werft.workspace-size` annotation に書いて設定と比べるだけで、`status.capacity` や使用量は読みません。強制の有無は CSI ドライバーとファイルシステムごとに違うので、設置の前にインフラ側へ確認します。
- **node-local(emptyDir、hostPath)に変えると保証が変わります。** 今は使えない仮定です。ディスク上の emptyDir なら、上限は volume のサイズではなく、Pod の `ephemeral-storage` limit と kubelet の退避(evict)になります。退避は `ENOSPC` ではなく Pod の削除で、emptyDir のデータは Pod と一緒に消えます。hostPath は `ephemeral-storage` の集計に入らないので Kubernetes が課す上限はなく、データは Pod が消えてもノードに残ります。どちらでも、ハードな上限や inode の上限がほしければ、ノードのファイルシステムに quota を別に設定する必要があります(Kubernetes の project quota 機能は使用量の測定用です)。これは Kubernetes の一般的な動作を書いたもので、このリポジトリでは測っていません(**未検証**)。
- `worker.workspace.quotaMb` を変えると、既存セッションの PVC は作成時のサイズと合わなくなり、そのセッションは拒否されます(`werft.workspace-size` annotation と比べる)。新しいセッションから適用するには、進行中のセッションがないときに変えます。
- kind の既定 StorageClass(local-path 系)は PVC のサイズを強制しないことが知られています。このリポジトリでは測っていません(**未検証**)。kind で PVC が `Bound` になっても、上限が効いているとは限りません。
- **既知の制限。** inode の上限がなく、容量の上限は StorageClass に任されています。サイズを強制しない StorageClass を選んでも chart は拒否しません。これを塞ぐコード変更はこのページの範囲外です。

## 1. バージョンを決める

バージョンは常に正確に指定します。`main` マージの chart バージョンは `0.1.0-main-<12>` で、`<12>` は commit SHA の先頭12文字です。`main` のバージョン同士の順序に意味はないので、`--devel` で最新を選びません。リポジトリの [Images workflow](https://github.com/JeongJaeSoon/werft/blob/main/.github/workflows/images.yml) で緑で終わった `main` の run の commit を選んで書きます。

```bash
VERSION=0.1.0-main-<12>
helm show chart oci://ghcr.io/jeongjaesoon/werft --version "$VERSION"
helm show values oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" | sed -n '/^images:/,/^$/p'
```

`images` の下に、3つのイメージの `digest` と `worker.runtime` が出れば正常です。これらは chart に入っているので、設置ごとの values には書きません。書くと、次の chart の値を上書きし続けます。

## 2. namespace と Secret を作る

Secret は、キーごとに1ファイルのディレクトリ(`0700`、ファイル名がキー)から作ります。値がコマンドラインやシェルの history に残りません。

| キー | 値 |
| --- | --- |
| `DATABASE_URL` | PostgreSQL の接続 URL |
| `EGRESS_AUTHORIZER_TOKEN` | ランダムな値。API と egress proxy が同じ値を使う |
| `PLATFORM_SECRET_KEY` | `openssl rand -hex 32` の64文字の hex。保存した認証情報を封印する。ないと Pod が起動しない |
| `AWS_ACCESS_KEY_ID`、`AWS_SECRET_ACCESS_KEY` | オブジェクトストアの key。IRSA で署名するなら2つとも省き、values に `secrets.objectStoreKeys: false` と `serviceAccounts.api.annotations` を置く |
| `ANTHROPIC_API_KEY` | 任意。セッションが使う Anthropic key の基本の経路は、インストール後にコンソールの**設定 > ワークスペース設定 > モデル接続 > 接続を追加**で入れる方法です。このキーは環境変数で渡す代替手段で、置いた場合は API にだけ渡ります。置かない場合は helm に `--set-json 'secrets.catalogEnv=[]'` を渡します。chart の既定値はこのキーを API に渡すので、Secret にないと Pod が起動しません |

```bash
kubectl create namespace werft
kubectl -n werft create secret generic werft --from-file=<secret-dir>
```

## 3. values ファイルを作る

設置ごとの値は `values-<installation>.yaml` 1つに置きます。最低限、checkpoint の bucket と、worker が bucket に届く経路が入ります。

```yaml
config:
  checkpoints:
    bucket: <bucket>
  egress:
    credentialAllowlist: "api.anthropic.com:443,registry.npmjs.org:443,rubygems.org:443,proxy.golang.org:443,sum.golang.org:443,github.com:443,<bucket>.s3.<region>.amazonaws.com:443"
```

`credentialAllowlist` は既定値をまるごと置き換えます。既定の一覧(provider とパッケージ registry)は残し、リポジトリのホスト(`github.com:443`、ほかの Git ホストを使うならそのホストも)と bucket のホストを後ろに足します。

`config.aws.region` の既定値は `ap-northeast-1` です。別のリージョンの bucket なら変えます。接続、リポジトリ、MCP サーバー、上限は values にありません。設置後に Web コンソールで追加するか、`bun run settings:k8s import` で取り込みます。既定値と説明は `helm show values` にあります。

## 4. 設置する

```bash
helm upgrade --install werft oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
  --namespace werft -f values-<installation>.yaml --timeout 10m
```

migrate Job が先に schema を上げ、終わると API、egress proxy、reconciler、scheduler、slack がまとめて適用されます。最初の設置がイメージのパスや pull 権限のエラーで失敗したら、値を直して同じコマンドをもう一度実行します。

```bash
kubectl -n werft get job werft-migrate
for d in api egress-proxy reconciler scheduler; do
  kubectl -n werft rollout status deploy/werft-$d --timeout=600s
done
```

release 名に `werft` が含まれないと、リソース名は `<release>-werft-…` になります。

## 5. 確認する

API Service をローカルに開いて `/readyz` を呼びます。readiness は DB、schema、設定を見ます。

```bash
kubectl -n werft port-forward svc/werft-api 13000:3000 &
PF=$!
until curl -fs -o /dev/null http://127.0.0.1:13000/healthz; do sleep 1; done
curl -fsS -w '\n%{http_code}\n' http://127.0.0.1:13000/readyz
curl -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:13000/docs
kill "$PF"
```

`{"status":"ready",…}` と `200` が出れば設置できています。`/docs` も 200 です。利用者には Ingress で公開します。`ingress.enabled: true` と controller ごとの設定は [Kubernetes の設置(Helm chart)](/run-server/self-hosting/operate/kubernetes-deployment#awsの値を入れる) にあります。

## 6. 最初の owner と API key

Web コンソールの `/bootstrap` で最初の owner と workspace を作ります。API Pod は起動時にトークンを生成し、ログに `BOOTSTRAP_TOKEN=…` の1行で出力します。最初の owner ができるまでは、そのログを読める人なら誰でも bootstrap できるので、ログを読める人は運用者に限ります。

chart の api は replica が2つなので、Pod ごとに別のトークンを生成し、それぞれのログに出力します(Pod ごとに値が違うことは kind で確認しました)。`/bootstrap` へのリクエストがトークンを読んだ Pod とは別の Pod に届くと 401 になることがあります(誤ったトークンが 401 になることは kind で確認しました。ただしどの Pod が受けるかは区別していないため、別の Pod に届いたときの 401 は再現していません)。避ける方法は2つです。`BOOTSTRAP_TOKEN` を Secret に入れてすべての Pod が同じ値を使うようにするか、replica 1 で始めます。前者は Secret にキー `BOOTSTRAP_TOKEN` を作り、`--set-json 'secrets.catalogEnv=["ANTHROPIC_API_KEY","BOOTSTRAP_TOKEN"]'` で api に渡します。この値は既定値 `["ANTHROPIC_API_KEY"]` を置き換えます。Secret に `ANTHROPIC_API_KEY` を置いたなら一緒に書き、モデルの key をコンソールの画面で入れて Secret に置かないなら `--set-json 'secrets.catalogEnv=["BOOTSTRAP_TOKEN"]'` だけを渡します。リストにある名前が Secret になければ Pod は起動しません。自分で決めるトークンは 32〜256 文字で、外れると API は起動しません。この方法でインストールした api(replica 2)が `/readyz` 200 まで起動すること、そのトークンで owner を作る呼び出しが 201 を返し、同じトークンをもう一度使うと 409 `BOOTSTRAP_DONE` になることは kind で確認しました。replica 1 で始める方法は実行していません。

API key は API Pod の中で発行します。次の `kubectl exec` 形式は checkout が要りません。この形式で key を発行し、その key で `GET /v1/sessions` が 200、key なしでは 401 になることを kind で確認しました(上の Secret のトークンで owner を作ったあと)。`bun run keys:k8s` を使う近道は [Kubernetes の設置(Helm chart)](/run-server/self-hosting/operate/kubernetes-deployment#api-key実行権限設定ドキュメント) にあります。

```bash
kubectl -n werft exec deploy/werft-api -c api -- \
  bun run apps/control-host/src/api/keys.ts create <owner_id> \
  --scopes sessions:read,sessions:write,sessions:approve,sessions:control,sessions:recover
```

stdout に平文の key が一度だけ、stderr に key id が出ます。利用者ごとに owner と key を別々に発行します。SDK と HTTP API は、サーバーのアドレスとこの key で接続します([SDK のインストール](/getting-started/install))。

## まず kind で試す

同じ chart をノート PC で試すには、kind クラスターに PostgreSQL とオブジェクトストアの代役を先に立てます。代役はリポジトリの `deploy/kind/deps.yaml` にあるので、リポジトリを取得します。代役は試用専用です。実サーバーの DB や bucket には使いません。

```bash
git clone https://github.com/JeongJaeSoon/werft.git
cd werft
kind create cluster --name werft-try
kubectl create namespace werft
kubectl -n werft create configmap localstack-init \
  --from-file=10-create-resources.sh=infra/localstack/init/10-create-resources.sh
kubectl -n werft apply -f deploy/kind/deps.yaml
SECRETS="$(mktemp -d)"
```

次のコマンド `read -rs` は、プロンプトなしで入力を待ちます。入力する値は `deploy/kind/deps.yaml` の `POSTGRES_PASSWORD` で、値をコマンドラインに書かないよう端末から読みます。端末なしで実行するスクリプトでは、同じ値を標準入力で渡してこの行を満たします(kind で確認しました)。Secret の値はすべてこの kind の試用専用です。実サーバーでは、手順2の方法で自分で作った値を使います。Secret を作った後は、変数と一時ディレクトリを削除します。

```bash
read -rs KIND_DB_PASSWORD
{ printf 'postgresql://postgres:'; printf '%s' "$KIND_DB_PASSWORD"; printf '@postgres:5432/sessions'; } > "$SECRETS/DATABASE_URL"
openssl rand -hex 32 | tr -d '\n' > "$SECRETS/EGRESS_AUTHORIZER_TOKEN"
openssl rand -hex 32 | tr -d '\n' > "$SECRETS/PLATFORM_SECRET_KEY"
printf test > "$SECRETS/AWS_ACCESS_KEY_ID"
printf test > "$SECRETS/AWS_SECRET_ACCESS_KEY"
kubectl -n werft create secret generic werft --from-file="$SECRETS"
unset KIND_DB_PASSWORD
rm -r "${SECRETS:?}"
helm upgrade --install werft oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
  --namespace werft -f deploy/kind/values.yaml --set-json 'secrets.catalogEnv=[]' --timeout 10m
```

Secret に `ANTHROPIC_API_KEY` を作らないので、helm に `secrets.catalogEnv=[]` を渡します。モデルの key は、インストール後にコンソールのモデル接続の画面で入れます。

続けて、手順4の rollout の確認と手順5の確認をそのまま行います。終わったら `kind delete cluster --name werft-try` でクラスターを削除します。

## アップグレードと削除

アップグレードで worker イメージが変わる場合は、直前の worker イメージも一緒に渡す必要があります。`--reuse-values` は新しい chart のイメージを適用しないので使いません。手順、アップグレード前の検査、ロールバックは[アップグレード](/run-server/self-hosting/upgrade)にあります。

```bash
helm -n werft uninstall werft
```

`uninstall` は `werft-migrate` Job を残します(kind で確認しました)。scheduler が作った worker Pod、workspace の PVC、自分で作った Secret も残ると考えられますが、セッションなしで動かした kind では確認していません。残った Job は同じ namespace への再インストールを妨げません。PVC を消すと checkpoint されていない作業が失われるので、先にセッションが終わっているか確認します。
