title: "アップグレード"
description: 設置済みの Werft を新しい公開バージョンに上げ、上げる前に止まるセッションを確認する

設置済みの Werft を新しい公開バージョンに上げます。初めての設置は [Kubernetes の設置](/run-server/self-hosting/kubernetes) か [単一サーバーの設置](/run-server/self-hosting/single-server) を読んでください。

<Callout type="warn">
`v` タグはまだありません。今は `main` にマージされるたびに公開される chart `0.1.0-main-<12>` とイメージタグ `main-<12>` に上げます。これらはリリースではありません。最初の `v` タグができると、`VERSION` は `v` を除いたタグ(`v1.2.3` なら `1.2.3`)にし、コマンドは同じです。上げる前に、リポジトリの [変更履歴](https://github.com/JeongJaeSoon/werft/blob/main/CHANGELOG.md) で運用担当者が手で行うことを読んでください。
</Callout>

## Kubernetes

<Callout type="warn">
この Kubernetes のアップグレード手順は、kind クラスター1つで1回実行して確認しました。以前の main バージョン(`0.1.0-main-940b1956d21c`)をインストールしてから `0.1.0-main-3c8a1f15488e` に上げ、手順1〜4(`worker-previous.json` の作成、`helm upgrade`、upgrade-check Job の `proceed`、rollout と `/readyz` 200)がこの順序で通りました。確認できていないことがあります。セッションがない状態で実行したため `verdict` は `proceed` だけを見ており、`refused` で止まる場合と承認の手順は実行していません。NetworkPolicy を適用する CNI での動作とロールバックも確認していません。新しい control-host と直前の worker イメージの組み合わせは CI で検査していないため、実サーバーの前に試用環境で実行してください。内容が違う場合は [Kubernetes の設置 (Helm chart)](/run-server/self-hosting/operate/kubernetes-deployment#公開chartのアップグレード) に従ってください。
</Callout>

この手順は `jq` も使います。公開 chart は新しい worker イメージを持ちますが、直前の worker イメージは持ちません。直前のイメージは設置ごとに違うからです。worker イメージが変わるアップグレードは、`images.workerPrevious` が今デプロイされているイメージでなければ `refused` で止まり、承認でも越えられません。そのため、今のイメージをファイルに保存して一緒に渡します。`--reuse-values` は使いません。古い chart の値が新しい chart のイメージを上書きします。

### 1. 新しいバージョンを決める

[Images workflow](https://github.com/JeongJaeSoon/werft/actions/workflows/images.yml) で緑で終わった `main` の run の commit を選び、正確なバージョンを書きます。`main` のバージョン同士に順序の意味はないので、`--devel` で最新を選びません。

```bash
VERSION=0.1.0-main-<12>
helm show chart oci://ghcr.io/jeongjaesoon/werft --version "$VERSION"
```

### 2. 上げる

今デプロイされている worker イメージと新バージョンの worker イメージを比べ、違えば今のイメージを候補ファイルに書いて一緒に渡します。`values-<installation>.yaml` は最初の設置で使ったファイルです。

```bash
DEPLOYED="$(helm -n werft history werft -o json | jq '[.[] | select(.status == "deployed")] | last.revision')"
CURRENT="$(helm -n werft get values werft --all --revision "$DEPLOYED" -o json | jq -r '.images.worker.digest')"
TARGET="$(helm show values oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
  | awk '/^  worker:/ {found = 1} found && /digest:/ {print $2; exit}')"
echo "deployed ${CURRENT}"
echo "target   ${TARGET}"
PREVIOUS=worker-previous.json
if [ -n "$TARGET" ] && [ "$CURRENT" != "$TARGET" ]; then
  PREVIOUS=worker-previous.next.json
  helm -n werft get values werft --all --revision "$DEPLOYED" -o json \
    | jq '{images: {workerPrevious: .images.worker}}' > "$PREVIOUS"
fi
set -- -f values-<installation>.yaml
if [ -f "$PREVIOUS" ]; then set -- "$@" -f "$PREVIOUS"; fi
if helm upgrade --install werft oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
  --namespace werft "$@" --timeout 10m; then
  if [ "$PREVIOUS" != worker-previous.json ]; then mv "$PREVIOUS" worker-previous.json; fi
fi
```

- `worker-previous.json` は設置の隣に保管し、次のアップグレードにも渡します。worker イメージが変わらないアップグレードで抜かすと、今デプロイされている直前のイメージがサポート期間から外れます。アップグレード前の検査は、対象のイメージ(現在のイメージと、あれば直前のイメージ)のどれとも合わないセッションと、組み合わせが記録されていないセッションを選び、承認するまで `refused` で止まります。誤って抜かした場合は承認せず、ファイルを入れてもう一度実行します。選ばれたセッションがなく、承認リスト(`upgrade.approvedSessions`)も空なら通ります。ただし、最初の checkpoint の前のセッションと、検査の後に直前のイメージの worker が残す checkpoint は検査に見えないため、そのセッションは再開時に `recovery_required` で止まることがあります。
- `--revision` を付けないと、失敗したアップグレードがある場合に上げようとしたイメージが出ます。今デプロイされている revision を指定します。
- `helm get values --all` の全体を values ファイルとして渡しません。古い digest が新しい chart の値を上書きします。`.images.worker` だけを取り出します。
- 初めての設置の後で worker イメージが変わらないアップグレードには、渡すファイルがありません。それで構いません。

### 3. アップグレード前の検査を読む

`helm upgrade` は migrate より先に、新バージョンの api イメージで `upgrade-check` Job を実行します。この Job は新しいイメージで再開できないセッションを選び、`verdict` を1行で知らせます。

```bash
kubectl -n werft logs job/werft-upgrade-check
```

| `verdict` | 意味 |
| --- | --- |
| `proceed` | 進みます |
| `refused` | 止まります。選ばれたセッションが承認リストと違うか、worker イメージが変わるのに `images.workerPrevious` が今デプロイされているイメージではありません。後者は承認で越えられません。worker イメージが変わらなくても、今デプロイされている直前のイメージを外すか変えるとセッションを比較するので、ここで止まることがあります。この場合は承認で越えられます |
| `check_failed` | 止まります。DB またはイメージの組み合わせを読めませんでした |

選ばれたセッションが再開できなくてもよい場合は、`affected` のリストを `--set-json 'upgrade.approvedSessions=["<sessionId>", ...]'` で渡し、同じアップグレードをもう一度実行します。承認リストは release の values に残るので、アップグレードのたびに `[]` で空にしてリストを読み直します。判定表と例外は [Kubernetes の設置 (Helm chart)](/run-server/self-hosting/operate/kubernetes-deployment#アップグレード前の検査) にあります。

### 4. 確認する

```bash
kubectl -n werft get job werft-migrate
for d in api egress-proxy reconciler scheduler; do
  kubectl -n werft rollout status deploy/werft-$d --timeout=600s
done
kubectl -n werft port-forward svc/werft-api 13000:3000 &
PF=$!
until curl -fs -o /dev/null http://127.0.0.1:13000/healthz; do sleep 1; done
curl -fsS -w '\n%{http_code}\n' http://127.0.0.1:13000/readyz
kill "$PF"
```

`{"status":"ready",…}` と `200` が出れば `/readyz` が ready を返しています。セッションが再開できるかは別に確認してください。

### 戻す

`helm rollback` は hook を実行しないので、アップグレード前の検査も実行されません。worker イメージを戻すロールバックの前に手で実行する検査は通常 `refused` で、ロールフォワードが先です。戻すときの検査コマンドと限界は [Kubernetes の設置 (Helm chart)](/run-server/self-hosting/operate/kubernetes-deployment#アップグレード前の検査) の `helm rollback` の項にあります。

## 単一サーバー (Docker Compose)

<Callout type="warn">
単一サーバーのアップグレードは、公開イメージで実行して確認していません。以下は `scripts/test-ops.sh` とコードを読んで書いた順序であり、実行を保証しません。内容が違う場合は、スクリプトが基準です。
</Callout>

新しいタグの digest で `release.json` を作り直し、新しい source commit を checkout して `upgrade` を呼びます。worker イメージが変わっていれば新しいイメージで現在の checkpoint を検査し、互換性のないセッションがあれば終了コード 3 で拒否します。このとき影響を受けるセッションの id が `$TEST_OPS_STATE_DIR/upgrade-<時刻>.sessions` に書かれます。一覧を確認して利用者に知らせた後、まさにその id を入れたファイルで `scripts/test-ops.sh upgrade release-new.json --approve-sessions approved.txt` をもう一度呼びます。一覧が1つでも違えば拒否し、進めると承認の記録を状態ディレクトリに残します。互換性のないセッションを `start_fresh` で復旧すると、以前の checkpoint の context を失います。影響を受けるセッションがなければ承認なしで進みます。

アップグレードの直前に[バックアップ](/run-server/self-hosting/single-server#バックアップと復元)を一度取ります。元に戻すには、以前の release ファイルで `upgrade` をもう一度呼びます。worker イメージがまた変わるので、同じ規則が適用されます。

アップグレードが新しい release の起動前に止まると(例: scheduler の quota 検査の失敗)、設置は止まったままになり、状態ディレクトリに `pending.json` が残ります。この状態では `status` 以外のコマンドが、以前の release へ戻す `upgrade` も含めて拒否されます。原因を直した後、同じ対象の release ファイルでもう一度 `upgrade` を呼ぶと解消します。

```bash
git fetch && git checkout <new source_commit> && bun install --frozen-lockfile
scripts/test-ops.sh upgrade release-new.json
```

## 変わった名前と運用担当者のすること

指標名と CSS 名が変わりました。古い名前の別名はありません。すでに設置している環境は、[変更履歴](https://github.com/JeongJaeSoon/werft/blob/main/CHANGELOG.md) の「운영자가 할 일」(運用担当者が行うこと)の節に従って、Datadog の定義を初めて適用するか、すでに適用している場合はその名前とクエリ・フィルターを新しい定義に合わせ、Prometheus ルールのクエリと上書きした CSS 名を変えます。
