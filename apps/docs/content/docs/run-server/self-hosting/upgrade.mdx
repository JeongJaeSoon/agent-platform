이미 설치한 Werft를 새 게시 버전으로 올린다. 처음 설치는 [Kubernetes 설치](/run-server/self-hosting/kubernetes)나 [단일 서버 설치](/run-server/self-hosting/single-server)를 읽는다.

<Callout type="warn">
첫 `v` 태그가 아직 없다. 지금은 `main`에 머지될 때마다 게시되는 chart `0.1.0-main-<12>`와 이미지 태그 `main-<12>`로 올린다. 이 버전은 릴리스가 아니다. 첫 `v` 태그가 생기면 `VERSION`을 태그의 버전(`v1.2.3`이면 `1.2.3`)으로 바꾸고, 명령은 같다. 올리기 전에 저장소의 [변경 기록](https://github.com/JeongJaeSoon/werft/blob/main/CHANGELOG.md)에서 운영자가 직접 해야 할 일을 읽는다.
</Callout>

## Kubernetes

<Callout type="warn">
이 Kubernetes 업그레이드 절차는 kind 클러스터 한 곳에서 한 번 돌려 확인했다. 이전 main 버전(`0.1.0-main-940b1956d21c`)을 설치한 뒤 `0.1.0-main-3c8a1f15488e`로 올렸고, 1~4단계(`worker-previous.json` 만들기, `helm upgrade`, upgrade-check Job의 `proceed`, rollout과 `/readyz` 200)가 이 순서대로 통과했다. 확인하지 못한 것이 있다. 세션이 없는 상태에서 돌렸으므로 `verdict`는 `proceed`만 봤고, `refused`로 멈추는 경우와 승인 절차는 돌리지 않았다. NetworkPolicy를 적용하는 CNI에서의 동작과 되돌리기도 확인하지 못했다. 새 control-host와 직전 worker 이미지의 조합은 CI가 검사하지 않으므로, 실서버 전에 시험 설치에서 먼저 돌린다. 내용이 다르면 [Kubernetes 설치 (Helm chart)](/run-server/self-hosting/operate/kubernetes-deployment#게시-chart를-올리기)를 따른다.
</Callout>

이 절차는 `jq`도 쓴다. 게시 chart는 새 worker 이미지만 담고 직전 worker 이미지는 담지 않는다. 직전 이미지는 설치마다 다르기 때문이다. worker 이미지가 바뀌는 업그레이드는 `images.workerPrevious`가 지금 배포된 이미지가 아니면 `refused`로 멈추고, 승인으로도 넘길 수 없다. 그래서 지금 이미지를 파일에 저장해 함께 넘긴다. `--reuse-values`는 쓰지 않는다. 옛 chart의 값이 새 chart의 이미지를 덮는다.

### 1. 새 버전 정하기

[Images workflow](https://github.com/JeongJaeSoon/werft/actions/workflows/images.yml)에서 초록색으로 끝난 `main` run의 commit을 골라 정확한 버전을 적는다. `main` 버전끼리는 순서에 뜻이 없으므로 `--devel`로 최신을 고르지 않는다.

```bash
VERSION=0.1.0-main-<12>
helm show chart oci://ghcr.io/jeongjaesoon/werft --version "$VERSION"
```

### 2. 올리기

지금 배포된 worker 이미지와 새 버전의 worker 이미지를 비교하고, 다르면 지금 이미지를 후보 파일에 쓴 뒤 함께 넘긴다. 설치별 `values-<installation>.yaml`은 처음 설치할 때 쓴 파일이다.

```bash
DEPLOYED="$(helm -n werft history werft -o json | jq '[.[] | select(.status == "deployed")] | last.revision')"
CURRENT="$(helm -n werft get values werft --all --revision "$DEPLOYED" -o json | jq -r '.images.worker.digest')"
TARGET="$(helm show values oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
  | awk '/^  worker:/ {found = 1} found && /digest:/ {print $2; exit}')"
echo "deployed ${CURRENT}"
echo "target   ${TARGET}"
PREVIOUS=worker-previous.json
if [ -n "$TARGET" ] && [ "$CURRENT" != "$TARGET" ]; then
  PREVIOUS=worker-previous.next.json
  helm -n werft get values werft --all --revision "$DEPLOYED" -o json \
    | jq '{images: {workerPrevious: .images.worker}}' > "$PREVIOUS"
fi
set -- -f values-<installation>.yaml
if [ -f "$PREVIOUS" ]; then set -- "$@" -f "$PREVIOUS"; fi
if helm upgrade --install werft oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
  --namespace werft "$@" --timeout 10m; then
  if [ "$PREVIOUS" != worker-previous.json ]; then mv "$PREVIOUS" worker-previous.json; fi
fi
```

- `worker-previous.json`은 설치 옆에 보관하고 다음 업그레이드에도 넘긴다. worker 이미지가 그대로인 업그레이드에서 빠뜨리면 지금 배포된 직전 이미지가 지원 창에서 빠진다. 업그레이드 전 검사는 대상 이미지(현재 이미지와, 있으면 직전 이미지) 어느 쪽과도 맞지 않는 세션과 조합이 기록되지 않은 세션을 골라, 승인할 때까지 `refused`로 멈춘다. 실수로 빠뜨렸다면 승인하지 말고 파일을 넣어 다시 돌린다. 고른 세션이 없고 승인 목록(`upgrade.approvedSessions`)이 비어 있으면 통과한다. 다만 첫 checkpoint 전인 세션과, 검사 뒤에 직전 이미지의 worker가 남기는 checkpoint는 검사가 보지 못하므로 그 세션은 재개할 때 `recovery_required`로 멈출 수 있다.
- `--revision`을 빼면 실패한 업그레이드가 있을 때 올리려던 이미지가 나온다. 지금 배포된 revision을 지정해야 한다.
- `helm get values --all` 전체를 values 파일로 넘기지 않는다. 옛 digest가 새 chart의 값을 덮는다. `.images.worker`만 꺼낸다.
- 처음 설치한 뒤 worker 이미지가 그대로인 업그레이드에는 넘길 파일이 없고, 그래도 된다.

### 3. 업그레이드 전 검사 읽기

`helm upgrade`는 migrate보다 먼저 `upgrade-check` Job을 새 버전의 api 이미지로 돌린다. 이 Job은 새 이미지로 재개할 수 없는 세션을 골라 `verdict` 한 줄로 알려 준다.

```bash
kubectl -n werft logs job/werft-upgrade-check
```

| `verdict` | 뜻 |
| --- | --- |
| `proceed` | 진행한다 |
| `refused` | 멈춘다. 고른 세션이 승인 목록과 다르거나, worker 이미지가 바뀌는데 `images.workerPrevious`가 지금 배포된 이미지가 아니다. 뒤의 경우는 승인으로 넘길 수 없다. worker 이미지가 그대로여도 지금 배포된 직전 이미지를 빼거나 바꾸면 세션을 비교하므로 여기서 멈출 수 있다. 이 경우는 승인으로 넘길 수 있다 |
| `check_failed` | 멈춘다. DB나 이미지 조합을 읽지 못했다 |

고른 세션이 재개하지 못해도 되면 `affected` 목록을 `--set-json 'upgrade.approvedSessions=["<sessionId>", ...]'`로 넘기고 같은 업그레이드를 다시 돌린다. 승인 목록은 release values에 남으므로 다음 업그레이드마다 `[]`로 비우고 목록을 다시 읽는다. 판정 표와 예외는 [Kubernetes 설치 (Helm chart)](/run-server/self-hosting/operate/kubernetes-deployment#업그레이드-전-검사)에 있다.

### 4. 확인하기

```bash
kubectl -n werft get job werft-migrate
for d in api egress-proxy reconciler scheduler; do
  kubectl -n werft rollout status deploy/werft-$d --timeout=600s
done
kubectl -n werft port-forward svc/werft-api 13000:3000 &
PF=$!
until curl -fs -o /dev/null http://127.0.0.1:13000/healthz; do sleep 1; done
curl -fsS -w '\n%{http_code}\n' http://127.0.0.1:13000/readyz
kill "$PF"
```

`{"status":"ready",…}`와 `200`이 나오면 `/readyz`가 ready를 돌려준 것이다. 세션이 이어지는지는 따로 확인한다.

### 되돌리기

`helm rollback`은 hook을 돌리지 않으므로 업그레이드 전 검사도 돌지 않는다. worker 이미지를 되돌리는 롤백 전에 손으로 돌리는 검사는 보통 `refused`이고, 롤포워드가 우선이다. 되돌릴 때의 검사 명령과 한계는 [Kubernetes 설치 (Helm chart)](/run-server/self-hosting/operate/kubernetes-deployment#업그레이드-전-검사)의 `helm rollback` 전 항목에 있다.

## 단일 서버 (Docker Compose)

<Callout type="warn">
단일 서버의 업그레이드는 게시 이미지로 실행해 확인하지 않았다. 아래는 운영 runbook의 순서일 뿐 실행을 보장하지 않으며, 내용이 다르면 [test-ops 운영 runbook](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/test-ops.md#업그레이드)을 따른다.
</Callout>

새 태그의 digest로 `release.json`을 다시 만든 뒤, 새 source commit을 checkout하고 `upgrade`를 부른다. worker 이미지가 바뀌었으면 새 이미지로 현재 checkpoint를 검사하고, 호환되지 않는 세션이 있으면 종료 코드 3으로 거부한다. 승인 절차는 runbook을 따른다.

```bash
git fetch && git checkout <new source_commit> && bun install --frozen-lockfile
scripts/test-ops.sh upgrade release-new.json
```

## 바뀐 이름과 운영자가 할 일

지표 이름과 CSS 이름이 바뀌었다. 옛 이름 별칭은 없다. 이미 설치한 곳은 [변경 기록](https://github.com/JeongJaeSoon/werft/blob/main/CHANGELOG.md)의 "운영자가 할 일"대로 Datadog 정의를 처음 적용하거나, 이미 적용했다면 그 이름과 쿼리·필터를 새 정의에 맞추고, Prometheus 규칙의 쿼리와 덮어쓴 CSS 이름을 바꾼다.
