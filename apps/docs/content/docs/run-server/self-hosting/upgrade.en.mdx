Move an installed Werft to a new published version. For a first install, read [Kubernetes install](/run-server/self-hosting/kubernetes) or [Single-server install](/run-server/self-hosting/single-server).

<Callout type="warn">
There is no `v` tag yet. For now, upgrade to the chart `0.1.0-main-<12>` and the image tag `main-<12>` published on every merge to `main`. They are not a release. Once the first `v` tag exists, set `VERSION` to the tag without the `v` (`1.2.3` for `v1.2.3`); the commands stay the same. Before you upgrade, read the [changelog](https://github.com/JeongJaeSoon/werft/blob/main/CHANGELOG.md) in the repository for what operators must do by hand.
</Callout>

## Kubernetes

<Callout type="warn">
These Kubernetes upgrade steps were run once on a single kind cluster. An earlier main version (`0.1.0-main-940b1956d21c`) was installed and then upgraded to `0.1.0-main-3c8a1f15488e`, and steps 1 to 4 (writing `worker-previous.json`, `helm upgrade`, the upgrade-check Job's `proceed`, the rollout and `/readyz` 200) passed in this order. Some things were not checked. The run had no sessions, so only the `proceed` verdict was seen; the case where it stops with `refused` and the approval step were not run. Behavior on a CNI that enforces NetworkPolicy, and rolling back, were not checked either. CI does not test the new control-host with the previous worker image, so try them on a test install before a real server. If they differ, follow [Kubernetes install (Helm chart)](/run-server/self-hosting/operate/kubernetes-deployment#upgrading-the-published-chart).
</Callout>

These steps use `jq` too. The published chart carries the new worker image but not the previous one, because the previous image differs per installation. An upgrade that changes the worker image stops with `refused` unless `images.workerPrevious` is the image deployed now, and an approval cannot get past that. So save the current image to a file and pass it along. Do not use `--reuse-values`: the old chart's values override the new chart's images.

### 1. Pick the new version

In the [Images workflow](https://github.com/JeongJaeSoon/werft/actions/workflows/images.yml), pick the commit of a `main` run that finished green and write the exact version. Versions from `main` have no order, so do not pick the latest with `--devel`.

```bash
VERSION=0.1.0-main-<12>
helm show chart oci://ghcr.io/jeongjaesoon/werft --version "$VERSION"
```

### 2. Upgrade

Compare the worker image deployed now with the worker image of the new version. If they differ, write the current image to a candidate file and pass it along. `values-<installation>.yaml` is the file you used at the first install.

```bash
DEPLOYED="$(helm -n werft history werft -o json | jq '[.[] | select(.status == "deployed")] | last.revision')"
CURRENT="$(helm -n werft get values werft --all --revision "$DEPLOYED" -o json | jq -r '.images.worker.digest')"
TARGET="$(helm show values oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
  | awk '/^  worker:/ {found = 1} found && /digest:/ {print $2; exit}')"
echo "deployed ${CURRENT}"
echo "target   ${TARGET}"
PREVIOUS=worker-previous.json
if [ -n "$TARGET" ] && [ "$CURRENT" != "$TARGET" ]; then
  PREVIOUS=worker-previous.next.json
  helm -n werft get values werft --all --revision "$DEPLOYED" -o json \
    | jq '{images: {workerPrevious: .images.worker}}' > "$PREVIOUS"
fi
set -- -f values-<installation>.yaml
if [ -f "$PREVIOUS" ]; then set -- "$@" -f "$PREVIOUS"; fi
if helm upgrade --install werft oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
  --namespace werft "$@" --timeout 10m; then
  if [ "$PREVIOUS" != worker-previous.json ]; then mv "$PREVIOUS" worker-previous.json; fi
fi
```

- Keep `worker-previous.json` next to the installation and pass it on the next upgrade too. If you leave it out of an upgrade that keeps the worker image, the previous image deployed now drops out of the support window. The pre-upgrade check then picks the sessions that match none of the target images (the current image and the previous one, if any) and those with no recorded combination, and stops with `refused` until you approve them. If you left the file out by mistake, do not approve: add it and run the upgrade again. With no picked session and an empty approved list (`upgrade.approvedSessions`), it passes. The check cannot see sessions with no first checkpoint, or checkpoints that workers on the previous image leave after it runs, so those sessions may stop with `recovery_required` when they resume.
- Without `--revision`, a failed upgrade makes the command return the image it tried to deploy. Name the revision that is deployed now.
- Do not pass the whole `helm get values --all` output as a values file. The old digests would override the new chart's values. Take `.images.worker` only.
- An upgrade after a first install, where the worker image has not changed, has no file to pass. That is fine.

### 3. Read the pre-upgrade check

Before migrate, `helm upgrade` runs the `upgrade-check` Job with the api image of the new version. The Job picks the sessions that cannot resume on the new images and reports a one-line `verdict`.

```bash
kubectl -n werft logs job/werft-upgrade-check
```

| `verdict` | Meaning |
| --- | --- |
| `proceed` | The upgrade continues |
| `refused` | Stops. The picked sessions differ from the approved list, or the worker image changes and `images.workerPrevious` is not the image deployed now. The second case cannot be approved. Even when the worker image stays, dropping or replacing the previous image deployed now compares the sessions, so the upgrade can stop here. That case can be approved |
| `check_failed` | Stops. The database or the image combination could not be read |

If it is acceptable that the picked sessions do not resume, pass the `affected` list as `--set-json 'upgrade.approvedSessions=["<sessionId>", ...]'` and run the same upgrade again. The approved list stays in the release values, so reset it to `[]` on each upgrade and read the list again. The verdict table and its exceptions are in [Kubernetes install (Helm chart)](/run-server/self-hosting/operate/kubernetes-deployment#pre-upgrade-check).

### 4. Check

```bash
kubectl -n werft get job werft-migrate
for d in api egress-proxy reconciler scheduler; do
  kubectl -n werft rollout status deploy/werft-$d --timeout=600s
done
kubectl -n werft port-forward svc/werft-api 13000:3000 &
PF=$!
until curl -fs -o /dev/null http://127.0.0.1:13000/healthz; do sleep 1; done
curl -fsS -w '\n%{http_code}\n' http://127.0.0.1:13000/readyz
kill "$PF"
```

`{"status":"ready",…}` and `200` mean `/readyz` returned ready. Check separately that sessions resume.

### Roll back

`helm rollback` runs no hooks, so the pre-upgrade check does not run either. For a rollback that reverts the worker image, the check you run by hand beforehand is usually `refused`; roll forward first. The check command for a rollback and its limits are in the `helm rollback` item of [Kubernetes install (Helm chart)](/run-server/self-hosting/operate/kubernetes-deployment#pre-upgrade-check).

## Single server (Docker Compose)

<Callout type="warn">
The single-server upgrade has not been run with the published images. What follows is the order read from `scripts/test-ops.sh` and the code; it does not promise that it runs. If it differs, the script is the reference.
</Callout>

Rebuild `release.json` from the digests of the new tag, check out the new source commit, then call `upgrade`. If the worker image changed, it checks the current checkpoints against the new image and refuses with exit code 3 if any session is incompatible. The ids of the affected sessions are written to `$TEST_OPS_STATE_DIR/upgrade-<timestamp>.sessions`. Review the list, tell the users, then call `scripts/test-ops.sh upgrade release-new.json --approve-sessions approved.txt` again with a file that holds exactly those ids. It refuses if the list differs by even one id, and when it proceeds it leaves an approval record in the state directory. Recovering an incompatible session with `start_fresh` loses the context of its earlier checkpoint. With no affected sessions it proceeds without approval.

Take a [backup](/run-server/self-hosting/single-server#backup-and-restore) right before upgrading. Rolling back means calling `upgrade` again with the previous release file; the worker image changes again, so the same rules apply.

```bash
git fetch && git checkout <new source_commit> && bun install --frozen-lockfile
scripts/test-ops.sh upgrade release-new.json
```

## Renamed names and what operators do

The metric names and the CSS names changed, and there are no aliases for the old names. An installation that already runs applies the Datadog definitions for the first time, or, if it already applied them, updates their names, queries and filters to match the new definitions, and changes the queries of its Prometheus rules, and renames any CSS names it overrode, as the section "운영자가 할 일" (what operators must do) in the [changelog](https://github.com/JeongJaeSoon/werft/blob/main/CHANGELOG.md) says.
