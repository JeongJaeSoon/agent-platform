---
title: "Kubernetes 설치"
description: 게시된 Helm chart로 Kubernetes에 Werft를 설치하고 /readyz 200까지 확인한다
---

게시된 Helm chart로 Kubernetes에 Werft를 설치한다. 저장소 checkout 없이 chart 하나가 세 이미지의 digest와 worker runtime을 담고 있다. 이 페이지만 따라 `/readyz`가 200을 돌려줄 때까지 간다. Linux 서버 한 대에 Docker Compose로 올린다면 [단일 서버 설치](/run-server/self-hosting/single-server)를 읽는다.

<Callout type="warn">
첫 릴리스 `v0.1.0`이 게시됐고 chart `0.1.0`(appVersion `v0.1.0`)이 같이 올라갔다. 릴리스를 설치하려면 `VERSION`을 `0.1.0`으로 바꾼다(`v` 없이 태그의 버전이 chart 버전이다). 아래 명령은 `VERSION`만 바꾸면 같다. 다만 kind에서 처음부터 끝까지 확인한 것은 `v0.1.0`과 같은 commit의 chart `0.1.0-main-<12>`이고, chart `0.1.0`으로 이 절차를 따라 설치해 보지는 않았다. `0.1.0-main-<12>`는 릴리스가 아니다.
</Callout>

## 준비물

| 항목 | 요구 |
| --- | --- |
| 클러스터 | Kubernetes. NetworkPolicy를 강제하는 CNI가 필요하다. 강제하지 않으면 worker 격리가 없다 |
| 도구 | `helm` 3, `kubectl`, `curl` |
| PostgreSQL | 16. 클러스터 안에서 닿는 주소 |
| S3 호환 object store | bucket 하나. 기본 보호 모드 `locked`는 versioning, Object Lock, 기본 암호화 SSE-S3(`AES256`)가 켜진 bucket을 요구한다. 아니면 api가 기동을 거부한다 |
| 외부 | `ghcr.io`에서 chart와 이미지를 받을 수 있다. 패키지는 로그인 없이 받는다 |

chart는 PostgreSQL, object store, Secret 값을 만들지 않는다. worker Pod도 만들지 않는다. scheduler가 세션마다 만든다. 게시 이미지는 `linux/amd64`와 `linux/arm64`를 담은 index이므로 노드가 자기 아키텍처를 받는다.

### workspace 저장소와 상한

단일 서버는 XFS `prjquota`가 workspace 용량과 inode를 막는다([디스크 준비](/run-server/self-hosting/single-server)). Kubernetes에는 그 조건이 없다. 대신 상한의 구조가 다르다. 아래 표는 두 경로를 같은 항목으로 놓은 것이다.

| 항목 | 단일 서버 | Kubernetes |
| --- | --- | --- |
| 저장 위치 | 세션마다 Docker `local` volume. Docker 데이터 루트의 XFS | 세션마다 PVC 하나(`werft-ws-<installationId>-<sessionId>`), worker의 `/workspace`에 마운트. `ReadWriteOnce`, `Filesystem`. `/tmp`와 HOME은 메모리 emptyDir이고 hostPath는 쓰지 않는다 |
| 용량 상한 | `EXECUTION_WORKSPACE_QUOTA_MB` 기본 4096MiB(최솟값 1024) | PVC의 `requests.storage`, helm `worker.workspace.quotaMb` 기본 4096MiB(최솟값 1024). 실제로 막는지는 StorageClass가 정한다 |
| inode 상한 | `EXECUTION_WORKSPACE_QUOTA_INODES` 기본 1,000,000 | **없다.** Werft도 chart도 걸지 않는다. 파일시스템 기본값을 따른다(ext4는 만들 때 개수가 정해진다) |
| 강제 주체 | XFS `prjquota`(커널). scheduler preflight가 확인 | kubelet과 CSI 드라이버. Werft는 크기를 요청만 하고 사용량을 읽지 않는다. 확인하는 preflight도 없다 |
| 넘었을 때 | worker 쓰기가 `ENOSPC`. 상한을 걸 수 없으면 scheduler가 기동하지 않음 | StorageClass가 용량을 강제하면 `ENOSPC`. 강제하지 않으면 상한이 없는 것과 같다. 노드 디스크(PVC 밖, 주로 로그)는 `worker.ephemeralStorageMb`(기본 1024MiB, requests=limits)를 넘으면 kubelet이 Pod를 evict |
| 운영자가 정할 값 | Docker 데이터 루트의 파일시스템과 크기, 위 두 상한 | `worker.storageClass`(비우면 클러스터 기본), `worker.workspace.quotaMb`, `worker.ephemeralStorageMb`, worker 노드의 파일시스템 크기 |
| 확인 명령 | `findmnt -no FSTYPE,OPTIONS -T "$(docker info -f '{{.DockerRootDir}}')"`, `xfs_quota -x -c 'report -p'` | 아래 |

```bash
kubectl get storageclass
kubectl -n werft get pvc -l app.kubernetes.io/part-of=werft,werft.installation=<installationId> \
  -o custom-columns=NAME:.metadata.name,REQUEST:.spec.resources.requests.storage,CAPACITY:.status.capacity.storage
kubectl -n werft exec <worker-pod> -- df -h /workspace
kubectl -n werft exec <worker-pod> -- df -i /workspace
```

`kubectl get storageclass`에서 쓸 StorageClass의 provisioner가 용량을 강제하는 볼륨(예: EBS gp3는 요청한 크기가 곧 블록 장치 크기다)을 만드는지 확인한다. PVC의 `REQUEST`는 Werft가 요청한 값이고 `CAPACITY`는 프로비저너가 만든 크기다. `df -h`의 총량은 파일시스템 오버헤드 때문에 이 값과 다를 수 있으므로 일치 여부로 판정하지 않는다. 확인할 것은 `CAPACITY`가 `REQUEST` 이상인지와, 같은 StorageClass로 만든 시험 PVC에 `REQUEST`보다 많이 썼을 때 `ENOSPC`가 나는지다. `df -i`로 inode 총량을 본다. 이 명령들은 클러스터에서 실행해 보지 않았다(**미검증**). 값은 코드(`specs.ts`, `config.ts`)와 chart에서 읽었다.

- **PVC는 필수다.** worker Pod가 쓰는 workspace 볼륨은 PVC뿐이고(`specs.ts`), emptyDir나 hostPath로 바꾸는 설정은 없다. 세션의 PVC는 Pod와 따로 살아서, Pod가 교체돼도 같은 이름의 PVC에 다시 붙는다. scheduler가 세션마다 Pod와 PVC를 만든다.
- **StorageClass가 크기를 하드로 강제하는지는 Werft가 보지 않는다.** 코드는 `requests.storage`를 요청하고 그 값을 `werft.workspace-size` annotation에 적어 설정과 비교할 뿐, `status.capacity`나 사용량을 읽지 않는다. 강제 여부는 CSI 드라이버와 파일시스템마다 다르므로 설치 전에 인프라 쪽에 확인한다.
- **node-local(emptyDir, hostPath)로 바꾼다면 보장이 달라진다.** 지금은 쓸 수 없는 가정이다. 디스크 기반 emptyDir라면 볼륨 크기 상한이 아니라 Pod의 `ephemeral-storage` limit과 kubelet의 축출이 상한이 된다. 축출은 `ENOSPC`가 아니라 Pod 삭제이고 emptyDir 데이터는 Pod와 함께 사라진다. hostPath는 `ephemeral-storage` 집계에 들어가지 않아 Kubernetes가 거는 상한이 없고, 데이터는 Pod가 지워져도 노드에 남는다. 어느 쪽이든 하드 상한이나 inode 상한을 원하면 노드 파일시스템에 quota를 따로 설정해야 한다(Kubernetes의 project quota 기능은 사용량 측정용이다). 이 동작은 Kubernetes 일반 동작을 적은 것이고 이 저장소에서 측정하지 않았다(**미검증**).
- `worker.workspace.quotaMb`를 바꾸면 이미 있는 세션의 PVC는 만들 때의 크기와 달라 그 세션이 거절된다(`werft.workspace-size` annotation과 비교한다). 새 세션부터 적용하려면 진행 중인 세션이 없을 때 바꾼다.
- kind의 기본 StorageClass(local-path 계열)는 PVC 크기를 강제하지 않는 것으로 알려져 있다. 이 저장소에서 측정하지 않았다(**미검증**). kind에서 `Bound`가 됐다고 상한이 선 것은 아니다.
- **알려진 한계.** inode 상한이 없고, 용량 상한은 StorageClass에 맡겨져 있다. 상한을 강제하지 않는 StorageClass를 골라도 chart는 거부하지 않는다. 이 한계를 막을 코드 변경은 이 페이지의 범위 밖이다.

## 1. 버전 정하기

버전은 항상 정확히 적는다. `main` 머지의 chart 버전은 `0.1.0-main-<12>`이고 `<12>`는 commit SHA의 앞 12자다. `main` 버전끼리는 순서에 뜻이 없으므로 `--devel`로 최신을 고르지 않는다. 저장소의 [Images workflow](https://github.com/JeongJaeSoon/werft/blob/main/.github/workflows/images.yml)에서 초록색으로 끝난 `main` run의 commit을 골라 적는다.

```bash
VERSION=0.1.0-main-<12>
helm show chart oci://ghcr.io/jeongjaesoon/werft --version "$VERSION"
helm show values oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" | sed -n '/^images:/,/^$/p'
```

`images` 아래 세 이미지의 `digest`와 `worker.runtime`이 나오면 된다. 이 값은 chart에 들어 있으므로 설치별 values에 다시 적지 않는다. 적으면 다음 chart의 값을 계속 덮는다.

## 2. namespace와 Secret 만들기

Secret은 키마다 파일 하나인 디렉터리(`0700`, 파일 이름이 키)에서 만든다. 값이 명령줄과 셸 history에 남지 않는다.

| 키 | 값 |
| --- | --- |
| `DATABASE_URL` | PostgreSQL 연결 URL |
| `EGRESS_AUTHORIZER_TOKEN` | 무작위 값. api와 egress proxy가 같은 값을 쓴다 |
| `PLATFORM_SECRET_KEY` | `openssl rand -hex 32`의 64자 hex. 저장한 자격 증명을 봉인한다. 없으면 Pod가 뜨지 않는다 |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | object store key. IRSA로 서명하려면 두 키를 빼고 values에 `secrets.objectStoreKeys: false`와 `serviceAccounts.api.annotations`를 둔다 |
| `ANTHROPIC_API_KEY` | 선택. 세션이 쓸 Anthropic key의 기본 경로는 설치 뒤 콘솔의 **설정 > 워크스페이스 설정 > 모델 연결 > 연결 추가**다. 이 키는 환경 변수로 주는 대안이고, 두면 api에만 간다. 두지 않으면 helm에 `--set-json 'secrets.catalogEnv=[]'`를 준다. chart 기본값은 이 키를 api에 넘기므로 Secret에 없으면 Pod가 뜨지 않는다 |

```bash
kubectl create namespace werft
kubectl -n werft create secret generic werft --from-file=<secret-dir>
```

## 3. values 파일 만들기

설치별 값은 `values-<installation>.yaml` 하나에 둔다. 최소한 checkpoint bucket과 worker가 bucket에 닿는 경로가 들어간다.

```yaml
config:
  checkpoints:
    bucket: <bucket>
  egress:
    credentialAllowlist: "api.anthropic.com:443,registry.npmjs.org:443,rubygems.org:443,proxy.golang.org:443,sum.golang.org:443,github.com:443,<bucket>.s3.<region>.amazonaws.com:443"
```

`credentialAllowlist`는 기본값을 통째로 바꾼다. 기본 목록(provider와 패키지 registry)을 그대로 두고 저장소 호스트(`github.com:443`, 다른 Git 호스트를 쓰면 그 호스트도)와 bucket 호스트를 뒤에 더한다.

`config.aws.region`의 기본값은 `ap-northeast-1`이다. 다른 리전의 bucket이면 바꾼다. 연결, 저장소, MCP 서버, 상한은 values에 없다. 설치한 뒤 웹 콘솔에서 더하거나 `bun run settings:k8s import`로 가져온다. 기본값과 설명은 `helm show values`에 있다.

## 4. 설치하기

```bash
helm upgrade --install werft oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
  --namespace werft -f values-<installation>.yaml --timeout 10m
```

migrate Job이 먼저 schema를 올리고, 끝나면 api, egress proxy, reconciler, scheduler, slack이 한꺼번에 적용된다. 첫 설치가 이미지 경로나 pull 권한 오류로 실패하면 값을 고치고 같은 명령을 다시 돌린다.

```bash
kubectl -n werft get job werft-migrate
for d in api egress-proxy reconciler scheduler; do
  kubectl -n werft rollout status deploy/werft-$d --timeout=600s
done
```

release 이름에 `werft`가 들어가지 않으면 리소스 이름은 `<release>-werft-…`가 된다.

## 5. 확인하기

api Service를 로컬로 열어 `/readyz`를 부른다. readiness는 DB, schema, 설정을 본다.

```bash
kubectl -n werft port-forward svc/werft-api 13000:3000 &
PF=$!
until curl -fs -o /dev/null http://127.0.0.1:13000/healthz; do sleep 1; done
curl -fsS -w '\n%{http_code}\n' http://127.0.0.1:13000/readyz
curl -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:13000/docs
kill "$PF"
```

`{"status":"ready",…}`와 `200`이 나오면 설치가 된 것이다. `/docs`도 200이다. 사용자에게는 Ingress로 내보낸다. `ingress.enabled: true`와 controller별 설정은 [Kubernetes 설치 (Helm chart)](/run-server/self-hosting/operate/kubernetes-deployment#aws-값-넣기)에 있다.

## 6. 첫 owner와 API key

웹 콘솔 `/bootstrap`에서 첫 owner와 workspace를 만든다. api Pod가 기동할 때 토큰을 만들어 로그에 `BOOTSTRAP_TOKEN=…` 한 줄로 출력한다. 첫 owner가 생길 때까지 로그를 읽는 사람은 누구나 bootstrap할 수 있으므로 로그를 읽는 사람은 운영자로 제한한다.

chart의 api는 replica가 2개라 Pod마다 토큰을 따로 만들어 각자 로그에 출력한다(Pod마다 값이 다른 것은 kind에서 확인했다). `/bootstrap` 요청이 토큰을 읽은 Pod가 아닌 쪽에 닿으면 401을 받을 수 있다(틀린 토큰이 401이 되는 것은 kind에서 확인했다. 다만 어느 Pod가 받는지 구분하지 않아서, 다른 Pod에 닿았을 때의 401은 재현하지 못했다). 피하는 방법은 두 가지다. `BOOTSTRAP_TOKEN`을 Secret에 넣어 모든 Pod가 같은 값을 쓰게 하거나, replica 1로 시작한다. 전자는 Secret에 키 `BOOTSTRAP_TOKEN`을 만들고 `--set-json 'secrets.catalogEnv=["ANTHROPIC_API_KEY","BOOTSTRAP_TOKEN"]'`로 api에 넘긴다. 이 값은 기본값 `["ANTHROPIC_API_KEY"]`를 대체하므로 `ANTHROPIC_API_KEY`도 함께 적는다. 직접 정한 토큰은 32~256자여야 하고, 벗어나면 API가 기동하지 않는다. 이렇게 설치한 api(replica 2)가 `/readyz` 200까지 뜨는 것, 그 토큰으로 owner를 만드는 호출이 201이고 같은 토큰을 다시 쓰면 409 `BOOTSTRAP_DONE`인 것을 kind에서 확인했다. replica 1로 시작하는 방법은 실행해 보지 않았다.

API key는 api Pod 안에서 발급한다. 아래 `kubectl exec` 형식은 checkout이 필요 없다. 이 형식으로 key를 발급하고, 그 key로 `GET /v1/sessions`가 200, key 없이는 401인 것을 kind에서 확인했다(위 Secret 토큰으로 owner를 만든 뒤). `bun run keys:k8s`로 줄여 쓰는 방법은 [Kubernetes 설치 (Helm chart)](/run-server/self-hosting/operate/kubernetes-deployment#api-key-실행-권한-설정-문서)에 있다.

```bash
kubectl -n werft exec deploy/werft-api -c api -- \
  bun run apps/control-host/src/api/keys.ts create <owner_id> \
  --scopes sessions:read,sessions:write,sessions:approve,sessions:control,sessions:recover
```

stdout에 평문 key가 한 번만 나오고 stderr에 key id가 나온다. 사용자마다 owner와 key를 따로 발급한다. SDK와 HTTP API는 서버 주소와 이 key로 붙는다([SDK 설치](/getting-started/install)).

## kind에서 먼저 해 보기

노트북에서 같은 chart를 시험하려면 kind 클러스터에 PostgreSQL과 object store 대역을 먼저 띄운다. 대역은 저장소의 `deploy/kind/deps.yaml`에 있으므로 저장소를 받는다. 이 대역은 시험용이다. 실서버의 DB와 bucket으로 쓰지 않는다.

```bash
git clone https://github.com/JeongJaeSoon/werft.git
cd werft
kind create cluster --name werft-try
kubectl create namespace werft
kubectl -n werft create configmap localstack-init \
  --from-file=10-create-resources.sh=infra/localstack/init/10-create-resources.sh
kubectl -n werft apply -f deploy/kind/deps.yaml
SECRETS="$(mktemp -d)"
```

다음 명령의 `read -rs`는 프롬프트 없이 입력을 기다린다. 입력할 값은 `deploy/kind/deps.yaml`의 `POSTGRES_PASSWORD`이고, 값을 명령줄에 쓰지 않으려고 터미널에서 읽는다. 터미널 없이 실행하는 스크립트에서는 같은 값을 표준 입력으로 넘겨 이 줄을 채운다(kind에서 확인했다). Secret 값은 모두 이 kind 시험용이다. 실서버에는 2단계의 방식으로 직접 만든 값을 쓴다. Secret을 만든 뒤에는 변수와 임시 디렉터리를 지운다.

```bash
read -rs KIND_DB_PASSWORD
{ printf 'postgresql://postgres:'; printf '%s' "$KIND_DB_PASSWORD"; printf '@postgres:5432/sessions'; } > "$SECRETS/DATABASE_URL"
openssl rand -hex 32 | tr -d '\n' > "$SECRETS/EGRESS_AUTHORIZER_TOKEN"
openssl rand -hex 32 | tr -d '\n' > "$SECRETS/PLATFORM_SECRET_KEY"
printf test > "$SECRETS/AWS_ACCESS_KEY_ID"
printf test > "$SECRETS/AWS_SECRET_ACCESS_KEY"
kubectl -n werft create secret generic werft --from-file="$SECRETS"
unset KIND_DB_PASSWORD
rm -r "${SECRETS:?}"
helm upgrade --install werft oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
  --namespace werft -f deploy/kind/values.yaml --set-json 'secrets.catalogEnv=[]' --timeout 10m
```

Secret에 `ANTHROPIC_API_KEY`를 만들지 않으므로 helm에 `secrets.catalogEnv=[]`를 준다. 모델 key는 설치한 뒤 콘솔의 모델 연결 화면에서 넣는다.

이어서 4단계의 rollout 확인과 5단계의 확인을 그대로 한다. 끝나면 `kind delete cluster --name werft-try`로 클러스터를 지운다.

## 업그레이드와 제거

새 버전으로 올릴 때 worker 이미지가 바뀌면 직전 worker 이미지를 함께 넘겨야 한다. `--reuse-values`는 새 chart의 이미지를 적용하지 않으니 쓰지 않는다. 절차와 업그레이드 전 검사, 롤백은 [업그레이드](/run-server/self-hosting/upgrade)에 있다.

```bash
helm -n werft uninstall werft
```

`uninstall`은 `werft-migrate` Job을 남긴다(kind에서 확인했다). scheduler가 만든 worker Pod, workspace PVC, 직접 만든 Secret도 남는다고 보지만, 세션 없이 돌린 kind에서는 확인하지 못했다. 남은 Job은 같은 namespace에 다시 설치하는 것을 막지 않는다. PVC를 지우면 checkpoint되지 않은 작업이 사라지므로 세션이 끝났는지 먼저 본다.
