---
title: "Single-server install"
description: The steps to install Werft on one Linux server from the published images
---

Install Werft on one Linux server with Docker Compose. You do not build the images. You pull the published ones, pinned by digest. This page lists the steps up to the point where `/readyz` returns 200. To run on Kubernetes, read [Kubernetes install](/run-server/self-hosting/kubernetes) instead.

<Callout type="warn">
These steps were run with the published images on an Ubuntu (arm64) machine in OrbStack, from step 1 through step 6 and `key create` in step 7. Creating the first owner on the `/bootstrap` screen in step 7 and a real model call were not checked. `reset` was run once on an installation with no sessions, after its containers were taken down without `-v`; it exited 0 and removed the postgres volume. If anything differs, the repository's `scripts/test-ops.sh` and `infra/` files are the reference.
</Callout>

<Callout type="warn">
There is no `v` tag yet. For now, use the `main-<12>` tag published on every merge to `main`. It is not a release, and you pin the image it points to by digest. Once the first `v` tag exists, change `TAG` below to `v<version>` and check out the same tag in step 2. Every other command stays the same.
</Callout>

## Decisions

- The target is one server with the `local-docker` execution base. High availability is out of scope for this install. If you need several nodes, use the [Kubernetes install](/run-server/self-hosting/kubernetes).
- One operator-owned provider key is shared by every session. Issue each user their own owner and API key, and do not share them.
- On a real server the object store is a dedicated AWS S3 bucket. The LocalStack on the same host loses its checkpoints when the host or Docker restarts, so use it only to try things out.
- Access is a loopback bind and an SSH tunnel by default. Use a reverse proxy only when you have both TLS and a VPN or an IP allowlist.

## Requirements

| Item | Requirement |
| --- | --- |
| OS | Linux, `x86_64` or `arm64` |
| Docker Engine | 28 or later |
| Docker Compose | 2.24.6 or later |
| Disk | The Docker data root is XFS mounted with `prjquota`. `preflight` does not check this. Otherwise the scheduler's quota check fails in `deploy` and the install stops. It does not work on Docker Desktop. The default OrbStack machine is btrfs and does not meet this. Inside the machine, make XFS with `mkfs.xfs` on a sparse image file (60G), mount it with `loop,prjquota` and set it as Docker's `data-root`; then the mount options show `prjquota` and the quota check in `deploy` passes (checked once on one OrbStack machine) |
| Time | NTP is in sync. Docker starts on its own after a reboot |
| Tools | `git`, `jq`, `curl`, `openssl`, Bun 1.3.14, the Docker Buildx plugin. An account that can reach the Docker daemon |
| Network | The host can pull images from `ghcr.io` and Docker Hub. The packages need no login. Sessions reach `api.anthropic.com` and `github.com` |

The install needs a repository checkout, because the compose files and `scripts/test-ops.sh` are read from it. The images are not built from the checkout.

## 1. Read the image digests

Pick a tag and read the digest of the three images. Each image is an index of `linux/amd64` and `linux/arm64`, so the server pulls its own architecture.

In `main-<12>`, `<12>` is the first 12 characters of the commit SHA. To choose a commit, open the [Images workflow](https://github.com/JeongJaeSoon/werft/actions/workflows/images.yml) and pick a `main` push run that finished green.

```bash
TAG=main-<12>
for app in control-host worker egress-proxy; do
  echo "$app $(docker buildx imagetools inspect "ghcr.io/jeongjaesoon/werft-$app:$TAG" --format '{{.Manifest.Digest}}')"
done
```

Each of the three lines should end in a digest that starts with `sha256:`. `TAG` only finds the digest; the install itself uses the digest.

### When you build the images yourself

This is the path for when you cannot pull the published images (a commit that was not published). From a checkout of the commit you will install, build the three images, push them to a registry the host can pull from, and write the digests that the push returns into the release file of step 4. Only `amd64` and `arm64` are supported. Images are built for the architecture of the machine that builds them, so build on the same architecture as the host. This path was carried over from the script and the compose files and was not run in the verification above.

```bash
R=<registry>   # for example 127.0.0.1:5000
export API_IMAGE=$R/werft-control-host:rc WORKER_IMAGE=$R/werft-worker:rc \
  EGRESS_PROXY_IMAGE=$R/werft-egress-proxy:rc
docker compose -f infra/compose.yml --profile apps --profile worker build api worker egress-proxy
for i in "$API_IMAGE" "$WORKER_IMAGE" "$EGRESS_PROXY_IMAGE"; do
  docker push -q "$i" && docker inspect --format '{{index .RepoDigests 0}}' "$i"
done
unset API_IMAGE WORKER_IMAGE EGRESS_PROXY_IMAGE
```

## 2. Get the checkout

Check out the same commit as the images. `<12>` is the 12 characters from `TAG` above. After the first `v` tag, use `git checkout v<version>`.

```bash
git clone https://github.com/JeongJaeSoon/werft.git
cd werft
git checkout <12>
bun install --frozen-lockfile
```

## 3. Write the configuration

Secrets live only in an env file outside the repository. Only the operator may read it; the script refuses a file that group or others can access.

```bash
sudo mkdir -p /etc/agent-platform
sudo install -m 600 -o "$USER" infra/test-ops.env.example /etc/agent-platform/test-ops.env
sudo install -d -m 700 -o "$USER" /var/lib/agent-platform/test-ops
```

Open `/etc/agent-platform/test-ops.env` in an editor and fill in the following. Use an editor that writes in place: tools such as `sed -i` create a temporary file and fail with `Permission denied` in `/etc/agent-platform`.

| Variable | Value |
| --- | --- |
| `POSTGRES_PASSWORD` | A random value. Use only letters, digits, `.` `_` `~` `-` |
| `EGRESS_AUTHORIZER_TOKEN` | A random value of 32 or more characters |
| `PLATFORM_SECRET_KEY` | 64 hex characters from `openssl rand -hex 32`. If you lose it, stored credentials cannot be read |
| `ANTHROPIC_API_KEY` | The Anthropic key sessions use. It goes only to the API container |
| `BOOTSTRAP_TOKEN` | Uncomment it and set 32 to 256 random characters. It creates the first owner. If you leave it out, the API generates one and prints it to the container log |

The example file already fills `EXECUTION_INSTALLATION_ID` (`test-ops`), `PLATFORM_SETTINGS_DOCUMENT` (`/etc/agent-platform/settings.json`), `EGRESS_CREDENTIAL_ALLOWLIST` (`api.anthropic.com:443,github.com:443`), `EGRESS_CREDENTIAL_PRIVATE_ALLOWLIST` (`localstack:4566`) and `EXECUTION_WORKSPACE_QUOTA` (`on`). For the default LocalStack install, leave them. If one is empty, compose refuses to render.

Do not print values to the terminal or pass them as command arguments. Generate random values with `openssl rand -hex 32` and paste them into the editor.

Put the settings document at `/etc/agent-platform/settings.json`. It names the model connection, the GitHub repository and the profile that sessions use. It holds environment variable names, not values, so it has no secrets. Change only the repository URL. The example assumes a public repository. The repository entry needs `"auth": { "kind": "github_app" }`. Without it the import would leave that repository out, so `preflight` stops the install. With this value added it passed. For a private one, follow the [API server page](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md) (in Korean).

The file must be `0644` because the migrate container reads it. Create an empty file first, then fill it in an editor with the content below.

```bash
sudo install -m 644 -o "$USER" /dev/null /etc/agent-platform/settings.json
```

```json
{
  "version": 1,
  "connections": {
    "anthropic": {
      "kind": "anthropic",
      "endpoint": "https://api.anthropic.com",
      "auth": { "kind": "api_key", "value_env": "ANTHROPIC_API_KEY" }
    }
  },
  "repositories": {
    "sample-app": {
      "url": "https://github.com/<owner>/<repo>.git",
      "branch": "main",
      "auth": { "kind": "github_app" },
      "profiles": ["claude-coding"]
    }
  },
  "mcp_servers": {},
  "profiles": {
    "claude-coding": {
      "runtime_kind": "claude_agent_sdk",
      "runtime_version": "0.3.270",
      "model": "claude-sonnet-5",
      "tools": ["Read", "Edit", "Write", "Glob", "Grep", "Bash"],
      "permission_mode": "default",
      "provider": {
        "kind": "anthropic",
        "endpoint": "https://api.anthropic.com",
        "auth": { "kind": "api_key", "value_env": "ANTHROPIC_API_KEY" }
      },
      "project_settings": { "claude_md": true }
    }
  }
}
```

Once the content is in, compute the file's digest.

```bash
bun run scripts/lib/test-ops.ts settings-digest /etc/agent-platform/settings.json
```

## 4. Write the release file

`release.json` names the commit to install, the digest of the three images and the digest of the settings document. An image given only by tag is refused. Run this in the shell where `TAG` from step 1 is still set.

```bash
SETTINGS_DIGEST="$(bun run scripts/lib/test-ops.ts settings-digest /etc/agent-platform/settings.json)"
digest() { docker buildx imagetools inspect "ghcr.io/jeongjaesoon/werft-$1:$TAG" --format '{{.Manifest.Digest}}'; }
jq -n \
  --arg commit "$(git rev-parse HEAD)" \
  --arg control "ghcr.io/jeongjaesoon/werft-control-host@$(digest control-host)" \
  --arg worker "ghcr.io/jeongjaesoon/werft-worker@$(digest worker)" \
  --arg egress "ghcr.io/jeongjaesoon/werft-egress-proxy@$(digest egress-proxy)" \
  --arg settings "$SETTINGS_DIGEST" \
  '{source_commit: $commit,
    images: {control_host: $control, worker: $worker, egress_proxy: $egress},
    settings_digest: $settings}' > release.json
```

## 5. Install

The object store is chosen at the first `deploy` and cannot be changed afterwards. The default is a LocalStack on the same host. For a real server, put `TEST_OPS_OBJECT_STORE=s3` in front of both commands below, prepare a dedicated AWS S3 bucket, and fill `AWS_REGION`, `S3_BUCKET`, `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` in the env file. Add `<bucket>.s3.ap-northeast-1.amazonaws.com:443` to `EGRESS_CREDENTIAL_ALLOWLIST` (`s3.ap-northeast-1.amazonaws.com:443` if the bucket name contains a `.`) and empty `EGRESS_CREDENTIAL_PRIVATE_ALLOWLIST` (`preflight` refuses it while `localstack:4566` remains). For the bucket, follow [Dedicated S3 bucket](#dedicated-s3-bucket). This S3 install was not run; the verification of steps 1 to 6 on this page was done on a LocalStack install.

`preflight` checks the Docker version, the checkout, the env file and the release file first. The scheduler checks the disk quota during `deploy`. If it passes, `deploy` installs from the same file.

```bash
scripts/test-ops.sh preflight release.json
scripts/test-ops.sh deploy release.json
```

`deploy` runs migrate, starts the API, scheduler and reconciler, and waits for their health checks. LocalStack loses checkpoints when the host or Docker restarts, and after a restart the API can refuse to start (recover with `reseed` or `reset` as [Reboot](#reboot) describes). Use it only to try things out.

If the first `deploy` fails, `reset` cannot remove it. Fix the cause, delete the containers, volumes and network of this project (`agent-platform-test-ops`) by hand, and run `deploy` again.

## 6. Check

The API listens only on `127.0.0.1:3000`.

```bash
curl -fsS -w '\n%{http_code}\n' http://127.0.0.1:3000/readyz
```

If you see `{"status":"ready",…}` and `200`, the install works. At the address your users will use, `/docs` should also return 200 without authentication.

To reach it from another machine, open an SSH tunnel.

```bash
ssh -N -L 3000:127.0.0.1:3000 <user>@<server>
```

To expose it on an internal DNS name, put a reverse proxy with TLS and a VPN or an IP allowlist in front. Turn buffering off for the event stream (SSE) and keep the read timeout long. Never expose PostgreSQL or the Docker socket. This reverse proxy was not set up and checked.

## 7. First owner and API key

Open `http://127.0.0.1:3000/bootstrap` in a browser and enter the `BOOTSTRAP_TOKEN` from the env file, the owner details and a workspace name. If you did not put it in the env file, find the line that starts with `BOOTSTRAP_TOKEN` in the API container's log and use its value. Anyone who can read that log can bootstrap until the first owner exists, so limit who can read it to operators. Sending the same token again returns `409 BOOTSTRAP_DONE`. Then sign in at `/login`. Creating the owner on this screen was not checked.

Issue a separate owner and API key for each user. The plain key is printed once, so capture it in a variable and hand it over directly.

```bash
KEY="$(scripts/test-ops.sh key create <owner_id> \
  --scopes sessions:read,sessions:write,sessions:approve,sessions:control,sessions:recover)"
```

`<owner_id>` is a name that groups the sessions of this key. Choose a different value for each user. It is separate from web console accounts, and you do not use the workspace id.

The SDK and the HTTP API connect with this server address and key ([SDK install](/getting-started/install)).

## Take it down

Check state with `scripts/test-ops.sh status`. To empty the installation, use `reset`.

```bash
scripts/test-ops.sh reset --yes
```

`reset` removes this installation's containers and volumes (the database and LocalStack), and the worker containers and workspace volumes that sessions created. Sessions, checkpoints and API keys go with them, so take a [backup](#backup-and-restore) first.

`reset` removes the volumes too. To take it down and keep the volumes, use `stop`; to bring a stopped installation back on the same volumes, use `start`.

```bash
scripts/test-ops.sh stop
scripts/test-ops.sh start
```

`stop` stops the api, scheduler, reconciler and the workers the scheduler launched, and removes the containers and network but keeps the volumes. `start` brings up the release that `current.json` in the state directory names and waits for the healthchecks. It works the same whether the installation went down through `stop`, a `compose down` or a host reboot. Do not use `deploy`: once a release is recorded it refuses with `use upgrade`, and `upgrade` on a stopped installation fails because postgres is not running. `start` also refuses a host that never deployed and an installation with an unfinished upgrade (`pending.json`); for the latter, call `upgrade` again with the same release file.

`start` accepts a checkout that is not the release's source commit as long as `infra/` is the same as at that commit, because only the compose files are read from the checkout.

What stays is the database volume. LocalStack keeps S3 in memory with no volume, so taking its container down loses the checkpoint objects even without `-v`. If the database still holds uncollected checkpoints while the bucket is empty, the API refuses to start; then use `reseed` or `reset` from [Reboot](#reboot). To keep the data, install with S3. These commands were checked on a LocalStack installation whose only session had failed (no uncollected checkpoint). Bringing back, with `start`, an installation that a hand-run `compose down` had taken down, and bringing one back after a reboot, were both run: `/readyz` returned 200 and the owner could log in. `start` on a LocalStack installation with uncollected checkpoints was not checked.

## Operations

<Callout type="warn">
This section was written by reading `scripts/test-ops.sh` and the code. On the verification machine, `backup`, `reseed`, `restore-drill`, a reboot, an S3 object-store install and a TLS reverse proxy were not run. The arguments and behavior below were checked against the script's argument handling and the code, not by running them end to end on a real server.
</Callout>

### Access path

The API (3000 by default) and PostgreSQL (5432 by default) listen only on the host's loopback. Users come in through an SSH tunnel, and only the operator uses PostgreSQL, from inside the server. The firewall allows only SSH and the TLS endpoint you chose.

To publish the API under an internal DNS name, put a reverse proxy in front. The upstream stays `127.0.0.1:3000`. Narrow who can reach the address with a VPN range or an IP allowlist, and terminate TLS there. The proxy passes the `Host` the browser sent on to the upstream unchanged. On a state-changing browser request the API refuses it when the host in `Origin` differs from `Host`, so rewriting `Host` to the upstream's makes the web console's changes fail. The event stream (SSE) keeps connections open for a long time, so turn off `proxy_buffering` and request buffering and set the read and send timeouts long, such as one hour. Whichever path you choose, never open PostgreSQL or the Docker socket outside the proxy or the firewall. The scheduler uses the Docker socket only to manage workers, and the host TCP socket stays off.

### Dedicated S3 bucket

On a real server, use one bucket per installation. This work brings AWS permissions and cost, so the person installing it does it themselves.

- The region is `ap-northeast-1`. Default encryption is SSE-S3 (`AES256`), and all public access is blocked.
- Turn on versioning and Object Lock. Set no default retention. Checkpoints are protected by legal hold alone, and a default retention makes checkpoint cleanup and the deletes in `preflight` fail.
- Give the API's IAM user, on this bucket only, `s3:PutObject`, `s3:GetObject`, `s3:GetObjectVersion`, `s3:GetObjectLegalHold`, `s3:PutObjectLegalHold`, `s3:DeleteObjectVersion`, and for reading the bucket settings `s3:ListBucket`, `s3:ListBucketVersions`, `s3:GetBucketVersioning`, `s3:GetBucketObjectLockConfiguration`, `s3:GetEncryptionConfiguration`. Do not grant permission to create buckets.
- Set no lifecycle rule that expires object versions. If an organization policy has one, exclude this bucket.
- A restore drill writes to a drill bucket with the same credentials. Name drill buckets `<bucket>-drill-*` and give that name the same permissions. The operator creates drill buckets with their own permissions.

The credentials go only to the API and maintenance containers. Workers go through the egress proxy, and the API signs that request for the session's scope. The `TEST_OPS_OBJECT_STORE=s3 preflight` in step 5 must pass its round trip of upload, legal hold, version read, hold release and scratch version delete before you install.

### Backup and restore

```bash
scripts/test-ops.sh backup
```

`backup` stops the api, scheduler, reconciler and worker containers, bundles the database and checkpoint objects into `$TEST_OPS_STATE_DIR/backups/backup-<timestamp>`, and starts the stopped services again. Turns in progress are cut off, and the reconciler reclaims them later. A failed backup stays as `.failed`, and one cut short by a forced stop stays as `.partial`; neither counts as a successful copy. If the services cannot be restarted, the command fails even when the backup succeeded, so check with `status`.

- Schedule: once a day at a quiet hour, and right before every upgrade.
- Retention: keep the last 14 days of successful copies on the host and the last 90 days in an encrypted off-host store. A backup holds the whole database and the API key hashes. Keep the directory at `0700`, encrypt transfer and storage, and keep access to a minimum.
- Alerts: treat a non-zero exit, a failure to restart the services, and 26 hours without a new successful copy as failures.
- Restore drill: once a month, and after the first backup following each upgrade.

A restore drill restores a backup into a new project and its object store and compares every checkpoint pointer by version. On a LocalStack install, call it without a bucket. On an S3 install, pass a freshly created, empty bucket with `--bucket` for every drill. It refuses a target that is the original bucket or is not empty. This restore drill was not run.

```bash
# Restore a backup into a throwaway project and a new, empty bucket, then verify it
scripts/test-ops.sh restore-drill /var/lib/agent-platform/test-ops/backups/backup-<timestamp> --bucket <drill-bucket>
```

The output goes to `restore-drills/` in the state directory, and the verdict is one line in `history.log`. The drill project is removed when it ends (add `--keep` to inspect it, and change the ports with `--port-base` if they collide; the default starts at 25432). Objects in a drill bucket carry a legal hold, so to delete the bucket, release the hold on each version, delete the versions, then delete the bucket.

A restore drill restores only PostgreSQL and the object store and does not start the API. It does not show that a real session continues on the restored data, so record that as not checked.

### Reboot

A LocalStack install loses its objects on reboot. Leave a backup before a reboot you know about and restore from it. The `backup --stop` and `reseed` procedure below was not run.

```bash
# Back up, leave the writers stopped, restart the host, then restore the objects
scripts/test-ops.sh backup --stop
sudo reboot
scripts/test-ops.sh reseed /var/lib/agent-platform/test-ops/backups/backup-<timestamp>
```

`reseed` checks the backup's manifest, project, bucket and checksum, uploads the objects into the empty LocalStack, pins every uncollected checkpoint again and brings the installation back up. If a new checkpoint appeared after the last backup it refuses, and then only `reset` is left. An API that refuses to start after an unexpected restart is in the same state and is fixed the same way.

After a reboot the stack does not come back by itself. On the verification machine (OrbStack, Docker starting at boot) only egress-proxy, reconciler and scheduler (`restart: unless-stopped`) were up afterwards; postgres, api and localstack (no restart policy) were `Exited`. After a reboot, run `scripts/test-ops.sh start` yourself. On that machine `start` exited 0, `/readyz` returned 200, the owner from before the reboot could log in and the session record was still there. An S3 install keeps its objects across a restart, so `start` alone is enough.

Before the reboot, check that no turn is in progress, that `status` is healthy and that the latest backup has been copied off the host. After it, check NTP, XFS `prjquota`, Docker's automatic start, and disk and inode headroom again. Then check that `status` and `/readyz` are healthy, and that resuming a session from before the reboot lets a new worker continue the old workspace. The API must be reachable only through the path you chose, and PostgreSQL and the Docker socket must be closed from outside.

### Day 1

- Run `scripts/test-ops.sh status` at the start, an hour later and before the end of the day. It shows the containers, the deployed release, the object store, `/readyz`, scheduler and reconciler health, and disk usage in one go.
- Read the api, scheduler and reconciler logs, and the disk, inode and quota of the Docker data root. Act before free space falls under 20%.
- Run checkpoint cleanup once a week, away from a backup. Run `bun run apps/control-host/src/api/checkpoint-gc.ts` in the API container, and check it first with `docker exec -e CHECKPOINT_GC_DRY_RUN=1`.
- Test the automated backup and its failure alert. Do not test by deleting a production backup.
- Settle how you hand over and revoke each user's API key.
- Set a monthly limit in the Anthropic console, and watch the per-session cap (`SESSION_COST_LIMIT_USD`, 25 by default) together with the real cost.
- For monitor definitions, use the [Datadog monitoring baseline](/run-server/self-hosting/operate/monitoring-datadog).
