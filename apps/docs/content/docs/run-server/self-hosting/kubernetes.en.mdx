Install Werft on Kubernetes from the published Helm chart. You do not need a repository checkout: one chart carries the digest of all three images and the worker runtime. Follow this page alone until `/readyz` returns 200. To run on one Linux server with Docker Compose, read [Single-server install](/run-server/self-hosting/single-server) instead.

<Callout type="warn">
The first release, `v0.1.0`, is published, and chart `0.1.0` (appVersion `v0.1.0`) went out with it. To install the release, set `VERSION` to `0.1.0` (the chart version is the tag without the `v`). Change only `VERSION` and the commands stay the same. The end-to-end run on kind used chart `0.1.0-main-<12>` of the same commit as `v0.1.0`, though; this procedure was not followed with chart `0.1.0`. `0.1.0-main-<12>` is not a release.
</Callout>

## Requirements

| Item | Requirement |
| --- | --- |
| Cluster | Kubernetes with a CNI that enforces NetworkPolicy. Without enforcement, workers are not isolated |
| Tools | `helm` 3, `kubectl`, `curl` |
| PostgreSQL | Version 16, reachable from inside the cluster |
| S3-compatible object store | One bucket. The default protection mode `locked` needs a bucket with versioning, Object Lock and default SSE-S3 (`AES256`) encryption; otherwise the API refuses to start |
| Network | The cluster can pull the chart and images from `ghcr.io`. The packages need no login |

The chart does not create PostgreSQL, the object store or Secret values. It does not create worker Pods either: the scheduler creates one per session. The published images are an index of `linux/amd64` and `linux/arm64`, so each node pulls its own architecture.

### Workspace storage and its limits

On a single server, XFS `prjquota` limits the workspace in both size and inodes ([Disk setup](/run-server/self-hosting/single-server)). Kubernetes has no such requirement, and the limits are built differently. The table puts the two paths side by side under the same headings.

| Item | Single server | Kubernetes |
| --- | --- | --- |
| Where it lives | One Docker `local` volume per session, on the XFS under the Docker data root | One PVC per session (`werft-ws-<installationId>-<sessionId>`), mounted at the worker's `/workspace`. `ReadWriteOnce`, `Filesystem`. `/tmp` and HOME are memory-backed emptyDirs; no hostPath is used |
| Size limit | `EXECUTION_WORKSPACE_QUOTA_MB`, default 4096 MiB (minimum 1024) | The PVC's `requests.storage`, helm `worker.workspace.quotaMb`, default 4096 MiB (minimum 1024). Whether it is enforced is up to the StorageClass |
| Inode limit | `EXECUTION_WORKSPACE_QUOTA_INODES`, default 1,000,000 | **None.** Neither Werft nor the chart sets one. The filesystem default applies (ext4 fixes the count when it is made) |
| Enforced by | XFS `prjquota` (the kernel). Checked by the scheduler preflight | The kubelet and the CSI driver. Werft only requests the size; it does not read usage, and no preflight checks it |
| When exceeded | Worker writes fail with `ENOSPC`. If the limits cannot be set, the scheduler does not start | `ENOSPC` if the StorageClass enforces the size. If it does not, there is no limit. Node disk outside the PVC (mostly the log) is capped by `worker.ephemeralStorageMb` (default 1024 MiB, requests = limits); past it the kubelet evicts the Pod |
| What the operator sets | The filesystem of the Docker data root and its size, and the two limits | `worker.storageClass` (empty is the cluster default), `worker.workspace.quotaMb`, `worker.ephemeralStorageMb`, and the filesystem size of the worker nodes |
| Check commands | `findmnt -no FSTYPE,OPTIONS -T "$(docker info -f '{{.DockerRootDir}}')"`, `xfs_quota -x -c 'report -p'` | Below |

```bash
kubectl get storageclass
kubectl -n werft get pvc -l app.kubernetes.io/part-of=werft,werft.installation=<installationId> \
  -o custom-columns=NAME:.metadata.name,REQUEST:.spec.resources.requests.storage,CAPACITY:.status.capacity.storage
kubectl -n werft exec <worker-pod> -- df -h /workspace
kubectl -n werft exec <worker-pod> -- df -i /workspace
```

In `kubectl get storageclass`, check that the provisioner of the StorageClass you use creates volumes whose size is enforced (for example, an EBS gp3 volume is as large as the size requested). `REQUEST` in the PVC listing is what Werft asked for, and `CAPACITY` is the size the provisioner made. The total in `df -h` can differ from either because of filesystem overhead, so do not judge by whether they match. Check that `CAPACITY` is at least `REQUEST`, and that writing more than `REQUEST` into a test PVC of the same StorageClass ends in `ENOSPC`. `df -i` shows the inode total. These commands were not run against a cluster (**NOT VERIFIED**). The values were read from the code (`specs.ts`, `config.ts`) and the chart.

- If you change `worker.workspace.quotaMb`, the PVC of an existing session no longer matches the size it was created with, and that session is refused (compared through the `werft.workspace-size` annotation). Change it while no session is in progress so that it applies from the new sessions on.
- The default StorageClass of kind (local-path style) is known not to enforce the PVC size. This was not measured in this repository (**NOT VERIFIED**). A PVC that is `Bound` on kind does not mean a limit is in place.
- **Known limit.** There is no inode limit, and the size limit is left to the StorageClass. The chart does not refuse a StorageClass that does not enforce the size. A code change to close this is outside the scope of this page.

## 1. Choose a version

Always give the version exactly. The chart version of a `main` merge is `0.1.0-main-<12>`, where `<12>` is the first 12 characters of the commit SHA. Order among `main` versions means nothing, so do not pick the latest with `--devel`. Open the [Images workflow](https://github.com/JeongJaeSoon/werft/blob/main/.github/workflows/images.yml) and pick the commit of a `main` run that finished green.

```bash
VERSION=0.1.0-main-<12>
helm show chart oci://ghcr.io/jeongjaesoon/werft --version "$VERSION"
helm show values oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" | sed -n '/^images:/,/^$/p'
```

You should see the `digest` of the three images and `worker.runtime` under `images`. They are inside the chart, so do not repeat them in your values file. If you do, they keep overriding the next chart.

## 2. Create the namespace and Secret

Build the Secret from a directory with one file per key (`0700`, the file name is the key). The values never reach the command line or shell history.

| Key | Value |
| --- | --- |
| `DATABASE_URL` | PostgreSQL connection URL |
| `EGRESS_AUTHORIZER_TOKEN` | A random value. The API and the egress proxy use the same one |
| `PLATFORM_SECRET_KEY` | 64 hex characters from `openssl rand -hex 32`. It seals stored credentials. Pods do not start without it |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | Object store keys. To sign with IRSA instead, leave both out and set `secrets.objectStoreKeys: false` and `serviceAccounts.api.annotations` in your values |
| `ANTHROPIC_API_KEY` | The Anthropic key sessions use. It goes only to the API |

```bash
kubectl create namespace werft
kubectl -n werft create secret generic werft --from-file=<secret-dir>
```

## 3. Write the values file

Keep installation-specific values in one `values-<installation>.yaml`. At minimum it holds the checkpoint bucket and the route workers use to reach it.

```yaml
config:
  checkpoints:
    bucket: <bucket>
  egress:
    credentialAllowlist: "api.anthropic.com:443,registry.npmjs.org:443,rubygems.org:443,proxy.golang.org:443,sum.golang.org:443,github.com:443,<bucket>.s3.<region>.amazonaws.com:443"
```

`credentialAllowlist` replaces the whole default. Keep the default list (the provider and the package registries) and append the repository hosts (`github.com:443`, plus any other Git host you use) and the bucket host.

`config.aws.region` defaults to `ap-northeast-1`; change it if your bucket is in another region. Connections, repositories, MCP servers and limits are not in the values file. After the install, add them in the web console or import them with `bun run settings:k8s import`. Defaults and explanations are in `helm show values`.

## 4. Install

```bash
helm upgrade --install werft oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
  --namespace werft -f values-<installation>.yaml --timeout 10m
```

The migrate Job raises the schema first. After it finishes, the API, egress proxy, reconciler, scheduler and slack are applied together. If the first install fails on an image path or a pull permission, fix the values and run the same command again.

```bash
kubectl -n werft get job werft-migrate
for d in api egress-proxy reconciler scheduler; do
  kubectl -n werft rollout status deploy/werft-$d --timeout=600s
done
```

If the release name does not contain `werft`, resource names become `<release>-werft-…`.

## 5. Check

Open the API Service locally and call `/readyz`. Readiness checks the database, the schema and the settings.

```bash
kubectl -n werft port-forward svc/werft-api 13000:3000 &
PF=$!
until curl -fs -o /dev/null http://127.0.0.1:13000/healthz; do sleep 1; done
curl -fsS -w '\n%{http_code}\n' http://127.0.0.1:13000/readyz
curl -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:13000/docs
kill "$PF"
```

If you see `{"status":"ready",…}` and `200`, the install works. `/docs` returns 200 too. Expose it to users through an Ingress. `ingress.enabled: true` and the controller-specific settings are in [Kubernetes install (Helm chart)](/run-server/self-hosting/operate/kubernetes-deployment#adding-aws-values).

## 6. First owner and API key

Create the first owner and workspace at the web console's `/bootstrap`. When the API Pod starts, it generates a token and prints it to its log as a single `BOOTSTRAP_TOKEN=…` line. Anyone who can read that log can bootstrap until the first owner exists, so limit who can read it to operators.

The chart runs two API replicas, and each Pod generates its own token and prints it to its own log (that the value differs per Pod was checked on kind). A `/bootstrap` request that reaches a Pod other than the one whose token you read can get 401 (that a wrong token gets 401 was checked on kind; the request was not pinned to a Pod, so the 401 from reaching another Pod was not reproduced). There are two ways around it. Put `BOOTSTRAP_TOKEN` in the Secret so every Pod uses the same value, or start with one replica. For the first, add a key `BOOTSTRAP_TOKEN` to the Secret and hand it to the API with `--set-json 'secrets.catalogEnv=["ANTHROPIC_API_KEY","BOOTSTRAP_TOKEN"]'`. This value replaces the default `["ANTHROPIC_API_KEY"]`, so list `ANTHROPIC_API_KEY` too. A token you choose yourself must be 32 to 256 characters, or the API does not start. That an API installed this way (two replicas) reaches `/readyz` 200, that the call creating the owner with that token returns 201, and that using the same token again returns 409 `BOOTSTRAP_DONE` were checked on kind. Starting with one replica was not run.

Issue API keys inside the API Pod. The `kubectl exec` form below needs no checkout. Issuing a key in this form, then `GET /v1/sessions` returning 200 with the key and 401 without it, were checked on kind (after creating the owner with the Secret token above); the `bun run keys:k8s` shortcut is described in [Kubernetes install (Helm chart)](/run-server/self-hosting/operate/kubernetes-deployment#api-keys-run-permissions-and-the-settings-document).

```bash
kubectl -n werft exec deploy/werft-api -c api -- \
  bun run apps/control-host/src/api/keys.ts create <owner_id> \
  --scopes sessions:read,sessions:write,sessions:approve,sessions:control,sessions:recover
```

The plain key is printed once on stdout and the key id on stderr. Issue a separate owner and key for each user. The SDK and the HTTP API connect with the server address and this key ([SDK install](/getting-started/install)).

## Try it on kind first

To try the same chart on a laptop, start stand-ins for PostgreSQL and the object store in a kind cluster first. The stand-ins are in the repository's `deploy/kind/deps.yaml`, so clone it. They are for trying things out. Never use them as a real server's database or bucket.

```bash
git clone https://github.com/JeongJaeSoon/werft.git
cd werft
kind create cluster --name werft-try
kubectl create namespace werft
kubectl -n werft create configmap localstack-init \
  --from-file=10-create-resources.sh=infra/localstack/init/10-create-resources.sh
kubectl -n werft apply -f deploy/kind/deps.yaml
SECRETS="$(mktemp -d)"
```

The next command, `read -rs`, waits for input without a prompt. Type the `POSTGRES_PASSWORD` value in `deploy/kind/deps.yaml`; it is read from the terminal so the value is not written on the command line. In a script that runs without a terminal, pass the same value on standard input to fill this line (checked on kind). Every Secret value is for this kind try-out only. On a real server, use values you create yourself as in step 2. After the Secret is created, the variable and the temporary directory are removed.

```bash
read -rs KIND_DB_PASSWORD
{ printf 'postgresql://postgres:'; printf '%s' "$KIND_DB_PASSWORD"; printf '@postgres:5432/sessions'; } > "$SECRETS/DATABASE_URL"
openssl rand -hex 32 | tr -d '\n' > "$SECRETS/EGRESS_AUTHORIZER_TOKEN"
openssl rand -hex 32 | tr -d '\n' > "$SECRETS/PLATFORM_SECRET_KEY"
printf test > "$SECRETS/AWS_ACCESS_KEY_ID"
printf test > "$SECRETS/AWS_SECRET_ACCESS_KEY"
printf unused > "$SECRETS/ANTHROPIC_API_KEY"
kubectl -n werft create secret generic werft --from-file="$SECRETS"
unset KIND_DB_PASSWORD
rm -r "${SECRETS:?}"
helm upgrade --install werft oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
  --namespace werft -f deploy/kind/values.yaml --timeout 10m
```

Then run the rollout checks of step 4 and the checks of step 5 as written. When you are done, delete the cluster with `kind delete cluster --name werft-try`.

## Upgrade and remove

When an upgrade changes the worker image, you must pass the previous worker image along. Do not use `--reuse-values`: it does not apply the new chart's images. The procedure, the pre-upgrade check and rollback are in [Upgrade](/run-server/self-hosting/upgrade).

```bash
helm -n werft uninstall werft
```

`uninstall` leaves the `werft-migrate` Job (checked on kind). It should also leave the worker Pods the scheduler created, the workspace PVCs and any Secret you made yourself, but the kind run had no sessions, so that was not checked. A leftover Job does not block installing again in the same namespace. Deleting a PVC loses work that was not checkpointed, so check first that sessions have ended.
