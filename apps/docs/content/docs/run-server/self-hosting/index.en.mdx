This is how to install a Werft server yourself so a team can share it. If you only want to try a server alone, [Run a dev server](/run-server/dev-server) is enough. There are two install methods: single server and Kubernetes. Pick one in the table below, and its page lists the install steps up to `/readyz` returning 200.

## Choose an install method

| Method | Runs on | Prerequisites | Page |
| --- | --- | --- | --- |
| Single server | One Linux server, Docker Compose. One worker container per session. HA is out of scope | Docker 28 or later, Compose 2.24.6 or later, a Docker data root on XFS mounted with `prjquota`, a repository checkout | [Single-server install](/run-server/self-hosting/single-server) |
| Kubernetes | The published Helm chart. One worker Pod per session | A CNI that enforces NetworkPolicy, `helm` 3, PostgreSQL 16, an S3-compatible object store (the default protection mode needs a bucket with versioning, Object Lock and SSE-S3). No repository checkout | [Kubernetes install](/run-server/self-hosting/kubernetes) |

The rule of thumb: choose single server to run on one machine and operate it with `scripts/test-ops.sh`; choose Kubernetes if you already have a cluster, PostgreSQL and an object store and want to install by chart. Both need to pull the published packages from `ghcr.io` without a login. If you have already installed, read [Upgrade](/run-server/self-hosting/upgrade).

With either method the server is the API (with the web console), the scheduler, the reconciler, the egress proxy, PostgreSQL and an S3-compatible object store. There is no Git server, so add the GitHub repositories sessions use in the settings document or the console.

## Published packages

The install uses published packages, not ones you build yourself. A merge to `main` makes the [Images workflow](https://github.com/JeongJaeSoon/werft/blob/main/.github/workflows/images.yml) publish the images and the chart with no approval. A `v*` tag goes through approval in the `release` environment.

| Package | Address | Merge to `main` | `v*` tag |
| --- | --- | --- | --- |
| Images | `ghcr.io/jeongjaesoon/werft-control-host`, `werft-worker`, `werft-egress-proxy` | Tag `main-<12>` | Tag `v<version>` |
| Helm chart | `oci://ghcr.io/jeongjaesoon/werft` | Version `0.1.0-main-<12>` | Version `<version>` (no `v`) |
| SDK | npm `@werft-ai/sdk` | [SDK install](/getting-started/install) | [SDK install](/getting-started/install) |

Each image is an index of `linux/amd64` and `linux/arm64`, and the install pins it by digest. The chart carries the three image digests and the worker runtime. The packages need no login. `<12>` is the first 12 characters of the commit SHA. `main` versions have no order among themselves, so select the commit of a successful Images workflow run and pin its exact version.

<Callout type="warn">
The first release, `v0.1.0`, is published. `main-<12>` is not a release, and it can be published without every corresponding source archive being confirmed. To install the release, change only the tag value in the install pages' commands to `v0.1.0`; the single-server install checks out the same tag. The `v` tag path (approval, GitHub Release, `release-manifest.json`) first ran for `v0.1.0`, and [Images run 42163099605](https://github.com/JeongJaeSoon/werft/actions/runs/42163099605) ended in success. The results below were checked with `main-<12>` packages of the same commit as `v0.1.0`; the install procedure was not followed with the `v0.1.0` packages. If you cannot pull the published images, check out the repository and [build the three images yourself](/run-server/self-hosting/single-server#when-you-build-the-images-yourself).
</Callout>

## Read the release manifest

Every release (`v*` tag) gets a GitHub Release with `release-manifest.json` attached. The three image digests, the worker runtime and the chart version are in that one file. Read it with `gh` and `jq`; no repository checkout is needed. The commands below take a release tag; the current release is `v0.1.0`.

```bash
TAG=v0.1.0   # the release tag to read
gh release download "$TAG" -R JeongJaeSoon/werft -p release-manifest.json -D "$TAG"   # one directory per tag
jq -r '.images[] | "\(.image)@\(.digest)"' "$TAG/release-manifest.json"   # the three digests to deploy
jq -c .workerRuntime "$TAG/release-manifest.json"                          # worker runtime
jq -r '"\(.chart.ref) \(.chart.version)"' "$TAG/release-manifest.json"     # chart location and version
```

Each digest is that of the index holding both architectures, and a deployment pins it. An attached manifest never changes. For the fields and how to check them, see [Read the release manifest](/run-server/self-hosting/operate/images-and-supply-chain#reading-the-release-manifest).

## Connect to the server

The SDK and the HTTP API connect with a server address and an API key. The TypeScript SDK takes `baseUrl` (default: the `WERFT_BASE_URL` environment variable) and `apiKey` (`WERFT_API_KEY`). There is no default server, so always pass the address. Options are in [Client setup and errors](/getting-started/client#client-options).
