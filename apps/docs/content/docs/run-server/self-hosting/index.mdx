Werft 서버를 직접 설치해 팀이 함께 쓰는 방법이다. 혼자 시험해 볼 서버라면 [개발용 서버 실행](/run-server/dev-server)으로 충분하다. 설치 방식은 둘이고, 고른 쪽의 페이지가 `/readyz`가 200을 돌려줄 때까지의 설치 순서를 안내한다. Kubernetes 설치는 게시 chart로 kind에서 확인했으나 DB Secret 단계는 문서 블록 그대로가 아니었고, 고친 kind Secret 블록과 Kubernetes 업그레이드 절차는 실행하지 않았다. 단일 서버 페이지는 처음부터 끝까지 실행해 확인하지 않았다.

## 설치 방식 고르기

| 방식 | 실행 기반 | 페이지 |
| --- | --- | --- |
| 단일 서버 | Linux 서버 한 대, Docker Compose. 세션마다 worker 컨테이너 | [단일 서버 설치](/run-server/self-hosting/single-server) |
| Kubernetes | 게시된 Helm chart. 세션마다 worker Pod | [Kubernetes 설치](/run-server/self-hosting/kubernetes) |

이미 설치했다면 [업그레이드](/run-server/self-hosting/upgrade)를 읽는다.

어느 방식이든 서버는 API(웹 콘솔 포함), scheduler, reconciler, egress proxy, PostgreSQL, S3 호환 object store로 이뤄진다. Git 서버는 없으므로 세션이 쓸 GitHub 저장소는 설정 문서나 콘솔로 더한다. 단일 서버 설치에서 HA는 범위 밖이다.

## 게시된 패키지

설치에는 직접 빌드한 것이 아니라 `main`에 머지될 때마다 게시되는 패키지를 쓴다.

| 패키지 | 주소 | 비고 |
| --- | --- | --- |
| 이미지 | `ghcr.io/jeongjaesoon/werft-control-host`, `werft-worker`, `werft-egress-proxy` | 태그는 `main-<12>`. `linux/amd64`와 `linux/arm64`를 담은 index. 설치에는 digest로 고정한다 |
| Helm chart | `oci://ghcr.io/jeongjaesoon/werft` | 버전은 `0.1.0-main-<12>`. 이미지 digest와 worker runtime을 담는다 |
| SDK | npm `@werft-ai/sdk` | [SDK 설치](/getting-started/install) |

패키지는 로그인 없이 받는다. `<12>`는 commit SHA의 앞 12자다.

<Callout type="warn">
첫 `v` 태그가 아직 없다. `main-<12>`는 릴리스가 아니고 대응 소스 보관을 일부 확인하지 못한 채 나갈 수 있다. 첫 `v` 태그가 생기면 이미지 태그는 `v<버전>`, chart 버전은 `v` 없는 `<버전>`이 된다. 설치 페이지의 명령은 그대로 같고, 단일 서버는 같은 태그를 checkout한다. 게시된 이미지를 받을 수 없으면 저장소를 checkout해 [세 이미지를 직접 빌드](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/test-ops.md#이미지를-직접-빌드한다)한다.
</Callout>

## 릴리스 manifest 읽기

릴리스(`v*` 태그)마다 GitHub Release가 생기고 `release-manifest.json`이 붙는다. 세 이미지 digest, worker runtime, chart 버전이 파일 하나에 있다. 저장소 checkout 없이 `gh`와 `jq`로 읽는다. 아래는 첫 릴리스가 생긴 뒤의 명령이다.

```bash
TAG=v0.1.0   # 읽을 릴리스 태그
gh release download "$TAG" -R JeongJaeSoon/werft -p release-manifest.json -D "$TAG"   # 태그마다 디렉터리 하나
jq -r '.images[] | "\(.image)@\(.digest)"' "$TAG/release-manifest.json"   # 배포에 쓰는 세 digest
jq -c .workerRuntime "$TAG/release-manifest.json"                          # worker runtime
jq -r '"\(.chart.ref) \(.chart.version)"' "$TAG/release-manifest.json"     # chart 위치와 버전
```

digest는 두 아키텍처를 담는 index의 digest이고, 배포는 이 값으로 고정한다. 한번 붙은 manifest는 바뀌지 않는다. 필드와 확인 방법은 [릴리스 manifest 읽기](/run-server/self-hosting/operate/images-and-supply-chain#릴리스-manifest-읽기)를 본다.

## 서버에 붙기

SDK와 HTTP API는 서버 주소와 API key로 서버에 붙는다. TypeScript SDK는 `baseUrl`(기본값은 환경 변수 `WERFT_BASE_URL`)과 `apiKey`(`WERFT_API_KEY`)를 받는다. 정해진 기본 서버는 없으므로 서버 주소는 꼭 넘긴다. 자세한 옵션은 [클라이언트 설정과 오류](/getting-started/client#클라이언트-옵션)에 있다.
