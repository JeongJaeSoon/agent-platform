workerがエンジンから受け取ったセッションデータ(モデルの回答、ツール呼び出しと結果、権限リクエスト、状態の変化)は、DBの`events`テーブルに入ります。このテーブルが、機能が頼る正本です。このページでは、テーブルが何を持つか、途切れると何が壊れるか、秘密値をどこで隠すか、誰が内容を読めるかを説明し、Langfuseコレクターのサンプルを起動する方法を示します。内容ごとに、根拠となるファイルも書いています。

現在の監視(stdoutのJSONログ、`/readyz`、DB queryをDatadog Agentが収集)は[Datadog監視基準](/run-server/self-hosting/operate/monitoring-datadog)にあります。アプリにはOpenTelemetry(OTel)の依存もtrace exporterもありません。ログの`trace_id`は、`packages/observability/src/index.ts`の`ObservabilityContext`にフィールドがあるだけで、値を入れる場所はありません。

## 全体像

```text
engine (Claude Agent SDK)
  -> worker
  -> API Worker Gateway          (events)
  -> PostgreSQL events table     (source of truth)
  -> SSE and Last-Event-ID reconnect, public API clients,
     turn finalization, pending-request notification
```

## `events`テーブル

| 項目 | 内容 |
|---|---|
| 持つもの | `system`・`assistant`・`tool_use`・`tool_result`・`question`・`result`・`status`・`error`のイベント |
| 使う場所 | 公開APIのSSEクライアント、turn終了の判定、待機リクエストの通知 |
| 配信 | 同じattemptの中で順番どおり、隙間なく保存されないとturnが終わらない |
| 途切れると | 機能が壊れる。SSEが止まり、turnをfinalizeできない |
| 内容の長さ | workerは切り詰めない |
| 届く先 | インストールしたPostgreSQL |

イベントの種類とpayloadの契約は、`packages/contracts/src/api/event.ts`の`SESSION_EVENT_NAMES`と`sessionEventVariants`です。workerのClaude adapterが、エンジンのメッセージをこのイベントに変換します(`packages/adapters/runtimes/claude/src/mapper.ts`の`projectPublicEvents`)。assistantメッセージはブロックごとに1つのイベントになり、ツール結果ブロックは受け取ったまま`tool_result`イベントになります。

workerの`EventPublisher`(`apps/worker/src/event-publisher.ts`)が、イベントにattempt単位の`source_sequence`を付け、Worker Gatewayの`/append-events`へ順番に送ります。gatewayが受け取ったと答えるまでは、キューから消しません。APIはイベントを`events`テーブル(`packages/db/src/schema.ts`の`events`)に書きます。同じattemptの同じsequenceは、ユニークインデックス`events_attempt_sequence_uniq`が1回だけ受け付けます。

このテーブルに頼る機能は次のとおりです。

- **SSEと再接続。** `apps/control-host/src/api/routes/events.ts`が、`Last-Event-ID`の次からこのテーブルを読み、ストリームとして送ります。使い方は[APIユースケースガイド](/reference/api-guide)の5節にあります。
- **turn終了の判定。** 前のsequenceが欠けていれば`sequence_gap`、finalizeのときにイベントの保存が足りなければ`events_incomplete`で拒否します(`packages/db/src/worker-unit-of-work.ts`、`packages/platform/src/workers/worker-gateway.ts`)。
- **待機リクエストの通知。** 質問・権限リクエストの`question`イベントと、セッションの`needs_input`状態は、同じトランザクションでコミットされます。そのため、クライアントは質問を見る前に`needs_input`を受け取りません(`packages/db/src/pending-control.ts`)。答えは`pending_requests`テーブルに残ります。workerがリクエストをどう閉じたかも、同じ行に残ります。`settled_outcome`は`answered`・`expired`・`cancelled`です。`settled_reason`は、workerが取り消した理由(`park`・`shutdown`・`interrupt`・`refused`)です。`settled_answer_result`は、ランタイムが答えをどう受け取ったか(`applied`・`stale`・`unknown`)です。人が拒否したリクエストは`answered`で、`answer`の`decision`が`deny`なので、取り消しと区別できます。
- **状態遷移。** 復旧・再開・一時停止・interruptのような制御の段階が、`recordStatus`・`recordEvent`(`packages/db/src/session-events.ts`)で状態と一緒にコミットされます。
- **クライアントによる作業完了の判断。** 公開APIのクライアントは、`assistant`・`tool_use`・`tool_result`イベントを読んで、仕事が終わったかを判断します([APIユースケースガイド](/reference/api-guide))。

コストと使用量の正本は、イベントではなく`provider_usage`テーブルです。egress proxyがMessages応答から使用量を読み(`apps/egress-proxy/src/usage.ts`)、APIがこのテーブルに書きます(`packages/db/src/worker-unit-of-work.ts`)。

## 内容の収集と秘密値のマスキング

### 何を持つか

イベントは内容を持ちます。assistantのテキスト、ツール入力(`tool_use`)、ツール結果の本文(`tool_result`)、質問と権限リクエストの入力が入ります(`packages/adapters/runtimes/claude/src/mapper.ts`の`projectPublicEvents`・`approvalView`)。

エンジン(Claude Code CLI)自体のtelemetryは有効にしません。エンジンに渡す環境変数はallowlistで(`packages/adapters/runtimes/claude/src/profile.ts`)、OTelの変数は1つも渡しません。

### 秘密値をどこで隠すか

現在の規則は3層です。

1. **エンジンのメッセージ。** Claude adapterの`sanitizeNativeMessage`(`packages/adapters/runtimes/claude/src/mapper.ts`)が、エンジンのメッセージごとに、機密性の高いキーの値、`Bearer …`のような秘密の形の値、`password=…`のような名前付きの値を`[REDACTED]`に置き換えます。イベントはこの結果から作ります。
2. **claimが渡した秘密値。** workerの`SecretScrubber`(`apps/worker/src/secret-scrubber.ts`)が、このattemptが受け取った秘密値そのものを探して`<redacted>`に置き換えます。`scrubbingGateway`が`appendEvents`と`registerPending`にこの処理を掛けます。エンジンがbase64のように再エンコードした値は捕まえられません。
3. **プロセスのログ。** `packages/observability/src/redaction.ts`の`sanitizeText`・`sanitizeFields`が、APIとworkerのstdoutログを隠します。egress proxyは同じファイルのコピー`apps/egress-proxy/src/redaction.ts`を使います。規則の一覧は[APIサーバー](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md)の「providerキーとリポジトリの認証情報はworkerに渡らない」の節にあります。この規則はログ用で、イベントには掛かりません。

1と3のパターン規則は、隠す範囲が違います。ログの規則`sanitizeText`は、秘密の形の値や`token=`のような断片を1つでも見つけると、文字列全体を`[REDACTED]`に置き換えます。mapperは多くの場合、一致した部分だけを置き換え、`name=value`の形で値の終わりが明確なら、値だけを隠します。ただし、mapperの`hideNamedValues`も、`password: …`のようにコロンでつながる値や、終わりを区切れない値を見つけると、テキスト全体を隠します。そのため、`password:`を含むYAMLファイルをReadしたツール結果は、イベントから丸ごと消えます。2つのファイルのパターン一覧も、互いに異なります。

## 誰が内容を読めるか

セッションイベントは、`sessions:read` scopeを持つ主体がそのセッションを見られるときだけ読めます(`apps/control-host/src/api/routes/events.ts`、`packages/platform/src/musterrolle/policy.ts`)。まず、セッションが主体と同じ範囲にある必要があります。人は自分のworkspace、API keyはそのkeyのownerです(`packages/contracts/src/musterrolle/authorization.ts`の`ownerScopeOf`)。その中で、セッションの共有範囲が`workspace`(一度も変えていないセッションの既定)ならworkspaceの全メンバーが読め、`people`や`team`なら作成者と、指定された人・チームのメンバーだけが読めます。個人keyは、そのkeyを作った人として判定します。エージェントkeyはメンバーではないので、key自身として判定し(そのエージェントのセッションに限られます)、自分が作ったセッション(作成者のいないセッション)では、作成者の位置に立ちます(`packages/platform/src/musterrolle/policy.ts`の`viewerOf`、`packages/db/src/session-shares.ts`の`sessionVisibleTo`)。見られないセッションは404です。共有範囲の変え方と、ownerやadminによる監査閲覧は、[APIサーバー](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md)の「セッションの共有範囲と監査閲覧」の節にあります。scopeはHTTPの境界で、`apps/control-host/src/api/scope-policy.ts`が検査します。

## 保存期間

`events`の内容は削除しません。長く止まっているセッションの行はobject storeに移り、APIはそのobjectから同じレスポンスを読みます([APIユースケースガイド](/reference/api-guide)の410 `CURSOR_EXPIRED`の説明)。保存期間のポリシーはまだありません。イベント以外にプラットフォームが残すデータ全体の場所・保存期間・削除条件と、セッション1つを追って確認する手順は、[プラットフォームが保持するデータ](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/data-retention.md)にあります。

## Langfuseのサンプルコレクターを起動する

`infra/observability/`にコレクターのサンプルが2つあります。Grafana LGTMを起動してtraceを探す方法は[オブザーバビリティ (OTel)](/observability)にあり、ここではLangfuseのサンプルを扱います。どちらのサンプルも、Werftのスタックとは別に起動するcompose projectで、手前にOpenTelemetry Collectorを1つずつ置いて、標準のOTLP/HTTPを受けます。1台のコンピューターでOTLPの受信を確認するための用途で、運用の推奨構成ではありません。どのコレクターを使い、どう運用するかは、運用者が決めます。

**確認できる範囲。** WerftはOTelトレースを出力しません。Werftのセッションを実行しても、コレクターにtraceはできません。この節で確認できるのは、サンプルのコレクターがOTLPのtraceを受け取って画面に表示するところまでで、送るtraceは`send-test-span.sh`が作る偽のspanです。

| サンプル | ディレクトリ | OTLP/HTTPの受け口 | 画面 | 受けるシグナル |
|---|---|---|---|---|
| Langfuse | `infra/observability/langfuse/` | `http://127.0.0.1:25318` | `http://localhost:25000` | トレース |
| Grafana LGTM | `infra/observability/lgtm/` | `http://127.0.0.1:26318` | `http://localhost:26000` | トレース、ログ、メトリクス |

ポートはすべてloopbackにだけ開き、既定のスタック(3000、3001、5432)と重なりません。データの流れは`送る側 → collector(collector.yaml) → Langfuseまたはgrafana/otel-lgtm`です。コレクターのcredentialを持つのはcollectorだけです。Langfuseのcompose内の秘密値の既定値(`local-…`で始まる値と例のキーペア)は、ローカル確認用のプレースホルダーです。このコンピューターの外で使うには、次の変数をすべて新しい値で渡します。`LANGFUSE_POSTGRES_PASSWORD`、`LANGFUSE_CLICKHOUSE_PASSWORD`、`LANGFUSE_REDIS_PASSWORD`、`LANGFUSE_MINIO_PASSWORD`、`LANGFUSE_SALT`、`LANGFUSE_ENCRYPTION_KEY`(`openssl rand -hex 32`で作った64文字)、`LANGFUSE_NEXTAUTH_SECRET`、`LANGFUSE_INIT_USER_EMAIL`、`LANGFUSE_INIT_USER_PASSWORD`。パスワードとアカウントはvolumeを最初に作るときに決まるので、すでに起動した後なら、`down -v`で消してから起動し直します。collectorのキーペアは、下の節のように別に変えます。

### 起動と停止

リポジトリのルートで実行します。Langfuseは初回の起動で、DB migrationのため1〜2分かかります。

```sh
docker compose -p werft-obs-lgtm -f infra/observability/lgtm/compose.yml up -d --wait
docker compose -p werft-obs-langfuse -f infra/observability/langfuse/compose.yml up -d --wait
```

止めるときは、次を実行します。`-v`は保存したトレースも消します。

```sh
docker compose -p werft-obs-lgtm -f infra/observability/lgtm/compose.yml down -v
docker compose -p werft-obs-langfuse -f infra/observability/langfuse/compose.yml down -v
```

### テストspanを送る

`infra/observability/send-test-span.sh`で偽のトレースを1つ送ります。`werft.turn`の下に`werft.llm_request`と`werft.tool`があり、turn spanにはユーザー入力を、モデル応答のspanには回答テキストを、`gen_ai.*`属性として載せます。`--with-log`を付けると、同じtraceに結び付いたログも1行送ります。Langfuseのサンプルのcollectorはログを受けないので、Langfuseには付けません。

```sh
infra/observability/send-test-span.sh http://127.0.0.1:26318 --with-log
infra/observability/send-test-span.sh http://127.0.0.1:25318
```

出力の`trace_id`と`session_id`で、下の画面から探します。

### Langfuseのプロジェクトキーを作る

Langfuseのサンプルは、最初の起動時に`LANGFUSE_INIT_*`の設定で、組織`Werft local`、プロジェクト`werft-local`、例のキーペア、ログインアカウントを作ります。ログインアカウントの既定は、メール`admin@example.com`とパスワード`local-password`です。collectorは同じ例のキーペアでLangfuseに送ります。

別のキーを使うには、次のようにします。

1. `http://localhost:25000`にログインし、Settings → API Keys → Create new API keysでキーペアを作ります。
2. 2つの値を環境変数で渡して、collectorだけを作り直します。値をファイルに書かないでください。

```sh
LANGFUSE_PUBLIC_KEY='<public key>' LANGFUSE_SECRET_KEY='<secret key>' \
  docker compose -p werft-obs-langfuse -f infra/observability/langfuse/compose.yml up -d --no-deps otel-collector
```

### 画面で探す

**Langfuse.** `http://localhost:25000`に例のアカウントでログインし、Tracingでtrace idを使って探します。直接開くには、`http://localhost:25000/project/werft-local/traces/<trace_id>`へ行きます。セッション単位で見るには、Sessionsで`session_id`を探します。サンプルのテストspanでLangfuse 4.66.0で確認したマッピングは次のとおりです。

| spanの属性 | Langfuseの画面 |
|---|---|
| `gen_ai.input.messages` | Input |
| `gen_ai.output.messages` | Output |
| `session.id` | Sessions |
| `gen_ai.request.model`、`gen_ai.usage.input_tokens`、`gen_ai.usage.output_tokens` | Generation種別の観測。モデル名とtoken数が付きます |
| `gen_ai.operation.name=execute_tool`、`gen_ai.tool.name` | Tool種別の観測。名前はツール名です |
| その他の属性(`werft.*`、resource属性) | Metadata |

**Grafana.** `http://localhost:26000`はログインなしで開きます。トレースは、Explore → Tempo → TraceQLにtrace idを入れて探します。1つのセッションのturnをすべて見るには、`{ span.werft.session_id = "<session_id>" }`で検索します。ログは、Explore → Lokiで`{service_name="werft-api"}`で探します。
