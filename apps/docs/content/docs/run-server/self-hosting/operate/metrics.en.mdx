---
title: "Platform metrics (Kubernetes)"
description: The Prometheus metrics the platform emits on a Helm install and how a collector reads them
---

When you turn on `metrics.enabled: true` in a Helm install, the platform emits metrics for the whole installation: session states, turn counts and durations, tool calls, provider tokens and estimated cost, and queues. Your collector (Prometheus, the Datadog Agent or an OpenTelemetry Collector) reads them in the Prometheus text format (0.0.4). You build the dashboards and alert rules. The CPU, memory, restarts and logs of Pods are gathered by the cluster's collectors, so they are not here.

## Turning it on

```yaml
metrics:
  enabled: true
  podAnnotations:          # how the collector finds the Pod; the install chooses
    prometheus.io/scrape: "true"
    prometheus.io/port: "9464"
networkPolicy:
  metrics:
    ingressFrom: []        # empty: reachable on 9464 from anywhere; narrow it to the collector namespace
```

When on, the chart creates a `<release>-metrics` Deployment (1 replica, `Recreate`), a ClusterIP Service of the same name (9464), and a NetworkPolicy that opens only 9464. When off (the default), it creates nothing, so the render of a default install does not change. The full list of values is the `metrics` block of `deploy/helm/agent-platform/values.yaml`.

Settings the `metrics` role reads:

| Setting | Default | Meaning |
|---|---|---|
| `METRICS_PORT` | `9464` | The port that serves `/metrics` and `/healthz`. The chart sets it from `metrics.port` |
| `DATABASE_URL` | None (required) | The database address, opened read-only. The chart uses the same Secret key as the other roles |
| The limits in `config.limits` | [Configuration reference](/run-server/self-hosting/operate/configuration) | The launch queue is counted with the same cost and token limits as the scheduler. The chart passes the same values as to the scheduler |
| `LOG_LEVEL` | `info` | The log level at which read failures are logged |

To check:

```sh
kubectl -n <namespace> port-forward deploy/<release>-metrics 9464
curl -s localhost:9464/metrics
```

## How a collector reads it

| Collector | How |
|---|---|
| Prometheus | The `prometheus.io/*` annotations of `metrics.podAnnotations`, or your ServiceMonitor pointing at the `metrics` port of the Service `<release>-metrics` |
| Datadog Agent (Helm) | The Autodiscovery `openmetrics` check. Put `ad.datadoghq.com/metrics.checks` in `metrics.podAnnotations`. The names under which Datadog stores the metrics (dotted names and so on) are set on the collector side |
| OpenTelemetry Collector | Scrape the same endpoint with the `prometheus` receiver and send it on as OTLP |

The platform does not push metrics over OTLP. One pull endpoint lets any kind of collector read the same definitions, and the app needs no collector address or SDK settings. Exporting session traces (OTLP, Langfuse) is a separate setting.

## How the values are made

- **Computed from the database at scrape time.** The `metrics` role (`bun run apps/control-host/src/main.ts metrics`) keeps no state. On each request it reads the database with the queries in `packages/db/src/metrics-reader.ts`, and `apps/control-host/src/metrics/families.ts` turns the result into metrics. So counters do not go back to 0 when the Pod restarts.
- **There is one target.** The values are totals for the whole installation, so two replicas would emit the same values twice. The chart fixes replicas at 1 and uses `Recreate`.
- **The connection is read-only.** The database connection opens with `default_transaction_read_only=on`, so the database refuses a write sent by mistake. This is a session setting, not a database privilege. The account in `DATABASE_URL` is the same as the other roles' and has write privileges, so writing is possible if the setting is reverted inside the connection. The setting is sent as the startup parameter `options`, so behind a connection pooler that rejects `options` (PgBouncer without `options` in `ignore_startup_parameters`, for example), only the metrics role fails to connect.
- **Concurrent scrapes share one read.** Requests that arrive while a read is in progress get the same result. If the read fails, it returns 503 and does not serve the previous values (the collector sees a failed scrape; `up` = 0 in Prometheus).
- **`/healthz`** only checks that the process responds. The probe does not read the database.

Each scrape aggregates the large tables (`tool_calls`, `provider_usage`, `turns`) in full. The shorter the scrape interval, the more load on the database. When the collection time passes half of the scrape interval, consider keeping a separate aggregate table.

## Metrics

The prefix is `werft_`. In the code it is set in one place, `METRIC_PREFIX` in `apps/control-host/src/metrics/families.ts`.

| Name | Type | Labels | Meaning |
|---|---|---|---|
| `werft_sessions` | gauge | `state`, `status`, `admission` | The number of sessions. `state` is set by the state table below. `status` is the state the API shows (including `needs_input`), and `admission` is `sessions.admission_state` |
| `werft_turns_total` | counter | `status` | The number of turns that ended as `completed`, `failed`, `interrupted` or `cancelled` |
| `werft_turn_duration_seconds` | histogram | `status`, `le` | For the turns above that started, the time from start to end. Buckets 1, 5, 15, 30, 60, 120, 300, 600, 1800, 3600 seconds |
| `werft_turns_outcome_unknown` | gauge | None | The number of turns whose execution disappeared and whose result is unknown. They wait for the operator's recovery decision |
| `werft_tool_calls_total` | counter | `tool` | The number of tool calls the engine made |
| `werft_tool_calls` | gauge | `tool`, `outcome` | The tool calls by their current result: `ok`, `failed`, `denied`, `unknown` (no result yet) |
| `werft_provider_tokens_total` | counter | `model`, `priced_by`, `kind` | Tokens measured in provider calls. `kind` is `input`, `output`, `cache_read` or `cache_creation` |
| `werft_provider_cost_usd_total` | counter | `model`, `priced_by` | The estimated provider cost (USD). It is not Kubernetes infrastructure cost |
| `werft_launch_queue_sessions` | gauge | None | The number of sessions waiting for a worker launch |
| `werft_launch_queue_oldest_wait_seconds` | gauge | None | The wait of the session that has waited longest in the launch queue. 0 when empty |
| `werft_input_queue_oldest_age_seconds` | gauge | None | The age of the oldest input that no worker has taken yet. 0 when empty |

Why `tool_calls` is a gauge, not a counter: a tool result can change later. When a result event arrives late, `unknown` becomes `ok` or `failed`, and when an earlier result arrives afterwards it replaces the existing one (the projection in `packages/db/src/tool-calls.ts`). If a counter value drops, the collector reads it as a reset and the increase jumps. Watch the increase in the number of calls with `tool_calls_total`, and the ratio by result with `tool_calls`.

The same reason keeps `outcome_unknown` turns out of `turns_total`. When the operator recovers one, it becomes `completed` or `cancelled`, and its end time changes to that moment. The changed turn enters `turns_total` and the histogram then.

### Session state table

The first line that matches, from the top, is the `state`. Every session fits exactly one line, so the sum over `state` equals the total number of sessions.

| `state` | Condition | State a user sees |
|---|---|---|
| `ended` | `admission` is `stopping`, `stopped`, `closing` or `closed`, or the stored status is `stopped` | Ended |
| `paused` | `admission` is `pausing` or `paused` | Paused |
| `recovery_required` | `admission` is `recovery_required` | — |
| `awaiting_approval` | The API status is `needs_input` and there is a permission request a person can answer | Awaiting approval |
| `awaiting_answer` | The API status is `needs_input` and the only request a person can answer is a question | — |
| `running`, `queued`, `idle`, `failed` | The API status as is | Running is `running` |

`needs_input` is not stored in the database. A session that is running, or one whose turn is parked, becomes `needs_input` when it is read if it has a request a person can answer (`publicStatus` in `packages/db/src/pending-requests.ts`). The metrics use the same rule (`actionableOfSession`). `ended` keeps growing because closed sessions are not deleted. Read the current load as the sum without `ended`.

### Tool results and denials

- `ok`, `failed` and `unknown` come from `tool_calls.outcome` (the `is_error` of the tool result block).
- `denied` is a call whose permission request a person answered with `deny`. `pending_requests` (`kind = 'permission'`, `answer.decision = 'deny'`) and `tool_calls` are joined on `(session_id, tool_use_id)`. The tool_use id is a unique value the provider gives, so a request that was parked and answered by the next attempt joins to the same call. If a tool_use has even one `deny` answer, it counts as `denied` even if it was allowed again and ran afterwards.
- A `deny` from the agent's tool policy, an expired or cancelled request, and a refusal by an old worker that does not send `tool_use_id` count by the result block (`failed` and so on), not as `denied`.

### Cost and tokens

- Cost is the sum of `provider_usage.cost_usd`. This value was computed when the call was recorded, by the platform price table (`priceProviderUsage` and `MODEL_PRICES` in `packages/platform/src/limits/model-prices.ts`). The metrics do not recompute unit prices and have no unit-price setting of their own.
- `priced_by` is the pricing basis of the call. `table` (a model in the price table), `fallback` (a model not in the price table, priced at the highest unit price), `unmetered` (the profile has `billing: none`, so the cost is 0). For calls with zero cost, such as a self-hosted model, read usage from the token counts with `priced_by="unmetered"`.
- **The period is based on the time the call was recorded (`provider_usage.recorded_at`).** Read the cost of a period as the counter increase, like `increase(werft_provider_cost_usd_total[1h])`.
- It differs from `GET /v1/usage/summary` in three ways. When there are only sessions that were created and billed inside the period, the two agree (`packages/db/src/metrics-reader.test.ts`).
  - The summary picks the sessions **created** in the period (`sessions.created_at`) and adds the whole cost of those sessions. The cost that a session created before the period spent inside the period is only in the metrics.
  - The summary adds `sessions.cost_usd`. This value stops at the session cost limit column (99,999,999.999999 USD), but the per-call cost does not stop.
  - The summary includes the session cost from before per-call records existed (before migration 0169, `session_pre_metering_cost`); the metrics do not.
- Tokens add up the per-call values in `provider_usage`. `cache_creation` is all cache writes, including 1-hour cache writes.

### Queues

- **Launch queue**: the sessions for which the scheduler can start a worker on its next pass. They are counted with the same SQL condition as the scheduler (`awaitingLaunch` in `packages/db/src/scheduler-store.ts`): an admission that allows a launch, no execution reclaim or takeover, within the cost and token limits, the restore retry time has passed, and no launch holding a slot. The limits are read from the same `config.limits` as the scheduler. The wait is measured from `unassigned_sessions.signaled_at`.
- **Input queue**: the inputs in `queue_messages` that no worker has taken and whose visible time has passed. It means the same as `werft.queue.oldest_age_seconds` in compose.

## Label rules

- Session id, turn id, user id, API key id, agent id and attempt id are not used as labels. Read cost per agent from `GET /v1/usage/*`.
- `state`, `status`, `admission`, `outcome`, `priced_by`, `kind` and `le` take only fixed values.
- `tool` and `model` come from data. An MCP tool `mcp__<server>__<tool>` is folded into `mcp__<server>`. Then, in order of first appearance, only 100 `tool` names and 50 `model` names are kept, and the rest are merged into `other`. Rows are not deleted, so a value that got a name normally keeps it. But after the limit is full, if a row that the projection inserted late (`tool`) or a row that committed late (`model`; `recorded_at` is the start time of the transaction) has an earlier time, one name can trade places with `other`. The series of the name that was pushed out breaks, the name that came in starts as a new series, and `other` jumps once or is read as a reset.
- Test: the cardinality section of `apps/control-host/src/metrics/families.test.ts` checks the list of label names, that no value looks like an id, and the limits.

## Mapping to the compose metrics

The Datadog overlay of compose emits similar values with PostgreSQL custom queries ([Datadog monitoring baseline](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/monitoring-datadog.md), `infra/datadog/conf.d/postgres.d/conf.yaml`). On a Kubernetes install, read these metrics instead.

| compose (DB query) | This metric |
|---|---|
| `werft.queue.oldest_age_seconds` | `werft_input_queue_oldest_age_seconds` (same meaning) |
| `werft.provider.cost_usd_1h` | `increase(werft_provider_cost_usd_total[1h])` |
| `werft.provider.unmetered_tokens_1h` | The sum of `increase(werft_provider_tokens_total{priced_by="unmetered"}[1h])` |
| `werft.provider.fallback_pricing_count_1h` | No counterpart (look at the cost and tokens with `priced_by="fallback"` instead of a call count) |
| `werft.turn.outcome_unknown_count` | No counterpart. `werft_turns_outcome_unknown` is the number remaining now, not the number that appeared in the last 5 minutes |
| `werft.checkpoint.pending_age_seconds`, `werft.lease.stale_count` | No counterpart |
