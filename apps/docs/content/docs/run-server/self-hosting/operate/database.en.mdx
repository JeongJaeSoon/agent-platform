This page covers how many connections the platform opens to PostgreSQL 16, the session settings it applies, and how to find slow queries and lock waits. A compose install starts Postgres itself, so compose also sets the server options. A Helm install uses the database you bring, so you turn the server options on. The rules the code asks of contributors (transaction scope, lock order, migrations) are in the [DB rules of the development guide](https://github.com/JeongJaeSoon/werft/blob/main/docs/contributing/development.md#db-사용-규칙).

## Connections per role

Every role builds its pool with `createEnforcedPool` in `packages/db/src/pool.ts`. The pool limit differs by role.

| Role | Pool limit | Why |
|---|---|---|
| api | 10 + readiness probe 1 + LISTEN 1 | Handles requests concurrently. The probe uses its own pool (limit 1) so it never competes with requests for a connection. The LISTEN connection that receives event notifications (`werft:api-listen`) sits outside the pool. |
| metrics | 10 | One scrape reads 7 aggregates at the same time. |
| scheduler | 4 | A pass issues one statement at a time. The pass lock holds one more connection. |
| reconciler | 4 | A pass issues one statement at a time. |
| slack | 4 | Drains the inbox and the outbox in turn. |
| checkpoint GC, upgrade check, migrate, operator CLI (`keys`, `grants` and so on) | 10 | Runs briefly and exits. |

With the Helm defaults (2 api, 1 slack, 1 scheduler, 1 reconciler, metrics off), the connections that can stay open are api 24 + scheduler 4 + reconciler 4 + slack 4 = 36. Turning on `metrics.enabled` adds 10, and when the GC, upgrade check and migrate jobs overlap, up to 30 more attach. Compose gives api 12 + scheduler 4 + reconciler 4 + slack 4 = 24. The PostgreSQL default `max_connections` is 100, and 3 of those are reserved for superusers. When you add api or slack replicas, add 12 per replica (4 for slack) and compare the total with `max_connections`. A managed database can have a `max_connections` below 100 depending on the instance size, so check that value.

## Session settings on every connection

`createEnforcedPool` applies these when it opens a connection. Even if `DATABASE_URL` has a query parameter of the same name, the value in the code wins for the timeouts.

| Setting | api and job value | migrate value | Meaning |
|---|---|---|---|
| Connection wait (`connectionTimeoutMillis`) | 5 s | 5 s | If the pool has no free connection, the request fails after this time. The api answers 503. |
| `statement_timeout` | 10 s | 300 s | The server cancels the statement. Time spent waiting for a lock counts. |
| Response read (`query_timeout`) | 20 s | 330 s | The client drops a socket the server does not answer on. |
| `idle_in_transaction_session_timeout` | 30 s | 30 s | The server closes a connection that keeps a transaction open for 30 s without a statement. The locks it held are released. |
| `application_name` | `werft:<role>` | `werft:migrate` | Tells the roles apart in `pg_stat_activity` and the server log. If `DATABASE_URL` has an `application_name`, that value is used. |

Check the number of open connections per role in the database. With compose, enter with `docker compose -f infra/compose.yml exec postgres psql -U postgres -d sessions`. With Helm, use your own database client.

```sql
SELECT application_name, state, count(*)
  FROM pg_stat_activity
 WHERE application_name LIKE 'werft:%'
 GROUP BY 1, 2 ORDER BY 1, 2;
```

Session settings apply only to that connection, so `SHOW` in an operator `psql` prints the server default. Read the values of a platform connection with the same pool inside the api container (the api Pod with Helm).

```bash
docker compose -f infra/compose.yml exec -T -w /app/apps/control-host api bun -e '
import { createLogger } from "@werft-ai/observability";
import { createApiPool } from "./src/api/pool.ts";
const pool = createApiPool(process["env"]["DATABASE_URL"], createLogger());
const { rows } = await pool.query(
  "SELECT current_setting($1) AS statement_timeout, current_setting($2) AS idle_in_transaction, current_setting($3) AS application_name",
  ["statement_timeout", "idle_in_transaction_session_timeout", "application_name"],
);
console.log(JSON.stringify(rows[0]));
await pool.end();'
# {"statement_timeout":"10s","idle_in_transaction":"30s","application_name":"werft:api"}
```

With Helm, run the same script with `kubectl -n werft exec deploy/werft-api -- sh -c 'cd /app/apps/control-host && bun -e …'` instead of `docker compose … exec -T -w /app/apps/control-host api`. If the release name is not `werft`, use the namespace and deployment name of your install.

## Finding slow queries and lock waits

### compose

The postgres in `infra/compose.core.yml` starts with these on.

- `log_min_duration_statement=500ms`: logs a statement that takes longer than 500 ms, with its text and duration. Change it with `POSTGRES_LOG_MIN_DURATION_STATEMENT`; `-1` turns it off.
- `log_lock_waits=on`: logs a lock wait longer than `deadlock_timeout` (1 s), together with the PID that holds the lock.
- `shared_preload_libraries=pg_stat_statements`: collects cumulative statistics per statement. To read them, run `CREATE EXTENSION IF NOT EXISTS pg_stat_statements;` once.

```bash
docker compose -f infra/compose.yml logs postgres | grep -E 'duration:|still waiting'
```

```sql
SELECT calls, round(mean_exec_time::numeric, 1) AS mean_ms,
       round(total_exec_time::numeric) AS total_ms, left(query, 120)
  FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 20;
```

Changing these settings recreates the postgres container. The data stays in the `postgres-data` volume.

### Helm (your own database)

The chart does not create the database, so it does not change server options either. Set these in the database parameters. On RDS or Aurora, change them in the parameter group; `shared_preload_libraries` takes effect only after the instance restarts.

| Parameter | Value |
|---|---|
| `log_min_duration_statement` | `500` (ms) |
| `log_lock_waits` | `on` |
| `shared_preload_libraries` | add `pg_stat_statements` to the existing value |

Then run `CREATE EXTENSION IF NOT EXISTS pg_stat_statements;` once in the platform database. This needs the privilege to create extensions (`rds_superuser` on RDS). The migrations do not create the extension, so that migrate does not fail on an install without that privilege.

Look for `duration:` and `still waiting` where the database keeps its log (the `postgresql` log in CloudWatch Logs on RDS). The Postgres in the kind check environment (`deploy/kind/deps.yaml`) starts with the values in this table.

## How long a migration locks

The migrate job spends up to 300 s per statement. When two migrates overlap (a hand-run `db:migrate` and the Helm hook Job, for example), the later one waits for the earlier one to finish and then applies only the remaining migrations. The Helm hook Job ends after `migrate.activeDeadlineSeconds` (600 s by default). A migration that adds an index to a growing table builds it with `CREATE INDEX CONCURRENTLY`, so writes are not blocked. If a table is so large that the build may pass 300 s, the release notes of that migration say so. A `CONCURRENTLY` index waits for every transaction that was open when it started, so a long-open operator session (an open `BEGIN` in `psql`) delays it by that much.
