3つのアプリイメージとcompose `apps` profile、workerイメージのアップグレード・ロールバック、サプライチェーンの脆弱性ポリシーをまとめます。イメージをビルド・公開するworkflowは[ci.md](https://github.com/JeongJaeSoon/werft/blob/main/docs/contributing/ci.md)にあります。

## イメージとCompose `apps` profile

アプリイメージは`apps/{control-host,worker,egress-proxy}/Dockerfile`の3つが定義します。3つともリポジトリのルートをcontextとし、`oven/bun:1.3.14`のmulti-arch index digest 1つをbaseとしてpinします(`tests/images.test.ts`がdigestの一致を検査)。control-hostイメージ1つがapi・scheduler・reconcilerの3つのroleをすべて動かします。composeでは`api`だけをビルドし、scheduler・reconcilerは同じ`API_IMAGE`を使います。同じタグを2つのサービスが一緒にビルドするとexportが競合するためです。control-host・workerは`bun install --frozen-lockfile --production`でworkspace closureだけをインストールしてからruntime stageにコピーし、egress-proxyは`bun install`なしで自分のソースだけを入れた1つのstageです。

公開するtargetは`release`で、Dockerfileの最後のstageなので既定のtargetです。images.ymlが`target: release`でビルドします。公開イメージには、テストソース(`*.test.ts(x)`、`*.stories.*`、`src/testing`、`src/test-support`、`__fixtures__`、`bench`)、`apps/storybook`、`packages/testkit`、デモアカウントCLI(`demo-accounts.ts`・`demo-data.ts`)が含まれません。インストール(`bun install --frozen-lockfile`)が終わった後に`scripts/image-prune.sh --delete`が削除するので、workspace manifestはそのまま固定されます。`image-smoke.sh`がイメージを開いて同じ一覧と名前の一覧を数え、1つでもあれば失敗します。control-hostには`local` targetが別にあります。`release`にtestkitとデモCLIを再び載せたもので、公開しません。`scripts/local.sh`(compose)と`deploy/kind/up.sh`がこのtargetでビルドします。公開イメージで`DEMO_ACCOUNTS=local`としてデモCLIを呼ぶと、ファイルがないので`Module not found`で失敗します。

digest pinは、Bunのバージョンと一緒にbaseのDebianパッケージも固定します。oven/bunは発行したtagを再ビルドしないため、2026-09-25時点で`oven/bun:1.3.14`の最後のビルドは2026-05-13です。そのため、3つのイメージのデプロイstageは`apt-get upgrade`でDebianのセキュリティ修正を取り込みます。Bunを上げずに修正を受け取る方法はこれしかないためです。代償は再現性です。同じcommitでも、ビルドした日によってDebianパッケージのバージョンが異なることがあります。デプロイしたものはrelease manifestがimage digestで固定し、ビルドごとにimages.ymlのライセンス照合とGrype検査がそのイメージを見ます。layer cacheは`APT_UPGRADE_KEY` build argで分かれます。images.ymlはUTCの日付を渡し、ローカルのcomposeビルドは空の値なので、一度作ったupgrade layerを使い続けます。ローカルで新しい修正を受け取るには、`--build-arg APT_UPGRADE_KEY=$(date -u +%F)`か`--no-cache`でビルドします。

| イメージ | 内容 | 実行主体 |
|---|---|---|
| `werft-control-host` | `apps/control-host`の実行物1つでapi・scheduler・reconcilerのroleをすべて動かします。`--filter`でそのアプリのclosureだけをインストールし、Agent SDK・Claude Code executableを含みません(ビルドが`node_modules/@anthropic-ai`の不在を確認)。既定はuid 1000で、scheduler roleだけがcomposeの`user: "0:0"`でrootになり、Docker socketを持ちます | `bun run apps/control-host/src/main.ts <role>` (CMDの既定は`api`) |
| `werft-worker` | `--filter ./apps/worker`でworkerとそれが依存するworkspaceのclosureだけをインストールします(pg・drizzle・Webコンソールのパッケージはありません)。SDK 0.3.270と同梱のClaude Code 2.1.270、git、non-root(uid 1000)、`/workspace`を1000の所有で事前に作成(LocalDockerBackendのvolume契約)。ビルド時に`resolvePinnedClaudeExecutable()`でexecutableのパスを確定して`/usr/local/bin/claude`にリンクし、`claude --version`を実行します | `bun run apps/worker/src/main.ts`。schedulerがenvで渡したbootstrap identityでセッションを1つclaimし、WorkerHostループを回します |
| (scheduler role) | Docker socketをmountする唯一のサービスで、rootで実行します(socketの所有者はどのみちdaemon hostのrootと同じで、socketのgidはdaemonごとに異なるため、固定uidは移植性を損なうだけです) | composeでは監督ループ(`main.ts scheduler`)が`SCHEDULER_INTERVAL_SEC`(既定5秒)ごとに子プロセス(`--serve`)にpassを1つ要求します。失敗またはkillされたpassは子プロセスとともに終わり、次のpassは新しい子プロセスで動きます([実行](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/execution.md))。失敗したpassが`SCHEDULER_MAX_CONSECUTIVE_FAILURES`(3)回続くと(degraded exit 76は数えません)ループがexit 1し、`restart: unless-stopped`が再起動します(`compose ps`に現れます)。`SCHEDULER_HEALTH_STALE_SEC`(200秒)の間に完了したpass(成功またはdegraded)がなければ、healthcheck(`main.ts scheduler --health`)がunhealthyになります。DBが止まると、passは自らexit 1で終わります。scheduler・reconcilerのpoolはAPIと同じtimeout(connect 5秒・statement 10秒・read 20秒、`packages/db/src/pool.ts`の`JOB_POOL_TIMEOUTS`)を使い、接続を一度失った後のstore呼び出しは待たずにすぐ失敗するので、DB待ちは失敗したstatement(5+20秒)とpass lockの解放(20秒)を合わせた約45秒が上限です(実測: pass前の停止で5秒、pass中の停止で約40秒)。`SCHEDULER_PASS_TIMEOUT_SEC`(180秒)は、この45秒とworkerの停止1回(stop timeout 120秒 + request timeout 30秒)より大きく置く外側のwatchdogで、それ以外のhangをkillして失敗として数えます(unhealthyだけではDockerは再起動しません)。pool timeoutを増やすなら、この値も`connect + 2 × read`より大きく上げます |
| `werft-egress-proxy` | `apps/egress-proxy`のソースだけ(依存関係なし、1つのstage)。コードはroot所有にしてuid 1000で実行し、proxyが次回起動時のコードを書き換えられないようにします | `bun run src/main.ts`。composeの`egress-proxy`で、すべてのworkerネットワークにつながる唯一の外への経路 |

```bash
docker compose -f infra/compose.yml --profile worker build          # WORKER_IMAGE(werft-worker:dev)
docker compose -f infra/compose.yml --profile worker run --rm worker claude --version
docker compose -f infra/compose.yml --profile apps up -d --build      # migrate → api(/readyz) → worker image smoke → scheduler loop, reconciler loop
curl -s http://127.0.0.1:3000/readyz
```

composeのエントリファイルは`infra/compose.yml`、復元用のlayerは`infra/compose.restore.yml`です。2026-10より前のcheckoutでは、それぞれ`infra/docker-compose.yml`・`infra/docker-compose.restore.yml`でした。古い名前を`-f`や`COMPOSE_FILE`に書いたスクリプト・aliasは新しい名前に変えます。project名(`agent-platform`)はそのままなので、すでに起動しているスタックとボリュームは新しい名前でそのまま引き継がれます。ルートで`docker compose`(`compose.yaml`)や`scripts/local.sh`で起動する場合は、変わるものはありません。

`apps` profileの値は、provider key 1つを除いてすべて既定値があるので、環境ファイルなしで起動します。`scripts/local.sh up`が取り込む設定ドキュメント(`tests/fixtures/settings/real-model.json`)はAPIプロセスの`ANTHROPIC_API_KEY`を読むので、シェルや`.env`にkeyがなければセッションは動きません(`up`は起動前に拒否します)。overlayなしの`docker compose`は設定ドキュメントを取り込みません。keyなしで起動するには、`scripts/local.sh up --fake-model`でfakeの設定ドキュメントを使います。このときAPIコンテナにはkeyが渡されません。`PLATFORM_SECRET_KEY`は、シェルや`.env`になければ`up`が作ってプロジェクトごとに保管します。`DATABASE_URL`だけは例外で、常にcomposeのpostgresを指します。`up`がmigrateを実行するので、シェルや環境ファイルにある別のDSNがローカルスタックの起動だけでmigrateされてはいけないためです。`AUTH_MODE`の既定値は`api-key`です。workerはproxy経由で`api:3000`に届くので、`none`だとworker内のコードが`X-Owner-Id`で任意のownerになりすませます(`/internal`のworkerルートは独自に認証します)。keyは`bun run keys create <owner> --scopes …`(composeの`api`コンテナ内でkey CLIを実行)で発行します。発行したkeyのidはstderrに`key_id <uuid>`として出ます(stdoutは平文のkey 1行そのままです)。失効は`bun run keys revoke <key_id>`です。失効したkeyは次のリクエストから401を受け、開いていたSSEはkeepalive周期内に切れます。同じownerが進行中の作業は取り消しません。セッションの実行権限を取り上げるのは、別の運用コマンド`bun run grants revoke <session_id> --reason <text>`です([セッション実行権限の回収と復旧](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md#세션-실행-권한-회수와-복구))。このコマンドは1つのtransactionの中でauth_revisionとepochを上げ、worker tokenを失効させ、kill intentを残し、dispatchを遮断します。ownerのresumeとstart_freshも拒否されます(403)。遮断は`bun run grants restore <session_id> --reason <text>`でのみ解除され、解除できるのは以前のexecutionが消えたことが確認された後です。APIポートは`127.0.0.1:3000`にだけbindします。`EXECUTION_WORKSPACE_QUOTA`はcomposeでは既定で`off`です。Docker Desktopはproject quotaに対応できないため、ローカルスタックは無制限のworkspaceを受け入れ、scheduler passごとに警告が1件残ります。xfs+prjquotaのdaemonなら`on`に戻します。残りの値は`.env`なしで起動します。`.env`があれば読みますが(`required: false`)、作成したり上書きしたりはしません。`secrets`(API専用のSecrets Manager、ホスト`127.0.0.1:4567`)と`fake-messages`は、`infra/compose.fake-model.yml`を重ねたときだけ起動します。`secret_id`を読む設定ドキュメントがfakeのドキュメントだけだからです。workerコンテナはcomposeのサービスではなく、schedulerがセッションごとに起動します。composeの`worker`項目は、そのイメージをビルドして`claude --version`で一度確認してから終わるone-shotです(`network_mode: none`)。schedulerがこれの成功を待つので、`apps` profileの`up`がworkerイメージまでビルドします。workerはforward proxyで`api:3000`(`EGRESS_PRIVATE_ALLOWLIST`の既定値)にだけ届き、`fake-git:3000`・`fake-messages:4010`・`localstack:4566`にはcredential routeでのみ届きます(`secrets`には届きません)。直接接続とmetadataアドレスはinternalネットワークが遮断します。

同じdaemonに2つのインストールを載せるなら、`EXECUTION_INSTALLATION_ID`をインストールごとに変えます。composeの`egress-proxy` labelはこの値に従うので、インストールごとに自分のproxyが付きます。別のworktreeのcompose projectが既定のポートを使っているなら、`-p <name>`と`ports: !override`のoverrideファイルで分離します。

`.github/workflows/images.yml`は、PR・main pushのたびに3つのイメージを`linux/amd64`と`linux/arm64`で、アーキテクチャごとにそのアーキテクチャのrunnerでビルドします。workerで`claude --version`が2.1.270であること、api・schedulerに`@anthropic-ai`がないことを確認したうえで、digest JSONを`image-digest-<app>-<arch>` artifactとして残します。公開は`main` pushと`v*` tag pushでだけ行われます。`main` pushについては、下の[mainへのマージごとに公開されるイメージ](#mainへのマージごとに公開されるイメージ)を参照してください。`v*` tagの**pushイベント**では(`workflow_dispatch`はどのrefでも指定できるのでイベントも見ます)、`publish`・`index`・`promote` jobが`ghcr.io/jeongjaesoon/werft-<app>`に公開します。package write権限は公開jobだけが持ちます。3つのjobは`release` environmentで動き、tagが指すcommitが`main`の祖先でなければ失敗します(tagはレビューではありません)。`publish`はイメージ・アーキテクチャごとにrun専用のstaging tagにpushしてから、そのdigestをpullして同じsmoke(`.github/scripts/image-smoke.sh`)を通します。`sources`は6つのイメージのDebianソースがsnapshot.debian.orgにあるかを問い合わせます。package writeもenvironmentもありません。`index`はイメージごとに2つのdigestを1つのindexにまとめてrun専用のstaging tagに載せ、indexが正確にその2つのdigestを指しているかを確認します。`promote`は3つのindexが揃ってから初めて`vX`・`sha-…` tagにretagします(registry-side、再ビルドなし)。このrunのstaged index digestがrelease candidateです。既存のtagが別のdigestを指していれば、どのtagも書く前に失敗し(1つのバージョンが2つのbuild attemptのイメージで混ざりません)、照会自体が失敗すれば(認証・rate limit・5xx)「ない」とはみなさずに中断します(fail-closed)。tagを書いた後、6つのreference(3イメージ × 2 tag)を読み直し、candidateと同じときだけ`image-digests-published` artifactを作ります。retagはリポジトリごとに順に行われるので、途中で失敗するとセットが半分だけtagされたまま残ります。そのときはstaged artifactが残っている間に、**同じrunの"Re-run failed jobs"**で埋めます(publish・index jobは再実行されないので、staged artifactとdigestはそのままです)。tagをもう一度pushすると新しいbuild(workerのapt layerはpinされません)になるので拒否されます。3つのdigestをまとめて含む利用者向けの記録は、タグのGitHub Releaseに添付される[`release-manifest.json`](#リリースmanifestを読む)です。`release` environmentのrequired reviewer・deployment branchのルールは、リポジトリ設定で掛けます。registry CDはまだありません。

### mainへのマージごとに公開されるイメージ

`main` push runの`publish-main`・`index-main`・`promote-main` jobが、3つのイメージを`ghcr.io/jeongjaesoon/werft-<app>:main-<12>`として公開します。`<12>`はcommit SHAの先頭12文字です。namespaceは`github.repository_owner`から来ます。schedule、pull request、`workflow_dispatch`のrunは公開しません。

- **検査。** これらのjobと`sources-main`は、タグ経路の`publish`・`sources`・`index`・`promote`と同じstepを実行します。`build`と`supply-chain`が通った後、イメージ・アーキテクチャごとに再びビルドしてrun専用のstaging tagにpushし、そのdigestでsmoke、ライセンス照合、Grype検査を実行します。6つのdigestがすべて通り、`sources-main`が終わってから、indexをまとめて`main-<12>`にretagします(再ビルドなし)。`release`の承認は受けません。マージがレビューだからです。
- **`main-<12>`はdigestで使います。** タグはcommitを探すためだけに使い、デプロイには`name@sha256:…`を書きます。動くタグはありません。`sha-<12>`は`v*`公開のタグで、main公開では使いません。
- **digestを読む。** 公開パッケージは、GitHubにログインせずにタグから読めます。3つのタグはリポジトリごとに順に書かれるので、3つの照会がすべて成功して初めて1セットです。

```bash
TAG="main-$(git rev-parse HEAD | cut -c1-12)"   # from a checkout of the commit to deploy
for app in control-host worker egress-proxy; do
  digest="$(docker buildx imagetools inspect "ghcr.io/jeongjaesoon/werft-${app}:${TAG}" --format '{{.Manifest.Digest}}')"
  echo "werft-${app}@${digest}"
done
```

このdigestは、2つのアーキテクチャを含むindexのdigestです。`main`のマージはReleaseを作りません。リリース(`v*`タグ)の3つのdigestは[リリースmanifest](#リリースmanifestを読む)から読みます。

- **上書きしません。** 書く前に3つのタグをすべて照会し、タグがすでに別のdigestを指していれば、どのタグも書かずに失敗します。同じdigestなら再実行とみなして通します。照会が「ない」以外の理由で失敗したら中断します。同じrunを全体再実行すると再ビルドするのでdigestが変わることがあり、その場合は拒否されて先に載せたイメージがそのまま残ります。セットが半分だけタグ付けされたときは、staged artifactが残っている間に"Re-run failed jobs"で同じdigestを埋めます。
- **`main-<12>`はリリースではありません。** 対応するソースの保管を一部確認できないまま出ることがあります。`sources-main`は6つのイメージのソースをまとめて一度だけ問い合わせ、答えを得られなかったソースを10分まで再度問い合わせます。それでも答えのなかったソースは警告として通し、その一覧をrunのjob summaryと`image-digests-published` JSONの`unverifiedSources`に残します。空の配列はすべて確認できたという意味で、フィールドのない古いJSONは記録がないという意味です。答えのなかったソースが実際には存在しない可能性は残ります。公式リリース(`v*`タグ)は、すべてのソースの保管を確認してから公開されます。`sources`は30分まで問い合わせ、それでも残れば失敗します。このときは、サービスが戻った後に"Re-run failed jobs"でそのjobだけを再実行します。
- **公開されないcommitがあります。** 再検査で修正版のあるhigh・criticalが出たり、脆弱性検査が答えを得られなかったり、snapshot.debian.orgがソースがないと答えたりすると、そのcommitは公開されず、Images runが赤で終わります。必須checkではないのでマージは止めず、次のマージが新しいセットを載せます。マージが1秒以内に続いて1つのpushにまとめられたcommitは、runがないのでタグもありません。
- **アーキテクチャ。** タグ経路と同じく、`linux/amd64`と`linux/arm64`を含むindexで公開します。2つのアーキテクチャがどちらもsmoke、ライセンス照合、Grype検査を通る必要があり、片方が失敗するとそのcommitは公開されません。この方式より前の`main-<12>`は`linux/amd64`だけです。
- **取得。** indexのdigestで取得すると、Dockerがホストのアーキテクチャを選びます。パッケージが非公開なら、先に`docker login ghcr.io`が必要です。

```bash
docker pull "ghcr.io/jeongjaesoon/werft-worker@<digest read above>"
```

### リポジトリ管理者: `v*`タグで公開

この節は、リポジトリにタグをpushする権限のある管理者の手順です。インストールする運用者はタグを付けず、[単一サーバーの設置](/run-server/self-hosting/single-server)や[Kubernetesの設置](/run-server/self-hosting/kubernetes)で公開済みのイメージを使います。

これまで`v*`タグを付けたことがないため、この経路は一度も実行されていません。

1. `main`の検証済みcommitに、`vX.Y.Z`または`vX.Y.Z-<プレリリース>`タグをpushします。そのcommitが`main`の祖先でなければ、公開jobが失敗します。ほかの形のタグ(`v1`、`v1.2.3+build`)はイメージだけが出て、`chart` jobで失敗します。
2. `publish`・`index`・`promote`・`chart-publish` jobが、`release` environmentの承認を受けて終わるかを確認します。承認はこの順に別々に4回要求されます。`publish`と`index`の間の`sources`は承認なしで動き、30分までかかることがあります。
3. `chart-publish`が終わると、`release` jobがタグのGitHub Releaseを作り、`release-manifest.json`を添付します。このjobは別に承認を受けません。先の4回の承認がすでに済んでおり、`contents: write`はこのjobだけが持ちます。Releaseはdraftとして作ってmanifestを載せ、読み直して確認してから公開します。[リリースmanifestを読む](#リリースmanifestを読む)のコマンドで、digestとchartのバージョンを確認します。
4. 同じタグを"Re-run failed jobs"で再実行しても安全です。すでに添付されたmanifestと内容が同じなら通り、違えば失敗して上書きしません。Releaseの作成やアップロードが途中で切れたら、同じ方法で残りを埋めます。イメージが同じタグで再ビルドされてdigestが変わる場合は、`promote`が先に拒否します。

リリース後は、`Chart.yaml`の`version`を次のバージョンに上げます。`main`のchartバージョンはこの値の後ろに付くので、そうすることでプレリリースが直前に出したリリースより後ろに並びます。

### リリースmanifestを読む

`v*`タグごとにGitHub Releaseが1つでき、ファイル`release-manifest.json`が添付されます。運用者はrunやartifactを探しません。リポジトリのcheckoutも不要で、`gh`と`jq`があれば足ります。まだ`v*`タグを付けたことがないため、Releaseはありません。下の`TAG`は、Releaseができた後のタグです。

```bash
TAG=v0.1.0   # the release tag to read
gh release download "$TAG" -R JeongJaeSoon/werft -p release-manifest.json -D "$TAG"   # one directory per tag
jq -r '.images[] | "\(.image)@\(.digest)"' "$TAG/release-manifest.json"   # the three digests used for deployment
jq -c .workerRuntime "$TAG/release-manifest.json"                          # worker runtime
jq -r '"\(.chart.ref) \(.chart.version)"' "$TAG/release-manifest.json"     # chart location and version
helm show chart "$(jq -r .chart.ref "$TAG/release-manifest.json")" --version "$(jq -r .chart.version "$TAG/release-manifest.json")"
```

リポジトリが公開なので、`gh`なしで`mkdir -p "$TAG" && curl -fsSL -o "$TAG/release-manifest.json" "https://github.com/JeongJaeSoon/werft/releases/download/$TAG/release-manifest.json"`でも取得できます。レジストリと照合するには、digestを1つ`docker buildx imagetools inspect <イメージ>@<digest>`に入れます。

| フィールド | 値 |
|---|---|
| `schema` | manifest形式のバージョン。現在は`1` |
| `tag`, `commit` | リリースタグとそのcommit(40文字のhex) |
| `images.<app>.image` | `ghcr.io/<owner>/werft-<app>`。`<app>`は`control-host`、`worker`、`egress-proxy` |
| `images.<app>.digest` | 2つのアーキテクチャを含むindexのdigest。デプロイはこの値で固定します |
| `images.<app>.platforms.amd64`, `.arm64` | そのアーキテクチャのmanifest digest |
| `workerRuntime` | workerイメージが含むClaudeの実行環境(`engine`、`sdkVersion`、`cliVersion`、`profileDigestScheme`) |
| `chart.name`, `chart.version`, `chart.appVersion`, `chart.ref` | 同じrunが公開したchart。`chart.ref`は`oci://`の場所 |

値は、`promote`がレジストリから読み直して確認したdigestと、`chart-publish`がログインなしで読んで確認したchartから来ます。manifestを作るとき、chartパッケージの`Chart.yaml`・`values.yaml`が同じdigestとバージョンを含んでいるかも照合します。一度添付されたmanifestは変わりません。同じタグを再実行して別の内容が出ると、jobが失敗します。

インストールする運用者は、このmanifestから[単一サーバーの設置](/run-server/self-hosting/single-server)に入れるイメージの行を得ます。

### Helm chartの公開

イメージのpromoteが終わると、同じrunがchart `werft`を`oci://ghcr.io/jeongjaesoon/werft`に公開します。経路は`main` push(`chart-main`、`chart-publish-main`)と`v*`タグpush(`chart`、`chart-publish`)の2つで、stepは同じです。schedule、pull request、`workflow_dispatch`のrunは公開しません。

- **バージョン。** タグ`v1.2.3`はchart `1.2.3`、appVersion `v1.2.3`です。`main`は`<Chart.yaml version>-main-<12>`、appVersion `main-<12>`です。`-main.<12>`でない理由は、12桁がすべて数字で0から始まるとsemverではなく、helmが拒否するためです。
- **値。** `.github/scripts/chart-package.ts`が、そのrunの`image-digests-published`から3つのdigestとworker runtimeを読み、パッケージ内の`values.yaml`に入れます。3つのアプリがちょうど1回ずつ、このcommitのpromoteされたイメージであり、repositoryがchartの既定値と同じである必要があります。リポジトリの`values.yaml`はそのままです。同じ値を`chart` artifactの`werft-<version>.values.yaml`にも残します。運用者はartifactなしで`helm show values`で読みます。digestはindexのdigestです。worker runtimeはアーキテクチャに依存しない値で、2つのアーキテクチャの値が異なれば`index`が止まります。workerの比較はdigestではなくこの値を見るので、単一manifestで公開されたchartからindexのchartに上げても、digestの値が変わるだけで再インストールの動作は変わりません。
- **検査。** `chart` jobは3つのindexとそのアーキテクチャ別のmanifestをログインなしで照会し、パッケージをamd64のkindにインストールして、`/readyz`と`/docs`が200のときだけパッケージを渡します。arm64は`publish`のsmokeとこの照会までを確認し、kindへのインストールはしません。空のインストールはworkerを起動しないので、workerは照会までだけを確認します。package write権限はありません。pull requestでは、`helm-chart` jobの`render-check.ts`がfixture digestでパッケージを作ってレンダリングします。
- **公開。** package writeは`chart-publish`・`chart-publish-main`だけが持ちます。タグ経路の`chart-publish`は`release` environmentを受け、`main`経路は受けません。イメージの公開が失敗したrunでは、chartの段階は動きません。
- **上書きしません。** `.github/scripts/chart-push.sh`は、同じバージョンがすでにあれば取得して展開したファイルを候補と比較します。同じなら再実行とみなしてpushせず、違えば失敗します。照会が「ない」ことを確認できなければ中断します。`denied`は存在しないパッケージに対してghcrが返しうる答えなので、ログインなしの照会でも`denied`のときに限って「ない」とみなします。
- **読み取りの確認。** push後、HelmとDockerのログイン情報をすべて空にした状態で取得して候補と比較し、`helm show chart`を出力します。パッケージが非公開で作られていれば、ここでrunが赤で終わります。公開範囲は、パッケージ設定でリポジトリ管理者が変えます。
- **ライセンス。** chartは、リポジトリと同じPolyForm Small Business License 1.0.0に従います。

### worker内で作ったcommitの作成者

workerイメージは、gitのsystem設定(`/etc/gitconfig`)に`user.name=Werft`、`user.email=noreply@werft.invalid`を置きます。そのため、Claudeがworkspaceで作ったcommitは、リポジトリやセッションが別に定めない限り、authorもcommitterも`Werft <noreply@werft.invalid>`です。この値がないとgitがcommitを拒否し、Claudeはユーザーに名前とアドレスを尋ねます。`.invalid`はどこにも配送されない予約ドメインなので、実在の人のアドレスと重なりません。checkpointの内部commitはこの値を使いません(`checkpoint@werft.invalid`)。同じsystem設定は、その後ろに`include.path=~/.werft/git-identity`を置きます。セッションのリポジトリがコンソールの作成用GitHub Appを使う場合、workerがそのファイルにApp botアカウント(`<slug>[bot]`)を書いて既定値を上書きします([GitHubアカウントの連携](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md#github-계정-연결)の「commitの作成者」)。ファイルがなければ、includeはスキップされます。

system設定はgit設定の中で優先順位が最も低いので、セッション内で決めた値があればそちらが勝ちます。セッションの作成者を変えるには、workspaceのリポジトリに`git config user.name`・`git config user.email`を書きます。`git commit --author`はauthorだけを変え、committerはそのままです。`git config --global`はtmpfsのHOMEに書かれるので、workerが替わると消えます。リポジトリ設定も、checkpointから復元したworkerでは消えます。復元がworkspaceを空にしてリポジトリを新しく作るためです。そこから先は、再び既定の作成者でcommitされます。カタログやインストール設定で既定値を変える機能は設けていません。ユーザーごとの作成者を既定値にするにはユーザーのアドレスをworkerに渡す必要があるので、まず製品としての決定が必要です。イメージのsmoke(`.github/scripts/image-smoke.sh`)が空のリポジトリでcommitしてこの作成者を確認し、e2e(`tests/e2e/alpha-path.e2e.ts`)が実際のClaude CodeのBashツールで同じことを確認します。

### worker内のGitHub CLI

workerイメージにはGitHub CLI(`gh`、`/usr/local/bin/gh`)があります。セッション内で`gh`コマンドがなくて迷わないようにするためのもので、GitHubに届く経路は増やしません。イメージにはGitHubのログインやtokenがなく、`api.github.com`はegress proxyの既定の一覧のどこにもありません。そのため、出荷イメージと既定のegress設定では、`gh --version`・`gh help`のようにネットワークを使わないコマンドだけが動き、GitHubを呼ぶコマンドは読み取りでも書き込みでも失敗します。ログインがなければ、`gh`はリクエスト前に`gh auth login`の案内とともにexit 4で終わります。セッションが`GH_TOKEN`を入れても、proxyが`api.github.com:443`のCONNECTを`destination is not allowlisted`で拒否し、`Forbidden`で終わります(2026-11-03のfake modelセッションで確認)。運用者が`EGRESS_ALLOWLIST`に`api.github.com:443`を加えると、この遮断はなくなります。その場合、セッションが自分で持っているtokenで`gh`がGitHub APIを呼べるようになり、プラットフォームのpush承認・ブランチ制限はその呼び出しには掛かりません。GitHubへの書き込みを内蔵の`github` MCPサーバーだけに通したいなら、このhostを一覧に入れません。バージョンはworker Dockerfileの`GH_VERSION`とarchごとのsha256(リリースのchecksumsファイルの値)で固定し、毎日のDebianセキュリティ更新では追従しないので、手で上げます。バイナリ1つでイメージが約38MB増えます。

### worker内のパッケージツール

出荷workerイメージには、Bun(Node互換shimを含む)とengineだけがあります。npm・pnpm・yarn・Ruby・Bundler・Goはありません。セッションでこれらのツールを使って依存パッケージをインストールするには、運用者が`WORKER_IMAGE`をこのイメージから派生したイメージに変えます。派生イメージは`/workspace`以外の`VOLUME`を宣言してはならず(実行基盤ドキュメントのイメージ契約)、engine・SDK・CLIの組み合わせを変えてはいけません。レジストリへのアクセスは、イメージに関係なくegress proxyの`packages` routeでのみ行えます([実行基盤 § egress](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/execution.md))。workerがclaim時にHOMEへnpm・Bundler・Goのuser設定を書くので、派生イメージにレジストリ設定を入れる必要はありません。

workerが書くnpm設定はuserレベルなので、リポジトリの`.npmrc`が`registry=`を決めていればそちらが勝ちます。そのレジストリのhostにはforward proxyで届かないので、インストールは`403`で失敗します。2026-11-01に派生イメージで`config get registry`により測った優先順位は、次のとおりです(リポジトリの`.npmrc`に`registry=https://registry.npmjs.org/`、user設定にroute)。

| ツール | user設定のみ | `npm_config_registry`環境変数 | CLI `--registry` | 備考 |
|---|---|---|---|---|
| npm 10.9.9 | リポジトリの値が勝つ | 環境変数が勝つ | CLIが勝つ | リポジトリの`.npmrc`がなければuser設定(route)を使います |
| pnpm 9.15.0 | リポジトリの値が勝つ | 環境変数が勝つ | `config get`はオプションを受け付けない | npmと同じ順序 |
| yarn 1.22.22 | npmのuser設定を読まない(`registry.yarnpkg.com`) | 読まない | CLIが勝つ | `YARN_REGISTRY`が勝つ。`registry.yarnpkg.com`は一覧にありません |

そのため、リポジトリがregistryを固定しているなら、セッションで`npm ci --registry <route>/packages/npm/`のようにCLIで上書きします。workerはengineの環境変数を決められた一覧だけ渡すので、`npm_config_registry`は入れません。yarn 1は`--registry`か`YARN_REGISTRY`を使う必要があります。

同じ日に実際のセッション(npmキャッシュを空にした状態)でインストールまで実行した結果も同じです。リポジトリが公開registryを固定したプロジェクトでは、`npm ci`は`403 Forbidden - GET https://registry.npmjs.org/...`で失敗しました。`pnpm install`はリポジトリのregistryに向かい、routeのアドレスにだけ結び付いたtokenを見つけられず、`No authorization header was set for the request`で失敗しました。固定していないプロジェクトの`npm ci`・`bundle install`は、routeから取得しました。

Goは、公式リリースのtarballをchecksumで固定して派生イメージの`/usr/local/go`に展開し、`PATH`に加えます。`GOTOOLCHAIN=local`も一緒に置きます。そうしないと、`go.mod`の`go`行がイメージより新しいとき、Goが新しいツールチェーンを取りに行きます。ユーザーは、イメージの元のユーザー(`USER 1000:1000`)に戻します。local-docker実行基盤のworkerの`/tmp`は、tmpfsのオプションに`exec`がないため、Dockerが`noexec`でマウントします。そのため、`go run`と`go test`は`/tmp`に作った実行ファイルを起動できず、`fork/exec /tmp/go-build…: permission denied`で失敗します(2026-11-02実測)。HOMEも同じtmpfsなので、`go install`が`~/go/bin`に置いたファイルも実行されません。`go test`は、`GOTMPDIR`をworkspace内の既存のディレクトリに指定すれば通ります。`go run`は実行ファイルを`GOCACHE`(既定値はHOMEの下)から起動するので、`GOCACHE`もworkspaceに移す必要があります(例: `mkdir -p .gotmp && export GOTMPDIR=$PWD/.gotmp GOCACHE=$PWD/.gotmp/cache`、同じ日に実測)。実行ファイルは`go build -o`でworkspaceに作ります。

```dockerfile
FROM <shipped worker image>
USER root
ADD --checksum=sha256:<release sha256> https://go.dev/dl/go<version>.linux-<arch>.tar.gz /tmp/go.tar.gz
RUN tar -xzf /tmp/go.tar.gz -C /usr/local && rm /tmp/go.tar.gz
ENV PATH=/usr/local/go/bin:$PATH GOTOOLCHAIN=local
USER 1000:1000
```

2026-11-02に、この形の派生イメージ(go1.27.3)で実際のGitHub sandboxセッションを実行しました。セッションのプライベートリポジトリにあるモジュールはリポジトリのrouteで、公開モジュールは`packages` routeで取得しました([api-server.md](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md)の「LFS・submodule・Goモジュール」の項目)。

出荷イメージの`bun install`は、userの`.npmrc`のregistryとtokenでmetadataをrouteから取得します。しかし、tarballはmetadataの`dist.tarball`に書かれた`https://registry.npmjs.org/...`のアドレスから直接取得しようとするので、forward proxyが`403`で遮断します(2026-11-01実測)。npmは`replace-registry-host`の既定値(`npmjs`)で、そのhostを設定したregistryに置き換えて取得します。Bunにはそのような設定がないため、現在はBunで公開npmパッケージをインストールできません。

### workerイメージのアップグレードとcheckpointの互換性

単一サーバー(compose)インストールの[アップグレード](/run-server/self-hosting/upgrade)でworkerイメージが変わると、新しいイメージのengine・SDK・CLI・profile digestで、現在の各checkpointのrestore planを計算します。4つの値がすべて同じで互換性のあるセッションは承認なしで続き、`INCOMPATIBLE_CHECKPOINT`のセッションだけをユーザーに知らせて、正確な一覧の承認を受けます。検査を最後まで実行できないか、ほかの検証失敗が混ざれば、未回収のcheckpointがあるセッションすべてを影響一覧とするfail-closedの動作をして、ログに残します。writerを止めた後にも、同じ検査をもう一度行います。互換性のないセッションで`start_fresh`を選ぶと、以前のcheckpointのcontextを捨てます。Kubernetes(helm)インストールでは、pre-upgrade hookが同じ判定を、イメージを実行せずにポインタの組み合わせで行います([Kubernetesインストール § アップグレード前の検査](/run-server/self-hosting/operate/kubernetes-deployment#アップグレード前の検査))。

workerイメージが変わると、upgradeは変わる前のイメージを直前のイメージとして残します(upgradeスクリプトの状態ディレクトリに`previous-worker`ファイルとして置きます)。schedulerはセッションごとに、checkpointポインタの組み合わせ(engine・SDK・CLI・profile digest scheme)と同じイメージを現在・直前の中から選び、両方が合えば現在のイメージを使います([設定リファレンス § scheduler・workerコンテナ・egressの設定](/run-server/self-hosting/operate/configuration#schedulerworkerコンテナegressの設定))。そのため、ゲートは、新しいイメージで復元できないセッションのうち、直前のイメージでも復元できないセッションだけを影響一覧に載せます。新しいイメージと直前のイメージのどちらか一方の検査でもfail-closedで終われば、新しいイメージ基準の一覧をそのまま使います。同じ組み合わせで再ビルドしたイメージなら、schedulerは新しいイメージで起動するので、新しいイメージで復元できると確認できなかったセッションは、直前のイメージが復元できるとしても一覧から外しません。どちらか一方が自分の組み合わせを出力できない古いイメージなら(`apps/worker/src/image-runtime.ts`がないビルド)、直前のイメージを使わず、ゲートも新しいイメージ基準の一覧をそのまま使います。サポート期間は1リリースです。もう一度アップグレードすると、その前のイメージに残ったセッションが再び影響一覧に載ります。

SDKを上げるリリースは、サンプル設定ドキュメント(`tests/fixtures/settings/`)の`runtime_version`も一緒に上げ、運用インストールの上限は新しいバージョンで保存します。現在のイメージが載せていない`runtime_version`のprofileは、新しいセッションを受け付けません。同じリリースに、新しいエンジン組み合わせの内蔵ツール対応一覧(`packages/adapters/runtimes/claude-codec/src/tool-catalog.ts`)も入れます。一覧のないバージョンの上限は、`deny`で作れません。新しい一覧に加わったツールは各上限の新しいバージョンでブロックされたまま続き、`accept_added_tools`で受け入れると開きます([api-server.md](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md#운영자-카탈로그-agent-profile--repository))。Kubernetes(helm)インストールのデプロイ順序と、変更ごとのセッションの動作は、[Kubernetesインストール § アップグレードとロールバック](/run-server/self-hosting/operate/kubernetes-deployment#アップグレードとロールバック)にあります。

### worker・control-hostのロールバックとincremental checkpoint

commit `95b0e7b5`から、workerは直前のcheckpointのbundleチェーンの上に、新しいオブジェクトだけを含むincremental bundleを載せます。そのチェーンはmanifestの`workspace.baseBundles`に書かれます。manifestの`version`はそのまま2で、incrementalかどうかはこのフィールドの有無だけで分かれます。**それより前のビルドにロールバックすると、このフィールドがあるcheckpointを復元できません。** 以前のビルドのmanifestスキーマは、未知のキーを拒否するためです。

- **古いworkerイメージ。** 復元時にmanifestのdecodeが`Invalid Claude checkpoint manifest: workspace Unrecognized key: "baseBundles"`で失敗します。この失敗はworkspaceを空にしたりbundleを取得したりする前に起きるので、半分だけ復元されたworkspaceは残りません。その代わりmanifestは固定されているので、再びlaunchしても同じ理由で`worker.failed`になります。
- **古いcontrol-host。** 復元計画が`CHECKPOINT_UNAVAILABLE`で拒否され、前のrevisionに戻りません。finalizeもincremental manifestを拒否するので、pointerが上がりません。新しいworkerと混在していれば、最初のcheckpointのように単独のbundleだけがcommitされます。古いGCはdecodeできないセッションをスキップするので、base bundleを削除することはありません。
- **影響セッションを探す。** DBにはmanifestの内容がありません。`sessions.checkpoint_revision`が指す`checkpoints`行(`collected_at IS NULL`)の`manifest_ref`・`manifest_version`でobject storeからmanifestを取得し、`jq -e '.workspace.baseBundles | length > 0'`で振り分けます。復元が`parent_revision`をたどって戻ることもあるので、親の行も一緒に見ます。workerログ`worker.checkpoint.published`の`base_bundles`が0より大きければ、incrementalで載せたものです。
- **ロールバック前にすること。** 影響セッションがあれば、ロールバックせずにロールフォワードします。新しい完全なbundleで再度checkpointさせる運用手段(環境変数・設定・CLI)はまだありません。workerは、チェーンがない、途切れている、または長さ32(`MAX_WORKSPACE_BUNDLE_CHAIN`)やbundle上限に達したときにだけ、自分で完全なbundleを載せます。そのため、どうしてもロールバックが必要なら、影響セッションはロールバックの間は復元されません。ロールフォワードすれば、そのまま復元されます。

### control-hostのロールバック下限: releaseのツールで実行

この変更から、control-hostはreleaseで作ったセッションを、releaseに固定されたツール(`agent_releases.runtime_config_snapshot.tools`、profileのツールの範囲内)で実行します。それ以前はprofileのツールすべてでした。ツールはworkerの起動時に受け取るclaimに載り、workerは終わるまでそのツールで動きます。そのため、カードで`tools`を選んだり`forbidden`を書いたりしたエージェントは、すでに進行中のセッションも次のclaimから絞られます。デプロイ前に起動したworkerは、最後のturnが終わった後に入力なしで`WORKER_IDLE_TIMEOUT_SEC`(既定1800秒)が過ぎるか、pause・再起動で終わるまで、profileのツールを使います。releaseのないセッションと、カードがprofileのツールをすべて残すreleaseのセッションはそのままです。workerイメージとworker protocolは変わりません。

- **ロールバック下限はcommit `2648f2ac`です。** ツール一覧はcheckpointのprofile digestに入ります。`2648f2ac`以降のcontrol-hostは、claimの復元候補にprofileのツールとreleaseのツールの2つの一覧をどちらも入れるので、この変更と`2648f2ac`の間は、どちらへ移っても互いのcheckpointを復元します(下の復元候補上限の例外は除きます)。それより前のビルドにロールバックすると、releaseのツールで作ったcheckpointを復元できず、そのセッションは最初のlaunch後に`recovery_required`(`incompatible_checkpoint`)で止まります。ロールフォワードした後、`retry_restore`で同じcheckpointを再試行すれば済みます。そのため、`2648f2ac`より前のビルドからこの変更を含むビルドへ直接上げず、`2648f2ac`以上のビルドを先にデプロイしてロールバック先にします。
- **絞られるreleaseの数。** デプロイ前に読み取りクエリで数えます。カードがprofileのツールをすべて選んだreleaseも数えるので、上限値です。

```sql
WITH narrowed AS (
  SELECT r.id FROM agent_releases r JOIN agent_versions v ON v.id = r.version_id
  WHERE v.card->'capabilities'->'tools' <> 'null'::jsonb
     OR jsonb_array_length(coalesce(v.card->'capabilities'->'forbidden', '[]')) > 0
)
SELECT
  (SELECT count(*) FROM narrowed) AS releases,
  (SELECT count(*) FROM sessions s JOIN narrowed n ON n.id = s.agent_release_id
    WHERE s.admission_state NOT IN ('closing', 'closed')) AS open_sessions,
  (SELECT count(*) FROM agent_releases
    WHERE CASE WHEN jsonb_typeof(runtime_config_snapshot->'tools') = 'array'
      THEN EXISTS (SELECT 1 FROM jsonb_array_elements(runtime_config_snapshot->'tools') t
                    WHERE jsonb_typeof(t) <> 'string')
      ELSE true END) AS unreadable;
```

`unreadable`は、`tools`がないか文字列の配列ではないsnapshotです。そのようなreleaseのセッションは、内蔵ツールなしで動きます(許可しない側に読みます)。正常な経路で作ったreleaseは、常に文字列配列の`tools`を載せます。
- **復元候補の上限。** claimの復元候補は16個までです(worker契約)。すべてのprofile一覧をrelease一覧より先に入れます。実際にツールが絞られるreleaseのセッションのうち、以前のprofileが多いセッション(GitHub設定がなければ16個、あれば8個以上)は、2つのものを失います。① この変更の後は、現在のprofileのprofile一覧がもう1枠使うので、最も古い以前のprofileの候補が1つ外れます。その候補でのみ合うcheckpointは、復元が`incompatible_checkpoint`で止まり、同じ候補ルールを使うビルドでは再試行しても同じです。そのセッションは`start_fresh`(以前のcontextを捨てる)か`close`で終えます。② `2648f2ac`にロールバックすると、そのビルドのclaimはprofile一覧だけで上限が埋まり、releaseのツールの候補を入れられないので、この変更の後にreleaseのツールで作ったcheckpointを復元できません。こちらは、ロールフォワードした後に`retry_restore`で再試行すれば済みます。

### worker protocolのフィールドを取り除く順序

APIをアップグレードしても、すでに起動しているworkerコンテナは古いイメージで動き続けます。入力のないworkerも、`WORKER_IDLE_TIMEOUT_SEC`(既定1800秒)の間は残ります。そのため、worker protocolのフィールドは、受け取る側がまずそのフィールドなしでも受け入れるように変え、そのリリースへの入れ替えがすべて終わってから、送る側がフィールドを外します。1つのリリースで両側を同時に変えません。

| フィールド | 第1段階: 受け取る側が要求しない | 第2段階: 送る側が外す(第1段階の入れ替えが終わった後) |
|---|---|---|
| heartbeat応答`auth_revision` | workerがフィールドのない応答も受け取る | APIが送らない。その前に、第1段階より前のイメージのworkerが1つも残っていないかを確認する |
| append-eventsリクエスト`batch_key` | APIがフィールドのないリクエストも受け取る(まだ行っていない) | workerが送らない。その前に、第1段階より前のAPIが1つも残っていないかを確認する |

第2段階を早くデプロイしすぎると、古い側が相手のリクエストや応答を契約違反として拒否します。workerは契約に合わないheartbeat応答を再試行できない失敗とみなすので、最初のheartbeatでleaseを失ったと判断して止まります。

checkpoint manifestにフィールドを加えるときは逆で、読む側が先です。control-host(commit前の検証・復元計画・GC)とworker(復元)は、どちらも未知のキーを拒否します。そのため、control-hostを先に上げるか同じリリースで上げ、workerはその後に上げます。そのフィールドを書いたcheckpointができた後にworkerをロールバックすると、上の`baseBundles`と同じ理由で、そのセッションは復元されません。

| フィールド | 先に: 読む側 | その次に: 書く側 |
|---|---|---|
| `workerState`(承認待ちのpark) | control-hostとworkerが、このキーのあるmanifestを受け付ける | workerが承認待ちのturnをparkするときだけ書く |

workerが送るworker protocolのフィールドを新しく加えるときも、APIが先です。APIのworker protocolリクエストschemaはstrictなので、古いAPIは未知のフィールドが載ったリクエスト全体を400 `BAD_REQUEST`で拒否します。

| フィールド | 先にデプロイ | 古いAPIに当たった新しいworker |
|---|---|---|
| pending-controlリクエスト`settled[].reason`・`settled[].answer_result` | API | `worker.pending.settlement_detail_refused`の警告を一度残し、そのattemptが終わるまで`outcome`だけを送る。receiptは以前のルールどおりに精算され、`pending_requests.settled_reason`・`settled_answer_result`は空になる |
| bootstrap-claim・pending-controlリクエスト`capabilities`、register-pendingリクエスト`remember_offer` | API | 互換性のための再試行がない。新しいworkerの最初のリクエストであるbootstrap-claimが400 `BAD_REQUEST`(再試行不可)で拒否されると、workerはエラーで終わり、turnを1つも実行しない。APIだけを戻しても同じ。APIを戻す前に、新しいworkerイメージを使うセッションがないかを確認する |

### DBスキーマを変える順序

migrationはrolloutの前に実行されます。そのため、新しいスキーマの上で古いcontrol-hostがしばらく動き、古いworkerイメージはサポート期間の間動き続けます。古いコードが読み書きする列・テーブルは、そのコードがすべてなくなるまで残っている必要があります。そのため、スキーマ変更は3つのリリースに分けて行います。1つのリリースで追加と削除を同時に行いません。

| 段階 | すること | 古いコードから見えるもの |
|---|---|---|
| 1. 拡張(expand) | 列・テーブルを加える。新しい列はnullを許容するか、既定値を置く。既定値を置くと既存の行でもその値が読まれ、INSERTがその列を省くと既定値が入る。明示的なNULLには既定値が適用されないので、null許容の列ならNULLで保存され、NOT NULLの列ならINSERTが失敗する。そのため、既存の行に合う値かどうかと、古いコードのINSERTがその列をどう扱うかを見て選ぶ | 未知の列ができるだけで、古いコードの書き込みはその列を省いて入る |
| 2. 切り替え | 新しいコードが新しい列にも書き始める。古いコードが古い列に書いている間は、古い列が基準。新しいコードは両方の列に書くが、古い列を読む。古いコードの書き込みを新しい列に移す仕組み(triggerなど)がなければ、古いwriterがすべてなくなった後、既存の行を最後にbackfillしてから、読み取りを新しい列に移す | 古い列がそのまま残っているので、読み書きが続く |
| 3. 整理(contract) | 古い列・テーブルを削除するか、NOT NULL・CHECKで制約を強める。その列を使うイメージがサポート期間の外に出て、そのイメージのworkerとcontrol-hostが実際に1つも残っていないことを確認した次のリリースで行う。制約を強める前に、既存の行と現在動いているすべてのwriterが新しい制約を満たすかを確認する | その列を使う古いコードはもうない |

列の名前を変えることも、古い名前をすぐになくすので同じ順序に従います。新しい列を加え、データを移してコードを変えた後、古い列を削除します。`WORKER_IDLE_TIMEOUT_SEC`は最後のturn後のアイドル時間であって、workerの寿命の上限ではありません。作業中のworkerはそれより長く残ることがあるので、整理の時期は時間ではなく、実際に残っているコンテナで判断します。

例: checkpointポインタのランタイム組み合わせ`checkpoints.runtime_*`(migration `0196_checkpoint_runtime`)は第1段階として、既定値のないnull許容の列だけを加えました。それより前にcommitされた行は、nullのまま残ります。`0199_worker_image_runtime`(launchの組み合わせ、checkpointのdigest scheme、`worker_image_refusals`表)も第1段階です。schemeがnullのcheckpointは、最初のscheme(1)として読みます。

## サプライチェーンの脆弱性ポリシー

**修正版があるhigh・criticalの脆弱性だけをブロックします。** 修正版のない発見は報告だけして、失敗させません。

- **何を見るか。** 3つのイメージ(Grype、Debianパッケージと`/app`のnpmパッケージ)と`bun.lock`全体(`bun audit`、dev依存関係を含む)です。「修正版がある」とは、イメージではGrypeの`fix.state`が`fixed`であるもの、npmではGitHub advisory databaseで、ロックされたバージョンを含む範囲に`first_patched_version`があるものです。Debianの`not-fixed`・`wont-fix`と、修正版のないnpm advisoryはブロックしません。
- **どこでブロックするか。** images.ymlの`supply-chain` jobが判定し、branch protectionのrequired checkです。PR、main push、毎日03:17 UTCの実行、手動実行、`v*` tagのすべてで動きます。tagの`publish`とmainの`publish-main`は`supply-chain`を待ち、昇格するdigestを再検査して同じ基準でブロックします。
- **検査が答えを得られないとき。** Grype DBやadvisoryサービスが応答しなかった`error`は、PRとmain pushでは警告だけを残します。外部サービスの障害ですべてのマージが止まってはいけないためです。毎日の実行とtagでは失敗します。main pushでも公開はしません。`publish-main`が`supply-chain`の結果を同じファイルで再判定し、`error`なら失敗します。イメージがビルドされず結果がまったくなければ、どこでも失敗します。
- **報告。** 修正版のないhigh・criticalも、各検査のstep summary(折りたたまれた一覧)と`supply-chain-results` artifact(検査ごとにJSON 1つ、項目ごとに`fix`がnull)に残ります。毎日の実行や手動実行が失敗すると、`ci-supply-chain`ラベルのissueが開きます。
- **夜間の新しいadvisory。** 修正版のあるadvisoryが新たに出ると、mainを含むすべてのPRの`supply-chain`が一斉に赤くなります。意図した動作です。依存関係やbaseを上げるPR 1つで解消します。Debianパッケージは、翌日の`APT_UPGRADE_KEY`で新しいビルドが取り込みます。当日に取り込むには、手動実行(`gh workflow run Images`)がその日のkeyでビルドします。
- **例外。** 上げられない修正(例: `upgrade`が保留したDebianパッケージ、コードパスが届かないadvisory)は、`.github/vulnerability-exceptions.json`に`{"id", "package", "reason", "expires"}`として書きます。`id`は検査結果の`id`(CVE-…またはGHSA-…)、`package`はパッケージ名です。`reason`と`expires`(YYYY-MM-DD、その日まで適用)がなければ、npm検査が`error`になります。期限が切れると、再びブロックします。例外はPRレビューを経ます。

```bash
bun .github/scripts/npm-audit.ts /tmp/sc && cat /tmp/sc/npm.txt   # the npm verdict, locally
.github/scripts/supply-chain-verdict.sh /tmp/sc warn              # verdict over the four result files (control-host, worker, egress-proxy, npm)
```

第三者への告知(`THIRD_PARTY_NOTICES.md`とイメージごとの`/app/DEBIAN_SOURCES.md`)を作る方法は、[ci.md](https://github.com/JeongJaeSoon/werft/blob/main/docs/contributing/ci.md)にあります。
