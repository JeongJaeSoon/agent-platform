This is the procedure for putting main on Kubernetes. The chart source is in `deploy/helm/agent-platform`, and every `main` merge and every `v*` tag publishes it to `oci://ghcr.io/jeongjaesoon/werft`. The defaults run on any Kubernetes (kind included). The AWS-only values (ALB Ingress, IRSA, ECR, External Secrets) are only in the chart's `values-aws.example.yaml`. How each component behaves and its environment variables are in [Kubernetes execution backend](https://jeongjaesoon.github.io/werft/en/run-server/self-hosting/operate/kubernetes-backend/), and backup is in [backup-restore.md § Kubernetes install](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/backup-restore.md#kubernetes-설치).

**Current status:** there is no official release (`v*` tag) yet. The chart published on every `main` merge carries that run's image digests and worker runtime, so you [install from the published chart](#install-from-the-published-chart) without a repository checkout. The repository's `values.yaml` has empty digests, so when you install from a checkout path you must supply the digests yourself. Rendered as is, it fails.

The Docker single-server install (`local-docker` execution base, compose) stays supported. Its procedure is the [single-server install](https://jeongjaesoon.github.io/werft/en/run-server/self-hosting/single-server/), and this page is the second install path beside it.

The memory of one worker Pod (`worker.memoryMb`) is sized to the transcript limit, and since requests = limits it decides how many sessions run on a node at once. Before you size nodes or change this value, read [Capacity](https://jeongjaesoon.github.io/werft/en/run-server/self-hosting/operate/capacity/).

Each command says where it was checked. **kind** means the command was run on a cluster started with `deploy/kind/up.sh`. **AWS only** means the command needs AWS resources and cannot run locally. The **kind** mark does not mean the document block ran as written in two cases. The Secret block under direct install differs from the form `up.sh` creates, and the block as written was not run. The commands under "Upgrading the published chart" were run against a fixture chart, not the published one. The previous-image path of the pre-upgrade check (the branch that reads the previous image with `lookup`, and the real `helm upgrade` that drops or changes the previous image) was not run on kind either.

## What the chart creates

| Resource | Count | Notes |
|---|---|---|
| api Deployment + Service(3000) + authorizer Service(3100) | 2 | Only egress-proxy reaches 3100 (NetworkPolicy). The Ingress routes only `/v1`, `/docs`, `/healthz` and `/readyz` on 3000. It does not open `/internal`, which is for workers. The web console `/` is added with `ingress.console.enabled` ([below](#the-web-console-and-internal)) |
| scheduler Deployment + Role/RoleBinding | 1, `Recreate` | Creates and deletes worker Pods, nonce Secrets and workspace PVCs, in its own namespace only |
| reconciler Deployment | 1 | |
| slack Deployment | 1 | Drains the Slack inbox. Absent when `slack.enabled: false`. Outbound only to DNS (53), 443 and the DB port (`networkPolicy.slack.databasePort`, default 5432) |
| egress-proxy Deployment + Service(3128, 3129) | 2 | The only path workers have to the outside |
| migrate Job | 1 per install and upgrade | `pre-install,pre-upgrade` hook |
| upgrade-check Job | 1 per upgrade | `pre-upgrade` hook, before migrate. Absent when `scheduler.enabled: false` ([Pre-upgrade check](#pre-upgrade-check)) |
| checkpoint GC CronJob | weekly | `checkpointGc.schedule` |
| session archive CronJob | weekly | `sessionArchive.schedule` (default `0 5 * * 0`), `afterDays` (default 180, 0 = off, 30 to 3650), `dryRun` (default `true`). Moves the events of long-idle sessions to the bucket ([data-retention.md](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/data-retention.md#세션-이벤트-보관)) |
| NetworkPolicy | 5 | Workers go out only through egress-proxy. Among the control-plane Pods, only slack has its outbound connections restricted |
| Ingress, ExternalSecret | optional | `ingress.enabled`, `secrets.externalSecret.enabled` |
| metrics Deployment + Service(9464) + NetworkPolicy | optional, 1, `Recreate` | `metrics.enabled`. Emits platform metrics ([Platform metrics](https://jeongjaesoon.github.io/werft/en/run-server/self-hosting/operate/metrics/)) |

What the chart does not create: PostgreSQL 16, an S3-compatible object store, Secret values, and worker Pods (the scheduler creates one per session). On kind, the PostgreSQL and LocalStack in `deploy/kind/deps.yaml` stand in.

The chart does not create a Git server either. The repository in the settings document is an address the Pod can reach through the egress proxy. In the kind check environment, when `KIND_MODEL` is `fake` or `real`, `deploy/kind/up.sh` starts a read-only fake-git from `deploy/kind/deps-session.yaml`. fake-git runs on the control-host image, serves `/agent/sample-app.git` and `/agent/gate-app.git` from Service `fake-git:3000`, is rebuilt with the same commits at every start, and answers push with 403.

## Prerequisites

- A CNI that enforces NetworkPolicy. On a CNI that does not, there is no worker isolation. The default CNI of kind v0.33 (kindnet) enforces it. On EKS, turn on the VPC CNI network policy agent.
- PostgreSQL 16 and an S3 bucket. The default protection mode `locked` requires a bucket with versioning and Object Lock turned on, and otherwise the api refuses to start.
- When you install the published chart, the image digests are inside the chart, so skip this item. When you install from a checkout chart, write down the digests of the three images (control-host, egress-proxy, worker). The default names in `values.yaml` are the publish location, so you only fill in the digests of the published images (read them with `helm show values` in [Install from the published chart](#install-from-the-published-chart)). On kind, `deploy/kind/up.sh` builds them from the checkout instead. When you cannot use the published images, build the images yourself and push them to your registry, then change `images.registry` and `images.*.repository` in values to that registry (the form of `values-aws.example.yaml`). The chart takes no tag and renders only `<registry>/<repository>@<digest>`. Without a digest, rendering fails. The `WORKER_IMAGE` the scheduler receives must also have the form `repository@sha256:<digest>`.
- The Secret named `secrets.name` (default `werft`). Its keys are below. Do not leave the values in command arguments or shell history.

| Key | Read by |
|---|---|
| `DATABASE_URL` | api, scheduler, reconciler, slack, migrate, checkpoint GC |
| `EGRESS_AUTHORIZER_TOKEN` | api, egress-proxy (the same value) |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | api, checkpoint GC. Only when `secrets.objectStoreKeys: true`. When `false`, requests are signed with the default AWS credential chain (IRSA) |
| the names in `secrets.catalogEnv` (default `ANTHROPIC_API_KEY`) | api only. The provider and repository credentials the settings document points to with `value_env`. slack does not receive them |
| `PLATFORM_SECRET_KEY` | api, slack. Required. A 64-character hex master key. It seals credentials saved from the console. If the Secret lacks it, the Pod does not start |

## Install order

The order is Secret → image digests → migrate → control plane. In the chart, only the Secret and the schema must come first; Helm orders the rest with hooks.

1. The ExternalSecret (when used, hook weight -10) writes the Secret.
   On an upgrade, the upgrade-check Job (hook weight -5) then checks for sessions that could no longer resume. If it fails, Helm stops and migrate does not run ([Pre-upgrade check](#pre-upgrade-check)).
2. The migrate Job (hook weight 0) raises the schema and, when you come from a chart that had a file catalog, imports the old ConfigMap into the settings (see "Upgrading from the file catalog" below). If it fails, Helm stops and the Deployments do not change.
3. The api, egress-proxy, reconciler, scheduler and slack Deployments are applied together. They do not wait for each other; each becomes ready once its probe passes. scheduler, reconciler and slack are ready only after their first pass ends.

### kind (local)

`deploy/kind/up.sh` does the order above in one go: it creates the cluster and registry, builds and pushes the images (to get digests), creates the namespace, PostgreSQL, LocalStack and Secret, runs `helm upgrade --install`, and then checks the rollout, `/readyz` and `/docs`. It writes the kubeconfig to `~/.cache/agent-platform/kind/<cluster>/kubeconfig`, not to `~/.kube/config`. **kind**

```bash
CLUSTER_NAME=<cluster> REGISTRY_PORT=<port> deploy/kind/up.sh
export KUBECONFIG=~/.cache/agent-platform/kind/<cluster>/kubeconfig
```

`CLUSTER_NAME` (default `agent-platform-dev`) and `REGISTRY_PORT` (default 5001) can be left out. Change them when they collide with another cluster or registry. The command to remove it is `CLUSTER_NAME=… deploy/kind/up.sh down` (it removes only the cluster and the registry container).

With `EXTRA_VALUES=<file>`, one values file is laid last on top of the other values files (the model one included). Use it to run only one api and one egress-proxy on a laptop (`api.replicas: 1`, `egressProxy.replicas: 1`).

### Install from the published chart

No repository checkout is needed. Always give the exact version with `--version`. A release uses the tag without the `v` (`1.2.3` for `v1.2.3`), and a `main` merge is `<chart version>-main-<12>`, where `<12>` is the first 12 characters of the commit SHA. The order among `main` versions has no meaning (the prerelease comparison compares the SHA strings). So do not pick "latest" with `--devel`; find the merged commit in the [Images run](https://github.com/JeongJaeSoon/werft/actions/workflows/images.yml) and write it down. The package is pulled anonymously.

```bash
VERSION=0.1.0-main-<12>
helm show chart oci://ghcr.io/jeongjaesoon/werft --version "$VERSION"
helm show values oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" | sed -n '/^images:/,/^$/p'
```

The digests under `images` and `images.worker.runtime` are the values that run published. One package bundles the three images and the runtime, so you do not write them into values again. Prepare the namespace, Secret and per-installation values file from the next section, then install by changing only the chart path.

```bash
helm upgrade --install werft oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
  --namespace werft -f values-<installation>.yaml --timeout 10m
```

Do not write the digests of `images.worker`, `images.controlHost` and `images.egressProxy` into the per-installation values file. If you do, they keep overriding the next chart's values. The published digest is an index holding `linux/amd64` and `linux/arm64`, so each node pulls its own architecture. The kind install check runs on amd64 only.

### Direct install

Create the namespace and the Secret first. Build the Secret from a directory with one file per key (`0700`, the file name is the key), so the values never appear on the command line. **kind**

```bash
kubectl create namespace werft
kubectl -n werft create secret generic werft --from-file=<secret-dir>
```

Keep the per-installation values in one values file. At minimum it holds the digests of the three images and the checkpoint bucket. Connections, repositories, MCP servers and limits are not in values. Add them from the console after installing, or import them with `bun run settings:k8s import --document - < settings.json` ([api-server.md](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md#설정-문서-가져오기내보내기)). Defaults and descriptions are in `values.yaml`. The same command does both the first install and upgrades. **kind** (`-f deploy/kind/values.yaml -f <a file holding only the digests>`)

```bash
helm upgrade --install werft deploy/helm/agent-platform \
  --namespace werft -f values-<installation>.yaml --timeout 10m
kubectl -n werft get job werft-migrate
for d in api egress-proxy reconciler scheduler; do
  kubectl -n werft rollout status deploy/werft-$d --timeout=600s
done
```

If the release name does not contain `werft`, the resource names become `<release>-werft-…`.

A release installed when the chart was named `agent-platform` cannot be upgraded in place. The resource names changed, so the upgrade-check Job cannot find the existing scheduler and stops. Make sure the sessions have ended, remove it by the old name (`helm -n agent-platform uninstall agent-platform`; see [Uninstall](#uninstall) for what is left), and install again. For a release that used the file catalog, save the ConfigMap from ["Upgrading from the file catalog"](#upgrading-from-the-file-catalog) before you remove it.

If the first install fails (an image path or pull permission error is common), fix the values and run the same command again. Helm leaves the release as `failed` and treats this as an upgrade, so the upgrade-check Job runs for the first time. When the scheduler Deployment is absent and the DB is empty or has no sessions, the Job ends with `proceed` and the install goes on ([Pre-upgrade check](#pre-upgrade-check)). If it failed after the Deployments were created, the retry follows the ordinary upgrade rules. A retry that fixes the worker image stops here (`check_failed`, or `refused` if you supplied a runtime), so if you have not started a session, [uninstall](#uninstall) and install again.

## Adding AWS values

Copy `values-aws.example.yaml` to the per-installation file, fill in the placeholders (account id, ARN, host, digest), and lay it on top of `values.yaml`. The render below runs locally, but applying its result is **AWS only**.

**The ALB is internal-network only.** This install assumes an entrance reachable only from the internal network, so the example Ingress annotation `scheme` is already `internal`. Do not change it to `internet-facing` in the per-installation file either. `render-check` rejects `internet-facing` in the example render. After applying, check that the ALB was created in the internal-network subnets (**AWS only**).

### The web console and `/internal`

The api serves the web console on port 3000. With `ingress.console.enabled: true` (default `false`), the Ingress sends `/` (Prefix) to the api Service. The same port also has `/internal`, which is for workers, and the `/` Prefix matches `/internal` too. So the chart puts a `/internal` (Prefix) rule before `/`, and that rule does not go to the api but to the fixed-response (404, `text/plain`) of the annotation `alb.ingress.kubernetes.io/actions.block-internal`. The AWS Load Balancer Controller evaluates longer Prefixes before shorter ones, so the ALB answers 404 for `/internal` and everything under it. `render-check` verifies that this rule is ahead of `/`, that it points to the 404 action, and that the remaining paths go to the `http` (3000) port of the api Service.

This rule works only on an ALB. Another controller can skip a path whose Service `block-internal` does not exist and open `/internal` through `/`, so the chart refuses to render when `ingress.className` is not `alb`. It also refuses to render when `ingress.annotations` holds an annotation that could send a `/internal` request outside the 404 rule (`actions.*`, `conditions.*`, `transforms.*` and `group.*` under `alb.ingress.kubernetes.io/`, and `kubernetes.io/ingress.class`). If the `IngressClassParams` of the IngressClass puts this Ingress in the same group as other Ingresses, the earlier Ingress's rules are evaluated first, so when you turn the console on, check that the `alb` IngressClass does not force a group (**AWS only**).

**Condition for turning it on.** The api routes by the percent-decoded path. An ALB path pattern cannot contain `%`, so an encoded path such as `/%69nternal/…` does not hit the `/internal` rule, takes the `/` rule and reaches the api. The api sends a request to the worker routes only when the undecoded path starts with `/internal`, and answers an encoded variant with 404 `NOT_FOUND`. Turn on `ingress.console.enabled` only with an api image that has this behavior.

Dot segments (`/x/../internal/…`, `/%2e/internal/…`) and backslashes (`/internal\…`, `/x/..\internal/…`) are normalized to `/internal/…` by Bun before it hands the request to the api, so the api cannot tell these paths from a plain `/internal/…`. What stops them is the ALB. The ALB normalizes the URI before it evaluates rules, but the documentation does not say what it normalizes. So after you turn the console on, send the requests below from the internal network and check (**AWS only**). For `/%69nternal/x`, the api's 404 (`application/json`) is the expected value (it is also safe if the ALB normalizes even this and answers a `text/plain` 404). For every other path, the ALB's 404 (`text/plain`) is expected. The api's `/internal` routes answer `application/json` whatever the state. So if a dot-segment or backslash path gets an `application/json` response, the ALB sent that path to the api, and you turn the console off again (it is safe if the ALB rejects with its own error such as 400).

```bash
for p in /internal/x /%69nternal/x /x/../internal/x /%2e/internal/x '/internal\x' '/x/..\internal/x'; do
  curl -s --path-as-is -o /dev/null -w "$p %{http_code} %{content_type}\n" "https://<host>$p"
done
```

To turn it on, put the following in the per-installation file. Turning it off removes the `/` and `/internal` rules together, and `/v1`, `/docs`, `/healthz` and `/readyz` stay as they are.

```yaml
ingress:
  className: alb
  console:
    enabled: true
```

After applying, check from the internal network (**AWS only**). `curl -s -o /dev/null -w '%{http_code}\n' https://<host>/` gives 200. `curl -si -X POST https://<host>/internal/worker/x` gives 404, and the response header must be `content-type: text/plain` without the `x-request-id` the api adds. The api's 404 is `application/json` with an `x-request-id`, so the status code alone does not tell you whether the ALB blocked it.

```bash
helm lint deploy/helm/agent-platform -f deploy/helm/agent-platform/values-aws.example.yaml   # kind 머신에서 확인
helm template werft deploy/helm/agent-platform \
  -f deploy/helm/agent-platform/values-aws.example.yaml >/dev/null                          # kind 머신에서 확인
helm upgrade --install werft deploy/helm/agent-platform \
  --namespace werft -f values-aws-<installation>.yaml --timeout 10m               # AWS 전용
```

| Value | What it changes |
|---|---|
| `images.registry`, `images.*.digest` | The ECR host and that image's digest |
| `secrets.objectStoreKeys: false`, `serviceAccounts.api.annotations` | IRSA instead of static AWS keys. The api and checkpoint GC sign S3 and Secrets Manager requests with this role. The scheduler and workers have no S3 permission |
| `secrets.externalSecret` | The External Secrets Operator writes the Secret from the Secrets Manager `remoteKey` (JSON, all the Secret keys above; with IRSA, leave out the two AWS keys). Needs the operator's CRDs |
| `ingress` | The ALB Ingress. `scheme` is `internal` (above). `healthcheck-path: /readyz`, idle timeout 300 seconds for SSE. Routes only the public paths (`/v1`, `/docs`, `/healthz`, `/readyz`) and does not open `/internal` or the authorizer (3100) |
| `ingress.console.enabled` | Default `false`. Turning it on adds the web console `/` and the `/internal` 404 rule. The conditions are [below](#the-web-console-and-internal) |
| `config.egress.credentialAllowlist` | Adds the checkpoint bucket's virtual-hosted endpoint to the provider hosts. A worker's checkpoint upload and restore leave through the credential route |
| `worker.storageClass`, `worker.nodeSelector`, `worker.tolerations` | A dedicated worker node group and the StorageClass (gp3) of the workspace PVC |
| `networkPolicy.enabled` | Takes effect only when the VPC CNI network policy agent is on |

If you must use static S3 keys, keep `secrets.objectStoreKeys: true` and put the two AWS keys in the Secret. When both exist, the static keys win over IRSA.

## Health checks

The chart defines the probes. A person checking calls the same ones.

| Component | readiness | liveness | startup |
|---|---|---|---|
| api | `GET /readyz` (DB, schema, settings) | `GET /healthz` (HTTP only) | `GET /healthz`, up to 120 seconds |
| scheduler | `main.ts scheduler --health` | same | same. Waits up to `intervalSec + passTimeoutSec + 39` seconds |
| reconciler | `main.ts reconciler --health` | same | same |
| egress-proxy | `/app/src/healthcheck.ts` | same | none |

There is no `/livez`. Liveness is `/healthz`. **kind**

```bash
kubectl -n werft port-forward svc/werft-api 13000:3000 &
curl -fsS -w '\n' http://127.0.0.1:13000/readyz
curl -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:13000/docs
kubectl -n werft exec deploy/werft-scheduler -- bun run apps/control-host/src/main.ts scheduler --health
kubectl -n werft exec deploy/werft-reconciler -- bun run apps/control-host/src/main.ts reconciler --health
kubectl -n werft exec deploy/werft-egress-proxy -- bun run /app/src/healthcheck.ts
```

When you are done, stop only that job's port-forward (`kill %1`). On AWS, call `/readyz` on the Ingress host instead of port-forwarding (**AWS only**).

## API keys, run permissions and the settings document

On a compose install, `bun run keys`, `grants` and `settings` run inside the api container. On a Kubernetes install, the script of the same name with `:k8s` runs the same CLI inside the api Pod through `scripts/k8s-api.sh`. The Pod already has `DATABASE_URL`, so secret values never pass through the operator's shell. The current kubectl context or `KUBECONFIG` picks the cluster, and `NAMESPACE` and `RELEASE` (both default `werft`) pick the installation. **kind**

```bash
bun run keys:k8s create <owner_id> --scopes sessions:read,sessions:write,sessions:approve,sessions:control,sessions:recover
# stdout: 평문 key(한 번만 나온다), stderr: key_id
bun run keys:k8s revoke <key_id>
bun run grants:k8s revoke <session_id> --reason <text>
bun run grants:k8s restore <session_id> --reason <text>
bun run settings:k8s export > settings.json
bun run settings:k8s import --document - --dry-run < settings.json
```

Without the script it looks like this. `deploy/…-api` picks one api Pod. The three CLIs use only the DB, so any Pod is the same.

```bash
kubectl -n werft exec deploy/werft-api -c api -- \
  bun run apps/control-host/src/api/keys.ts create <owner_id> --scopes sessions:read
```

The `Session catalog loaded` log line records the limits and the repository count the api Pod read from the DB.

```bash
kubectl -n werft logs deploy/werft-api | grep 'Session catalog loaded'
```

## Upgrade and rollback

For a checkout install, an upgrade changes the digests in the values file to the new images; for a published-chart install, you [raise it to the new chart version](#upgrading-the-published-chart) and then run the same `helm upgrade --install` as the install. The migrate hook runs first, and if it fails the Deployments stay as they were. The scheduler is `Recreate`, so the new Pod starts after the old one is down. In between, no scheduler pass runs (new worker launches and reclaiming stop). **kind**

```bash
helm -n werft history werft
helm -n werft rollback werft <revision> --wait --timeout 10m
```

A rollback does not run the migrate hook (it is not `pre-rollback`). The DB stays on the new schema, and an old build becomes ready even on a schema ahead of it (the schema check of `/readyz` only looks at whether its own migration list equals the leading part of the applied list). So you do not deploy a migration that cannot be rolled back. When you roll back the worker image, first read [images-and-supply-chain.md § Rolling back workers and control-host, and incremental checkpoints](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/images-and-supply-chain.md#workercontrol-host-롤백과-incremental-checkpoint) for checkpoint compatibility.

### Rollout order

The worker Pod's image is fixed when the scheduler launches it. The image is not part of the isolation stamp, so even when an upgrade changes `images.worker`, the worker Pods already running are not replaced and run on the old image until they end. A worker with no input also stays for `WORKER_IDLE_TIMEOUT_SEC` (default 1800 seconds). The new image is used from the launches after that.

- A release that adds a protocol field the worker sends, or a field to the checkpoint manifest, first runs an upgrade that changes only `images.controlHost`, and changes `images.worker` in the next upgrade. With a single upgrade there is no guarantee that the new worker does not start before the old api. The per-field order is in [images-and-supply-chain.md § The order for removing a worker protocol field](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/images-and-supply-chain.md#worker-protocol-필드를-걷어내는-순서).
- A DB change follows expand → switch → clean-up in [images-and-supply-chain.md § The order for changing the DB schema](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/images-and-supply-chain.md#db-스키마를-바꾸는-순서). The migrate hook runs before the rollout, so the old api and old workers run on the new schema.
- CI does not yet check the combination of the new control-host with the previous release's worker image. Check it yourself on kind or a trial install before a release. Upgrade with values that set only `images.controlHost` to the new digest and `images.worker` to the previous release's digest, and see that one session finishes turn 1. Delete that session's worker Pod with `kubectl delete pod`, send one more input, and see that the new Pod continues from the checkpoint and finishes turn 2. The api log must have no 400 `BAD_REQUEST` for worker requests. `deploy/kind/up.sh` overrides `images.worker` with `--set`, so `EXTRA_VALUES` cannot change the worker image. Run `helm upgrade` directly.

### Upgrading the published chart

The published chart carries `images.worker.runtime` and leaves `images.workerPrevious` empty. The chart cannot know the previous image, and it differs per installation. An upgrade that changes the worker digest stops with `refused` unless the target's `images.workerPrevious` is the image deployed now, and an approval cannot get past that ([Pre-upgrade check](#pre-upgrade-check)). So you save the current image to a file and pass it along.

```bash
VERSION=<새 버전>
DEPLOYED="$(helm -n werft history werft -o json | jq '[.[] | select(.status == "deployed")] | last.revision')"
CURRENT="$(helm -n werft get values werft --all --revision "$DEPLOYED" -o json | jq -r '.images.worker.digest')"
TARGET="$(helm show values oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
  | awk '/^  worker:/ {found = 1} found && /digest:/ {print $2; exit}')"
echo "deployed ${CURRENT}"
echo "target   ${TARGET}"
PREVIOUS=worker-previous.json
if [ -n "$TARGET" ] && [ "$CURRENT" != "$TARGET" ]; then
  PREVIOUS=worker-previous.next.json
  helm -n werft get values werft --all --revision "$DEPLOYED" -o json \
    | jq '{images: {workerPrevious: .images.worker}}' > "$PREVIOUS"
fi
set -- -f values-<installation>.yaml
if [ -f "$PREVIOUS" ]; then set -- "$@" -f "$PREVIOUS"; fi
if helm upgrade --install werft oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
  --namespace werft "$@" --timeout 10m; then
  if [ "$PREVIOUS" != worker-previous.json ]; then mv "$PREVIOUS" worker-previous.json; fi
fi
```

Without `--revision`, when a failed upgrade exists you get that revision's values, that is, the image you were trying to raise. When the worker digest differs, the current image is written to a candidate file, and only after the upgrade succeeds is `worker-previous.json` replaced with that file. A failed upgrade does not touch the kept file. When the digest is the same, the existing file is passed as it is. For an upgrade after the first install in which the worker did not change, there is no file to pass yet, and that is fine.

- Keep `worker-previous.json` beside the installation and pass it in the next upgrade too. If you leave this file out of an upgrade where the worker digest is the same, the deployed previous image drops out. The pre-upgrade check then compares sessions, and stops with `refused` (approvable) if a session's combination does not match either target image (the current image and, when present, the previous image) or has no recorded combination. If you left it out by mistake, do not approve; put the file in and run again. With no picked sessions and an empty `upgrade.approvedSessions`, it passes (if the approval of an earlier upgrade remains, it is `refused`). For sessions the check cannot see, read "What the check does not see" below. A `main` chart merged on the same day can have the same worker digest.
- Do not use `--reuse-values`. It uses the old chart's values as defaults, so with a new chart version the images stay as they were.
- Do not pass all of `helm get values --all` as a values file. The old digests override the new chart's values. Take only `.images.worker`.
- A chart published from a `v*` tag follows the same procedure.

### Upgrading from the file catalog

The old chart's `catalog` ConfigMap is not in this chart. Helm removes old resources after the hooks end, so the pre-upgrade migrate Job optionally mounts the same ConfigMap at `/legacy-config` and imports it with `settings import --from-dir /legacy-config --if-present`. From the next upgrade there is no ConfigMap, so it does nothing. If only some files exist or a value is broken, the Job fails and the Deployments do not change.

1. Put `PLATFORM_SECRET_KEY` in the Secret first. If it is already there, leave the same value.
2. Remove the `catalog` section from values and run `helm upgrade`. If you put `PLATFORM_CONFIG_DIR` in `api.extraEnv`, remove it.
3. When it ends, look at the added entries with `bun run settings:k8s export`. If `installation_profiles` already has rows, the limits from the file are not put in again. The procedure and the floor for reverting are in [api-server.md](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md#설정-문서-가져오기내보내기).

A release whose chart was named `agent-platform` is removed and installed anew, so the ConfigMap disappears with it, and the new chart looks for a different name. Before you remove the old release, save the ConfigMap under the new name, and create it before `helm install`. The migrate Job also runs on install and imports that ConfigMap. The ConfigMap holds only references and no secret values.

```bash
kubectl -n agent-platform get configmap agent-platform-catalog -o json \
  | jq '{apiVersion, kind, data, metadata: {name: "werft-catalog", namespace: "werft"}}' > catalog-configmap.json
# 옛 release를 지우고 namespace를 만든 뒤
kubectl apply -f catalog-configmap.json
```

### How sessions continue, by what changes

| What changes | Running worker Pods | How the session continues |
|---|---|---|
| The worker image (`images.worker`) | Runs on the old image until it ends | The next launch picks the image whose engine, SDK, CLI and profile digest method match the checkpoint pointer, in the order new image (`images.worker`) then previous image (`images.workerPrevious`), and restores with it. If neither matches, it stops at `recovery_required` before launch. The pre-check below shows such sessions before the upgrade |
| Isolation settings (values in the stamp: egress proxy address, storage size, worker ServiceAccount, limits, and so on) | They become stale. A claimed Pod drains to a turn boundary and then goes down | If the checkpoint covers up to the last finished turn, a new Pod continues from the PostgreSQL pointer and the S3 checkpoint. If a turn ended without a checkpoint, the session stops at `recovery_required` (`CONTEXT_GAP`). A turn past the drain deadline (`MAX_TURN_SECONDS` + 5 minutes) becomes `outcome_unknown`, and that session stops at `recovery_required` and waits for an operator decision ([execution.md § Draining a claimed worker when the contract is raised](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/execution.md#계약이-오를-때-claim된-worker의-drain)) |
| Node replacement, Kubernetes upgrade | The Pod disappears. On SIGTERM it releases by draining; if it does not get one, the heartbeat stops | If released, it is reclaimed at once; otherwise after the scheduler confirms the Pod is gone or the lease ends. If no turn was running and the checkpoint covers up to the last finished turn, the next launch continues from that checkpoint. If the checkpoint is behind, the session stops at `recovery_required` (session detail attention `CONTEXT_GAP`). If there was an unconfirmed turn, that turn becomes `outcome_unknown` and the session stops at `recovery_required` ([execution.md](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/execution.md)) |
| The checkpoint bucket (`config.checkpoints.bucket`) | The bucket is in the stamp, so they are replaced as stale | It does not continue automatically. The old bucket's objects are not in the new bucket. If there are unreclaimed checkpoint rows and the new bucket has no object version at all, the api does not start ([api-server.md](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md)). A Kubernetes install has no procedure for moving checkpoints to another bucket. Restore also points to a version in the same bucket ([backup-restore.md § Kubernetes install](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/backup-restore.md#kubernetes-설치)). While unreclaimed checkpoints exist, do not change the bucket |

### Pre-upgrade check

`helm upgrade` runs the `upgrade-check` Job with the target release's api image before migrate (hook weight -5). For every session with an unreclaimed checkpoint, the Job reads the pointer's combination and picks the sessions that can be resumed with neither the target release's `images.worker` nor its `images.workerPrevious`. It also picks pointers committed before the combination was recorded. The result is one JSON line in the Job log.

```bash
kubectl -n werft logs job/werft-upgrade-check
```

| `verdict` | exit | upgrade | Meaning |
|---|---|---|---|
| `proceed` | 0 | continues | `upgrade.approvedSessions` is exactly equal to the `sessionId`s in `affected`. When no session is picked, or the worker image is unchanged and the deployed previous image is absent or unchanged, or it was never deployed, the approval list must be empty |
| `refused` | 2 | stops | Any difference in the approval list (including when the approval of an earlier upgrade stays in values). Even when the worker image is unchanged, if the deployed previous image drops out of the target or changes, sessions are compared, and sessions whose combination matches neither target image (the current image and, when present, the previous image) or has no recorded combination go on the list. Or the worker image changes and the target's `images.workerPrevious` is not the worker image deployed now. An approval cannot get past this case |
| `check_failed` | 1 | stops | The DB could not be read, or the image combination could not be read or is needed per the table below but absent, or the deployed worker image is unknown. It is also this when a deployed worker image exists but `UPGRADE_DEPLOYED_WORKER_IMAGE_PREVIOUS` is missing (give an empty value when there is no previous image). It is also this when the scheduler Deployment is absent but the DB has sessions or part of a schema. No setting gets past it |

`images.worker.runtime` may be absent on the first install. Whether an upgrade needs it depends on the deployed state and the target values.

| Deployed state | Target | With no runtime |
|---|---|---|
| No scheduler Deployment, DB empty or no sessions (first-install retry) | Any worker image, no `images.workerPrevious` | `proceed` |
| One worker image, no runtime or previous image | The same worker image, no `images.workerPrevious` | `proceed` |
| One worker image, no runtime or previous image | A different worker image | `check_failed`. Put `images.worker.runtime` and an `images.workerPrevious` holding the current image in the target |
| A runtime or previous image exists | Values without `images.worker.runtime` | `check_failed`. Without the combination, sessions cannot be checked |

How to get the runtime value is in the API settings of the [Configuration reference](https://jeongjaesoon.github.io/werft/en/run-server/self-hosting/operate/configuration/#api-settings). A minimal-values install starts with no runtime, and the first upgrade that changes the worker image puts in both images' runtimes together.

An upgrade that leaves `images.worker` alone and drops or changes the deployed `images.workerPrevious` compares sessions. If a session's combination matches neither target image (the current image and, when present, the previous image) or has no recorded combination, it is `refused`, and approving that list lets it through. A session with no recorded combination is picked in every case, the same as in an upgrade that changes the image. When the deployed previous image did not exist or is unchanged, sessions are not compared and an empty approval list gives `proceed` (a remaining approval is `refused`). A rebuild that differs only in the image with the same combination is not on the list even when you drop the previous image, because the sessions resume on the current image.

If the picked sessions may fail to resume, put that list into values as it is and run the same upgrade again. An approval does not change session state. A session picked as `no_image` stops at `recovery_required` when it resumes. A session picked as `unrecorded` starts on the new image, and the restore decides whether it continues or stops at `recovery_required`.

```bash
helm upgrade --install ... --set-json 'upgrade.approvedSessions=["<sessionId>", ...]'
```

The approval list stays in the release values. At every next upgrade, empty it with `--set-json 'upgrade.approvedSessions=[]'` and read and approve that upgrade's list again. A remaining list stops with `refused` if it differs from that upgrade's `affected`, but if it is the same and the support window condition also holds, it passes as it is.

The Job receives the approval list as `UPGRADE_APPROVED_SESSIONS` (a JSON array), the deployed worker image as `UPGRADE_DEPLOYED_WORKER_IMAGE`, and the deployed previous image as `UPGRADE_DEPLOYED_WORKER_IMAGE_PREVIOUS` (empty when absent). The chart reads the deployed images with `lookup` from the `WORKER_IMAGE` and `WORKER_IMAGE_PREVIOUS` of the scheduler Deployment as it is now, and passes them. The `lookup` branch that reads the previous image, and the real `helm upgrade` that drops or changes the previous image, were not run on a cluster. Only the check entry point was run against a real PostgreSQL. The only thing that can open an exception in the table above is the `UPGRADE_DEPLOYED_STATE` the chart passes along. `absent` means the scheduler Deployment is absent and the `default` ServiceAccount of the namespace could be read (so this path needs `get` permission on that ServiceAccount). `unpinned` means the Deployment runs with no runtime or previous image. In `helm template` and the client `--dry-run`, `lookup` reads nothing and all three values are empty, so a Job run from that render is `check_failed`. `--dry-run=server` reads the cluster but does not run hooks, so it does not stand in for the verdict. The check trusts that `DATABASE_URL` is this installation's DB. If it points to another empty DB, the `absent` path passes. The Job is not created on the first install (`pre-install`) or with `scheduler.enabled: false`. So that the Job and the scheduler see the same image, `WORKER_IMAGE`, `WORKER_IMAGE_PREVIOUS`, `WORKER_IMAGE_RUNTIME` and `WORKER_IMAGE_PREVIOUS_RUNTIME` cannot be given through `*.extraEnv`, `config.limits` or `secrets.catalogEnv`. If you do, rendering fails. Give them with `images.worker` and `images.workerPrevious`.

**Before `helm rollback`.** A rollback runs no hooks, so you run the same command by hand in the api Pod. Put in the values of the revision you are going back to (`helm get values --revision <revision>`).

```bash
kubectl -n werft exec deploy/werft-api -- env \
  UPGRADE_DEPLOYED_WORKER_IMAGE='<지금 scheduler의 WORKER_IMAGE>' \
  UPGRADE_DEPLOYED_WORKER_IMAGE_PREVIOUS='<지금 scheduler의 WORKER_IMAGE_PREVIOUS, 없으면 빈 값>' \
  WORKER_IMAGE='<되돌릴 revision의 worker 이미지>' WORKER_IMAGE_RUNTIME='<그 runtime JSON>' \
  WORKER_IMAGE_PREVIOUS='<그 revision의 workerPrevious>' WORKER_IMAGE_PREVIOUS_RUNTIME='<그 runtime JSON>' \
  bun run apps/control-host/src/api/upgrade-check.ts
```

An ordinary rollback that reverts the worker image is `refused`, because the `images.workerPrevious` of the revision you go back to is not the image deployed now (the check compares image references, not combinations). If the config or the DB cannot be read, it is `check_failed`. A worker running on the current image keeps writing checkpoints with that image's combination after the rollback until it ends, and the check cannot see those checkpoints. `affected` in the output is the sessions already picked at the time of the check. Rolling forward comes first. If you roll back anyway, the scheduler picks the image by combination when it resumes. A session whose combination matches neither the rolled-back revision's worker image nor its previous image (if any) stops at `recovery_required` (if the current image carries a new SDK or CLI, this is a session that wrote checkpoints with the current image during the rollback). A rollback that leaves `images.worker` alone is `proceed` with an empty approval list when the deployed previous image is still in the revision you go back to (a remaining approval is `refused`), and if it drops out or changes, sessions are compared as in the upgrade above. This command is not a hook, so it does not stop a rollback for you. When you get `refused`, read `affected` and decide whether to go back. If a deployed worker image exists and you omit `UPGRADE_DEPLOYED_WORKER_IMAGE_PREVIOUS`, it is `check_failed`.

**What the check does not see.** Unlike the single-server upgrade check, this check does not run the target image. It compares only the combination recorded in the pointer (engine, SDK, CLI and profile digest method), and the actual profile digest is decided at restore. It also does not stop the writers and check again after the check. An upgrade that changes the worker image passes only when the target's `images.workerPrevious` equals the image deployed now, so checkpoints that a worker on the current image writes after the check are inside the target's support window. An upgrade that leaves the worker image alone and drops the previous image has no such guarantee. A worker running on the previous image can still write checkpoints with that combination after the check. The same holds for a session before its first checkpoint. So before you drop the previous image, first see that those workers have ended. For a session of a worker running on an image older than that, if the pointer is already that combination, it goes on the list. A session before its first checkpoint is not on the list. This limit applies equally to every image that falls out of the support window, and to an upgrade that changes the previous image. It also does not check whether the target image can be pulled from the registry. If it cannot be pulled, it appears as a launch failure.

## Mapping to the 10 single-server steps

This is where the steps of [server-deployment.md](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/server-deployment.md) go on Kubernetes.

|---|---|

## Uninstall

```bash
helm -n werft uninstall werft
```

**kind**. What `helm uninstall` leaves behind:

- The worker Pods, nonce Secrets and workspace PVCs the scheduler created. Before deleting, check that the sessions have ended (or been checkpointed). Deleting a PVC loses work that was not checkpointed. The list: `kubectl -n werft get pods,secrets,pvc -l app.kubernetes.io/part-of=agent-platform,agent-platform.installation=<installationId>`
- The migrate Job and upgrade-check Job made by hooks, and the ExternalSecret and the Secret it wrote (`creationPolicy: Orphan`). A Secret you made by hand stays too. A leftover Job does not block the next install: Helm deletes it first when a hook of the same name runs. To delete it now, run `kubectl -n werft delete job werft-migrate werft-upgrade-check --ignore-not-found`.
