title: "Kubernetes実行backend"
description: schedulerがworkerをKubernetes Podとして起動するときの動作と設定
---

schedulerがworkerをDockerコンテナではなくKubernetes Podとして起動するときの動作と設定です。Helm chartでインストールする手順は[Kubernetesインストール(Helm chart)](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/kubernetes-deployment.md)に、Docker backendの動作は[実行基盤とworkerの隔離](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/execution.md)にあります。

`packages/adapters/execution/kubernetes`は、launch 1回につきworker Podを1つ作ります。Podごとに、そのPodが所有するnonce Secretが1つ付き、セッションのworkspace PVCがマウントされます。

schedulerは`EXECUTION_BACKEND`でbackendを選びます。値は`local_docker`(既定。空でも同じ)と`kubernetes`の2つで、それ以外の値は、その値を書いたエラーで起動を拒否します。`kubernetes`のときは、Dockerの設定(`DOCKER_HOST`、`EXECUTION_DOCKER_*`、`EXECUTION_WORKSPACE_QUOTA`)を読まず、Docker socketも使いません。Docker専用のpreflightであるegress proxyの隔離確認とworkspace quota probeも動きません。Kubernetesではworkerの隔離はchartのNetworkPolicyが担い、workspaceの上限はPVCのサイズです。停止とリクエストのtimeoutは固定値(120秒 + 30秒)なので、`SCHEDULER_PASS_TIMEOUT_SEC`は150より大きくする必要があります。`migrate-workspace`はDocker volumeを移すツールなので、`local_docker`でだけ動きます。

readOnlyRootFilesystemのPodでは、status fileを書き込み可能なパスに置きます。既定のパス`/tmp/scheduler-status.json`・`/tmp/reconciler-status.json`は、`/tmp`にemptyDirをマウントすればそのまま使えます。別のパスにするなら、`SCHEDULER_STATUS_FILE`・`RECONCILER_STATUS_FILE`で変えます。ループはstatus fileと同じディレクトリに一時ファイル(`<status file>.<pid>.tmp`)を書いてからrenameします。schedulerはその隣に`.quota-verified`の記録も置きます。そのため、ファイル1つではなくディレクトリ全体が書き込み可能である必要があります。

共有env(`WORKER_IMAGE`、`WORKER_GATEWAY_URL`、`EXECUTION_EGRESS_PROXY_URL`、`EXECUTION_EGRESS_CREDENTIAL_PORT`、`EXECUTION_INSTALLATION_ID`、`EXECUTION_WORKSPACE_QUOTA_MB`、`EXECUTION_WORKSPACE_GC_MIN_AGE_SEC`、`S3_BUCKET`、`AWS_REGION`)はDocker backendと同じです。kubernetesモードでは、次の2つの値に制約が加わります。

- `WORKER_IMAGE`は`repository@sha256:<digest>`の形式でなければなりません。
- `EXECUTION_INSTALLATION_ID`は、32文字以下の小文字のDNS labelでなければなりません。

kubernetesモードでだけ読む設定は次のとおりです。

| 変数 | 意味 |
| --- | --- |
| `EXECUTION_K8S_NAMESPACE` | worker Pod・Secret・PVCを置くnamespace。既定はschedulerと同じnamespaceです。クラスターの外で動かすときは必ず指定します。 |
| `EXECUTION_K8S_WORKER_SERVICE_ACCOUNT` | worker PodのServiceAccount。tokenはマウントしません。 |
| `EXECUTION_K8S_STORAGE_CLASS` | workspace PVCのStorageClass。空ならクラスターの既定を使います。 |
| `EXECUTION_K8S_IMAGE_PULL_SECRETS` | 任意。カンマ区切りのSecret名。 |
| `EXECUTION_K8S_WORKER_NODE_SELECTOR` | 任意。JSON object。 |
| `EXECUTION_K8S_WORKER_TOLERATIONS` | 任意。JSON array。 |
| `EXECUTION_K8S_WORKER_EPHEMERAL_STORAGE_MB` | workerコンテナのephemeral-storageのrequestsとlimits(MB)。既定1024。超えるとkubeletがPodをevictします。 |

失敗したworkerの終了理由とログ末尾(最後の8 KiB)は、schedulerログの`Execution resource failed; log tail kept`の行に残ります。保存場所と保存期間は、リポジトリの`packages/adapters/execution/kubernetes/README.md`(終了理由とログ末尾の節)にあります。

## chartが入れる値

Helm chart(`deploy/helm/agent-platform`。手順は[Kubernetesインストール(Helm chart)](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/kubernetes-deployment.md))でインストールすると、上のenvを自分で書く必要はありません。chartがvaluesから作ります。

| env | values | 備考 |
| --- | --- | --- |
| `EXECUTION_BACKEND` | なし | 常に`kubernetes` |
| `EXECUTION_K8S_WORKER_SERVICE_ACCOUNT` | なし | chartが作る`<fullname>-worker`。tokenはマウントしません |
| `EXECUTION_K8S_NAMESPACE` | なし | 入れません。schedulerと同じnamespace(release namespace)になります |
| `EXECUTION_K8S_STORAGE_CLASS` | `worker.storageClass` | 空なら入れません |
| `EXECUTION_K8S_IMAGE_PULL_SECRETS` | `images.pullSecrets` | 制御プレーンのPodにも同じSecretを使います |
| `EXECUTION_K8S_WORKER_NODE_SELECTOR`、`EXECUTION_K8S_WORKER_TOLERATIONS` | `worker.nodeSelector`、`worker.tolerations` | JSONに変換して入れます |
| `WORKER_IMAGE` | `images.registry`、`images.worker.*` | `<registry>/<repository>@<digest>`。digestがないとrenderが失敗します |
| `WORKER_GATEWAY_URL`、`EXECUTION_EGRESS_PROXY_URL`、`EXECUTION_EGRESS_CREDENTIAL_PORT` | なし | api Serviceの3000、egress-proxy Serviceの3128、3129 |
| `EXECUTION_INSTALLATION_ID` | `installationId` | worker NetworkPolicyのlabel値でもあります |
| `EXECUTION_WORKSPACE_QUOTA_MB`、`EXECUTION_WORKSPACE_GC_MIN_AGE_SEC` | `worker.workspace.*` | quotaはworkspace PVCのサイズです |
| `WORKER_CPUS`、`WORKER_MEMORY_MB` | `worker.cpus`、`worker.memoryMb` | |
| `EXECUTION_K8S_WORKER_EPHEMERAL_STORAGE_MB` | `worker.ephemeralStorageMb` | 既定1024 |
| インストール上限(`EXECUTION_SLOT_LIMIT`など) | `config.limits` | apiとschedulerに同じ値 |
| `SCHEDULER_*` | `scheduler.intervalSec`など | `SCHEDULER_PASS_TIMEOUT_SEC`(`scheduler.passTimeoutSec`、既定180)は150より大きくします |
| `SLACK_ROLE_INTERVAL_SEC`、`SLACK_ROLE_PASS_TIMEOUT_SEC`、`SLACK_ROLE_MAX_CONSECUTIVE_FAILURES`、`SLACK_ROLE_HEALTH_STALE_SEC`、`SLACK_ROLE_BATCH_SIZE`、`SLACK_ROLE_LEASE_SEC` | `slack.intervalSec`、`slack.passTimeoutSec`、`slack.maxConsecutiveFailures`、`slack.healthStaleSec`、`slack.batchSize`、`slack.leaseSec` | 既定は2、60、3、90、10、60。`slack.enabled: false`ならslack Deploymentを描きません |
| `PLATFORM_ALLOW_UNATTENDED_PERMISSIONS`(slack) | `api.extraEnv` | slackはapiと同じカタログを読むので、apiの値に従います。`slack.extraEnv`に書くとその値が優先されます |

どのDeploymentにも`extraEnv`でenvを追加できます。Secretから来る値(`DATABASE_URL`、`EGRESS_AUTHORIZER_TOKEN`、AWSキー、カタログのcredential)は、[Kubernetesインストール(Helm chart)の準備の節](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/kubernetes-deployment.md#준비)の表にあります。

## probe

| 構成要素 | readiness | liveness | startup |
| --- | --- | --- | --- |
| api | `GET /readyz` | `GET /healthz` | `GET /healthz`(5秒 × 24) |
| scheduler | `bun run apps/control-host/src/main.ts scheduler --health` | 同じ | 同じ。失敗の許容回数は`(intervalSec + passTimeoutSec + 39) / 10` |
| reconciler | `bun run apps/control-host/src/main.ts reconciler --health` | 同じ | schedulerと同じ式 |
| slack | `bun run apps/control-host/src/main.ts slack --health` | 同じ | schedulerと同じ式 |
| egress-proxy | `bun run /app/src/healthcheck.ts` | 同じ | なし |

`/healthz`はHTTPを受け付けるかだけを見て、DBは見ません。そのためlivenessに使い、DB・schema・設定を見る`/readyz`はreadinessにだけ使います。DBが一時的に切れても、api Podは再起動されず、トラフィックから外れるだけです。`/livez`はありません。scheduler・reconciler・slackの`--health`は、ループが書くstatus fileを読み、直前のpassが失敗した場合、期限を超えた場合、または`SCHEDULER_HEALTH_STALE_SEC`・`RECONCILER_HEALTH_STALE_SEC`・`SLACK_ROLE_HEALTH_STALE_SEC`以内に終わったpassがない場合に失敗します。startup probeは最初のpassが終わるまで待ちます。

## schedulerはreplica 1、`Recreate`

scheduler passはPostgreSQLのadvisory lock(`pg_try_advisory_lock`)1つで直列化されます。2つ目のschedulerはlockを取れずにpassをスキップし、成功したpassがないので`--health`がstaleになり、livenessがそのPodを再起動し続けます。増やしても処理量は増えません。そのためchartは`replicas: 1`を固定し(valuesにキーはありません)、rolloutも`RollingUpdate`ではなく`Recreate`で、古いPodを先に落とします。アップグレード中は短時間passが止まります。reconcilerはpassを行lockの下で判断し直すので、leader electionなしで`reconciler.replicas`を増やせます。既定は1です。

## worker NetworkPolicy

chartのNetworkPolicyが、Docker backendのexecutionごとのinternalネットワークの代わりになります。worker Pod(`app.kubernetes.io/part-of=agent-platform`、`app.kubernetes.io/component=worker`、`agent-platform.installation=<installationId>`)はどの接続も受けず、外へはegress-proxyの3128・3129にだけ接続します。DB、api、ほかのworker、nodeやクラウドのmetadataアドレスには直接届きません。apiへ向かうgatewayリクエストもproxyを通ります。egress-proxyはworkerからの接続だけを受け、apiのauthorizer(3100)はegress-proxyからだけ受けます。クラスターのCNIがNetworkPolicyを強制しない場合、この隔離はありません(kindのkindnetは強制します。EKSではVPC CNIのnetwork policy agentを有効にします)。

## API serverの認証

API serverの認証は、`KUBECONFIG`があればそれを使い、なければPodのServiceAccountを使います。ServiceAccountの経路は、`KUBERNETES_SERVICE_HOST`・`KUBERNETES_SERVICE_PORT`とtoken・CAファイルを読みます。schedulerのRole動詞とpidsLimitの扱いは、リポジトリの`packages/adapters/execution/kubernetes/README.md`にあります。
