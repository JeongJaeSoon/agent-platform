This page covers the three app images and the compose `apps` profile, upgrading and rolling back the worker image, and the supply chain vulnerability policy. The workflow that builds and publishes the images is in [ci.md](https://github.com/JeongJaeSoon/werft/blob/main/docs/contributing/ci.md).

## Images and the Compose `apps` profile

The app images are defined by three files, `apps/{control-host,worker,egress-proxy}/Dockerfile`. All three use the repository root as context and pin one multi-arch index digest of `oven/bun:1.3.14` as the base (`tests/images.test.ts` checks that the digests match). One control-host image runs all three roles: api, scheduler and reconciler. In compose only `api` builds it, and scheduler and reconciler use the same `API_IMAGE`. This is because exports race when two services build the same tag together. control-host and worker install only the workspace closure with `bun install --frozen-lockfile --production` and then copy it into the runtime stage. egress-proxy is a single stage that holds only its own source, without `bun install`.

The published target is `release`. It is the last stage of the Dockerfile, so it is the default target. images.yml builds with `target: release`. The published images do not contain test sources (`*.test.ts(x)`, `*.stories.*`, `src/testing`, `src/test-support`, `__fixtures__`, `bench`), `apps/storybook`, `packages/testkit`, or the demo account CLI (`demo-accounts.ts`, `demo-data.ts`). `scripts/image-prune.sh --delete` removes them after the install (`bun install --frozen-lockfile`) is done, so the workspace manifests stay fixed. `image-smoke.sh` opens the image and counts the same list and a list of names, and fails if any one of them is present. control-host has a separate `local` target. It is `release` with testkit and the demo CLI added back, and it is not published. `scripts/local.sh` (compose) and `deploy/kind/up.sh` build this target. Calling the demo CLI with `DEMO_ACCOUNTS=local` on a published image fails with `Module not found`, because the files are not there.

The digest pin fixes the Debian packages of the base along with the Bun version. oven/bun does not rebuild tags it has released, so as of 2026-09-25 the last build of `oven/bun:1.3.14` is from 2026-05-13. So the deployment stage of the three images raises Debian security fixes with `apt-get upgrade`. This is the only way to get the fixes without raising Bun. The cost is reproducibility. Even for the same commit, Debian package versions can differ depending on the day of the build. What is deployed is fixed by image digest in the release manifest, and on every build the license check and the Grype scan in images.yml look at that image. The layer cache is split by the `APT_UPGRADE_KEY` build arg. images.yml passes the UTC date, and a local compose build passes an empty value, so it keeps using the upgrade layer it made once. To get new fixes locally, build with `--build-arg APT_UPGRADE_KEY=$(date -u +%F)` or `--no-cache`.

| Image | Contents | What runs it |
|---|---|---|
| `werft-control-host` | One `apps/control-host` executable runs all of the api, scheduler and reconciler roles. `--filter` installs only that app's closure, and it does not contain the Agent SDK or the Claude Code executable (the build checks that `node_modules/@anthropic-ai` is absent). Default uid 1000. Only the scheduler role becomes root with compose `user: "0:0"` and holds the Docker socket | `bun run apps/control-host/src/main.ts <role>` (the CMD default is `api`) |
| `werft-worker` | `--filter ./apps/worker` installs only the closure of the worker and the workspaces it depends on (no pg, drizzle or web console packages). SDK 0.3.270 with bundled Claude Code 2.1.270, git, non-root (uid 1000), and `/workspace` created in advance and owned by 1000 (the volume contract of LocalDockerBackend). At build time `resolvePinnedClaudeExecutable()` fixes the executable path, links it as `/usr/local/bin/claude` and runs `claude --version` | `bun run apps/worker/src/main.ts`: claims one session with the bootstrap identity the scheduler passed in env and runs the WorkerHost loop |
| (scheduler role) | The only service that mounts the Docker socket, and it runs as root (the socket owner is the same as root on the daemon host anyway, and the socket gid differs per daemon, so a fixed uid would only cost portability) | In compose, the supervision loop (`main.ts scheduler`) asks a child process (`--serve`) for one pass every `SCHEDULER_INTERVAL_SEC` (default 5 seconds). A pass that fails or is killed ends together with the child, and the next pass runs in a new child ([Execution](/run-server/self-hosting/operate/execution)). When failed passes continue `SCHEDULER_MAX_CONSECUTIVE_FAILURES` (3) times (degraded exit 76 is not counted), the loop exits 1 and `restart: unless-stopped` restarts it (visible in `compose ps`). When no pass completes (success or degraded) for `SCHEDULER_HEALTH_STALE_SEC` (200 seconds), the healthcheck (`main.ts scheduler --health`) becomes unhealthy. When the DB stops, the pass ends by itself with exit 1: the scheduler and reconciler pools use the same timeouts as the API (connect 5 seconds, statement 10 seconds, read 20 seconds; `JOB_POOL_TIMEOUTS` in `packages/db/src/pool.ts`), and store calls after the connection has been lost once fail at once without waiting, so the DB wait is capped at about 45 seconds, the failed statement (5+20 seconds) plus the release of the pass lock (20 seconds) (measured: stop before a pass 5 seconds, stop during a pass about 40 seconds). `SCHEDULER_PASS_TIMEOUT_SEC` (180 seconds) is an outer watchdog set larger than these 45 seconds plus one worker stop (stop timeout 120 seconds + request timeout 30 seconds). It kills any other hang and counts it as a failure (unhealthy alone does not make Docker restart it). If you raise the pool timeouts, raise this value too, above `connect + 2 × read` |
| `werft-egress-proxy` | Only the source of `apps/egress-proxy` (no dependencies, one stage). The code is owned by root and the process runs as uid 1000, so the proxy cannot change the code of its next start | `bun run src/main.ts`: compose `egress-proxy`, the only outside path, attached to every worker network |

```bash
docker compose -f infra/compose.yml --profile worker build          # WORKER_IMAGE(werft-worker:dev)
docker compose -f infra/compose.yml --profile worker run --rm worker claude --version
docker compose -f infra/compose.yml --profile apps up -d --build      # migrate → api(/readyz) → worker image smoke → scheduler loop, reconciler loop
curl -s http://127.0.0.1:3000/readyz
```

The compose entry file is `infra/compose.yml`, and the layer for restore is `infra/compose.restore.yml`.
Every value of the `apps` profile has a default, so it starts without an environment file. The model key is not required either. The default way is to enter it after start, in the console under **Settings > Workspace settings > Model connections > Add connection**. The settings document that `scripts/local.sh up` imports (`tests/fixtures/settings/real-model.json`) can also read `ANTHROPIC_API_KEY` of the API process through `value_env`, and uses it when it is in the shell or `.env`, as the alternative. Without it, `up` does not switch to the fake: it starts with no model connection, and sessions on that profile are refused with the screen path until a connection is entered. `docker compose` without the overlay does not import a settings document. To start without a model account, use the fake settings document with `scripts/local.sh up --fake-model`. In that case the key is not passed to the API container. If `PLATFORM_SECRET_KEY` is not in the shell or `.env`, `up` creates it and keeps it per project. `DATABASE_URL` alone is the exception and always points at the compose postgres: `up` runs migrate, so another DSN in the shell or an environment file must not be migrated just by starting the local stack. The default of `AUTH_MODE` is `api-key`: workers reach `api:3000` through the proxy, so with `none` code inside a worker could pose as any owner with `X-Owner-Id` (the `/internal` worker routes have their own authentication). Keys are issued with `bun run keys create <owner> --scopes …` (runs the key CLI inside the compose `api` container). The id of the issued key appears on stderr as `key_id <uuid>` (stdout is the one line of the plaintext key as is). Revocation is `bun run keys revoke <key_id>`. A revoked key gets 401 from the next request on, and open SSE streams are cut within the keepalive interval. Work in progress for the same owner is not canceled. Withdrawing a session's execution permission is a separate operations command, `bun run grants revoke <session_id> --reason <text>` ([세션 실행 권한 회수와 복구](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md#세션-실행-권한-회수와-복구)). In one transaction this command raises auth_revision and epoch, revokes the worker token, leaves a kill intent and blocks dispatch. The owner's resume and start_fresh are also refused (403). The block is lifted only with `bun run grants restore <session_id> --reason <text>`, and it can be lifted only after the previous execution is confirmed gone. The API port binds only to `127.0.0.1:3000`. `EXECUTION_WORKSPACE_QUOTA` defaults to `off` in compose: Docker Desktop cannot handle project quota, so the local stack accepts unlimited workspaces and each scheduler pass leaves one warning; on an xfs+prjquota daemon, set it back to `on`. The other values start without `.env`. If `.env` exists it is read (`required: false`), but it is never created or overwritten. `secrets` (Secrets Manager for the API only, host `127.0.0.1:4567`) and `fake-messages` start only when `infra/compose.fake-model.yml` is layered on. This is because the fake document is the only settings document that reads `secret_id`. Worker containers are not compose services; the scheduler starts one per session. The `worker` entry in compose is a one-shot that builds that image, checks it once with `claude --version` and ends (`network_mode: none`). The scheduler waits for it to succeed, so `up` of the `apps` profile builds the worker image too. Workers reach only `api:3000` through the forward proxy (the `EGRESS_PRIVATE_ALLOWLIST` default), and reach `fake-git:3000`, `fake-messages:4010` and `localstack:4566` only through credential routes (they do not reach `secrets`). The internal network blocks direct connections and metadata addresses.

When you put two installations on the same daemon, give each installation a different `EXECUTION_INSTALLATION_ID`. The compose `egress-proxy` label follows this value, so each installation gets its own proxy. If a compose project of another worktree holds the default ports, separate them with `-p <name>` and an override file with `ports: !override`.

`.github/workflows/images.yml` builds the three images for `linux/amd64` and `linux/arm64` on every PR and main push, each architecture on a runner of that architecture. It checks that `claude --version` is 2.1.270 in the worker and that `@anthropic-ai` is absent from api and scheduler, and then leaves the digest JSON as an `image-digest-<app>-<arch>` artifact. Publishing happens only on `main` push and `v*` tag push. For `main` push, see [Images published on every main merge](#images-published-on-every-main-merge) below. On the **push event** of a `v*` tag (the event is checked too, because `workflow_dispatch` can name any ref), the `publish`, `index` and `promote` jobs publish to `ghcr.io/jeongjaesoon/werft-<app>`. Only the publishing jobs have package write permission. The three jobs run in the `release` environment, and fail if the commit the tag points at is not an ancestor of `main` (a tag is not a review). `publish` pushes each image and architecture to a staging tag of its own run, then pulls that digest and passes it through the same smoke (`.github/scripts/image-smoke.sh`). `sources` asks whether the Debian sources of the six images are on snapshot.debian.org. It has neither package write nor the environment. `index` bundles the two digests of each image into one index, puts it on a staging tag of its own run, and checks that the index points at exactly those two digests. `promote` retags to the `vX` and `sha-…` tags only after the three indexes are ready (registry-side, no rebuild). The staged index digests of this run are the release candidate. If an existing tag points at a different digest, it fails before writing any tag (one version is not mixed from images of two build attempts), and if the lookup itself fails (authentication, rate limit, 5xx), it stops rather than treating it as "absent" (fail-closed). After writing the tags it reads the six references (three images × two tags) again and makes the `image-digests-published` artifact only when they equal the candidate. The retag runs per repository in order, so a failure partway leaves the set half tagged. In that case, fill it in with **"Re-run failed jobs" of the same run** while the staged artifacts still exist (the publish and index jobs do not run again, so the staged artifacts and digests stay as they are). Pushing the tag again means a new build (the apt layer of the worker is not pinned), so it is refused. The consumer record that holds the three digests together is [`release-manifest.json`](#reading-the-release-manifest), attached to the tag's GitHub Release. The required reviewer and deployment branch rules of the `release` environment are set in the repository settings. There is no registry CD yet.

### Images published on every main merge

The `publish-main`, `index-main` and `promote-main` jobs of a `main` push run publish the three images as `ghcr.io/jeongjaesoon/werft-<app>:main-<12>`. `<12>` is the first 12 characters of the commit SHA. The namespace comes from `github.repository_owner`. Schedule, pull request and `workflow_dispatch` runs do not publish.

- **Checks.** These jobs and `sources-main` run the same steps as `publish`, `sources`, `index` and `promote` on the tag path. After `build` and `supply-chain` pass, they build again per image and architecture, push to a staging tag of their own run, and run the smoke, the license check and the Grype scan on that digest. Only when all six digests pass and `sources-main` has finished do they bundle the indexes and retag them as `main-<12>` (no rebuild). They do not take `release` approval, because the merge is the review.
- **Use `main-<12>` by digest.** Use the tag only to find the commit, and write `name@sha256:…` in deployments. There is no moving tag. `sha-<12>` is a tag of `v*` publishing, and main publishing does not use it.
- **Read the digests.** Public packages are read from the tags without a GitHub login. The three tags are written per repository one after another, so the set is complete only when all three lookups succeed.

```bash
TAG="main-$(git rev-parse HEAD | cut -c1-12)"   # from a checkout of the commit to deploy
for app in control-host worker egress-proxy; do
  digest="$(docker buildx imagetools inspect "ghcr.io/jeongjaesoon/werft-${app}:${TAG}" --format '{{.Manifest.Digest}}')"
  echo "werft-${app}@${digest}"
done
```

This digest is the digest of the index that holds both architectures. A `main` merge does not make a Release. Read the three digests of a release (`v*` tag) from the [release manifest](#reading-the-release-manifest).

- **No overwrite.** Before writing, it looks up all three tags, and if a tag already points at a different digest, it writes no tag and fails. If the digest is the same, it treats this as a rerun and passes. If a lookup fails for any reason other than "absent", it stops. Rerunning the whole run builds again, so the digest can change; in that case it is refused and the image published first stays as it is. When the set is half tagged, fill in the same digests with "Re-run failed jobs" while the staged artifacts still exist.
- **`main-<12>` is not a release.** It can go out without confirming that some of the corresponding sources are archived. `sources-main` asks once about the sources of all six images together, and asks again for up to 10 minutes about sources that got no answer. Sources that still do not answer are passed with a warning, and the list is left in the job summary of the run and in `unverifiedSources` of the `image-digests-published` JSON. An empty array means everything was confirmed, and an old JSON without the field means there is no record. It remains possible that a source that did not answer is actually missing. An official release (`v*` tag) is published only when the archiving of every source is confirmed. `sources` asks for up to 30 minutes, and fails if anything is still left. In that case, after the service comes back, rerun only that job with "Re-run failed jobs".
- **Some commits are not published.** If the recheck finds a high or critical with a fix available, if the vulnerability scan gets no answer, or if snapshot.debian.org answers that a source is missing, that commit is not published and the Images run ends red. It is not a required check, so it does not block the merge, and the next merge publishes a new set. Commits merged within 1 second of each other and bundled into one push have no run, so they have no tag either.
- **Architectures.** As on the tag path, it publishes an index that holds `linux/amd64` and `linux/arm64`. Both architectures must pass the smoke, the license check and the Grype scan, and if one side fails, that commit is not published. `main-<12>` from before this scheme is `linux/amd64` only.
- **Pulling.** When you pull by the digest of the index, Docker picks the host's architecture. If the package is private, `docker login ghcr.io` comes first.

```bash
docker pull "ghcr.io/jeongjaesoon/werft-worker@<digest read above>"
```

### Repository maintainers: publishing with a `v*` tag

This section is the procedure for maintainers who have permission to push tags to the repository. Operators who install do not add tags; they use the published images in [Single-server install](/run-server/self-hosting/single-server) or [Kubernetes install](/run-server/self-hosting/kubernetes).

This path first ran for `v0.1.0`. In [Images run 42163099605](https://github.com/JeongJaeSoon/werft/actions/runs/42163099605), `sources`, `publish` (6 jobs), `index`, `promote`, `chart`, `chart-publish` and `release` all succeeded, and the `release` environment approval was requested 4 times. No tag run has happened since the change that reduced the approval to one before `publish` ([JeongJaeSoon/werft#1275](https://github.com/JeongJaeSoon/werft/pull/1275)).

1. Push a `vX.Y.Z` or `vX.Y.Z-<prerelease>` tag to a verified commit on `main`. If that commit is not an ancestor of `main`, the publishing jobs fail. Tags of any other form (`v1`, `v1.2.3+build`) publish only images and fail in the `chart` job.
2. Watch the `publish` job get `release` environment approval, and `index`, `promote` and `chart-publish` then finish without approval. Approval is requested once, before `publish`. The later jobs run only after `publish` succeeds, so that one approval guards them all. `sources`, between `publish` and `index`, can take up to 30 minutes.
3. When `chart-publish` finishes, the `release` job creates the tag's GitHub Release and attaches `release-manifest.json`. This job does not take approval of its own. The approval before `publish` has already passed, and only this job has `contents: write`. The Release is created as a draft, the manifest is uploaded and read back, and only then is the Release made public. Check the digests and the chart version with the commands in [Reading the release manifest](#reading-the-release-manifest).
4. Rerunning the same tag with "Re-run failed jobs" is safe. If the content is the same as the manifest already attached, it passes; if it differs, it fails and does not overwrite. If creating the Release or uploading was cut off partway, finish it the same way. If an image is rebuilt under the same tag and its digest changes, `promote` refuses it first.

After a release, raise `version` in `Chart.yaml` to the next version. The `main` chart version is appended after this value, so this is what makes prereleases sort after the release just made.

### Reading the release manifest

Each `v*` tag gets one GitHub Release with the file `release-manifest.json` attached. Operators do not look for runs or artifacts. They do not need a repository checkout either; `gh` and `jq` are enough. The first Release is `v0.1.0` (the asset is `release-manifest.json`, and the commit it records is `9e2098e5`). Put the tag of the Release you want to read in `TAG` below.

```bash
TAG=v0.1.0   # the release tag to read
gh release download "$TAG" -R JeongJaeSoon/werft -p release-manifest.json -D "$TAG"   # one directory per tag
jq -r '.images[] | "\(.image)@\(.digest)"' "$TAG/release-manifest.json"   # the three digests used for deployment
jq -c .workerRuntime "$TAG/release-manifest.json"                          # worker runtime
jq -r '"\(.chart.ref) \(.chart.version)"' "$TAG/release-manifest.json"     # chart location and version
helm show chart "$(jq -r .chart.ref "$TAG/release-manifest.json")" --version "$(jq -r .chart.version "$TAG/release-manifest.json")"
```

The repository is public, so you can also download it without `gh`: `mkdir -p "$TAG" && curl -fsSL -o "$TAG/release-manifest.json" "https://github.com/JeongJaeSoon/werft/releases/download/$TAG/release-manifest.json"`. To check against the registry, pass one digest to `docker buildx imagetools inspect <image>@<digest>`.

| Field | Value |
|---|---|
| `schema` | The manifest format version. Currently `1` |
| `tag`, `commit` | The release tag and its commit (40-character hex) |
| `images.<app>.image` | `ghcr.io/<owner>/werft-<app>`. `<app>` is `control-host`, `worker` or `egress-proxy` |
| `images.<app>.digest` | The digest of the index that holds both architectures. Deployments are fixed to this value |
| `images.<app>.platforms.amd64`, `.arm64` | The manifest digest of that architecture |
| `workerRuntime` | The Claude runtime the worker image carries (`engine`, `sdkVersion`, `cliVersion`, `profileDigestScheme`) |
| `chart.name`, `chart.version`, `chart.appVersion`, `chart.ref` | The chart the same run published. `chart.ref` is the `oci://` location |

The values come from the digests that `promote` read back from the registry and confirmed, and from the chart that `chart-publish` read without a login and confirmed. When the manifest is made, it is also checked that `Chart.yaml` and `values.yaml` of the chart package hold the same digests and version. Once attached, a manifest does not change. If running the same tag again produces different content, the job fails.

Operators who install get the image lines for [Single-server install](/run-server/self-hosting/single-server) from this manifest.

### Publishing the Helm chart

When the image promote finishes, the same run publishes the chart `werft` to `oci://ghcr.io/jeongjaesoon/werft`. There are two paths, `main` push (`chart-main`, `chart-publish-main`) and `v*` tag push (`chart`, `chart-publish`), and the steps are the same. Schedule, pull request and `workflow_dispatch` runs do not publish.

- **Version.** Tag `v1.2.3` gives chart `1.2.3` with appVersion `v1.2.3`. `main` gives `<Chart.yaml version>-main-<12>` with appVersion `main-<12>`. It is not `-main.<12>` because when all 12 characters are digits and start with 0, it is not semver and helm rejects it.
- **Values.** `.github/scripts/chart-package.ts` reads the three digests and the worker runtime from that run's `image-digests-published` and puts them into `values.yaml` inside the package. Each of the three apps must appear exactly once, be the promoted image of this commit, and have a repository equal to the chart default. The repository's `values.yaml` is left as it is. The same values are also kept in `werft-<version>.values.yaml` of the `chart` artifact. Operators read them with `helm show values`, without the artifact. The digest is the digest of the index. The worker runtime is a value independent of architecture, and if the values of the two architectures differ, `index` stops. The worker comparison looks at this value, not at the digest, so moving from a chart published with single manifests to an index chart changes only the digest values, and the reinstall behavior stays the same.
- **Checks.** The `chart` job looks up the three indexes and their per-architecture manifests without a login, installs the package on amd64 kind, and passes the package on only when `/readyz` and `/docs` return 200. For arm64 it checks up to the smoke of `publish` and this lookup, and does not install on kind. An empty install starts no worker, so the worker is checked only up to the lookup. It has no package write permission. On pull requests, `render-check.ts` of the `helm-chart` job builds a package with fixture digests and renders it.
- **Publishing.** Only `chart-publish` and `chart-publish-main` have package write. The `release` environment approval sits only on `publish` of the tag path; `chart-publish` runs after it without approval. The `main` path has no approval. In a run where image publishing failed, the chart stage does not run.
- **No overwrite.** If the same version already exists, `.github/scripts/chart-push.sh` downloads it and compares the unpacked files with the candidate. If they are the same, it treats this as a rerun and does not push; if they differ, it fails. If the lookup cannot confirm "absent", it stops. `denied` is an answer ghcr can give for a package that does not exist, so a lookup without a login treats only `denied` as absent.
- **Read check.** After the push, it downloads with all Helm and Docker login information cleared, compares with the candidate, and prints `helm show chart`. If the package was created private, the run ends red here. The visibility is changed by a repository maintainer in the package settings.
- **License.** The chart follows the same PolyForm Small Business License 1.0.0 as the repository.

### Author of commits made inside the worker

The worker image sets `user.name=Werft` and `user.email=noreply@werft.invalid` in the git system configuration (`/etc/gitconfig`). So commits Claude makes in the workspace have `Werft <noreply@werft.invalid>` as both author and committer, unless the repository or the session sets otherwise. Without these values git refuses to commit, and Claude asks the user for a name and address. `.invalid` is a reserved domain that is delivered nowhere, so it does not collide with a real person's address. The internal commits of checkpoints do not use this value (`checkpoint@werft.invalid`). The same system configuration then sets `include.path=~/.werft/git-identity`. When the session repository uses the console's authoring GitHub App, the worker writes the App bot account (`<slug>[bot]`) into that file and overrides the default ("commit author" in [GitHub 계정 연결](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md#github-계정-연결)). If the file does not exist, the include is skipped.

The system configuration has the lowest priority of the git configurations, so a value set inside the session wins. To change the session's author, write `git config user.name` and `git config user.email` in the workspace repository. `git commit --author` changes only the author and leaves the committer as it is. `git config --global` is written to the tmpfs HOME, so it disappears when the worker changes. The repository configuration also disappears on a worker restored from a checkpoint, because the restore empties the workspace and creates the repository anew. From then on, commits are made with the default author again. There is no feature to change the default through the catalog or the installation settings. Using a per-user author as the default would require passing the user's address to the worker, so a product decision comes first. The image smoke (`.github/scripts/image-smoke.sh`) commits in an empty repository to check this author, and the e2e (`tests/e2e/alpha-path.e2e.ts`) checks the same with the Bash tool of real Claude Code.

### GitHub CLI inside the worker

The worker image has the GitHub CLI (`gh`, `/usr/local/bin/gh`). It is there so that sessions do not get lost when the `gh` command is missing, and it does not add paths to GitHub. The image has no GitHub login or token, and `api.github.com` is in none of the default lists of the egress proxy. So with the shipped image and the default egress settings, only commands that do not use the network, such as `gh --version` and `gh help`, work, and commands that call GitHub fail, whether they read or write. Without a login, `gh` ends with exit 4 before the request, with a `gh auth login` hint. Even if the session sets `GH_TOKEN`, the proxy refuses the `api.github.com:443` CONNECT with `destination is not allowlisted`, and it ends with `Forbidden` (confirmed in a fake model session on 2026-11-03). If the operator adds `api.github.com:443` to `EGRESS_ALLOWLIST`, this block goes away. Then `gh` can call the GitHub API with a token the session holds on its own, and the platform's push approval and branch restrictions do not apply to those calls. To send GitHub writes only through the built-in `github` MCP server, do not add this host to the list. The version is pinned with `GH_VERSION` in the worker Dockerfile and a sha256 per arch (the values in the release's checksums file). It does not move up with the daily Debian security updates, so it is raised by hand. The one binary adds about 38MB to the image.

### Package tools inside the worker

The shipped worker image has only Bun (including the Node compatibility shim) and the engine. It has no npm, pnpm, yarn, Ruby, Bundler or Go. For sessions to install dependencies with these tools, the operator changes `WORKER_IMAGE` to an image derived from this image. The derived image must not declare a `VOLUME` other than `/workspace` (the image contract of the execution base document), and must not change the engine, SDK and CLI combination. Regardless of the image, registry access goes only through the `packages` route of the egress proxy ([실행 기반 § egress](/run-server/self-hosting/operate/execution)). The worker writes npm, Bundler and Go user configuration into HOME at claim time, so there is no need to put registry configuration into the derived image.

The npm configuration the worker writes is at the user level, so if the repository's `.npmrc` sets `registry=`, that wins. That registry host cannot be reached through the forward proxy, so the install fails with `403`. The precedence measured with `config get registry` on a derived image on 2026-11-01 is below (`registry=https://registry.npmjs.org/` in the repository `.npmrc`, the route in the user configuration).

| Tool | User configuration only | `npm_config_registry` environment variable | CLI `--registry` | Notes |
|---|---|---|---|---|
| npm 10.9.9 | The repository value wins | The environment variable wins | The CLI wins | Without a repository `.npmrc`, it uses the user configuration (route) |
| pnpm 9.15.0 | The repository value wins | The environment variable wins | `config get` does not accept the option | Same order as npm |
| yarn 1.22.22 | Does not read the npm user configuration (`registry.yarnpkg.com`) | Not read | The CLI wins | `YARN_REGISTRY` wins. `registry.yarnpkg.com` is not in the list |

So if the repository has fixed a registry, override it from the CLI in the session, as in `npm ci --registry <route>/packages/npm/`. The worker passes only a fixed list of engine environment variables, so it does not set `npm_config_registry`. yarn 1 must use `--registry` or `YARN_REGISTRY`.

Running all the way to install in a real session on the same day (with the npm cache emptied) gave the same result. In a project whose repository fixed the public registry, `npm ci` failed with `403 Forbidden - GET https://registry.npmjs.org/...`. `pnpm install` went to the repository registry, could not find the token that is attached only to the route address, and failed with `No authorization header was set for the request`. In projects that did not fix it, `npm ci` and `bundle install` downloaded through the route.

For Go, pin the official release tarball by checksum, unpack it into `/usr/local/go` of the derived image, and add it to `PATH`. Set `GOTOOLCHAIN=local` along with it. Otherwise, when the `go` line of `go.mod` is newer than the image, Go goes out to download a new toolchain. Switch the user back to the image's original user (`USER 1000:1000`). The worker `/tmp` of the local-docker execution base has no `exec` in its tmpfs options, so Docker mounts it `noexec`. So `go run` and `go test` cannot start the executables they create in `/tmp`, and fail with `fork/exec /tmp/go-build…: permission denied` (measured on 2026-11-02). HOME is on the same tmpfs, so files that `go install` puts in `~/go/bin` do not run either. `go test` passes when `GOTMPDIR` is set to a directory that already exists inside the workspace. `go run` starts the executable from `GOCACHE` (by default under HOME), so `GOCACHE` must move to the workspace too (for example `mkdir -p .gotmp && export GOTMPDIR=$PWD/.gotmp GOCACHE=$PWD/.gotmp/cache`, measured the same day). Build executables into the workspace with `go build -o`.

```dockerfile
FROM <shipped worker image>
USER root
ADD --checksum=sha256:<release sha256> https://go.dev/dl/go<version>.linux-<arch>.tar.gz /tmp/go.tar.gz
RUN tar -xzf /tmp/go.tar.gz -C /usr/local && rm /tmp/go.tar.gz
ENV PATH=/usr/local/go/bin:$PATH GOTOOLCHAIN=local
USER 1000:1000
```

On 2026-11-02 a real GitHub sandbox session ran with a derived image of this form (go1.27.3). Modules in the session's private repository were downloaded through the repository route, and public modules through the `packages` route (the "LFS·submodule·Go 모듈" item of [api-server.md](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md)).

`bun install` in the shipped image gets the metadata from the route with the registry and token of the user `.npmrc`. But it tries to download the tarballs directly from the `https://registry.npmjs.org/...` address written in `dist.tarball` of the metadata, and the forward proxy blocks that with `403` (measured on 2026-11-01). npm replaces that host with the configured registry through the default of `replace-registry-host` (`npmjs`). Bun has no such setting, so for now public npm packages cannot be installed with Bun.

### Worker image upgrade and checkpoint compatibility

When the worker image changes in an [upgrade](/run-server/self-hosting/upgrade) of a single-server (compose) installation, the restore plan of each current checkpoint is computed with the engine, SDK, CLI and profile digest of the new image. Sessions where all four values match and are compatible continue without approval, and only sessions that are `INCOMPATIBLE_CHECKPOINT` are reported to the user and the exact list is approved. If the check cannot run to the end, or other validation failures are mixed in, it behaves fail-closed: every session with an uncollected checkpoint becomes the affected list, and this is logged. The same check runs again after the writers are stopped. Choosing `start_fresh` for an incompatible session discards the context of the previous checkpoint. In a Kubernetes (helm) installation, a pre-upgrade hook makes the same judgment from the combination in the pointer, without running the image ([Kubernetes install (Helm chart) § Pre-upgrade check](/run-server/self-hosting/operate/kubernetes-deployment#pre-upgrade-check)).

When the worker image changes, the upgrade keeps the image from before the change as the previous image (as the `previous-worker` file in the state directory of the upgrade script). For each session the scheduler picks, between the current and the previous image, the one that matches the combination of the checkpoint pointer (engine, SDK, CLI, profile digest scheme), and uses the current image when both match ([Configuration reference § Scheduler, worker container and egress settings](/run-server/self-hosting/operate/configuration#scheduler-worker-container-and-egress-settings)). So the gate puts on the affected list only the sessions that cannot be restored with the new image and cannot be restored with the previous image either. If the check of either the new image or the previous image ends fail-closed, the list based on the new image is used as is. For an image rebuilt with the same combination, the scheduler starts the new image, so a session not confirmed to restore with the new image is not removed from the list even if the previous image restores it. If either side is an old image that cannot print its own combination (a build without `apps/worker/src/image-runtime.ts`), the previous image is not used, and the gate also uses the list based on the new image as is. The support window is one release. After one more upgrade, sessions left on the image before that go on the affected list again.

A release that raises the SDK also raises `runtime_version` in the example settings documents (`tests/fixtures/settings/`), and the limits of an operational installation are saved with the new version. A profile whose `runtime_version` the current image does not carry does not accept new sessions. The same release also adds the list of supported built-in tools for the new engine combination (`packages/adapters/runtimes/claude-codec/src/tool-catalog.ts`). A limit for a version without a list cannot be made `deny`. Tools that appear in the new list carry over as blocked in the new version of each limit, and open only when accepted with `accept_added_tools` ([api-server.md](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md#운영자-카탈로그-agent-profile--repository)). The deployment order of a Kubernetes (helm) installation and the session behavior for each kind of change are in [Kubernetes install (Helm chart) § Upgrade and rollback](/run-server/self-hosting/operate/kubernetes-deployment#upgrade-and-rollback).

### Worker and control-host rollback and incremental checkpoints

From commit `95b0e7b5`, the worker uploads an incremental bundle that holds only new objects on top of the bundle chain of the previous checkpoint. That chain is written in `workspace.baseBundles` of the manifest. The manifest `version` stays 2, and whether it is incremental is decided only by whether this field is present. **If you roll back to a build before that, checkpoints with this field cannot be restored.** This is because the manifest schema of earlier builds rejects unknown keys.

- **Old worker image.** On restore, manifest decode fails with `Invalid Claude checkpoint manifest: workspace Unrecognized key: "baseBundles"`. This failure happens before the workspace is emptied or bundles are downloaded, so no half-restored workspace is left. But the manifest is fixed, so launching again ends in `worker.failed` for the same reason.
- **Old control-host.** The restore plan is rejected with `CHECKPOINT_UNAVAILABLE`, and it does not fall back to an earlier revision. finalize also rejects incremental manifests, so the pointer does not advance. When mixed with new workers, only standalone bundles, like the first checkpoint, are committed. The old GC skips sessions it cannot decode, so it does not delete base bundles.
- **Finding affected sessions.** The DB does not hold manifest contents. Download the manifest from the object store with `manifest_ref` and `manifest_version` of the `checkpoints` row (`collected_at IS NULL`) that `sessions.checkpoint_revision` points at, and sort them with `jq -e '.workspace.baseBundles | length > 0'`. The restore can fall back along `parent_revision`, so check the parent rows too. If `base_bundles` of the worker log `worker.checkpoint.published` is greater than 0, it was uploaded as incremental.
- **Before rolling back.** If there are affected sessions, roll forward instead of rolling back. There is not yet an operational means (environment variable, setting, CLI) to make a session checkpoint again with a new full bundle. The worker uploads a full bundle by itself only when the chain is missing or broken, or when it reaches length 32 (`MAX_WORKSPACE_BUNDLE_CHAIN`) or the bundle limit. So if a rollback is truly needed, affected sessions are not restored during the rollback. If you roll forward, they restore as they are.

### control-host rollback floor: running with release tools

From commit `756f0a220` on, control-host runs sessions made from a release with the tools fixed in the release (`agent_releases.runtime_config_snapshot.tools`, within the profile tools). Before it, they ran with all of the profile's tools. The tools are carried in the claim the worker receives when it starts, and the worker runs with those tools until it ends. So for agents whose card picks `tools` or lists `forbidden`, even sessions already in progress are narrowed from the next claim. Workers started before the deployment use the profile's tools until they end, either when `WORKER_IDLE_TIMEOUT_SEC` (default 1800 seconds) passes without input after the last turn, or through pause or restart. Sessions without a release, and sessions of a release whose card keeps all of the profile tools, are unchanged. The worker image and the worker protocol do not change.

- **The rollback floor is commit `2648f2ac`.** The tool list goes into the profile digest of the checkpoint. control-host from `2648f2ac` on puts both lists, the profile tools and the release tools, into the restore candidates of the claim, so between `756f0a220` and `2648f2ac`, moving in either direction restores each other's checkpoints (except for the restore candidate limit exception below). If you roll back to a build earlier than that, checkpoints made with release tools cannot be restored, and those sessions stop at `recovery_required` (`incompatible_checkpoint`) after the first launch. Roll forward and retry the same checkpoint with `retry_restore`. So do not go directly from a build earlier than `2648f2ac` to a build that includes `756f0a220`; deploy a build at `2648f2ac` or later first so that it becomes the rollback target.
- **Number of releases to be narrowed.** Count them with a read query before deploying. It also counts releases whose card picked all of the profile tools, so it is an upper bound.

```sql
WITH narrowed AS (
  SELECT r.id FROM agent_releases r JOIN agent_versions v ON v.id = r.version_id
  WHERE v.card->'capabilities'->'tools' <> 'null'::jsonb
     OR jsonb_array_length(coalesce(v.card->'capabilities'->'forbidden', '[]')) > 0
)
SELECT
  (SELECT count(*) FROM narrowed) AS releases,
  (SELECT count(*) FROM sessions s JOIN narrowed n ON n.id = s.agent_release_id
    WHERE s.admission_state NOT IN ('closing', 'closed')) AS open_sessions,
  (SELECT count(*) FROM agent_releases
    WHERE CASE WHEN jsonb_typeof(runtime_config_snapshot->'tools') = 'array'
      THEN EXISTS (SELECT 1 FROM jsonb_array_elements(runtime_config_snapshot->'tools') t
                    WHERE jsonb_typeof(t) <> 'string')
      ELSE true END) AS unreadable;
```

`unreadable` is a snapshot whose `tools` is missing or is not a string array. Sessions of such a release run without built-in tools (it is read toward not allowing). Releases made through the normal path always carry `tools` as a string array.
- **Restore candidate limit.** The restore candidates of a claim are capped at 16 (worker contract). All profile lists are put in before the release lists. Among sessions of releases whose tools are actually narrowed, sessions with many earlier profiles (16 without GitHub settings, 8 or more with them) lose two things. ① After `756f0a220`, the profile list of the current profile takes one more slot, so one candidate of the oldest earlier profile drops out. A checkpoint that matches only that candidate stops its restore with `incompatible_checkpoint`, and retrying gives the same result on builds that use the same candidate rule. End such a session with `start_fresh` (discards the previous context) or `close`. ② If you roll back to `2648f2ac`, the claim of that build fills the limit with profile lists alone and cannot add release tool candidates, so checkpoints made with release tools after `756f0a220` cannot be restored. For this one, roll forward and retry with `retry_restore`.

### Order for removing worker protocol fields

Even when the API is upgraded, worker containers that are already up keep running on the old image. A worker with no input also stays for `WORKER_IDLE_TIMEOUT_SEC` (default 1800 seconds). So for a worker protocol field, the receiving side is first changed to accept messages without the field, and only after everything has been replaced with that release does the sending side drop the field. Do not change both sides in one release.

| Field | Step 1: the receiver does not require it | Step 2: the sender drops it (after step 1 replacement is done) |
|---|---|---|
| heartbeat response `auth_revision` | The worker also accepts responses without it | The API does not send it. Before that, check that no worker on an image from before step 1 is left |
| append-events request `batch_key` | The API also accepts requests without it (not done yet) | The worker does not send it. Before that, check that no API from before step 1 is left |

If step 2 is deployed too early, the old side rejects the other side's request or response as a contract violation. The worker treats a heartbeat response that does not fit the contract as a non-retryable failure, so on the first heartbeat it decides it has lost its lease and stops.

When adding a field to the checkpoint manifest, it is the other way around: the reader goes first. Both control-host (validation before commit, restore plan, GC) and the worker (restore) reject unknown keys. So raise control-host first or in the same release, and raise the worker after it. If you roll back the worker after checkpoints that use the field exist, those sessions are not restored, for the same reason as `baseBundles` above.

| Field | First: the reader | Then: the writer |
|---|---|---|
| `workerState` (park while waiting for approval) | control-host and the worker accept manifests with this key | The worker writes it only when it parks a turn waiting for approval |

When adding a new worker protocol field that the worker sends, the API also goes first. The API's worker protocol request schema is strict, so an old API rejects a whole request that carries an unknown field with 400 `BAD_REQUEST`.

| Field | Deploy first | A new worker meeting an old API |
|---|---|---|
| pending-control request `settled[].reason`, `settled[].answer_result` | API | Logs the `worker.pending.settlement_detail_refused` warning once and sends only `outcome` until that attempt ends. Receipts are settled by the old rules, and `pending_requests.settled_reason` and `settled_answer_result` stay empty |
| bootstrap-claim and pending-control request `capabilities`, register-pending request `remember_offer` | API | There is no compatibility retry. When bootstrap-claim, the first request of a new worker, is rejected with 400 `BAD_REQUEST` (non-retryable), the worker ends with an error and runs no turn at all. Rolling back only the API gives the same result. Before rolling back the API, check that no session uses the new worker image |

### Order for changing the DB schema

Migrations run before the rollout. So the old control-host runs on the new schema for a while, and old worker images keep running during the support window. Columns and tables that old code reads and writes must stay until all of that code is gone. So a schema change is split across three releases. Do not add and remove in the same release.

| Step | What it does | What old code sees |
|---|---|---|
| 1. Expand | Add columns and tables. New columns allow null or have a default. With a default, existing rows read that value too, and an INSERT that leaves the column out gets the default. A default does not apply to an explicit NULL, so a nullable column stores NULL and a NOT NULL column makes the INSERT fail. So choose by checking whether the value fits existing rows and how old code's INSERT uses the column | Only an unknown column appears, and old code's writes go in without that column |
| 2. Switch | New code starts writing to the new column too. While old code writes to the old column, the old column is the reference. New code writes to both columns but reads the old one. If there is no mechanism (a trigger or the like) that moves old code's writes to the new column, then after all old writers are gone, backfill existing rows one last time and then move reads to the new column | The old column is still there, so reads and writes continue |
| 3. Contract | Remove old columns and tables, or tighten constraints with NOT NULL or CHECK. Do it in the release after the images that use the column have left the support window and it has been confirmed that no worker or control-host of those images is actually left. Before tightening a constraint, check that existing rows and every writer currently running satisfy the new constraint | No old code that uses the column is left |

Renaming a column removes the old name at once, so it follows the same order: add the new column, move the data and change the code, then remove the old column. `WORKER_IDLE_TIMEOUT_SEC` is the idle time after the last turn, not an upper bound on a worker's lifetime. A working worker can stay longer than that, so judge the time to contract not by time but by the containers actually left.

Example: the runtime combination of the checkpoint pointer, `checkpoints.runtime_*` (migration `0196_checkpoint_runtime`), was step 1 and added only nullable columns without a default. Rows committed before that stay null. `0199_worker_image_runtime` (the combination of a launch, the digest scheme of a checkpoint, the `worker_image_refusals` table) is also step 1. A checkpoint whose scheme is null is read as the first scheme (1).

## Supply chain vulnerability policy

**Only high and critical vulnerabilities with a fix available are blocked.** Findings without a fix are only reported and do not cause a failure.

- **What is checked.** The three images (Grype, Debian packages and the npm packages in `/app`) and all of `bun.lock` (`bun audit`, dev dependencies included). "A fix is available" means, for images, that Grype's `fix.state` is `fixed`, and for npm, that the GitHub advisory database has a `first_patched_version` in a range that includes the locked version. Debian `not-fixed` and `wont-fix`, and npm advisories without a fix, are not blocked.
- **Where it blocks.** The `supply-chain` job of images.yml decides, and it is a required check of branch protection. It runs on PRs, main push, the daily run at 03:17 UTC, manual runs and `v*` tags. `publish` on tags and `publish-main` on main wait for `supply-chain`, check the digests to be promoted again, and block by the same criteria.
- **When the check gets no answer.** An `error` where the Grype DB or the advisory service did not respond only leaves a warning on PRs and main push, because an outside service outage must not stop every merge. On the daily run and on tags it fails. A main push does not publish either: `publish-main` judges the `supply-chain` result again from the same file and fails on `error`. If the image was not built and there is no result at all, it fails everywhere.
- **Reporting.** High and critical findings without a fix are also left in each check's step summary (a collapsed list) and in the `supply-chain-results` artifact (one JSON per check, `fix` is null for each item). When the daily run or a manual run fails, an issue labeled `ci-supply-chain` is opened.
- **New advisories overnight.** When a new advisory with a fix comes out, `supply-chain` turns red on every PR at once, main included. This is intended. Resolve it with one PR that raises the dependency or the base. For Debian packages, a new build picks them up with the next day's `APT_UPGRADE_KEY`. To get them the same day, a manual run (`gh workflow run Images`) builds with that day's key.
- **Exceptions.** Fixes that cannot be applied (for example a Debian package that `upgrade` held back, or an advisory whose code path is not reached) are written in `.github/vulnerability-exceptions.json` as `{"id", "package", "reason", "expires"}`. `id` is the `id` of the check result (CVE-… or GHSA-…), and `package` is the package name. Without `reason` and `expires` (YYYY-MM-DD, applied through that day), the npm check becomes `error`. Once expired, it blocks again. Exceptions go through PR review.

```bash
bun .github/scripts/npm-audit.ts /tmp/sc && cat /tmp/sc/npm.txt   # the npm verdict, locally
.github/scripts/supply-chain-verdict.sh /tmp/sc warn              # verdict over the four result files (control-host, worker, egress-proxy, npm)
```

How the third-party notices (`THIRD_PARTY_NOTICES.md` and `/app/DEBIAN_SOURCES.md` in each image) are made is in [ci.md](https://github.com/JeongJaeSoon/werft/blob/main/docs/contributing/ci.md).
