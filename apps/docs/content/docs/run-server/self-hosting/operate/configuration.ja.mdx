インストール上限、API設定、scheduler・workerコンテナ・egressの設定をまとめます。reconcilerとschedulerの監督ループの設定は[実行基盤とworkerの隔離](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/execution.md)に、接続・保存先・上限(コンソールと設定ドキュメント)と認証の設定は[APIサーバー](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md)に、Kubernetes backendの設定は[Kubernetes実行backend](/run-server/self-hosting/operate/kubernetes-backend)にあります。

## インストール上限

APIとschedulerは、次の値のうち`SESSION_TOKEN_LIMIT`を除く6つのどれかがない場合、またはどれかの形式が誤っている場合、問題をすべて1行でログに出して起動しません。`SESSION_TOKEN_LIMIT`は後から加えた値なので、なければ0(上限なし)として読みます。2つのプロセスは同じparser(`packages/platform/src/limits/installation-limits.ts`)を使います。`SESSION_TOKEN_LIMIT`の0を除き、コードに既定値はなく、composeの`x-installation-limits`ブロックがローカルの既定値を与えます。起動中のAPIの`/readyz`は、同じ検証を`config`チェックとしてもう一度行います。

| 変数 | 意味 | 超えたとき |
|---|---|---|
| `EXECUTION_SLOT_LIMIT` | 同時にスロットを持つworkerの数。0なら受け付けるだけで何も起動しません | 入力は拒否せず`queued`のままにします |
| `QUEUED_INPUT_LIMIT_PER_SESSION` | 1つのセッションが溜めておける`queued`のturn数 | `429 RATE_LIMITED`、`retryable:true`、`Retry-After: 5` |
| `STORAGE_LIMIT_BYTES` | インストール全体が保持する入力messageのUTF-8バイト数。event・checkpoint object・workerのディスクは数えません(ディスクはworkspace quotaが担当します) | `413 STORAGE_LIMIT_EXCEEDED`、`retryable:false` |
| `MAX_TURN_SECONDS` | 1つのturnの実時間の上限。承認待ちも含みます。worker envの`WORKER_MAX_TURN_SEC`として渡されます | turnは`failed(turn_timeout)`。エンジンが応答しなければ`outcome_unknown(turn_timeout)` |
| `SESSION_COST_LIMIT_USD` | セッションの累積コスト(egress proxyが計測したMessages呼び出しごとのusageを、プラットフォームの価格表で換算した合計。推定値) | 新しいturnをdispatchしません。セッション詳細に`attention.code=BUDGET_EXCEEDED`が出て、workerはスロットを返します。入力は引き続き`queued`で受け付けます |
| `SESSION_TOKEN_LIMIT` | セッションの累積provider token数。コスト上限と同じ呼び出しを数えますが、単価には依存しません。0なら上限なし(既定) | `SESSION_COST_LIMIT_USD`と同じです。2つの上限は同じ判定(`budgetExceeded`)を通り、どちらが先に届いても`BUDGET_EXCEEDED`になります。`attention.reason`には届いた上限だけが書かれます |
| `PROVIDER_MAX_RETRIES` | 失敗したMessagesリクエストを再送する回数。worker envの`WORKER_PROVIDER_MAX_RETRIES`を経由して、SDKの`CLAUDE_CODE_MAX_RETRIES`として渡されます。0なら最初の失敗でturnが終わります | turnは`failed(api_error)`。turn詳細の`result`に`api_error_status`・`provider_error`・`last_retry_status`が残ります |

- セッションのコストはcredential routeが数えます。proxyは2xxの`/v1/messages`応答(JSONもSSEも)からusageを読みます。応答が終わるか途切れると、authorizer listenerの`POST /usage`に報告します。`count_tokens`とエラー応答は数えません。
  - 応答がusageをすべて伝えない場合は、多めに推定します。`message_stop`の前に途切れたstreamは、届いたcontent 1文字をtoken 1個としてoutputに入れ、届いたweb search結果ブロック1つを検索1回として数えます。usageを読めなかったJSON応答(途切れ、8 MiB超過、JSONではない)は、リクエストから数えます。リクエスト1バイトをinput token 1個、`max_tokens`をoutputのすべてとみなします。このような呼び出しでは、proxyが`Provider usage estimated`の警告を出し、ledgerに`estimated=true`と記録されます。
  - APIは価格表でUSDを求め、micro-dollar単位に切り上げます。その金額を`provider_usage`にやり取り1回につき1行で書き、同じトランザクションでセッションのコストに足します。そのため、ledgerの合計とセッションのコストが一致します。
  - エンジンの呼び出しと、ツールがエンジンのtokenで直接行った呼び出しを、同じように数えます。
  - 報告には、proxyがやり取りごとに作ったidが付きます。authorizerが答えられなければ、1・5・15秒後に再送し、同じidは1回だけ数えます。最後まで報告できなければ、proxyが`Provider usage went unreported`のエラーログを出し、そのやり取りは数えません。
- turn終了時にSDKが知らせる`total_cost_usd`の増分は、turn結果(`cost_usd`)にだけ残り、セッションのコストには足しません。エンジンのturnごとの`maxBudgetUsd`は、そのままSDKの値で判定します。proxyが計測する前に作られたセッションは、それまでSDKの値を足したコストを引き継ぎます。
- 価格表はプラットフォームのコード(`packages/platform/src/limits/model-prices.ts`)が持ちます。モデルidごとに、input、output、cache write(5分は1.25倍、1時間は2倍)、cache readの単価を置きます。モデルが追加されたり価格が変わったりしたら、リリースと一緒に直します。
  - fast modeは別に置いたfast単価表で数えます。現在はOpus 5.5($8/$40)とOpus 5・Opus 4.8($10/$50)だけです。cacheの倍率はfast単価の上にそのまま掛けます。speedは応答の`usage.speed`に従い、応答が言わなければリクエストの`speed`に従います。どちらもなければ`standard`です。
  - 表にないモデル、fast単価のないモデルのfast応答、名前ではないspeed値は、項目ごとに2つの表を通じて最も高い単価で数えます。authorizerが`Provider usage priced at the fallback rate`の警告を出し、ledgerには`priced_by=fallback`と記録されます。
  - 応答の`usage.server_tool_use`にあるweb searchは、1回ごとに$0.01(1,000回で$10)を足します。web fetchはtoken以外に料金がありません。code executionは足しません。web searchやweb fetchと一緒に使うと料金がなく、そうでなければ呼び出し数ではなくコンテナ時間で課金され、組織ごとの無料時間があるからです。3つの回数とspeedはledger(`provider_usage`)に一緒に記録されます。
  - 4.6以降のモデルは、US限定の推論(`inference_geo: "us"`)ならtoken単価のすべて(fastとcacheを含む)に1.1倍を掛けます。web searchの料金には掛けません。geoは応答の`usage.inference_geo`に従い、応答が言わなければリクエストの`inference_geo`に従います。どちらもなければ`unknown`です。workspaceの既定が`us`のことがあるためです。`global`と`us`以外の値は、最も高い単価に1.1倍で数えます(`priced_by=fallback`)。geoはledgerに`inference_geo`として記録されます。`inference_geo`を知らない古いAPIは、このフィールドの付いた報告を`400`で拒否し、proxyはそのやり取りを数えられません(`Provider usage went unreported`)。そのため、アップグレードするときはAPI(migrationを含む)をegress proxyより先に上げます。1回の`up -d`はこの順序を守らないので、composeのインストールでは`docker compose -f infra/compose.yml --profile apps up -d api`(migrateが先に動きます)でAPIを上げ、`curl -s http://127.0.0.1:3000/readyz`がreadyになるのを確認してから、`docker compose -f infra/compose.yml --profile apps up -d egress-proxy`でproxyを上げます。新しいAPIは、このフィールドのない古いproxyの報告も受け付けます。
  - 4.6より前のモデル(Opus 4.5・4、Sonnet 4.5・4、Haiku 4.5)は`inference_geo`を受け付けないので、geoに関係なく標準単価で数えます。これらのモデルのウィンドウは200Kで、公開されたlong-context単価がありません。そのため、input・cache write・cache readの合計が200Kを超える呼び出しは、最も高い単価で数えます(`priced_by=fallback`)。4.6以降のモデルは、1M全体が標準単価です。
  - batchは、credential routeが`/v1/messages/batches`を開かないので該当しません。
- token上限は、`provider_usage`の1行の`input_tokens + cache_creation_input_tokens + cache_read_input_tokens + output_tokens`を`sessions.provider_tokens`に足して数えます。足す処理は`provider_usage`のinsert triggerが同じトランザクションで行います。そのため、rollout中やロールバック後に0127より前のAPIが記録した呼び出しも漏れません。cache readもモデルが処理したtokenなので数えます。多めに推定した報告は、推定値のまま足します。この累計を加えたmigrationは、既存セッションの値を`provider_usage`の合計で埋めます。それ以前にSDKの値だけでコストを数えていたセッションのtokenは、埋められません。累計は2^53-1(`Number.MAX_SAFE_INTEGER`)で止まります(migration 0129)。triggerはnumericで足すので、異常に大きなtoken値が来ても、エラーでusage記録とコストを巻き戻すことはありません。
  - SDKにはtoken予算のオプションがありません。そのため、turn途中のtoken上限は、下のegress拒否と再認可だけが担います。上限に届いた後に開かれたMessages呼び出しは拒否され、turnは`failed(budget_exceeded)`で終わり、次のturnからは`BUDGET_EXCEEDED`でdispatchされません。proxyは、authorizerの`BUDGET_EXCEEDED`拒否をMessagesのエラー形式(`message`が`BUDGET_EXCEEDED:`で始まる)で伝えます。理由はこの文言では決めません。エンジンはこの403を`api_error`として報告し、再認可で切られたやり取りも、再試行が残っていなければ(`PROVIDER_MAX_RETRIES=0`)切れた接続のまま`api_error`として報告します。finalizeは、`api_error`で終わったturnのセッションがすでに上限を超えていれば、理由を`budget_exceeded`、receiptのエラーを`BUDGET_EXCEEDED`と記録し、エンジンのprovider診断(`provider_error`)は空にします。上限未満で起きた403は、これまでどおり`api_error`です。
- コスト上限とtoken上限は、呼び出しが終わった後に判定します。同時に開いた呼び出しはすべて認可を通過でき、進行中のturnは上限を超えることがあります。
- 累積コストまたは累積tokenが上限以上のセッションのprovider egress tokenは、authorizerが403 `BUDGET_EXCEEDED`で拒否します。新しいproviderのやり取りはすぐに拒否され、すでに開いているやり取りは次の再認可(30秒周期)で切られます。repositoryとobject storeのrouteは拒否しません。

### 課金のないprofile(`billing: none`)

自己ホストのモデル(Ollama、プライベートネットワークのLiteLLMなど)には、token単位の請求がありません。価格表にもないので、そのままにするとfallbackの最高単価で計算され、`SESSION_COST_LIMIT_USD`とSDKの`maxBudgetUsd`に掛かってturnが切れます。このようなprofileは`provider.billing: none`と宣言します。

```yaml
provider:
  kind: litellm
  endpoint: http://litellm:4000
  billing: none
  auth:
    kind: bearer
    value_env: LITELLM_MASTER_KEY
```

- 省略すると`per_token`です。省略したprofileと`per_token`と書いたprofileはfingerprintが同じで、今と同じく価格表とfallbackで計算します。
- `none`のprofileで作ったセッションのprovider呼び出しは、応答がどのmodel名を名乗っても、コスト0、ledgerは`priced_by=unmetered`と記録されます。tokenはそのまま記録されます。セッションのコストが増えないので、コスト上限を判定する4か所(egress認可、`nextInput`、メッセージ受付、エンジン)には掛かりません。
- claimの`remaining_budget_usd`は`null`で、workerはSDKに`maxBudgetUsd`を渡しません。SDKは知らないmodelを独自の推定単価で計算し、予算でturnを切るからです。縛る予算がないので、`/clear`などでSDKのコスト集計が再開しても、workerはdrainしません。
- `GET /v1/sessions/{id}/usage`は`cost.kind: "unmetered"`で答えます。`amount_usd`は`"0.000000"`です。このセッションにはコスト上限が適用されないので、`cost_limit_usd`は`null`です。上限到達の案内(`attention.reason`)にもドル上限は出ません。`budget_exceeded`は、token上限に届いたときだけ`true`になります。
- 課金の有無は、セッションを作るときにセッション行(`sessions.unmetered`)に固定されます。価格、claimの予算、usage表示はこの値を読み、報告を受け取ったAPIのカタログは見ません。そのため、rolling update中にそのprofileを知らないreplicaが報告を受け取っても、コストは付きません。`billing`を変えるとfingerprintが変わるので、新しいidで追加します(同じidを直すと、既存のセッションは`CATALOG_MISMATCH`になります)。
- `none`のprofileでセッションを作るのは、すべてのAPI replicaとすべてのschedulerの`WORKER_IMAGE`をこのバージョンに上げた後にします。古いAPIは`unmetered`セッションの報告も価格表で計算し、古いworkerはclaimの`remaining_budget_usd: null`を契約違反として拒否してエンジンを起動できません。同じ理由で、`unmetered`セッションが残っている間は、APIとworkerを古いバージョンに戻しません。
- token上限(`SESSION_TOKEN_LIMIT`)と、時間・並行数の上限(`MAX_TURN_SECONDS`、`EXECUTION_SLOT_LIMIT`、`QUEUED_INPUT_LIMIT_PER_SESSION`)はそのまま掛かります。`unmetered`の行のtokenも`sessions.provider_tokens`に足されます。
- APIが`none`を受け付けるのは、endpoint hostがプライベートアドレス(10/8、172.16/12、192.168/16、100.64/10、127/8、169.254/16、`::1`、fc00::/7、fe80::/10)であるか、公開DNSにない名前(ドットのないcomposeサービス名、`localhost`、`.internal`・`.local`・`.localhost`・`.lan`・`.home.arpa`)のときだけです。それ以外では起動しません。egress proxy側では、そのhostを`EGRESS_CREDENTIAL_PRIVATE_ALLOWLIST`に置きます。
- プライベートアドレスは必要条件にすぎません。プライベートネットワークのLiteLLMも、有料のupstreamを代理できます。`none`の宣言が正しいかどうかは運用者の責任です。誤って宣言すると、有料の呼び出しがコスト上限なしで出ていきます。`SESSION_TOKEN_LIMIT`を設定しておけば、その場合もセッションあたりのtokenは縛られます。Datadogの`werft.provider.unmetered_tokens_1h`(直近1時間の`unmetered`行のtoken合計)と、providerコンソールの使用量を合わせて見てください。

## API設定

APIは、インストール上限のほかに、次の値を起動時に1つのparser(`apps/control-host/src/api/api-settings.ts`)で読みます。設定しなければ既定値を使います。設定したのに誤った値(空文字を含む)なら、既定値には戻りません。数値の設定は、API・scheduler・reconciler・worker・インストール上限のすべてがこの規則に従います(`packages/contracts/src/shared/settings.ts`)。既定値のない値は、設定しなければ`X is required`、誤った値は`X must be a positive integer`のように、期待する範囲を書いて拒否します。受け取った値は書きません。ログに残り、別の変数に誤って入れた秘密かもしれないからです。このとき`Refusing to start: API settings are invalid`の1行に問題をすべて残し、起動しません。起動中のAPIの`/readyz`も、同じ検証を`config`チェックとしてもう一度行います。

| 変数 | 既定値 | 許容範囲 |
|---|---|---|
| `HEARTBEAT_TTL_SEC` | 30 | 20を超え86400以下。workerはleaseが切れる10秒前にleaseを手放し(`WORKER_LEASE_SAFETY_MARGIN_SEC`)、5秒ごとにheartbeatを送ります(`WORKER_HEARTBEAT_INTERVAL_SEC`。以前のバージョンのworkerは10秒)。マージンと10秒の合計以下だと、以前のバージョンのworkerのattemptが最初のheartbeatのころにleaseを失います。launcherは2つのworker値を渡さないので、既定値を基準に判定します |
| `PENDING_REQUEST_TTL_SEC` | 1800 | 整数1–604800。承認・質問のリクエストを受け付ける期間です。登録されたリクエストを、workerはこの値だけ待ちます。workerの`QUESTION_TIMEOUT_SEC`は、gatewayが登録を確認する前にだけ適用されます。turnの実時間`MAX_TURN_SECONDS`には待ち時間も含まれるので、待ちはその上限を超えられません |
| `SSE_MAX_STREAMS` · `SSE_MAX_STREAMS_PER_OWNER` · `SSE_REPLAY_MAX_BYTES` | 256 · 8 · 1 MiB | 正の整数 |
| `LOG_LEVEL` | `info` | `debug`・`info`・`warn`・`error`(大文字小文字は無関係、空は`info`)。schedulerとreconcilerのloop、egress-proxyも、同じ規則で起動を拒否します。workerはschedulerの値を受け取ります |
| `WEB_DIST_DIR` | なし(Webコンソールを配信しません)。control-hostイメージは`/app/apps/web/dist` | `index.html`のある絶対パス。Webコンソール(`apps/web`)のビルド結果です |

すべての`/v1`応答は`api.request.completed`を残します。実際のidを含まないHonoの`route_template`、`method`、`status`、認証とrouteの処理を含む`duration_ms`、`operation=api_request`、`outcome`、`reason_code`があり、`request_id`はlog contextにあります。リクエストbody・credential・provider keyは入れません。terminateリクエストは、同じ`request_id`で`Terminate control transaction completed`も残し、ここにはpool checkout、binding・launch・session lock、各SQL、commitまたはrollback、control transaction全体のミリ秒計測が入ります。デプロイ環境で受付の遅延を調べるときは、2つのログを`request_id`で結び付けて、どの段階が遅かったかを判断します。

terminateがすでに消えたexecutionに対してすぐ終わったとき、またはschedulerやreconcilerがexecutionの不在を確認したときは、`control.result`が`operation=terminate`、receipt idである`control_id`、`outcome`、`reason_code`、durableな受付から確認までの`effect_ms`(`duration_ms`と同じ)を残します。期限を超えたreceiptは、まず`outcome=unknown`・`reason_code=deadline_exceeded`を残し、その後executionの不在を確認してreceiptを成功に上げたときは、`outcome=succeeded`・`reason_code=execution_gone`の結果を追加で残します。

`WEB_DIST_DIR`があると、APIがWebコンソールを同じoriginで配信します。`/v1`と`/internal`の外のGETとHEADは、そのディレクトリのファイルを返し、ファイルがなければ`index.html`を返します(SPA fallback)。そのため、`/login`や`/bootstrap`を再読み込みしても画面が開きます。`/v1`と`/internal`の下にはfallbackしません。認証済みの`/v1/nope`はJSONの`404 NOT_FOUND`です。`/assets/`の下のファイルは、content hash付きの名前なので`immutable`でキャッシュし、存在しないassetにはページではなく404を返します。`index.html`は`no-cache`で、inline scriptを許さないCSP(`script-src 'self'`)が付きます。control-hostイメージは、`web`のbuild stageで`apps/web`をビルドし、`dist/`だけを含めます。別のwebイメージはありません。ローカルでWebだけを直すときは、`bun run --cwd apps/web dev`(Vite。`/v1`を`VITE_API_TARGET`、既定`http://127.0.0.1:3000`にproxyします)を使います。

`AUTH_MODE=none`は、egress authorizer(`EGRESS_AUTHORIZER_PORT`)と一緒には使えません。authorizerが有効ということは、workerがproxyを経由してこのAPIに届くという意味です。`none`モードでは、worker内のコードが`X-Owner-Id`で任意のownerになりすませるので、起動を拒否します。`AUTH_MODE`の値そのもの(`none`か`api-key`)は、readinessが判定します。

workerも起動時に交差検査をします。`WORKER_PROVIDER_MAX_RETRIES`がなければ起動しません。コードに既定値のないインストール上限で、schedulerが必ず渡します。`WORKER_NEXT_INPUT_WAIT_SEC`が`WORKER_REQUEST_TIMEOUT_SEC`以上でも起動しません。その設定では、すべてのlong pollがリクエストtimeoutで切れるからです。schedulerとreconcilerは、空の`DATABASE_URL`を未設定とみなして`QUEUE_DATABASE_URL`を使います。

APIとslack roleは、`WORKER_IMAGE_RUNTIME`と`WORKER_IMAGE_PREVIOUS_RUNTIME`で、現在と直前のworkerイメージのランタイムの組み合わせを読みます。値は手で書かず、images.ymlが残したworker digest JSONの`runtime`フィールドをそのまま入れます(`{"engine":…,"sdkVersion":…,"cliVersion":…,"profileDigestScheme":…}`)。`engine`は今のところ`claude`だけで、chartは別の名前をレンダリング時に`images.worker.runtime.engine must be one of: claude`で拒否します。自分でビルドしたイメージには、そのJSONがありません。images.ymlと同じコマンドで、イメージから読みます。

```bash
docker run --rm -i --network none --entrypoint bun <worker-image> \
  run apps/worker/src/image-runtime.ts <<<'{}' | jq -c 'del(.profiles)'
```

どちらもなければ、これまでどおり動きます。`WORKER_IMAGE_PREVIOUS_RUNTIME`だけがある場合や、値を読めない場合は起動しません。設定すると、profileの`runtime_version`を次のイメージバージョンに上げても、直前のイメージバージョンで作られた開いているセッションのprofile pinが維持されます。現在のイメージが載せていない`runtime_version`のprofileは、新しいセッションを受け付けません。そのため、SDKを上げるリリースは、上限ごとに`runtime_version`を上げた新しいバージョンを一緒に作ります(コンソール、または`POST /v1/installation-profiles`)。

APIとslack roleは、`SESSION_PROMPT_REVISION`(既定0、許容値は0と1、誤った値なら起動しません)で、エージェントreleaseセッションのsystem promptの冒頭の段落を決めます。1なら、新しいセッションは作るときに、エージェントの名前・説明、開始した場所(Slackのチャンネル・DM、Webコンソール、API)、カードの言語、セッションリポジトリのGitHub名(`owner/repo`)を`sessions.platform_prompt`に残し、workerがそれで段落を作ります。段落に役割の文はありません。役割はエージェントの作成者が指示文に書きます。GitHubの案内は、設定の有無に関係なく1段落です。GitHubの作業は組み込みの`mcp__github__`ツールで行い、使えるリポジトリは`list_repositories`が答えると伝えます。`git push`はGitHubに届かないことも伝えます。そのツールがない、またはGitHubを使えないと答えた場合は、「このセッションではGitHubの作業はできません。管理者がコンソールのエージェントのGitHubタブで設定し、新しいセッションが必要な場合があります」と答えさせます。GitHub設定のないreleaseで始めたセッションには、後で設定してもツールが付かないからです。0なら、新しいセッションも段落がありません(この設定の前と同じ)。保存した値は、セッションが終わるまで変わりません。段落はcheckpoint fingerprintに入るので、エージェントの名前・説明やreleaseを変えても、進行中のセッションはそのまま再開されます。

有効にする順序: migration(`0229_session_platform_prompt`) → claimを処理するすべてのAPI replicaとすべてのworkerイメージ(現在・直前)をこのバージョン以上にデプロイ → 1に設定。古いworkerはこの値を載せたclaimを拒否し、古いAPIはこの値をclaimに載せないので、新しいworkerが段落なしで動き、そのセッションのcheckpointが再開されません。0に戻すと、新しいセッションだけ段落がなくなります。すでに1で作ったセッションは、段落を受け取り続けます。1を有効にした後で、APIやworkerをこのバージョンより前に戻すことはサポートしません。ローカルのcompose(`infra/compose.local.yml`)は、API・slack・workerを1つのtreeからビルドするので、1を既定にしています。

GitHub Packagesのbot token([決定](https://github.com/JeongJaeSoon/werft/blob/main/docs/contributing/decisions/github-packages-bot-token.md))を別のhostに送る必要があるときだけ、次の値を置きます。GitHub Enterprise Serverやテスト用の偽レジストリがそうです。値はhttp(s)のURLで、userinfo・query・fragmentがあるとAPIは起動しません。レジストリのhostは、proxyの`EGRESS_CREDENTIAL_ALLOWLIST`(プライベートアドレスなら`EGRESS_CREDENTIAL_PRIVATE_ALLOWLIST`)にも必要です。

| 変数 | 既定値 | 意味 |
|---|---|---|
| `GITHUB_PACKAGES_API_URL` | `https://api.github.com` | 登録するtokenのscopeを問い合わせる先(`GET /user`) |
| `GITHUB_PACKAGES_NPM_URL` | `https://npm.pkg.github.com` | `github-npm` routeのupstream |
| `GITHUB_PACKAGES_RUBYGEMS_URL` | `https://rubygems.pkg.github.com` | `github-rubygems` routeのupstream |

`WERFT_API_KEY`と`WERFT_BASE_URL`はサーバー設定ではありません。TypeScript SDK(`packages/sdk`)を使う呼び出し側のスクリプトが読む値で、SDKの例は`WERFT_PROFILE_ID`と`WERFT_REPOSITORY_ID`も読みます([クライアント設定とエラー](/getting-started/client))。

## scheduler・workerコンテナ・egressの設定

schedulerがworkerコンテナを作るときに読む値です。なければ既定値を使い、形式が誤っていれば起動しません。user、HOMEとworkspaceのパス、tmpfsのサイズ、credentialのポート、stop timeoutは、`agent-platform.isolation`のフィンガープリントに入ります([実行基盤とworkerの隔離](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/execution.md#reconcilerscheduler와-worker-격리))。そのため、変えると実行中のworkerが入れ替わります。CPU・メモリ・PIDの上限は、次のlaunchから適用されます。

`WORKER_MEMORY_MB`は、transcript上限(`MAX_TRANSCRIPT_BYTES`)と一緒に決めた値です。2つの関係、実測、ノードあたりのセッション数、変え方は[容量管理](/run-server/self-hosting/operate/capacity)にあります。

schedulerは、`WORKER_IMAGE`と`WORKER_IMAGE_RUNTIME`で現在のイメージを、`WORKER_IMAGE_PREVIOUS`と`WORKER_IMAGE_PREVIOUS_RUNTIME`で直前のリリースのイメージを受け取ります。ランタイムの値はAPIと同じです(上のAPI設定)。直前のイメージは2つの値を一緒に設定し、片方だけなら起動しません。`WORKER_IMAGE_RUNTIME`がなければ、今までどおり、すべてのlaunchが`WORKER_IMAGE`で起動します。設定すると、launchごとに、セッションのcheckpointポインタが記録した組み合わせ(engine・SDK・CLI・profile digest scheme)に合うイメージを選び、両方合えば現在のイメージを使います。新しいセッション、checkpointのないセッション、組み合わせを記録していない古いcheckpointは、現在のイメージで起動します。どのイメージとも合わないセッションはworkerを起動せず、`recovery_required`(`incompatible_checkpoint`)で止まり、セッションイベント`checkpoint_restore_failed`に`detected_at: "launch"`が残ります。`retry_restore`でやり直せます。

workerはclaimのとき、自分のイメージが実際に載せている組み合わせを送ります。設定した組み合わせと違えば、APIがclaimを拒否し(`LAUNCH_FAILED`、`reason_code`は`worker_image_mismatch`)、そのイメージをその設定値に対して拒否されたものとして記録します。その後、そのイメージで起動するはずのセッションはlaunchされずに待ち、scheduler passは`images_refused`をerrorログに残してexit 1で終わります。イメージの設定を直せば(値が変われば)、次のpassから再びlaunchします。セッション自体は失敗にはなりません。

デプロイ順序: 新しいworkerは、claimに`image_runtime`を載せます。このフィールドを知らない古いAPIはリクエストを拒否するので、APIを先に上げてから、schedulerの`WORKER_IMAGE`を新しいイメージに変えます。

| 変数 | 既定値 | 意味 |
|---|---|---|
| `WORKER_CPUS` | 1 | workerの1つあたりのCPU割り当て。0.01以上 |
| `WORKER_MEMORY_MB` | 4608 | workerの1つあたりのメモリ上限(MiB)。圧縮なしの512 MiBのtranscriptをresumeしたエンジンが、上限の半分未満に収まるように決めた値です |
| `WORKER_PIDS_LIMIT` | 512 | workerの1つあたりのPID上限。composeは渡しません |
| `EXECUTION_DOCKER_USER` | `1000:1000` | workerの数値`uid[:gid]`。uidまたはgidが0なら起動を拒否します。workerイメージの`/workspace`の所有者と同じである必要があります |
| `EXECUTION_DOCKER_HOME_DIR` | `/home/worker` | tmpfsとしてマウントするHOME。絶対パス |
| `EXECUTION_DOCKER_WORKSPACE_DIR` | `/workspace` | セッションvolumeをマウントする場所。絶対パスでHOMEと異なり、空白とバックスラッシュは使えません。workerには`WORKER_WORKSPACE_DIR`として渡ります |
| `EXECUTION_DOCKER_TMPFS_SIZE_MB` | 256 | HOMEと`/tmp`のtmpfsそれぞれのサイズ(MiB) |
| `EXECUTION_DOCKER_STOP_TIMEOUT_SEC` | 120 | SIGTERMからSIGKILLまでの猶予。30未満なら起動を拒否します。workerには`WORKER_STOP_GRACE_SEC`として渡り、workerはdrainをその中に収めます |
| `EXECUTION_DOCKER_REQUEST_TIMEOUT_SEC` | 30 | Docker Engine APIリクエスト1つの期限 |
| `EXECUTION_DOCKER_COMMAND` | なし | イメージのentrypointの代わりに実行するコマンド(空白で分割します)。テスト用です |
| `DOCKER_HOST` | `unix:///var/run/docker.sock` | Docker daemonのアドレス |
| `DOCKER_API_VERSION` | `v1.44` | リクエストに使うEngine APIのバージョン |
| `EXECUTION_EGRESS_CREDENTIAL_PORT` | 3129 | proxy credential routeのポート。proxyの`EGRESS_CREDENTIAL_PORT`と同じで、`EXECUTION_EGRESS_PROXY_URL`のポートとは違う必要があります |

`EXECUTION_DOCKER_NETWORK`と`EXECUTION_DOCKER_NETWORK_ALLOWLIST`は、もう読みません。値があると起動を拒否します。

egress-proxyとAPIのauthorizer listenerは、次の値を読みます。

| 変数 | 既定値 | 意味 |
|---|---|---|
| `EGRESS_PROXY_HOST` | `0.0.0.0` | proxyの2つのlistener(forwardとcredential route)が開くアドレス |
| `EGRESS_PROXY_PORT` | 3128 | forward proxyのポート |
| `EGRESS_CREDENTIAL_PORT` | 3129 | credential routeのポート |
| `LOG_LEVEL` | `info` | proxyのログレベル。規則は上のAPI設定と同じです |
| `EGRESS_AUTHORIZER_HOST` | `0.0.0.0` | APIのauthorizer listener(`EGRESS_AUTHORIZER_PORT`)が開くアドレス |

composeの3つのポートと2つの内部URLは、`infra/compose.core.yml`の先頭にある`x-egress-ports`の1か所で決めます。proxyの`EGRESS_PROXY_PORT`・`EGRESS_CREDENTIAL_PORT`・`EGRESS_AUTHORIZER_URL`、apiの`EGRESS_AUTHORIZER_PORT`、schedulerの`EXECUTION_EGRESS_PROXY_URL`・`EXECUTION_EGRESS_CREDENTIAL_PORT`は、すべてそのanchorを使います。ポートを変えるときは、同じブロックのlistenerとURLの組を一緒に変えます。`tests/images.test.ts`が、`docker compose config`の結果で、2つのURLのポートと3つのlistenerが合っているかを確認します。

APIコンテナのメモリは、checkpoint bundleの検証が決めます。検証は同時に2つまで動き、検証ごとにgit fetchとindex-packがそれぞれ`CHECKPOINT_GIT_MEMORY_MB`のアドレス空間上限の下で一緒に動きます。2つの値は一緒に変えます。上限だけを上げると、OOM killerが何を殺すかを決めることになります。計算は`infra/compose.core.yml`のapiサービスのコメントにあります。

| 変数 | 既定値 | 意味 |
|---|---|---|
| `API_MEMORY_MB` | 7168 | compose apiコンテナの`mem_limit`(MiB) |
| `CHECKPOINT_GIT_MEMORY_MB` | 1536 | bundle検証のgitプロセス1つのアドレス空間上限(MiB)。512未満なら起動を拒否します |

composeのPostgresは、`POSTGRES_USER`(`postgres`)・`POSTGRES_PASSWORD`(`dev`)・`POSTGRES_DB`(`sessions`)で作り、すべてのサービスが同じ値でDSNを作ります。

workerは、次の値もenvとして読みます。ただし、schedulerが渡さないので、運用ではコードの既定値で固定です。`WORKER_ANSWER_POLL_SEC`(1)、`WORKER_ATTACH_FETCH_TIMEOUT_SEC`(300。セッション途中で付けたリポジトリ1つを取得する時間)、`WORKER_ATTACH_FETCH_MAX_MB`(2048。そのリポジトリを取得したscratch mirrorのサイズ)、`WORKER_CLAIM_TIMEOUT_SEC`(60)、`WORKER_DRAIN_TIMEOUT_SEC`(100。stopの猶予の中に収まるよう縮みます)、`WORKER_HEARTBEAT_INTERVAL_SEC`(5)、`WORKER_IDLE_TIMEOUT_SEC`(1800)、`WORKER_LEASE_SAFETY_MARGIN_SEC`(10)、`WORKER_NEXT_INPUT_RETRY_SEC`(60)、`WORKER_NEXT_INPUT_WAIT_SEC`(20)、`WORKER_REQUEST_TIMEOUT_SEC`(30)、`WORKER_STARTUP_TIMEOUT_SEC`(3600)、`QUESTION_TIMEOUT_SEC`(1800)、`WORKER_CLAUDE_CONFIG_DIR`(`$HOME/.claude`)。
