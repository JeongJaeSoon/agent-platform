This page lists the installation limits, the API settings, and the scheduler, worker container and egress settings. The settings of the reconciler and scheduler supervision loops are in [Execution base and worker isolation](/run-server/self-hosting/operate/execution). Connections, storage, limits (console and settings document) and authentication settings are in [API server](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md). The Kubernetes backend settings are in [Kubernetes execution backend](/run-server/self-hosting/operate/kubernetes-backend).

## Installation limits

The API and the scheduler refuse to start, and log every problem on one line, when any of the six values below (all but `SESSION_TOKEN_LIMIT`) is missing or when any value has the wrong format. A missing `SESSION_TOKEN_LIMIT` is read as 0 (no limit). Both processes use the same parser (`packages/platform/src/limits/installation-limits.ts`). Apart from the 0 of `SESSION_TOKEN_LIMIT`, the code has no defaults; the `x-installation-limits` block of compose supplies the local defaults. The `/readyz` of a running API repeats the same validation as the `config` check.

| Variable | Meaning | When exceeded |
|---|---|---|
| `EXECUTION_SLOT_LIMIT` | The number of workers that hold a slot at the same time. At 0 the platform accepts input but starts nothing | Input is not rejected; it stays `queued` |
| `QUEUED_INPUT_LIMIT_PER_SESSION` | The number of `queued` turns one session may hold | `429 RATE_LIMITED`, `retryable:true`, `Retry-After: 5` |
| `STORAGE_LIMIT_BYTES` | The UTF-8 bytes of input messages the whole installation keeps. Events, checkpoint objects and worker disk are not counted (the workspace quota covers disk) | `413 STORAGE_LIMIT_EXCEEDED`, `retryable:false` |
| `MAX_TURN_SECONDS` | The wall-clock limit of one turn, including time spent waiting for approval. Passed to the worker as env `WORKER_MAX_TURN_SEC` | The turn is `failed(turn_timeout)`. If the engine does not respond, `outcome_unknown(turn_timeout)` |
| `SESSION_COST_LIMIT_USD` | The accumulated cost of the session (the usage of each Messages call, metered by the egress proxy and converted with the platform price table; an estimate) | No new turn is dispatched. The session detail shows `attention.code=BUDGET_EXCEEDED` and the worker returns its slot. Input is still accepted as `queued` |
| `SESSION_TOKEN_LIMIT` | The accumulated provider tokens of the session. It counts the same calls as the cost limit but does not depend on unit prices. 0 means no limit (default) | Same as `SESSION_COST_LIMIT_USD`. Both limits go through the same check (`budgetExceeded`), and whichever is reached first gives `BUDGET_EXCEEDED`. `attention.reason` names only the limit that was reached |
| `PROVIDER_MAX_RETRIES` | How many times a failed Messages request is sent again. Passed through the worker env `WORKER_PROVIDER_MAX_RETRIES` to the SDK as `CLAUDE_CODE_MAX_RETRIES`. At 0 the turn ends on the first failure | The turn is `failed(api_error)`. `api_error_status`, `provider_error` and `last_retry_status` are kept in the `result` of the turn detail |

- The credential route counts the session cost. The proxy reads usage from a 2xx `/v1/messages` response (both JSON and SSE). When the response ends or is cut off, it reports to `POST /usage` of the authorizer listener. `count_tokens` and error responses are not counted.
  - When a response does not state all of its usage, the platform estimates high. For a stream cut off before `message_stop`, each delivered character of content counts as one output token, and each delivered web search result block counts as one search. A JSON response whose usage could not be read (cut off, over 8 MiB, not JSON) is counted from the request: 1 byte of request is one input token, and `max_tokens` is taken as all of the output. For such a call the proxy logs a `Provider usage estimated` warning and the ledger records `estimated=true`.
  - The API computes USD with the price table and rounds up to micro-dollars. It writes the amount to `provider_usage`, one row per exchange, and adds it to the session cost in the same transaction. So the ledger total and the session cost agree.
  - Calls made by the engine, and calls a tool makes directly with the engine's token, are counted the same way.
  - Each report carries an id the proxy made for the exchange. If the authorizer cannot answer, the proxy sends it again after 1, 5 and 15 seconds, and the same id is counted once. If it can never report, the proxy logs a `Provider usage went unreported` error and that exchange is not counted.
- The `total_cost_usd` increment that the SDK reports at the end of a turn stays in the turn result (`cost_usd`) only and is not added to the session cost. The engine's per-turn `maxBudgetUsd` is still judged on the SDK value. A session created before the proxy metered cost carries over the cost it had added from the SDK value until then.
- The price table belongs to the platform code (`packages/platform/src/limits/model-prices.ts`). It holds input, output, cache write (1.25× for 5 minutes, 2× for 1 hour) and cache read unit prices per model id. It is updated with a release when a model is added or a price changes.
  - Fast mode is counted with a separate fast price table. For now it has only Opus 5.5 ($8/$40) and Opus 5 and Opus 4.8 ($10/$50). The cache multipliers apply on top of the fast price. The speed follows `usage.speed` of the response, then `speed` of the request if the response does not say; if neither does, it is `standard`.
  - A model that is not in the table, a fast response of a model with no fast price, and a speed value that is not a known name are each priced at the highest unit price across both tables. The authorizer logs a `Provider usage priced at the fallback rate` warning and the ledger records `priced_by=fallback`.
  - Each web search in `usage.server_tool_use` of the response adds $0.01 ($10 per 1,000). Web fetch has no charge beyond tokens. Code execution is not added: it is free when used together with web search or web fetch, and otherwise it is billed by container time rather than by calls, with a free allowance per organization. The three counts and the speed are recorded in the ledger (`provider_usage`).
  - For models after 4.6, US-only inference (`inference_geo: "us"`) multiplies every token unit price (fast and cache included) by 1.1. It does not multiply the web search charge. The geo follows `usage.inference_geo` of the response, then `inference_geo` of the request if the response does not say; if neither does, it is `unknown`, because the workspace default can be `us`. Values other than `global` and `us` are priced at the highest unit price times 1.1 (`priced_by=fallback`). The geo is recorded in the ledger as `inference_geo`. An old API that does not know `inference_geo` rejects a report with this field using `400`, and the proxy cannot count that exchange (`Provider usage went unreported`). So when you upgrade, raise the API (migrations included) before the egress proxy. One `up -d` does not keep this order, so on a compose install raise the API with `docker compose -f infra/compose.yml --profile apps up -d api` (migrate runs first), check that `curl -s http://127.0.0.1:3000/readyz` says ready, and then raise the proxy with `docker compose -f infra/compose.yml --profile apps up -d egress-proxy`. The new API also accepts reports from an old proxy that lacks this field.
  - Models before 4.6 (Opus 4.5 and 4, Sonnet 4.5 and 4, Haiku 4.5) do not accept `inference_geo`, so they are priced at the standard unit price whatever the geo. Their window is 200K and there is no published long-context price. So a call whose input, cache write and cache read add up to more than 200K is priced at the highest unit price (`priced_by=fallback`). For models after 4.6 the whole 1M is at the standard price.
  - Batch does not apply, because the credential route does not open `/v1/messages/batches`.
- The token limit counts `input_tokens + cache_creation_input_tokens + cache_read_input_tokens + output_tokens` of each `provider_usage` row by adding them to `sessions.provider_tokens`. The `provider_usage` insert trigger does the addition in the same transaction. So a call recorded by an API older than 0127 during a rollout, or after a rollback, is not missed. Cache reads count too, because they are tokens the model processed. A high estimate is added as the estimate. The migration that added this total fills the value of existing sessions from the sum of `provider_usage`. The tokens of a session whose cost was counted only from SDK values before that cannot be filled in. The total stops at 2^53-1 (`Number.MAX_SAFE_INTEGER`) (migration 0129). The trigger adds as numeric, so even an abnormally large token value does not raise an error that rolls back the usage record and the cost.
  - The SDK has no token budget option. So the token limit during a turn rests on the egress rejection and the re-authorization below. A Messages call opened after the limit is reached is rejected and the turn ends `failed(budget_exceeded)`; from the next turn on, dispatch is refused with `BUDGET_EXCEEDED`. The proxy passes the authorizer's `BUDGET_EXCEEDED` rejection in the Messages error format (`message` starts with `BUDGET_EXCEEDED:`). The reason is not decided from this text. The engine reports this 403 as `api_error`, and an exchange cut off by re-authorization is also reported as the cut connection, `api_error`, when no retry is left (`PROVIDER_MAX_RETRIES=0`). When a turn ended with `api_error` and its session is already over the limit, finalize records the reason as `budget_exceeded` and the receipt error as `BUDGET_EXCEEDED`, and clears the engine's provider diagnostic (`provider_error`). A 403 below the limit stays `api_error`.
- The cost limit and the token limit are judged after a call ends. Calls that are open at the same time can all pass authorization, and a turn in progress can go over the limit.
- The authorizer rejects the provider egress token of a session whose accumulated cost or accumulated tokens are at or over the limit with 403 `BUDGET_EXCEEDED`. A new provider exchange is rejected at once, and an exchange that is already open is cut at the next re-authorization (every 30 seconds). Repository and object store routes are not rejected.

### Profiles without billing (`billing: none`)

A self-hosted model (Ollama, LiteLLM on a private network and so on) has no per-token charge. It is not in the price table either, so left as is it is priced at the highest fallback unit price, and the turn is cut by `SESSION_COST_LIMIT_USD` and the SDK `maxBudgetUsd`. Declare such a profile with `provider.billing: none`.

```yaml
provider:
  kind: litellm
  endpoint: http://litellm:4000
  billing: none
  auth:
    kind: bearer
    value_env: LITELLM_MASTER_KEY
```

- When omitted, it is `per_token`. A profile that omits it and a profile that says `per_token` have the same fingerprint, and both are priced from the price table and the fallback.
- A provider call in a session made from a `none` profile costs 0 whatever model name the response gives, and the ledger records `priced_by=unmetered`. Tokens are still recorded. The session cost does not grow, so the four places that judge the cost limit (egress authorization, `nextInput`, message intake, the engine) never trigger.
- `remaining_budget_usd` in the claim is `null`, and the worker does not pass `maxBudgetUsd` to the SDK. The SDK prices a model it does not know with its own estimated unit price and cuts the turn against the budget. There is no budget to bind, so the worker does not drain even when the SDK's cost accounting restarts with `/clear` and the like.
- `GET /v1/sessions/{id}/usage` answers `cost.kind: "unmetered"`. `amount_usd` is `"0.000000"`. The cost limit does not apply to this session, so `cost_limit_usd` is `null`. The notice for reaching a limit (`attention.reason`) does not show a dollar limit either. `budget_exceeded` becomes `true` only when the token limit is reached.
- Whether a session is billed is fixed in the session row (`sessions.unmetered`) when the session is created. Pricing, the claim budget and the usage display read this value, not the catalog of the API that received the report. So during a rolling update, a replica that does not know the profile adds no cost when it receives a report. Changing `billing` changes the fingerprint, so add the profile under a new id (editing the same id turns existing sessions into `CATALOG_MISMATCH`).
- Create sessions from a `none` profile only after every API replica and the `WORKER_IMAGE` of every scheduler are at this version. An old API prices the reports of an `unmetered` session from the price table, and an old worker rejects `remaining_budget_usd: null` in the claim as a contract violation and cannot start the engine. For the same reason, do not roll the API or worker back to an old version while `unmetered` sessions remain.
- The token limit (`SESSION_TOKEN_LIMIT`) and the time and concurrency limits (`MAX_TURN_SECONDS`, `EXECUTION_SLOT_LIMIT`, `QUEUED_INPUT_LIMIT_PER_SESSION`) still apply. The tokens of an `unmetered` row are also added to `sessions.provider_tokens`.
- The API accepts `none` only when the endpoint host is a private address (10/8, 172.16/12, 192.168/16, 100.64/10, 127/8, 169.254/16, `::1`, fc00::/7, fe80::/10) or a name that is not in public DNS (a compose service name without a dot, `localhost`, `.internal`, `.local`, `.localhost`, `.lan`, `.home.arpa`). Otherwise it does not start. On the egress proxy side, put that host in `EGRESS_CREDENTIAL_PRIVATE_ALLOWLIST`.
- A private address is only a necessary condition. LiteLLM on a private network can also front a paid upstream. Whether the `none` declaration is right is the operator's responsibility. If it is wrong, paid calls go out with no cost limit. If you set `SESSION_TOKEN_LIMIT`, tokens per session are still bound. Watch the Datadog metric `werft.provider.unmetered_tokens_1h` (the sum of tokens of `unmetered` rows in the last hour) together with the usage in the provider console.

## API settings

Besides the installation limits, the API reads the values below at startup with one parser (`apps/control-host/src/api/api-settings.ts`). A value that is not set uses its default. A value that is set but wrong (an empty string included) does not fall back to the default. Numeric settings of the API, scheduler, reconciler, worker and the installation limits all follow this rule (`packages/contracts/src/shared/settings.ts`). A value with no default is refused with `X is required` when missing, and a wrong value is refused with the expected range, such as `X must be a positive integer`. The value received is not printed: it would end up in the log and could be a secret put in the wrong variable. All problems go on one `Refusing to start: API settings are invalid` line and the API does not start. The `/readyz` of a running API repeats the same validation as the `config` check.

| Variable | Default | Allowed range |
|---|---|---|
| `HEARTBEAT_TTL_SEC` | 30 | Over 20 and up to 86400. The worker gives up its lease 10 seconds before it ends (`WORKER_LEASE_SAFETY_MARGIN_SEC`) and sends a heartbeat every 5 seconds (`WORKER_HEARTBEAT_INTERVAL_SEC`; 10 seconds for a worker of an earlier version). At or below the sum of the margin and 10 seconds, the attempt of an earlier-version worker loses its lease around its first heartbeat. The launcher does not pass the two worker values, so the check uses the defaults |
| `PENDING_REQUEST_TTL_SEC` | 1800 | Integer 1–604800. How long approval and question requests are accepted. A registered request is waited on by the worker for this long. The worker's `QUESTION_TIMEOUT_SEC` applies only before the gateway confirms the registration. The turn wall clock `MAX_TURN_SECONDS` includes the wait, so the wait cannot exceed that limit |
| `SSE_MAX_STREAMS` · `SSE_MAX_STREAMS_PER_OWNER` · `SSE_REPLAY_MAX_BYTES` | 256 · 8 · 1 MiB | Positive integers |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn`, `error` (case-insensitive; empty means `info`). The scheduler and reconciler loops and the egress-proxy refuse to start by the same rule. The worker receives the scheduler's value |
| `WEB_DIST_DIR` | None (the web console is not served). The control-host image uses `/app/apps/web/dist` | An absolute path that contains `index.html`. The build output of the web console (`apps/web`) |

Every `/v1` response logs `api.request.completed`. It has the Hono `route_template` (without real ids), `method`, `status`, `duration_ms` (including authentication and route handling), `operation=api_request`, `outcome` and `reason_code`; `request_id` is in the log context. The request body, credentials and provider keys are not included. A terminate request also logs `Terminate control transaction completed` with the same `request_id`, which carries millisecond timings for the pool checkout, the binding, launch and session locks, each SQL statement, the commit or rollback, and the whole control transaction. When you investigate acceptance latency in a deployment, join the two logs on `request_id` to see which step was slow.

When a terminate ends at once on an execution that is already gone, or when the scheduler or reconciler confirms that the execution is absent, `control.result` logs `operation=terminate`, `control_id` (the receipt id), `outcome`, `reason_code`, and `effect_ms` from the durable acceptance to the confirmation (the same as `duration_ms`). A receipt past its deadline first logs `outcome=unknown` and `reason_code=deadline_exceeded`; if the absence of the execution is confirmed later and the receipt is raised to success, it logs another result with `outcome=succeeded` and `reason_code=execution_gone`.

When `WEB_DIST_DIR` is set, the API serves the web console from the same origin. For GET and HEAD outside `/v1` and `/internal`, it returns the file in that directory, and returns `index.html` when there is no such file (SPA fallback). So reloading `/login` or `/bootstrap` still opens the screen. Under `/v1` and `/internal` there is no fallback. An authenticated `/v1/nope` is a JSON `404 NOT_FOUND`. Files under `/assets/` have content-hashed names, so they are cached as `immutable`, and a missing asset gets a 404 instead of the page. `index.html` is `no-cache` and carries a CSP that forbids inline scripts (`script-src 'self'`). The control-host image builds `apps/web` in the `web` build stage and keeps only `dist/`. There is no separate web image. To work on the web alone locally, use `bun run --cwd apps/web dev` (Vite, which proxies `/v1` to `VITE_API_TARGET`, default `http://127.0.0.1:3000`).

`AUTH_MODE=none` cannot be used together with the egress authorizer (`EGRESS_AUTHORIZER_PORT`). A running authorizer means workers reach this API through the proxy. In `none` mode, code inside a worker could act as any owner with `X-Owner-Id`, so startup is refused. The `AUTH_MODE` value itself (`none` or `api-key`) is judged by readiness.

The worker also runs cross-checks at startup. It does not start without `WORKER_PROVIDER_MAX_RETRIES`; this is an installation limit with no default in the code, and the scheduler always passes it. It also does not start when `WORKER_NEXT_INPUT_WAIT_SEC` is at or above `WORKER_REQUEST_TIMEOUT_SEC`, because with that setting every long poll is cut by the request timeout. The scheduler and the reconciler treat an empty `DATABASE_URL` as not set and use `QUEUE_DATABASE_URL`.

The API and the slack role read the runtime combination of the current and previous worker images from `WORKER_IMAGE_RUNTIME` and `WORKER_IMAGE_PREVIOUS_RUNTIME`. Do not write the value by hand: put in the `runtime` field of the worker digest JSON that images.yml leaves (`{"engine":…,"sdkVersion":…,"cliVersion":…,"profileDigestScheme":…}`). `engine` is only `claude` for now, and the chart rejects any other name at render time with `images.worker.runtime.engine must be one of: claude`. An image you built yourself has no such JSON. Read it from the image with the same command images.yml uses.

```bash
docker run --rm -i --network none --entrypoint bun <worker-image> \
  run apps/worker/src/image-runtime.ts <<<'{}' | jq -c 'del(.profiles)'
```

With neither set, the runtime combination is not read, so the pin below does not apply. With only `WORKER_IMAGE_PREVIOUS_RUNTIME`, or a value that cannot be read, the process does not start. When set, even if you raise the `runtime_version` of a profile to the next image version, the profile pin of open sessions created with the previous image version stays. A profile whose `runtime_version` the current image does not carry accepts no new session. So a release that raises the SDK also creates, for each limit, a new version with a raised `runtime_version` (in the console or with `POST /v1/installation-profiles`).

The API and the slack role set the opening paragraph of the system prompt of agent release sessions with `SESSION_PROMPT_REVISION` (default 0, allowed values 0 and 1, a wrong value stops startup). At 1, a new session stores in `sessions.platform_prompt`, when it is created, the agent name and description, where it started (a Slack channel or DM, the web console, the API), the card language, and the GitHub name of the session repository (`owner/repo`), and the worker builds the paragraph from it. The paragraph has no sentence about the role. The agent author writes the role in the instructions. The GitHub guidance is one paragraph whether or not GitHub is configured. It says that GitHub work is done with the built-in `mcp__github__` tools and that `list_repositories` answers which repositories are available. It also says that `git push` does not reach GitHub. If those tools are absent or say GitHub cannot be used, the agent is made to answer that "GitHub work is not possible in this session; an administrator configures it in the console's agent GitHub tab, and a new session may be needed". This is because a session started from a release without GitHub settings does not get the tools even if they are configured later. At 0, new sessions also have no paragraph. The stored value does not change until the session ends. The paragraph is part of the checkpoint fingerprint, so changing the agent name, description or release does not stop an in-progress session from resuming.

The order to turn it on: migration (`0229_session_platform_prompt`) → deploy every API replica that handles claims and every worker image (current and previous) at this version or later → set 1. An old worker rejects a claim that carries this value, and an old API does not put this value into the claim, so a new worker runs without the paragraph and the checkpoint of that session does not resume. Setting 0 again removes the paragraph only for new sessions. Sessions already made at 1 keep receiving the paragraph. After turning on 1, rolling the API or worker back to a version before this one is not supported. Local compose (`infra/compose.local.yml`) builds the API, slack and worker from one tree, so it defaults to 1.

Set the values below only when the GitHub Packages bot token ([decision](https://github.com/JeongJaeSoon/werft/blob/main/docs/contributing/decisions/github-packages-bot-token.md)) has to go to another host. GitHub Enterprise Server and a fake registry for tests are such cases. A value is an http(s) URL, and the API does not start if it has userinfo, a query or a fragment. The registry host must also be in the proxy's `EGRESS_CREDENTIAL_ALLOWLIST` (`EGRESS_CREDENTIAL_PRIVATE_ALLOWLIST` for a private address).

| Variable | Default | Meaning |
|---|---|---|
| `GITHUB_PACKAGES_API_URL` | `https://api.github.com` | Endpoint used to check the scopes of the registered token (`GET /user`) |
| `GITHUB_PACKAGES_NPM_URL` | `https://npm.pkg.github.com` | The upstream of the `github-npm` route |
| `GITHUB_PACKAGES_RUBYGEMS_URL` | `https://rubygems.pkg.github.com` | The upstream of the `github-rubygems` route |

`WERFT_API_KEY` and `WERFT_BASE_URL` are not server settings. They are read by caller-side scripts that use the TypeScript SDK (`packages/sdk`), and the SDK examples also read `WERFT_PROFILE_ID` and `WERFT_REPOSITORY_ID` ([Client settings and errors](/getting-started/client)).

## Scheduler, worker container and egress settings

These are the values the scheduler reads when it creates a worker container. A missing value uses its default, and a wrongly formatted one stops startup. The user, the HOME and workspace paths, the tmpfs size, the credential port and the stop timeout go into the `agent-platform.isolation` fingerprint ([Execution base and worker isolation](/run-server/self-hosting/operate/execution#reconciler-scheduler-and-worker-isolation)). So changing them replaces the running workers. The CPU, memory and PID limits apply from the next launch.

`WORKER_MEMORY_MB` is set together with the transcript limit (`MAX_TRANSCRIPT_BYTES`). Their relation, the measurements, sessions per node and how to change them are in [Capacity](/run-server/self-hosting/operate/capacity).

The scheduler takes the current image from `WORKER_IMAGE` and `WORKER_IMAGE_RUNTIME`, and the image of the previous release from `WORKER_IMAGE_PREVIOUS` and `WORKER_IMAGE_PREVIOUS_RUNTIME`. The runtime values are the same as the API's (the API settings above). Set both for the previous image; with only one, startup is refused. Without `WORKER_IMAGE_RUNTIME`, every launch uses `WORKER_IMAGE`. When set, each launch picks the image that matches the combination (engine, SDK, CLI, profile digest scheme) that the session's checkpoint pointer recorded, and uses the current image when both match. A new session, a session without a checkpoint, and an old checkpoint that did not record the combination start on the current image. A session that matches no image starts no worker and stops at `recovery_required` (`incompatible_checkpoint`), and the session event `checkpoint_restore_failed` carries `detected_at: "launch"`. You can try again with `retry_restore`.

At claim time the worker sends the combination its own image really carries. If it differs from the configured one, the API rejects the claim (`LAUNCH_FAILED`, `reason_code` `worker_image_mismatch`) and records that image as refused for that setting. Sessions that would start on that image are not launched afterwards and wait, and the scheduler pass logs `images_refused` as an error and ends with exit 1. When you correct the image setting (the value changes), launches resume from the next pass. The session itself does not turn into a failure.

Deployment order: a new worker puts `image_runtime` in the claim. An old API that does not know this field rejects the request, so raise the API first and then change the scheduler's `WORKER_IMAGE` to the new image.

| Variable | Default | Meaning |
|---|---|---|
| `WORKER_CPUS` | 1 | The CPU share of one worker. At least 0.01 |
| `WORKER_MEMORY_MB` | 4608 | The memory limit of one worker (MiB). Set so that the engine that resumes an uncompressed 512 MiB transcript stays under half of the limit |
| `WORKER_PIDS_LIMIT` | 512 | The PID limit of one worker. Compose does not pass it |
| `EXECUTION_DOCKER_USER` | `1000:1000` | The numeric `uid[:gid]` of the worker. Startup is refused if the uid or gid is 0. It must match the owner of `/workspace` in the worker image |
| `EXECUTION_DOCKER_HOME_DIR` | `/home/worker` | HOME, mounted as tmpfs. An absolute path |
| `EXECUTION_DOCKER_WORKSPACE_DIR` | `/workspace` | Where the session volume is mounted. An absolute path that differs from HOME, with no spaces or backslashes. It goes to the worker as `WORKER_WORKSPACE_DIR` |
| `EXECUTION_DOCKER_TMPFS_SIZE_MB` | 256 | The size (MiB) of each of the HOME and `/tmp` tmpfs |
| `EXECUTION_DOCKER_STOP_TIMEOUT_SEC` | 120 | The grace from SIGTERM to SIGKILL. Startup is refused below 30. It goes to the worker as `WORKER_STOP_GRACE_SEC`, and the worker fits its drain inside it |
| `EXECUTION_DOCKER_REQUEST_TIMEOUT_SEC` | 30 | The deadline of one Docker Engine API request |
| `EXECUTION_DOCKER_COMMAND` | None | A command to run instead of the image entrypoint (split on spaces). For tests |
| `DOCKER_HOST` | `unix:///var/run/docker.sock` | The Docker daemon address |
| `DOCKER_API_VERSION` | `v1.44` | The Engine API version used in requests |
| `EXECUTION_EGRESS_CREDENTIAL_PORT` | 3129 | The port of the proxy credential route. It must equal the proxy's `EGRESS_CREDENTIAL_PORT` and differ from the port of `EXECUTION_EGRESS_PROXY_URL` |

`EXECUTION_DOCKER_NETWORK` and `EXECUTION_DOCKER_NETWORK_ALLOWLIST` are no longer read. Startup is refused if either has a value.

The egress-proxy and the API's authorizer listener read the values below.

| Variable | Default | Meaning |
|---|---|---|
| `EGRESS_PROXY_HOST` | `0.0.0.0` | The address the two proxy listeners (forward and credential route) open on |
| `EGRESS_PROXY_PORT` | 3128 | The forward proxy port |
| `EGRESS_CREDENTIAL_PORT` | 3129 | The credential route port |
| `LOG_LEVEL` | `info` | The proxy log level. The rule is the same as in the API settings above |
| `EGRESS_AUTHORIZER_HOST` | `0.0.0.0` | The address the API's authorizer listener (`EGRESS_AUTHORIZER_PORT`) opens on |

The three ports and the two internal URLs of compose are decided in one place, `x-egress-ports` at the top of `infra/compose.core.yml`. The proxy's `EGRESS_PROXY_PORT`, `EGRESS_CREDENTIAL_PORT` and `EGRESS_AUTHORIZER_URL`, the api's `EGRESS_AUTHORIZER_PORT`, and the scheduler's `EXECUTION_EGRESS_PROXY_URL` and `EXECUTION_EGRESS_CREDENTIAL_PORT` all use that anchor. When you change a port, change the listener and URL pairs in the same block together. `tests/images.test.ts` checks, in the output of `docker compose config`, that the ports of the two URLs and the three listeners match.

The memory of the API container is set by checkpoint bundle verification. Up to two verifications run at once, and in each one the git fetch and the index-pack run together, each under an address-space limit of `CHECKPOINT_GIT_MEMORY_MB`. Change the two values together. If you raise only the limit, the OOM killer decides what dies. The calculation is in the comment of the api service in `infra/compose.core.yml`.

| Variable | Default | Meaning |
|---|---|---|
| `API_MEMORY_MB` | 7168 | The `mem_limit` (MiB) of the compose api container |
| `CHECKPOINT_GIT_MEMORY_MB` | 1536 | The address-space limit (MiB) of one bundle-verification git process. Startup is refused below 512 |

The compose Postgres is created with `POSTGRES_USER` (`postgres`), `POSTGRES_PASSWORD` (`dev`) and `POSTGRES_DB` (`sessions`), and every service builds its DSN from the same values.

The worker also reads the values below from env. But the scheduler does not pass them, so in operation they are fixed at the code defaults: `WORKER_ANSWER_POLL_SEC` (1), `WORKER_ATTACH_FETCH_TIMEOUT_SEC` (300, the time to fetch one repository attached during a session), `WORKER_ATTACH_FETCH_MAX_MB` (2048, the size of the scratch mirror that holds that repository), `WORKER_CLAIM_TIMEOUT_SEC` (60), `WORKER_DRAIN_TIMEOUT_SEC` (100, shortened to fit inside the stop grace), `WORKER_HEARTBEAT_INTERVAL_SEC` (5), `WORKER_IDLE_TIMEOUT_SEC` (1800), `WORKER_LEASE_SAFETY_MARGIN_SEC` (10), `WORKER_NEXT_INPUT_RETRY_SEC` (60), `WORKER_NEXT_INPUT_WAIT_SEC` (20), `WORKER_REQUEST_TIMEOUT_SEC` (30), `WORKER_STARTUP_TIMEOUT_SEC` (3600), `QUESTION_TIMEOUT_SEC` (1800), `WORKER_CLAUDE_CONFIG_DIR` (`$HOME/.claude`).
