プラットフォームがPostgreSQL 16に張る接続数とセッション設定、そして遅いクエリとロック待ちの見方を説明します。composeのインストールはPostgresを自分で起動するので、サーバー設定もcomposeが入れます。Helmのインストールは運用者が用意したDBを使うので、サーバー設定は運用者が有効にします。コードが貢献者に求めるルール(トランザクションの範囲、ロックの順序、migration)は[開発ガイドのDB利用ルール](https://github.com/JeongJaeSoon/werft/blob/main/docs/contributing/development.md#db-사용-규칙)にあります。

## ロールごとの接続数

すべてのロールは`packages/db/src/pool.ts`の`createEnforcedPool`でプールを作ります。プールの上限はロールごとに違います。

| ロール | プール上限 | 理由 |
|---|---|---|
| api | 10 + readiness probe 1 + LISTEN 1 | リクエストを同時に処理します。probeは自分のプール(上限1)を使い、リクエストと接続を取り合いません。イベント通知を受けるLISTEN接続(`werft:api-listen`)はプールの外に1本置きます。 |
| metrics | 10 | 1回のscrapeが集計7件を同時に読みます。 |
| scheduler | 4 | passは文を1つずつ出します。pass lockが接続をもう1本握ります。 |
| reconciler | 4 | passは文を1つずつ出します。 |
| slack | 4 | inboxとoutboxを順に空にします。 |
| checkpoint GC、upgrade check、migrate、運用者CLI(`keys`・`grants`など) | 10 | 短時間動いて終わります。 |

Helmの既定値(api 2、slack 1、scheduler・reconciler 1、metricsオフ)で開いたままになり得る接続は、api 24 + scheduler 4 + reconciler 4 + slack 4 = 36本です。`metrics.enabled`をオンにすると10本、GC・upgrade check・migrateのjobが重なると最大30本が加わります。composeはapi 12 + scheduler 4 + reconciler 4 + slack 4 = 24本です。PostgreSQLの既定`max_connections`は100で、そのうち3本はsuperuser用です。apiやslackのreplicaを増やすときは、replica 1つにつき12本(slackは4本)を足して`max_connections`と比べます。マネージドDBはインスタンスサイズによって`max_connections`が100より小さいことがあるので、その値を確認してください。

## 接続ごとに設定するセッション設定

`createEnforcedPool`が接続を開くときに設定します。`DATABASE_URL`に同名のquery parameterがあっても、timeoutはコードの値が優先されます。

| 設定 | api・jobの値 | migrateの値 | 意味 |
|---|---|---|---|
| 接続待ち(`connectionTimeoutMillis`) | 5秒 | 5秒 | プールが空かなければ、この時間の後に失敗します。apiは503を返します。 |
| `statement_timeout` | 10秒 | 300秒 | サーバーが文をキャンセルします。ロックを待つ時間も含みます。 |
| 応答読み取り(`query_timeout`) | 20秒 | 330秒 | サーバーが答えないソケットをクライアントが捨てます。 |
| `idle_in_transaction_session_timeout` | 30秒 | 30秒 | トランザクションを開いたまま30秒間文を出さない接続をサーバーが切ります。その接続が握っていたロックも解放されます。 |
| `application_name` | `werft:<ロール>` | `werft:migrate` | `pg_stat_activity`とサーバーログでロールを見分けます。`DATABASE_URL`に`application_name`があればその値を使います。 |

ロールごとの開いている接続数はDBで見ます。composeは`docker compose -f infra/compose.yml exec postgres psql -U postgres -d sessions`で入り、Helmは運用者のDBクライアントを使います。

```sql
SELECT application_name, state, count(*)
  FROM pg_stat_activity
 WHERE application_name LIKE 'werft:%'
 GROUP BY 1, 2 ORDER BY 1, 2;
```

セッション設定はその接続にだけ掛かるので、運用者の`psql`で`SHOW`すると、サーバーの既定値が見えます。プラットフォーム接続の値は、apiコンテナ(Helmではapi Pod)の中で同じプールを使って読みます。

```bash
docker compose -f infra/compose.yml exec -T -w /app/apps/control-host api bun -e '
import { createLogger } from "@werft-ai/observability";
import { createApiPool } from "./src/api/pool.ts";
const pool = createApiPool(process["env"]["DATABASE_URL"], createLogger());
const { rows } = await pool.query(
  "SELECT current_setting($1) AS statement_timeout, current_setting($2) AS idle_in_transaction, current_setting($3) AS application_name",
  ["statement_timeout", "idle_in_transaction_session_timeout", "application_name"],
);
console.log(JSON.stringify(rows[0]));
await pool.end();'
# {"statement_timeout":"10s","idle_in_transaction":"30s","application_name":"werft:api"}
```

Helmでは`docker compose … exec -T -w /app/apps/control-host api`の代わりに、`kubectl -n werft exec deploy/werft-api -- sh -c 'cd /app/apps/control-host && bun -e …'`で同じスクリプトを実行します。release名が`werft`でなければ、namespaceとdeployment名をそのインストールのものに替えます。

## 遅いクエリとロック待ちの見方

### compose

`infra/compose.core.yml`のpostgresは、次を有効にして起動します。

- `log_min_duration_statement=500ms`: 500msを超えた文を、本文と時間つきでログに残します。`POSTGRES_LOG_MIN_DURATION_STATEMENT`で変更でき、`-1`でオフになります。
- `log_lock_waits=on`: `deadlock_timeout`(1秒)より長く待ったロックを、そのロックを握っているPIDと一緒に残します。
- `shared_preload_libraries=pg_stat_statements`: 文ごとの累積統計を集めます。見るには最初に一度`CREATE EXTENSION IF NOT EXISTS pg_stat_statements;`を実行します。

```bash
docker compose -f infra/compose.yml logs postgres | grep -E 'duration:|still waiting'
```

```sql
SELECT calls, round(mean_exec_time::numeric, 1) AS mean_ms,
       round(total_exec_time::numeric) AS total_ms, left(query, 120)
  FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 20;
```

この設定を変えると、postgresコンテナが作り直されます。データは`postgres-data` volumeに残ります。

### Helm(運用者のDB)

chartはDBを作らないので、サーバー設定も変えません。運用者がDBのパラメータに次を設定します。RDS・Auroraはparameter groupで変更し、`shared_preload_libraries`はインスタンスを再起動すると反映されます。

| パラメータ | 値 |
|---|---|
| `log_min_duration_statement` | `500` (ms) |
| `log_lock_waits` | `on` |
| `shared_preload_libraries` | 既存の値に`pg_stat_statements`を追加 |

そのあと、プラットフォームのDBで`CREATE EXTENSION IF NOT EXISTS pg_stat_statements;`を一度実行します。拡張を作る権限(RDSは`rds_superuser`)が必要です。migrationは拡張を作りません。権限のないインストールでもmigrateが失敗しないようにするためです。

ログはDBがログを残す場所(RDSはCloudWatch Logsの`postgresql`ログ)で、`duration:`と`still waiting`を探します。kind確認環境(`deploy/kind/deps.yaml`)のPostgresは、この表の値で起動します。

## migrationがロックする時間

migrate jobは1文あたり最大300秒かかります。migrateが2つ重なると(手で実行した`db:migrate`とHelm hook Jobなど)、後のほうは先のほうが終わるまで待ってから、残りのmigrationだけを適用します。Helm hook Jobは`migrate.activeDeadlineSeconds`(既定600秒)が過ぎると終わります。大きくなるテーブルにインデックスを作るmigrationは、`CREATE INDEX CONCURRENTLY`で書き込みを止めずに作ります。テーブルが大きくて300秒を超えそうなときは、そのmigrationのリリースノートが別に知らせます。`CONCURRENTLY`のインデックスは、開始時に開いていたトランザクションがすべて終わるのを待つので、長く開いたままの運用者セッション(`psql`で開いたままの`BEGIN`)があると、その分遅れます。
