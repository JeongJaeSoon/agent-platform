This page describes how the scheduler behaves, and what it reads, when it runs workers as Kubernetes Pods instead of Docker containers. The steps to install with the Helm chart are in [Kubernetes install (Helm chart)](/run-server/self-hosting/operate/kubernetes-deployment). The Docker backend is described in [Execution base and worker isolation](/run-server/self-hosting/operate/execution).

`packages/adapters/execution/kubernetes` creates one worker Pod per launch. Each Pod gets one nonce Secret that it owns, and the session's workspace PVC is mounted.

The scheduler picks the backend with `EXECUTION_BACKEND`. The values are `local_docker` (the default; an empty value means the same) and `kubernetes`. Any other value stops startup with an error that names it. With `kubernetes`, the scheduler does not read the Docker settings (`DOCKER_HOST`, `EXECUTION_DOCKER_*`, `EXECUTION_WORKSPACE_QUOTA`) and does not use the Docker socket. The Docker-only preflight checks, the egress proxy isolation check and the workspace quota probe, do not run either. On Kubernetes the chart's NetworkPolicy isolates workers, and the workspace limit is the PVC size. The stop and request timeouts are fixed (120 s + 30 s), so `SCHEDULER_PASS_TIMEOUT_SEC` must be greater than 150. `migrate-workspace` moves Docker volumes, so it runs only with `local_docker`.

In a Pod with a read-only root filesystem, put the status file on a writable path. The default paths `/tmp/scheduler-status.json` and `/tmp/reconciler-status.json` work as they are when you mount an emptyDir on `/tmp`. For another path, set `SCHEDULER_STATUS_FILE` and `RECONCILER_STATUS_FILE`. The loop writes a temporary file (`<status file>.<pid>.tmp`) in the same directory as the status file and then renames it. The scheduler also keeps a `.quota-verified` record next to it. So the whole directory must be writable, not just one file.

The shared env (`WORKER_IMAGE`, `WORKER_GATEWAY_URL`, `EXECUTION_EGRESS_PROXY_URL`, `EXECUTION_EGRESS_CREDENTIAL_PORT`, `EXECUTION_INSTALLATION_ID`, `EXECUTION_WORKSPACE_QUOTA_MB`, `EXECUTION_WORKSPACE_GC_MIN_AGE_SEC`, `S3_BUCKET`, `AWS_REGION`) is the same as for the Docker backend. In kubernetes mode, two of these values carry extra constraints.

- `WORKER_IMAGE` must have the form `repository@sha256:<digest>`.
- `EXECUTION_INSTALLATION_ID` must be a lowercase DNS label of at most 32 characters.

These settings are read in kubernetes mode only.

| Variable | Meaning |
| --- | --- |
| `EXECUTION_K8S_NAMESPACE` | The namespace for worker Pods, Secrets and PVCs. The default is the scheduler's own namespace. Required when the scheduler runs outside the cluster. |
| `EXECUTION_K8S_WORKER_SERVICE_ACCOUNT` | The ServiceAccount of the worker Pod. The token is never mounted. |
| `EXECUTION_K8S_STORAGE_CLASS` | The StorageClass of the workspace PVC. When empty, the cluster default is used. |
| `EXECUTION_K8S_IMAGE_PULL_SECRETS` | Optional. Secret names, comma-separated. |
| `EXECUTION_K8S_WORKER_NODE_SELECTOR` | Optional. A JSON object. |
| `EXECUTION_K8S_WORKER_TOLERATIONS` | Optional. A JSON array. |
| `EXECUTION_K8S_WORKER_EPHEMERAL_STORAGE_MB` | The ephemeral-storage requests and limits (MB) of the worker container. Default 1024. The kubelet evicts the Pod when it goes over. |

The exit reason and the log tail (last 8 KiB) of a failed worker go to the `Execution resource failed; log tail kept` line in the scheduler log. Where they are stored and how long they stay is in `packages/adapters/execution/kubernetes/README.md` in the repository (the section on exit reasons and log tails).

## Values the chart sets

When you install with the Helm chart (`deploy/helm/werft`; the steps are in [Kubernetes install (Helm chart)](/run-server/self-hosting/operate/kubernetes-deployment)), you do not write the env above yourself. The chart builds it from the values.

| env | values | Note |
| --- | --- | --- |
| `EXECUTION_BACKEND` | none | Always `kubernetes` |
| `EXECUTION_K8S_WORKER_SERVICE_ACCOUNT` | none | `<fullname>-worker`, created by the chart. The token is not mounted |
| `EXECUTION_K8S_NAMESPACE` | none | Not set. It becomes the scheduler's own namespace (the release namespace) |
| `EXECUTION_K8S_STORAGE_CLASS` | `worker.storageClass` | Not set when empty |
| `EXECUTION_K8S_IMAGE_PULL_SECRETS` | `images.pullSecrets` | The control plane Pods use the same Secrets |
| `EXECUTION_K8S_WORKER_NODE_SELECTOR`, `EXECUTION_K8S_WORKER_TOLERATIONS` | `worker.nodeSelector`, `worker.tolerations` | Converted to JSON |
| `WORKER_IMAGE` | `images.registry`, `images.worker.*` | `<registry>/<repository>@<digest>`. Rendering fails without a digest |
| `WORKER_GATEWAY_URL`, `EXECUTION_EGRESS_PROXY_URL`, `EXECUTION_EGRESS_CREDENTIAL_PORT` | none | Port 3000 of the api Service, ports 3128 and 3129 of the egress-proxy Service |
| `EXECUTION_INSTALLATION_ID` | `installationId` | Also the label value of the worker NetworkPolicy |
| `EXECUTION_WORKSPACE_QUOTA_MB`, `EXECUTION_WORKSPACE_GC_MIN_AGE_SEC` | `worker.workspace.*` | The quota is the size of the workspace PVC |
| `WORKER_CPUS`, `WORKER_MEMORY_MB` | `worker.cpus`, `worker.memoryMb` | |
| `EXECUTION_K8S_WORKER_EPHEMERAL_STORAGE_MB` | `worker.ephemeralStorageMb` | Default 1024 |
| Install limits (`EXECUTION_SLOT_LIMIT` and so on) | `config.limits` | The same value for api and scheduler |
| `SCHEDULER_*` | `scheduler.intervalSec` and so on | `SCHEDULER_PASS_TIMEOUT_SEC` (`scheduler.passTimeoutSec`, default 180) must be greater than 150 |
| `SLACK_ROLE_INTERVAL_SEC`, `SLACK_ROLE_PASS_TIMEOUT_SEC`, `SLACK_ROLE_MAX_CONSECUTIVE_FAILURES`, `SLACK_ROLE_HEALTH_STALE_SEC`, `SLACK_ROLE_BATCH_SIZE`, `SLACK_ROLE_LEASE_SEC` | `slack.intervalSec`, `slack.passTimeoutSec`, `slack.maxConsecutiveFailures`, `slack.healthStaleSec`, `slack.batchSize`, `slack.leaseSec` | Defaults 2, 60, 3, 90, 10, 60. With `slack.enabled: false` the slack Deployment is not rendered |
| `PLATFORM_ALLOW_UNATTENDED_PERMISSIONS` (slack) | `api.extraEnv` | slack reads the same catalog as the api, so it follows the api's value. A value in `slack.extraEnv` wins |

You can add env to any Deployment with `extraEnv`. The values that come from Secrets (`DATABASE_URL`, `EGRESS_AUTHORIZER_TOKEN`, the AWS key, catalog credentials) are in the table of the [preparation section of Kubernetes install (Helm chart)](/run-server/self-hosting/operate/kubernetes-deployment#prerequisites).

## Probes

| Component | readiness | liveness | startup |
| --- | --- | --- | --- |
| api | `GET /readyz` | `GET /healthz` | `GET /healthz` (5 s × 24) |
| scheduler | `bun run apps/control-host/src/main.ts scheduler --health` | same | same. The allowed failure count is `(intervalSec + passTimeoutSec + 39) / 10` |
| reconciler | `bun run apps/control-host/src/main.ts reconciler --health` | same | same formula as scheduler |
| slack | `bun run apps/control-host/src/main.ts slack --health` | same | same formula as scheduler |
| egress-proxy | `bun run /app/src/healthcheck.ts` | same | none |

`/healthz` only checks that the process accepts HTTP and does not look at the database. That is why it is used for liveness, and `/readyz`, which checks the database, schema and settings, is used for readiness only. If the database drops for a moment, the api Pod is not restarted; it only leaves the traffic. There is no `/livez`. The `--health` of scheduler, reconciler and slack reads the status file the loop writes. It fails when the last pass failed, ran past its deadline, or when no pass finished within `SCHEDULER_HEALTH_STALE_SEC`, `RECONCILER_HEALTH_STALE_SEC` or `SLACK_ROLE_HEALTH_STALE_SEC`. The startup probe waits until the first pass ends.

## One scheduler replica, `Recreate`

Scheduler passes are serialized by one PostgreSQL advisory lock (`pg_try_advisory_lock`). A second scheduler cannot get the lock and skips its pass. With no successful pass, its `--health` goes stale and liveness keeps restarting that Pod. More replicas do not add throughput. So the chart fixes `replicas: 1` (there is no key for it in the values), and the rollout is `Recreate`, not `RollingUpdate`, so the old Pod goes down first. Passes pause for a moment during an upgrade. The reconciler re-checks each pass under a row lock, so you can raise `reconciler.replicas` without leader election; the default is 1.

## Worker NetworkPolicy

The chart's NetworkPolicy replaces the per-execution internal network of the Docker backend. A worker Pod (`app.kubernetes.io/part-of=agent-platform`, `app.kubernetes.io/component=worker`, `agent-platform.installation=<installationId>`) accepts no connection, and it connects out only to ports 3128 and 3129 of the egress-proxy. It cannot reach the database, the api, other workers or the node and cloud metadata addresses directly. Even the gateway requests to the api go through the proxy. The egress-proxy accepts connections only from workers, and the api's authorizer (3100) accepts them only from the egress-proxy. If the cluster CNI does not enforce NetworkPolicy, this isolation does not exist (kindnet in kind enforces it; on EKS, turn on the network policy agent of the VPC CNI).

## API server authentication

The scheduler authenticates to the API server with `KUBECONFIG` when it is set, and otherwise with the Pod's ServiceAccount. The ServiceAccount path reads `KUBERNETES_SERVICE_HOST`, `KUBERNETES_SERVICE_PORT` and the token and CA files. The Role verbs of the scheduler and the pidsLimit handling are in `packages/adapters/execution/kubernetes/README.md` in the repository.
