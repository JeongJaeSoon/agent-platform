このドキュメントは、サーバーデプロイで確認する最小の監視基準です。Kubernetes(Helm)インストールでプラットフォームが出すメトリクスは、[プラットフォームのメトリクス(Kubernetes)](https://jeongjaesoon.github.io/werft/ja/run-server/self-hosting/operate/metrics/)にあります。アプリにDatadog SDKやOTelは入れません。Datadog Agentが、DockerのJSON stdoutログ、`/readyz`、読み取り専用のPostgreSQL query、ホストのメトリクスを収集します。定義は[`infra/datadog/definitions`](https://github.com/JeongJaeSoon/werft/tree/main/infra/datadog/definitions)だけでバージョン管理し、このリポジトリのツールやCIはDatadog APIを呼び出しません。

すべてのしきい値は、**サーバーデプロイ後の最初の7日間で調整する初期値**です。`threshold_stage:first-week-tuning` tagが付いたmonitorを、最初の週のデータなしに長期の基準とみなしません。すでに埋めた空白は`なし`、その範囲外のためサーバーデプロイ後に優先度を決め直す項目は`デプロイ後に判断`と表記します。

## 起動とシークレットの管理

Agentは、選択式の[`infra/compose.datadog.yml`](https://github.com/JeongJaeSoon/werft/blob/main/infra/compose.datadog.yml)でだけ作られます。このファイルを指定しない既定のstackには、Agent、mount、label、必須の環境変数が1つも追加されません。Agentのimageは`gcr.io/datadoghq/agent:7.83.3`に固定します。

`DD_API_KEY`とDatadog用のPostgreSQL passwordは、リポジトリやshell historyに入れません。サーバーで運用者が`/etc/agent-platform/datadog.env`を作り、mode 600を確認します。別の絶対パスを使う必要があるときだけ`DATADOG_ENV_FILE`で変えます。値は例のプレースホルダーなので、実際の値をドキュメント・チケット・ログにコピーしません。

```dotenv
DD_API_KEY=<operator-supplied>
DD_SITE=datadoghq.com
DD_ENV=alpha
DD_VERSION=<release-sha>
DD_POSTGRES_PASSWORD=<read-only-role-password>
```

```bash
sudo chown root:root /etc/agent-platform/datadog.env
sudo chmod 600 /etc/agent-platform/datadog.env
stat -c '%a %U:%G' /etc/agent-platform/datadog.env
```

Agent serviceは、この絶対パスを`env_file`としてだけ読みます。compose YAMLには`DD_API_KEY`の名前も値のinterpolationもないので、ambientの`DD_API_KEY`で迂回できません。`DD_ENV`と`DD_VERSION`は、同じファイルをcomposeの2つ目の`--env-file`として読み、product containerのunified tagsに使います。

PostgreSQL roleは、`queue_messages`、`sessions`、`turns`、`attempts`、`provider_usage`に`SELECT`だけを許可し、既定のtransactionをread-onlyに固定します。次のコマンドは、サーバーの運用者がadmin connectionで1回実行します。

```sql
CREATE ROLE datadog LOGIN PASSWORD :'datadog_password';
ALTER ROLE datadog SET default_transaction_read_only = on;
GRANT CONNECT ON DATABASE sessions TO datadog;
GRANT USAGE ON SCHEMA public TO datadog;
GRANT SELECT ON TABLE queue_messages, sessions, turns, attempts, provider_usage TO datadog;
```

既存のデプロイコマンドのlayerはそのままにして、最後の`-f`でこのoverlayだけを加え、`--env-file`に上のファイルをもう1つ渡します。エントリーファイル`infra/compose.yml`の上に加える形は次のとおりです。

```bash
docker compose \
  --env-file /etc/agent-platform/datadog.env \
  -f infra/compose.yml \
  -f infra/compose.datadog.yml \
  --profile apps up -d
```

この形を、リポジトリのcomposeファイルで`docker compose config`まで確認しました。overlayを加えると、サービス一覧に`datadog-agent`が1つ増えるだけで、既存のサービスは変わりません。`DD_ENV`や`DD_VERSION`がないと、レンダリングが拒否されます。実際のサーバーで`up`まで実行し、AgentがDatadogに報告することは確認していません(NOT VERIFIED)。

Agentは、Docker socketとcontainer log directoryをread-onlyでmountし、hostのPID・cgroup namespaceを読みます。`DD_LOGS_CONFIG_CONTAINER_COLLECT_ALL=true`で動的なworkerも収集します。compose serviceは`service`・`env`・`version` labelを受け取ります。動的なworkerの`service`はcontainerのshort-imageから導かれ、`env`はAgentのグローバルな`DD_ENV`から、`version`はグローバルな`DD_TAGS`から受け取ります。`session_id`・`turn_id`は調査用のログattributeとしてだけ残し、metric tagやfacetにはしません。

## シグナルと初期monitor

構造化loggerの元のrecordは、`timestamp`、`level`、機械が読む`event`、人が読む`message`、任意の`fields`、context(`session_id`など)です。log pipelineはJSONをparseし、以前のrecordに`event`がないときだけ`message`をfallbackとして使います。詳細な値は`fields.*`の下にあります。queryのmetric名は、[`log-metrics.json`](https://github.com/JeongJaeSoon/werft/blob/main/infra/datadog/definitions/log-metrics.json)とPostgreSQL custom queryが作る名前です。

| リスク | 現在のシグナル(ログevent・フィールド、DB query、readyz) | Datadog monitor(query・しきい値・ウィンドウ) | アラート時の対応runbook | 計測の空白 |
| --- | --- | --- | --- | --- |
| interrupt effectが5秒を超える | `control.result`の`fields.operation:interrupt`、`effect_ms`、`outcome`、`reason_code`、`control_id` → `werft.control.effect.duration_ms`。段階別の診断には、同じ`control_id`の`worker.turn.interrupt.stage`を使います | p95 `avg(last_5m):p95:werft.control.effect.duration_ms{operation:interrupt} > 5000`; unknownの結果 `> 0/5m` | [interrupt後に結果がわからないturn](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/execution.md#interrupt-뒤-결과를-알-수-없는-turn) | なし |
| terminate・controlの受け付け遅延 | すべての`/v1`完了の`api.request.completed`(`route_template`、`method`、`status`、`duration_ms`、`request_id`)。terminate 202は`werft.terminate.acceptance.duration_ms`にし、同じ`request_id`のcontrol transactionの段階と相関させます | p95 `avg(last_5m):p95:werft.terminate.acceptance.duration_ms{*} > 200` | [API設定のterminate計測](https://jeongjaesoon.github.io/werft/ja/run-server/self-hosting/operate/configuration/#api設定) | なし |

## DB点検queryの契約

[`infra/datadog/conf.d/postgres.d/conf.yaml`](https://github.com/JeongJaeSoon/werft/blob/main/infra/datadog/conf.d/postgres.d/conf.yaml)の`custom_queries`が正本です。どのqueryも`SELECT`1つで、tableを変更しません。

- queue oldest age: まだclaimされておらず、すでにvisibleなmessageのうち最も古い`created_at`を、DBのclockと比較します。
- checkpoint pending age: `checkpoint_pending_reason IS NOT NULL`のsessionの`updated_at`のうち最も古い値を使います。checkpointと無関係な同じsessionの更新がこの時刻を動かすことがあるので、正確なSLIではなく下限のproxyです。
- `outcome_unknown`: 直近5分に作られた`turns.outcome_unknown = true`のrow数です。
- stale lease: `exited`・`lost`でないattemptのうち、`lease_expires_at < clock_timestamp()`である数です。
- providerのコスト: 直近1時間の`cost_usd`の合計と、`priced_by = 'fallback'`のrow数です。`werft.provider.unmetered_tokens_1h`は、同じ1時間の`priced_by = 'unmetered'`のrowのトークン合計(input・output・cache write・cache read)です。`billing: none` profileはコストが0のまま残るので、有料のupstreamを誤って宣言したときに表に出るのはこのトークン数だけです。monitorは定義しません。正常値がインストールのローカルモデルの使用量に依存するためです。

どのqueryも`session_id`を返しません。[`log-metrics.json`](https://github.com/JeongJaeSoon/werft/blob/main/infra/datadog/definitions/log-metrics.json)のgroup-byも、`service`・`env`とcardinalityの低い状態だけを使います。`session_id`は、incidentで元のログやDBを絞り込むときだけ使います。

## 定義の適用と検証

定義は自動では適用されません。運用者はJSONをレビューしてから、各ファイルの`endpoint`に`requests`の項目を1つずつ適用します。[`log-facets.json`](https://github.com/JeongJaeSoon/werft/blob/main/infra/datadog/definitions/log-facets.json)は、UIで作るfacetと、作らないhigh-cardinality attributeの一覧です。[`dashboard.json`](https://github.com/JeongJaeSoon/werft/blob/main/infra/datadog/definitions/dashboard.json)はdashboardのcreate bodyです。すでに適用したmonitor・dashboard・log pipelineは再度createせず、既存のものの名前とquery・filterを新しい定義に合わせて直します。再度createすると、同じ定義が2つになります。

サーバーデプロイで次を確認します。

1. 既定のstackをoverlayなしでrender・起動したとき、service一覧と設定が以前と同じである。
2. overlayを加えた`docker compose config`が`DD_ENV`・`DD_VERSION`の欠落を拒否し、AgentのDocker socket mountが`ro`で、`/etc/agent-platform/datadog.env`だけを読む。
3. Agent statusで、Docker log、`http_check:werft-readyz`、PostgreSQL custom queryがすべて成功する。
4. `/readyz`を一時的に失敗させて、service checkが変わり、復旧することをサーバーで確認する。実際の長期stack実行とmonitor notificationの配信は、ローカルの検証証拠で代替しません。
