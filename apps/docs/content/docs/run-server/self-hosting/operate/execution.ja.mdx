reconciler・schedulerがworkerを起動して回収する方法、workerの隔離、止まったセッションの復旧、workerのworkspaceとworkerネットワークの上限と回収を記します。設定値の表は[設定リファレンス](/run-server/self-hosting/operate/configuration)に、カタログ・認証情報・認証は[APIサーバー](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md)にあります。

## reconciler・schedulerとworkerの隔離

reconciler pass(`main.ts reconciler --once`、package scriptは`reconciler`)は、1 batchだけ処理して終了します。leaseの期限は自分では解釈しません。APIがheartbeatを受け取るときに`workers.lease_expires_at`に期限の時刻を書き、reconcilerはその時刻とDBの時計を比べます。`HEARTBEAT_TTL_SEC`はAPIだけが読み(既定30、20以下または86400を超えると起動を拒否します。[API設定](/run-server/self-hosting/operate/configuration#api設定)を参照)、reconcilerはこの値が設定されていると起動しません。実際に変更する前に対象だけを確認するには、dry-runを明示します。未処理のrowまたは`queued`のturnだけを自動で再配信し、実行中のrowや状態を証明できないrowは、sessionを`failed`にして、明示的な復旧の対象として残します。

```bash
DATABASE_URL=postgres://postgres:dev@127.0.0.1:5432/sessions \
RECONCILER_DRY_RUN=true \
  bun run --cwd apps/control-host reconciler

DATABASE_URL=postgres://postgres:dev@127.0.0.1:5432/sessions \
RECONCILER_DRY_RUN=false \
  bun run --cwd apps/control-host reconciler
```

composeの`apps` profileでは、`reconciler`サービスがこのpassを既定で繰り返し実行します。role名だけを渡した`main.ts reconciler`が監督ループ(`apps/control-host/src/pass-loop`)で、passはループが起動した子プロセス(`main.ts reconciler --serve`)で動きます。子プロセスは、ループがIPCで要求するたびにpassを1つ実行し、次の要求を待ちます。passのたびにbunを新しく起動してモジュールを読み直すと、pass自体の数倍のCPUが掛かり、遊んでいるスタックでもroleが1つでコアの数十%を使っていたからです。poolは今もpassごとに新しく開いて閉じます。失敗したpass、制限時間を超えてkillされたpass、終了シグナルを受けたpassは、子プロセスと一緒に終わるので、次のpassは新しいプロセスで動きます。pass同士の間に子プロセスが死んだ場合は、失敗したpassとして数えます。passは重ならず、直列で動きます。healthcheckは`main.ts reconciler --health`です。ループがSIGTERMを受けると、新しいpassを始めず、進行中のpassにSIGTERMを送り、10秒後にSIGKILLします。書き込みはそれぞれトランザクションなので、どこで途切れても失うものはありません。compose `stop_grace_period`は20sです。composeは、監督ループを使う3つのrole(reconciler・scheduler・slack)に`BUN_OPTIONS=--smol`を渡します。ループ、子プロセス、healthcheckがすべてこの値を引き継ぎ、GCをより頻繁に回してヒープを小さく保ちます。2026-11-04のローカルスタックの測定では、コンテナあたりのメモリが5〜23MiB減り、CPUは120秒間で最大6%増えました(slack 2.2秒 → 2.3秒)。

| 設定 | 既定 | 意味 |
|---|---|---|
| `RECONCILER_INTERVAL_SEC` | 10 | passが終わってから次のpassまで休む時間 |
| `RECONCILER_PASS_TIMEOUT_SEC` | 60 | この時間を超えたpassはSIGTERM、10秒後にSIGKILLで終わらせ、失敗として数える。DBが止まったpassがpool timeoutで自ら終わる約45秒より大きくする |
| `RECONCILER_MAX_CONSECUTIVE_FAILURES` | 3 | 失敗したpassがこの回数続くと、ループがexit 1し、`restart: unless-stopped`が再起動する。それより少なければ、次のpassがそのまま再試行になる |
| `RECONCILER_HEALTH_STALE_SEC` | 90 | healthcheckは、最後に終わったpassが失敗した、進行中のpassが制限時間を超えた、この時間のあいだ成功したpassがない、のいずれかでunhealthyになる。成功の直後に止まったpassも、制限時間でそのままunhealthyになる。`RECONCILER_INTERVAL_SEC + RECONCILER_PASS_TIMEOUT_SEC`より大きくないと起動しない |
| `RECONCILER_STATUS_FILE` | `/tmp/reconciler-status.json` | ループがpassのたびに更新する状態(`lastSuccessAt`・`lastDegradedAt`・`lastFailureAt`・`lastFailureReason`・`consecutiveFailures`・`lastPassDurationMs`、進行中のpassの`passDeadlineAt`)。healthcheckが読む |
| `RECONCILER_BATCH_SIZE` | 100 | passの各段階(orphan・lease・interruptの回収、期限を超えたinterrupt・terminate receiptの`unknown`での締め、入力待ちの通知)が一度に処理するrow数の上限。残りのrowは次のpassが処理する。schedulerのterminate期限sweepはこの値を読まず、passごとに固定の上限100個ずつ処理する |

直近の成功・失敗は、`docker compose -f infra/compose.yml exec reconciler cat /tmp/reconciler-status.json`と、ログの`Reconciler pass completed`/`Reconciler pass failed`で見ます。reconcilerサービスは環境ファイルを読みません。環境ファイルによくある`HEARTBEAT_TTL_SEC`を受け取ると、起動を拒否するからです。上の値は、`docker compose`を実行するシェルで渡します。ただしcomposeは`RECONCILER_STATUS_FILE`と`RECONCILER_DRY_RUN`を渡しません。そのため、composeのreconcilerは、シェルの値に関係なく既定のパスに状態を書き、常に実際に修正します。dry-runは、上の例のようにpassを直接1回動かして確認します。reconcilerコンテナにはDocker socketがありません。reconcilerはepoch fenceと`desired_state = terminated`だけをDBに書き、コンテナの削除と不在の確認はschedulerが行います。2つのreconcilerが重なって動いても、pass の途中で再起動されても、各書き込みがrow lockの下で判定し直されるので、同じlease・interrupt・orphanを2回処理することはありません(`apps/control-host/src/reconciler/overlap.integration.test.ts`)。

passの最後の段階は、ツール呼び出しの投影です。前のpassのあとに溜まった`tool_use`・`tool_result`イベントを組にして、`tool_calls`と日別の合計`tool_call_days`に書きます。使用量API(`GET /v1/usage/tools`)は、イベントを解析し直さず、この2つの表だけを読みます。1トランザクションにつきイベント5,000個ずつ、passごとに10秒間処理し、残りは次のpassが引き継ぎます。batchが文のtimeout(10秒)に掛かると、batchを10分の1に減らして処理し直し、減らしたサイズを`tool_call_progress.batch_size`にすぐコミットします。pass timeout(60秒)がpassを切っても、次のpassはそのサイズから始めるので、最終的に1つのbatchは通り過ぎます。timeoutなしで終わったpassは、サイズを10倍ずつ戻します(設定値に届いたらNULL)。timeoutのたびに`Tool call batch timed out`のログ(`batch_size`、`retry_size`)をすぐ残し、passの終わりの`Tool calls projected`には`timed_out_batches`で回数を残します。進行位置は`tool_call_progress.applied_through`(イベントid)です。このカーソルは60秒より古いイベントまでしか進まないので、遅れてコミットされた小さいidのイベントも漏らしません。それより新しいイベントは次のpassが読み直し、もう一度適用しても結果は同じです。そのため、新しい呼び出しがAPIに見えるまでには、普通はpass 1回分(10秒余り)かかります。migrationのあとの最初のpassたちは、カーソル0から既存のイベントをすべて埋めます(backfill)。ローカルのPG16で、イベント2,000万個を休まず投影するのに約26分かかりました。passの間に`RECONCILER_INTERVAL_SEC`だけ休むので、実際にはその2倍ほど(1時間前後)かかり、そのあいだAPIのツール集計は満ちていない値です。dry-runは投影しません。

schedulerのpassもone-shotです(`main.ts scheduler --once`、package scriptは`scheduler`)。compose `scheduler`サービスは、同じ監督ループでこのpassを繰り返し実行します(`main.ts scheduler`、healthcheck `main.ts scheduler --health`)。設定は、`SCHEDULER_INTERVAL_SEC`(5)・`SCHEDULER_PASS_TIMEOUT_SEC`(180、`EXECUTION_DOCKER_STOP_TIMEOUT_SEC` + `EXECUTION_DOCKER_REQUEST_TIMEOUT_SEC`より大きくないと起動しない。kubernetes backendは[Kubernetes実行backend](/run-server/self-hosting/operate/kubernetes-backend))・`SCHEDULER_MAX_CONSECUTIVE_FAILURES`(3)・`SCHEDULER_HEALTH_STALE_SEC`(200、interval + timeoutより大きくないと起動しない)・`SCHEDULER_STATUS_FILE`(`/tmp/scheduler-status.json`、composeは渡さない)で、意味は上のreconcilerの表と同じです。ほかのpassがlockを持っているために飛ばしたpassは、exit 75で終わり、成功でも失敗でもありません。飛ばすだけが続くと成功がないので、stale時間のあとにunhealthyになります。やるべきことはすべてやったものの、今回のpassでは助けられないセッションを残したpass(launchがbackoff中の(`launch_backoff_count`)、今quarantineされた(`launch_quarantined_count`)、入れ替えの上限を使い切った(`replacement_exhausted_count`)セッション)は、exit 76(degraded)で終わります。その状態はDBにあり、再起動では解けないので、degradedは連続失敗として数えず、失敗のstreakを切ります。healthは直近のdegraded passをhealthyとして見ますが、reasonに`completed degraded`を書き、statusには`lastDegradedAt`として残ります(`lastSuccessAt`はクリーンなpassだけ)。同じpassにほかの失敗が1つでもあれば、これまでどおりexit 1です。ループがSIGTERMを受けると、進行中のpassは次の安全な地点(pass lockを失ったときに止まる場所と同じ)で止まり、それ以上予約せず、30秒以内に終わらなければkillされます。passが待っていたworkerの停止は、killされてもdaemonで続きます(Engine 25からは、要求が切れてもstopを取り消しません)。compose `stop_grace_period`は45sです。kill の意図(terminate、lease期限切れ、quarantine)を実行するとき、passはworkerがturnをdrainするのを待ちません。stopを要求して5秒以内に終わらなければ、そのコンテナを`kills_stopping_count`で数えて先に進み、失敗としては数えません。daemonはSIGTERMのあと`EXECUTION_DOCKER_STOP_TIMEOUT_SEC`が過ぎるとSIGKILLし、次のpassがコンテナが消えたことを確認してslotを返します。drainの期限を超えたclaimed workerの入れ替えと、launch intentのないorphanコンテナの停止も同じです(orphanは`orphan_stopping_count`で数え、消えるまでslotを占めます)。unclaimed workerの入れ替えは待ちます。turnがなくてすぐ終わり、入れ替えを試みるたびに入れ替えの上限を使うからです。それでも、unclaimedのコンテナを消して作り直す経路では、passが停止1つを最後まで待つことがあります。そのため、pass timeoutがstop timeout + request timeoutより小さいと、schedulerは起動を拒否します。コンテナのcreate・start要求が`EXECUTION_DOCKER_REQUEST_TIMEOUT_SEC`以内に答えを受け取れないと、コンテナができたかどうか分からないので、launchの失敗としては数えません。nonceを破棄せず、backoffも掛けません。そのpassは失敗(exit 1)で終わります。次のpassがinspectして、コンテナがあれば採用します(作られただけなら起動します)。なければ、そこで初めてlaunchの失敗として数えます。このときnonceを破棄してbackoffを掛けるので、いつまでもできないcreateがslotを握り続けず、失敗の上限でquarantineされます。破棄のあとに遅れてできたコンテナは、失敗した試行として見て消します。daemonが拒否で答えた場合(4xx・5xx)は、これまでどおりlaunchの失敗として数えます。schedulerを止めても、workerは終わりません。slotは、passがworkerの不在を確認したあとにだけ返されます。1回のpassは、① 生きている`executions` rowをDockerと突き合わせる(コンテナがなければ同じintentで作り直し、exitしていれば`terminated`を記録して削除) ② launch intentのない管理コンテナをログに残してから停止し、コンテナが消えたworkerネットワークを削除するか、proxyが外れたネットワークにつなぎ直す ③ `EXECUTION_SLOT_LIMIT`の範囲で、unassigned sessionごとにintentをコミット → コンテナを作成 ④ 終わったsessionのworkspace volumeを回収、の順に進みます。workerコンテナはDocker socketとhostのHOMEを受け取らず、envは、bootstrap claimに必要な`WORKER_EXECUTION_ID`・`WORKER_EXECUTION_GENERATION`・`WORKER_BOOTSTRAP_NONCE`・`WORKER_GATEWAY_URL`、tmpfsを指す`HOME`、egress proxyを指す`HTTP_PROXY`・`HTTPS_PROXY`・`NO_PROXY`(大文字と小文字の2つの表記。`NO_PROXY`にはproxy自身の名前が入る)、proxyのcredential routeを指す`WORKER_EGRESS_CREDENTIAL_URL`([APIサーバーのcredential routeの節](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md#provider-키와-저장소-자격-증명은-worker에-가지-않는다))、そしてobject storeの名前(`S3_BUCKET`・`AWS_REGION`と、セッションのprefix `WORKER_OBJECT_PREFIX`(`sessions/<sessionId>/`))を受け取ります。schedulerは、bucketとregionがなければ起動しません。object storeの認証情報とendpointは受け取りません。workerはproxyのobject store routeを通してだけobject storeに届き、境界はそのrouteです(同じ節)。worker側の`scopedCheckpointObjectStore`(`packages/storage`)は、prefixの外のkeyを要求の前に拒否する、早期失敗にすぎません。worker内で`@werft-ai/storage`をimportするファイルは`apps/worker/src/object-store.ts`だけで、`tests/architecture.test.ts`がこれを強制します。Docker daemonの応答がcreate要求の本文を返す場合に備えて、backendはエラーメッセージからnonceを消します。`/tmp`とHOMEのtmpfsは、workerのuid/gid所有でマウントされます。`/workspace` named volumeは、Dockerがイメージの同じパスから初期化するので、workerイメージが`/workspace`をworkerのuid所有で前もって作っておく必要があります(イメージの契約)。workerイメージ(`apps/worker/Dockerfile`)は`WORKER_IMAGE`で受け取ります。passの全体はPostgresのsession advisory lock(`scheduler:pass`)で直列化され、重なった実行はログだけを残して飛ばされます。同じDocker daemonを複数のインストールが共有する場合は、`EXECUTION_INSTALLATION_ID`をインストールごとに変えて渡します。schedulerはこの値がなければ起動しません(adapterだけがテスト用の既定値`local`を持ちます)。同じ値を使う2つのインストールがdaemonを共有すると、互いのコンテナをorphanとして回収します。

```bash
DATABASE_URL=postgres://postgres:dev@127.0.0.1:5432/sessions \
WORKER_IMAGE=werft-worker:dev \
WORKER_GATEWAY_URL=http://host.docker.internal:3000 \
EXECUTION_SLOT_LIMIT=10 \
QUEUED_INPUT_LIMIT_PER_SESSION=20 \
STORAGE_LIMIT_BYTES=1073741824 \
MAX_TURN_SECONDS=3600 \
SESSION_COST_LIMIT_USD=25 \
PROVIDER_MAX_RETRIES=2 \
EXECUTION_INSTALLATION_ID=local \
EXECUTION_EGRESS_PROXY_URL=http://egress-proxy:3128 \
EXECUTION_WORKSPACE_QUOTA=off \
  bun run --cwd apps/control-host scheduler
```

workerコンテナは、schedulerがexecutionごとに作る**専用ネットワーク**`ap-net-<installationId>-<executionId>-g<generation>`の1つにだけつながります。このネットワークは、bridge driver、`internal: true`、`EnableIPv6: false`、`com.docker.network.bridge.gateway_mode_ipv4=isolated`で作られます。Dockerはこのネットワークから外へ出る経路を作らず、host側のbridgeアドレス(IPAM gateway)も置きません。そのため、workerは、host、hostで動くプロセス、LAN、instance metadata(`169.254.169.254`)、ほかのcomposeサービス、ほかのworkerに直接届きません。このネットワークのメンバーは、worker自身とegress proxyの2つだけです。schedulerは、`agent-platform.egress-proxy=<installationId>` labelが付いた**実行中のコンテナちょうど1つ**をそのインストールのproxyと見なし、ネットワークごとに`EXECUTION_EGRESS_PROXY_URL`のhost名をaliasとして付けてconnectします。workerは`HTTP_PROXY`/`HTTPS_PROXY`でその名前を指します。proxyのアドレスがネットワークごとに違うので、`EXECUTION_EGRESS_PROXY_URL`のhostは名前でなければならず、IP literalと`localhost`は拒否します。composeの`egress-proxy`サービスはこのlabelを付けています。workerには`host.docker.internal:host-gateway`のマッピングがありません。gatewayもproxyを通ります。

遮断ポリシーは、proxyの2つのリストでバージョン管理します。`EGRESS_ALLOWLIST`は公開の宛先(`host:port`)で、解決されたアドレスがすべてpublic unicastであれば通ります。`EGRESS_PRIVATE_ALLOWLIST`は、プライベート帯域にあると分かった上で許可する宛先(gateway)です。composeの既定値は、`EGRESS_ALLOWLIST`が空で、`EGRESS_PRIVATE_ALLOWLIST`が`api:3000,host.docker.internal:3000`です。provider・リポジトリ・object storeは、どちらのリストにも置きません。forward proxyで届くと、それぞれのcredential routeを迂回するからです。providerには、workerが持つ任意のkeyでコスト計測の外から届き、publicなリポジトリはtokenなしで読め、object storeにはAPIが各要求を検証して署名するrouteを通らなければなりません。ローカルのSeaweedFSもSigV4を検査しますが、ストレージの認証だけではセッションごとのprefixの権限の代わりになりません。これらは、credential routeだけが届くリスト`EGRESS_CREDENTIAL_ALLOWLIST`(composeの既定値`api.anthropic.com:443`、GitHubリポジトリを使うなら`github.com:443`を加える)と`EGRESS_CREDENTIAL_PRIVATE_ALLOWLIST`(ローカルスタックの既定値`fake-git:3000,fake-messages:4010,fake-mcp:4020,localstack:4566`、`infra/compose.local.yml`)に置きます。credentialリストの宛先がforwardリストにもあると、proxyは起動を拒否します。そのため、環境ファイルのforwardリストにそのような値が残っていたら、消さないとproxyが起動しません。比較は書かれた`host:port`のままなので、同じupstreamを別の名前やIPで書いても検出できません。`.env.example`も同じ値です(`tests/images.test.ts`が両者を結び付けます)。どちらのリストも、link-local(`169.254.0.0/16`・`fe80::/10`)・multicast・reservedに解決されると拒否するので、allowlistに載った名前がmetadataアドレスに解決されるrebindingも防ぎます。リストにないhost・portは、CONNECTもabsolute-formも`403`で、absolute-formではない要求は`/healthz`以外では`400`です。リストにある名前が引けないとき(再起動中の`api`コンテナがDocker DNSから一時的に外れるとき)は、ポリシーの拒否ではなく`502`で、引くのが時間内に終わらなければ`504`です。workerはどちらも再試行します。

公開パッケージレジストリ(npm・RubyGems・Go module proxyとGo checksum DB)は、forwardリストではなく、credential routeの`packages` routeで開きます。SNIだけを見るforwardの許可は、CDNの背後にある別の宛先への漏れを防げないからです。workerは、`GET`・`HEAD /packages/<registry>/<path>`を`WORKER_EGRESS_CREDENTIAL_URL`に送ります。`<registry>`は、`npm`(`https://registry.npmjs.org`)・`rubygems`(`https://rubygems.org`)・`go`(`https://proxy.golang.org`)・`gosum`(`https://sum.golang.org`)の4つです。`proxy.golang.org`は`/sumdb/`のプロキシ要求に404で答えるので、checksum DBは別に置きます。要求には、attemptごとに発行する`packages`専用のegress token(接頭辞`wek_`)を、`Authorization: Bearer`で、URL userinfoのパスワード(Basic)で、またはパスセグメント`/packages/<registry>/_token/<token>/<path>`で載せます。Goはhttpプロキシ URLのuserinfoでは認証情報を送らないので(`refusing to pass credentials to insecure URL`)、パスセグメントを使います。proxyはこのセグメントを取り除いたパスだけをupstreamに送り、ログにも残しません。ヘッダーとパスにtokenが両方来たら`401`です。セッション内でこのtokenが見える範囲はほかのマネージャーの設定ファイルと同じで、GoのエラーメッセージにURLが出力されると、tokenも一緒に出力されることがあります(workerの出力scrubberが隠します)。BundlerとGoはbearerを送れないので、Basicも受け付けます。authorizerは、tokenのattemptがまだセッションを持っているかどうかだけを見て、レジストリのアドレスを返します。認証情報は付けません。ほかのmethod(`PUT`・`POST`・`DELETE`など、つまりpublish・unpublish)はrouteがないので`404`で、authorizerに尋ねもしません。パスに`.`・`..`に解決されるsegmentがあっても`404`です。

どのレジストリを開くかは、proxyのグローバル設定で決めます。4つのhostを`EGRESS_CREDENTIAL_ALLOWLIST`に置くと開き、外すとすべてのセッションで閉じます。compose・helm・`.env.example`の既定値は`api.anthropic.com:443,registry.npmjs.org:443,rubygems.org:443,proxy.golang.org:443,sum.golang.org:443`です。リストにないレジストリへの要求は`403 egress denied`です。これまでレジストリを開くためにこれらのhostを`EGRESS_ALLOWLIST`に入れていたなら、アップグレードのときにその値を消します。新しい既定値と重なると、proxyが起動を拒否します。profileやエージェントごとに違う開き方をする機能は、まだありません。レジストリがほかのhostにredirectするときは、`packages` routeだけが、`EGRESS_PACKAGES_REDIRECT_ALLOWLIST`(`host:port`、カンマ区切り、publicアドレスだけ、既定値は空)にあるhostに限って、proxyがサーバー側でたどります(1要求につき最大5回)。たどるときは、workerが送った`Authorization`も、authorizerがレジストリ要求に付けたヘッダーも載せません。リスト外のhost、`http`・`https`ではない位置、userinfoを含む位置、5回を超えるredirectは`502`です。同じレジストリhostの中でパスだけを変えるredirectも、そのhostがredirectリストにあれば、たどります。キャッシュの再検証に対する`304`はredirectではないので、そのままworkerに返します。ほかのrouteのredirectは、これまでどおりたどらず`502`です。リポジトリrouteのGit LFSオブジェクトも、このリストのhostからだけ、認証情報なしで受け取ります。GitHubリポジトリのLFSを使うなら、`github-cloud.githubusercontent.com:443`を加えます([APIサーバー](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md)のLFSの項目)。redirectリストのhostがforwardリストにもあると、proxyは起動を拒否します。2026-11-01にnpm metadata・tarball、RubyGemsの`versions`・`info`・`.gem`、Go proxyの`list`・`.mod`・`.zip`を実際に取得してみたところ、redirectはありませんでした。そのため、既定値は空です。

proxyログの`Credential route`の行に、`purpose: packages`、`registry`、`session_id`、`attempt_id`、upstreamのhostとstatusが残ります。たどったredirectは`Credential route redirect followed`(`to_host`・`to_port`)、拒否したredirectは`Credential route redirect refused`または`Credential route denied`として残ります。

#### GitHub Packages(プライベートnpm・gem)

組織のプライベートnpm・gemは、`<registry>`の`github-npm`(`https://npm.pkg.github.com`)と`github-rubygems`(`https://rubygems.pkg.github.com`)で受け取ります。公開レジストリと違い、authorizerが、ワークスペース管理者の登録したbot classic PATを`Authorization: Bearer`で付けます。この値はworkerには渡りません。登録・許可リスト・監査の設計は、[決定: GitHub Packages bot token](https://github.com/JeongJaeSoon/werft/blob/main/docs/contributing/decisions/github-packages-bot-token.md)にあります。運営者がやることは3つです。

1. `EGRESS_CREDENTIAL_ALLOWLIST`に`npm.pkg.github.com:443,rubygems.pkg.github.com:443`を加えます。抜けていると、登録したtokenがあっても要求は`403 egress denied`です。
2. `EGRESS_PACKAGES_REDIRECT_ALLOWLIST`に`pkg-npm.githubusercontent.com:443,rubygemsregistryv2prod.blob.core.windows.net:443`を加えます。GitHubはtarballと`.gem`をこのhostへ302でredirectします(2026-10-31に実測)。proxyはこのredirectをtokenなしでたどります。
3. GitHub Enterprise Serverなら、`GITHUB_PACKAGES_*_URL`を設定します([設定リファレンス](/run-server/self-hosting/operate/configuration#api設定))。

authorizerは、GitHubへの要求をパスで判定します。許可リストにないパッケージ、判別できないパス、tokenがない、または期限切れの場合は`403`で、`fetch_github_package` receiptが`failed`と`reason_code`で残ります。許可した要求も、同じreceiptが`succeeded`で残ります。receiptを書けなければ、要求は失敗します。この経路のproxyログは、ほかのpackages要求と同じです。

npm 11は、GitHubのtarballの場所をデフォルトのregistryを基準に書き換えるので(`replace-registry-host=always`)、tarballの要求は`npm` routeに来ます。authorizerは、`/download/@owner/<name>/<version>/<digest>`の形の`npm`パスをGitHubへの要求と判定します。公開npmには、この形のパスがありません。

workerは、claimを受けるたびに、engineのHOME(tmpfs)にuserレベルの設定だけを書きます。リポジトリのファイル(`.npmrc`・`Gemfile`・`.bundle/config`・`go.mod`)は変更しません。

| ツール | ファイル(HOME基準) | 内容 |
|---|---|---|
| npm(pnpm・Bunも読む) | `.npmrc` | `registry=<route>/packages/npm/`、`//<route host>/packages/npm/:_authToken=<token>` |
| Bundler | `.bundle/config` | `BUNDLE_MIRROR__HTTPS://RUBYGEMS__ORG/`を`<route, userinfoにtoken>/packages/rubygems`に |
| Go | `.config/go/env` | `GOPROXY=<route>/packages/go/_token/<token>`(`direct`なし)、`GOSUMDB=sum.golang.org <route>/packages/gosum/_token/<token>`、`GOFLAGS=-mod=readonly` |

許可リストにGitHub ownerがあると、claimの`packages.github`にowner名だけが載って来て(tokenはありません)、workerは上のファイルに次を加えます。`.npmrc`には、`replace-registry-host=always`、ownerごとに`@<owner>:registry=<route>/packages/github-npm/`、そして`//<route host>/packages/github-npm/:_authToken=<token>`が入ります。`.bundle/config`には、ownerごとに`https://rubygems.pkg.github.com/<owner>/`を`<route>/packages/github-rubygems/<owner>`に向けるmirrorが入ります。Bundlerはmirrorのkeyを小文字で読むので、`Gemfile`の`source`もownerを小文字で書かないとmirrorに乗りません。リポジトリの`.npmrc`が`@<owner>:registry=https://npm.pkg.github.com`を固定していると、その設定がHOMEの設定に勝って、要求がcredential routeではなくforward proxyに行き、そこで拒否されます。その行はリポジトリから外す必要があります。

`GOPROXY`に`direct`を置かないので、GoがVCS hostに直接出ることはありません。`GONOSUMDB`・`GOPRIVATE`・`GONOSUMCHECK`は置かないので、すべてのモジュールがchecksum DBの検証を受けます。このファイルはtokenを含むので0600で、claimに`packages`がない古いAPIに出会ったら消します。セッション内でユーザーが`go env -w`や`npm config set`で変えることはできますが、境界はproxyなので、変えてもほかの場所には届きません。

lockfileの外のバージョンを止める作業は、proxyは行いません。proxyはlockfileを知りません。セッションでは、frozenインストール(`npm ci`、`bundle install --deployment`または`BUNDLE_FROZEN=true`、`go mod download`と`-mod=readonly`)を使います。リポジトリのnpm設定がregistryを固定しているときの動作とE2Eの結果は、[イメージとサプライチェーン § worker内のパッケージツール](/run-server/self-hosting/operate/images-and-supply-chain#worker内のパッケージツール)にあります。

CONNECTトンネルはTLSだけを運びます。proxyは`200 Connection Established`を書いたあと、クライアントの最初のバイトをupstreamに流す前にTLS ClientHelloとして読み、DNS名のauthorityなら`server_name`がそのauthorityと(大文字と小文字だけを無視して)同じでなければならず、allowlistに明示されたIP literalのauthorityなら`server_name`がなければなりません。`encrypted_client_hello`(0xfe0d)は、GREASEかどうかに関係なく拒否します。proxyは両者を区別できず、本物のECHは検査対象の名前を隠すからです。handshakeではない最初のrecord、host_nameが2つあるhello、最初の16KiB(record headerを含む)または15秒(`handshakeTimeoutMs`)以内に完成しないhelloは、すべて接続を切ります。拒否は200のあとに起こるので、クライアントにはhandshakeの途中で接続が閉じたように見えます。

この関門の限界:

* 検査の対象は、平文で見える**外側の**ClientHelloのSNIです。TLSを終端しないので、その中のHTTP `Host`・パス・本文や、許可されたサービスがさらに中継する先は見えません。domain frontingをCDN側で防ぐことは、別の統制です。
* IP literalのallowlistは`IP:port`へのアクセス権限であって、hostnameの保証ではありません。共有CDN edgeのアドレスをIPでallowlistに載せてはいけません。
* **Bun 1.3.10〜1.3.13の`fetch`・`node:https`はGREASE ECHを送るので、このproxyにCONNECTすると拒否されます。**1.3.14は送りません(2026-09-25に実測)。`egress.integration.test.ts`の"Bun's own fetch handshakes through the tunnel"がこれを固定します。Bunの`node:tls`・`Bun.connect({tls})`、Node、curl、そしてworkerのSDKがspawnするClaude Codeバイナリも送りません(2026-09-23に実測)。workerのobject storeはCONNECTを使いません。workerネットワーク内のproxyのobject store routeに平文httpで送り、upstreamのTLSはproxyが張ります。AWSでは、routeがvirtual-hostedの名前で呼ぶので、`<bucket>.s3.<region>.amazonaws.com:443`が`EGRESS_CREDENTIAL_ALLOWLIST`にある必要があります(ドットを含むbucket名はpath-styleの`s3.<region>.amazonaws.com:443`)。workerのBun HTTPクライアントでhttps upstreamをCONNECTで呼ぶコードは、サポートしません。ランタイム・クライアントのバージョンを上げたら、もう一度測ります。

**worker同士は互いに届きません。**ほかのworkerと同じネットワークにいないので、そのアドレスへの経路がなく、コンテナ名も引けません。proxyを経由しようとしても、プライベートアドレスは`EGRESS_PRIVATE_ALLOWLIST`になければ拒否されます。ほかのインストールのworkerとproxyにも届きません。ネットワークとproxyの選択がどちらもインストールごとだからです。統合テスト(`egress.integration.test.ts`の"workers do not reach one another")がこれを確認します。同じネットワークの兄弟コンテナなら開いているポートに届く、という陽性対照と一緒に確認します。残る限界:

* proxyは、すべてのworkerネットワークにつながる信頼されたコンポーネントです。proxyが侵害されると、そのインストールのすべてのworkerに届きます。`EGRESS_PRIVATE_ALLOWLIST`には、workerに解決され得る名前を入れてはいけません。

**hostのプロセスにも届きません。**デフォルトのgateway mode(`nat`)のinternal bridgeは、hostにsubnetの最初のアドレスを与えます。すると、daemon hostがそのアドレスやwildcardでlistenしている**hostプロセス**(publishされたポートではなく、hostで直接起動したプロセス)に、workerがproxyなしで届きます。そのため、workerネットワークは`gateway_mode_ipv4=isolated`で作り、hostがそのネットワークにアドレスを持たないようにします。このmodeは**Docker 28(API 1.48)以上**にしかありません。schedulerは、起動時のpreflight(`verifyNetworkIsolation`)で、daemonのAPIバージョンが1.48未満なら、警告で済ませず拒否します(`GatewayModeUnsupportedError`)。これを切る設定はありません。統合テスト(`egress.integration.test.ts`の"a host process on a wildcard address")は2つを一緒に確認します。modeのないinternalネットワークでは、hostのlistenerに届きます(陽性対照)。workerネットワークでは届きません。native Linux(CI)では、テストのプロセス自身が`0.0.0.0`のlistenerです。Docker Desktopはdaemonが VMの中にあるので、VMのnetwork namespaceを使う`--network host`コンテナがlistenerの代わりをします。IPv6はworkerネットワークで無効なので、該当しません。

schedulerは、passの前に、そのインストールのproxyがちょうど1つ起動していることを確認します(`verifyNetworkIsolation`)。なかったり2つ以上あったりすると、pass lockを取ってworkerネットワークのreconcileだけを実行します(orphanの回収、2つ以上あるときはproxyの切り離し)。その後、何も起動しないまま非ゼロで終了します。workerネットワークはlaunchのたびに検査します。同じ名前のネットワークがすでにあれば、新しく作らず、次を確認します。1つでも食い違うと、`NetworkIsolationError`でlaunchを拒否します(fail closed)。

* bridge・internal・IPv6無効・所有label(インストール・execution・generation)が合っているか
* hostがネットワークにアドレスを持たないか。`Options`の`gateway_mode_ipv4`が`isolated`で、IPAMにgatewayがないこと。知らないオプションを記録するだけでgatewayを与える古いdaemonがあるので、両方の条件を見ます
* workerとproxy以外のメンバーがいないか

proxyのattachの結果は、応答コードではなく、proxyコンテナが報告するattachとaliasで判定します。すでにつながっていると403が返り、aliasなしでつながっているとDNSが引けないからです。すでにあるコンテナをadoptするときは、そのコンテナが自分のネットワーク(同じid)**だけに**つながっている必要があります。コンテナはネットワーク名ではなくidで作ります。そのため、同じ名前で作り直されたネットワークが、検査を受けたネットワークの代わりになることはできません。

以前の設定`EXECUTION_DOCKER_NETWORK`・`EXECUTION_DOCKER_NETWORK_ALLOWLIST`は、もう読みません。値が残っていると、黙って無視せず、起動を拒否します。環境ファイルから消して、proxyコンテナにlabelを付けます。

コンテナには、作られたときの隔離契約が、`agent-platform.isolation` labelに`<version>:<fingerprint>`の形で刻まれます。fingerprintは、proxy URL・credential routeのポート・`NO_PROXY`の値・user・workspace/HOMEのパス・tmpfsのサイズ・workspace quotaの設定とinode上限・stop timeout・workerの上限(turn時間、providerの再試行)、そしてobject storeのbucket・regionのハッシュなので、コードを変えずに`EXECUTION_EGRESS_PROXY_URL`や`S3_BUCKET`だけを変えても値が変わります。object storeのendpointと認証情報は、fingerprintにありません。workerは両方を受け取らず、proxyのobject store routeを通り、その要求はAPIが署名します。そのため、`AWS_ENDPOINT_URL`やkeyを変えても、workerは入れ替わらず、APIを再起動すると、次の要求から新しい値が使われます。CPU・memory・pidsの上限も、意図的にfingerprintの外に置きます。上限はlaunchのもので、reserveのときに`worker_launches.resources`に固定され、`agent-platform.launch-spec` labelで突き合わされます。そのため、上限を下げても、実行中のworkerを一斉に入れ替えず、次のlaunchから適用されます。ただし、`agent-platform.launch-spec` labelのないコンテナは、突き合わせなしでadoptされます。実行中のコンテナの隔離は、制御ホストを上げても変わらないので、schedulerは、labelが現在の値と異なるコンテナを`stale`と見て、停止・削除したあと、保存されたintentで作り直します(`ensureExecution`もそのようなコンテナはadoptしません)。バージョンが**より高い**コンテナは、ロールバック中の新しい制御ホストが作ったものです。その境界が今求められているものと同じかどうか分からないので、adoptも入れ替えもせず、`IsolationContractError`で拒否します。rowは生きていて、passは非ゼロで終わるので、運営者がロールフォワードするか、直接削除する必要があります。隔離の形そのものが変わるときは、`ISOLATION_CONTRACT`を上げます。契約5から、workerネットワークはexecutionごとです。そのため、契約4以下からアップグレードすると、共有ネットワーク上の既存のコンテナがすべてstaleとして入れ替えられます。入れ替え前の確認(`assertReplaceable`: イメージ・workspace・proxy・新しいネットワーク)が失敗した場合、普通は古いコンテナをそのまま置いて、次のpassで再試行します。ただし、契約5未満のコンテナは、共有ネットワークで隣のworkerに届くことがあります。そのため、まだclaimされていないそのコンテナは、**すべてのネットワークから切り離した**状態で置きます。claim の前なので、進行中のturnはありません。確認が通るpassで、正常に入れ替えられます。結果は、入れ替え失敗ログのエラーメッセージの末尾に付きます。claimされた契約5未満のworkerは、この確認なしでteardownされるので、ここでは触りません。確認とdisconnectを一度にまとめるfenceはありません。そのため、disconnectのあとにclaimの有無をもう一度確認し、その間にclaimされていたら、ネットワークをつなぎ直して、schedulerのteardown(SIGTERMでdrain)に任せます。disconnectが続くその短い間にclaim要求がやり取りされていたworkerは、要求が切れることがあります。

契約6から、workerネットワークにhostアドレスがありません。契約5のコンテナのネットワークは名前が同じですが、gateway modeはその場では変えられないので、入れ替えは次の順序で進みます。

* **入れ替え前の確認(`assertReplaceable`):** 同じlaunchの契約5のworkerがそのネットワークに実際につながっていて、欠陥がhostアドレスの1つだけなら、古いネットワークを通します。続くteardownが、コンテナと一緒にネットワークを消します。その後、`ensureExecution`が`isolated`で新しく作ります。
* **通常のlaunch経路:** workerなしで残った古いネットワーク(teardownのネットワーク削除が失敗した場合)は、proxyだけがつながっていれば、消して作り直します。ほかのメンバーがいれば拒否します。古いworkerがまだつながっている古いネットワークに、新しいコンテナを載せることはありません。
* **`reconcileNetworks`:** 契約5のworkerがつながった古いネットワークからは、proxyを切り離しません。claimされたworkerは、確認なしでdrain・teardownされるので、その前にegressを切らないためです。契約6のworkerがhostアドレスのあるネットワークにいるときは、欠陥と見て、proxyを切り離します。

この入れ替えも、claimされたworkerは、下のturn境界のdrainのあとで閉じる規則に従います。**デプロイ順序:** daemonを先にDocker 28以上に上げます。古いdaemonでは、preflightがpassの全体を止めます。すると、契約5のworkerも入れ替えられず、そのまま動きます(新しいadmissionだけがfail-closed)。

アップグレードのあと、古い共有ネットワーク(`agent-platform-worker`、`EXECUTION_DOCKER_NETWORK`で名前を変えていたらその名前)は、composeがもう宣言しません。それでも自然には消えず、アドレスプールのsubnetを1つ占め続けます。契約4のコンテナがすべて入れ替えられたあとで、`docker network rm agent-platform-worker`で消します。実行中のコンテナがつながっていると、Dockerは削除を拒否します(403)。そのため、使用中のネットワークを誤って消すことはありません。**すでにclaimされたworkerは作り直せないので、turn境界までdrainしてからteardownされます。**下の節に従います。

#### 契約が上がるときのclaimされたworkerのdrain

claimされたコンテナがstaleなら、schedulerはすぐには壊しません。
1. 最初のpassが`worker_launches.drain_requested_at`をDBの時計で記録します。その時点から、そのworkerは新しいturnを受けません。すでに受けたturnは最後まで動き、あとから来た入力はqueuedのまま残ります。
2. 動いているturn(`running`・`needs_input`)があるか、workerがまだ最初の入力を求めていなければ(workspaceの準備・checkpointの復元中。このとき切ると失敗した起動として数える)、コンテナをそのまま置いて、pass summaryの`draining`(ログの`draining_count`、`Claimed execution draining before its replacement`)に載せます。
3. turnが終わったあとの最初のpassが、コンテナをteardownします。turnのcheckpointは、そのfinalizeに載って、すでに確定しています。SIGTERMを受けたworkerはidle drainでreleaseし、queuedの入力は、新しいlaunch(現在の契約)が受けて、checkpointから続けます。
4. drainの期限が過ぎてもturnが開いたままだったり、起動が終わっていなかったりしたら、そのままteardownします。このとき、そのturnは以前と同じく`outcome_unknown`になります。終わっていない起動は、workerがSIGTERMでdrainとしてreleaseすれば数えず、releaseなしで死ねば失敗1回として数えます。pass summaryの`drainsOverdue`(ログの`drain_overdue_count`)と、警告`Drain deadline passed with the worker still busy; replacing anyway`が1行残ります。期限は`MAX_TURN_SECONDS` + 5分です。どのturnも`MAX_TURN_SECONDS`を超えられず、5分は、そのturnを終えるfinalize・checkpointの分です。

claimされていないstaleコンテナは、以前と同じくすぐに入れ替えられます。

**ロールアウトの手順:** 契約を上げるデプロイは、claimされたworkerの入れ替えが最大でdrainの期限だけ遅れます。そのあいだ、古い契約のコンテナが生きていて、そのセッションには新しいturnが始まりません。すぐに切るべき隔離の欠陥なら、該当のセッションをterminateして、待ちません。ロールバックでコンテナがもう一度currentになっても、drainの要求は残ります。そのworkerは、新しいturnなしで、アイドル時間のあとに自分で終わり、セッションは次のlaunchに引き継がれます。

### checkpointの復元が失敗し続けるセッション

復元を引き継いだworkerがreadyを報告する前に終わると、schedulerはすぐには再起動しません。このような終了が2回目までは、30秒、60秒待ちます。3回目には、セッションが`recovery_required`で止まり、新しいgenerationを作りません。待っているあいだや止まったあとのセッション詳細のattentionは`RESTORE_FAILED`です。
- `reason`: 最後のworkerが残したエラーです。releaseなしで死んだなら`execution_gone`です。
- `failures`: 続いた失敗の回数です。
- `retry_at`: 次の試行の時刻です。止まったあとはnullです。

`INCOMPATIBLE_CHECKPOINT`は、再試行しても、同じworker runtime・profileでは成功できない、決定的な失敗です。この場合、最初のlaunchのあとすぐ`recovery_required`で止まり、attentionと`checkpoint_restore_failed`イベントの`reason`は`incompatible_checkpoint`、`failures`は1、`retry_at`はnullです。運営者は、互換性のあるruntime・profileに戻したうえで、`retry_restore`で同じcheckpointをもう一度試すか、以前のcontextを捨ててよければ`start_fresh`を選ぶか、セッションを終えるなら`close`を選びます。

イベントストリームには、失敗のたびにsystemの`checkpoint_restore_failed`が残ります。workerログの`worker.checkpoint.restore_refused`、`worker.failed`で原因を確認します。ストレージ応答のchecksumの不一致(転送中の破損)も、`CHECKPOINT_UNAVAILABLE`に分類されます。
- ストレージやegress-proxyの`/object-store`経路が一時的に答えられなかったことは、失敗として数えません。接続の失敗・DNSの失敗・request/body timeout・途切れたbodyと、HTTP 408・429・5xxが、一時的な障害です。checkpointの復元は`worker.checkpoint.restore_unavailable`、checkpointがまだない新しいgenerationのtranscriptストレージの確認は`worker.checkpoint.store_unavailable`の警告を残します。どちらも同じworkerの中で、1秒から2倍ずつ、最大30秒の間隔で、`WORKER_STARTUP_TIMEOUT_SEC`(既定3600秒)まで再試行します。ストレージが戻れば、そのworkerが続けるので、generationを新しく作りません。
- 起動の予算が尽きるまで障害が続くと、そのworkerの終了を起動失敗1回として数えます。次のgenerationは、30秒、60秒のセッションbackoffのあとにだけ起動し、3回目の失敗で`recovery_required`で止まります。したがって、ストレージの障害が、workerの無制限の即時再起動に変わることはありません。`WORKER_STARTUP_TIMEOUT_SEC`は、schedulerがworkerに別の値を渡さないので、現在のデプロイではコードの既定値で固定です。
- オブジェクトが実際にない(404/`NoSuchKey`)、401・403で拒否される、checksum・digestが合わない場合は、一時的な障害ではありません。manifestやmanifestが指すオブジェクトがなければ`CHECKPOINT_UNAVAILABLE`で、再起動で復旧したと見なしません。bucket全体が空なのにDB pointerが残っている場合は、API起動時の検査が先に止めます。`restore_refused`は、ストレージ経路ではなく、checkpointの恒久的な破損・不一致を調べよ、という合図です。
- 原因がセッションの外にあったなら(proxyの転送中の破損、ストレージ経路の設定ミス)、それを直したあとで、`retry_restore`で同じcheckpointをもう一度復元します。回数が0に戻り、queuedの入力がもう一度通知されます。次のworkerは、失敗していたworkerと同じpointerから復元計画をもう一度受け取ります。
```sh
# KEY: an API key with the sessions:recover scope
curl -X POST "$API/v1/sessions/$SESSION/recovery-decisions" \
  -H "Authorization: Bearer $KEY" -H "Idempotency-Key: $(uuidgen)" \
  -H 'Content-Type: application/json' \
  -d '{"decision":"retry_restore","expected_revision":<revision>,"reason":"proxy fixed"}'
```

上限に届いて止まったセッションにだけ受け付けます。backoff中のセッションや、ほかの理由(context gap、unknown turn、復元のない`STARTUP_FAILED`)で止まったセッションは、409 `REQUEST_STALE`です。
- checkpointを諦めてよければ、`start_fresh`で続けます。checkpointなしで、新しいengine sessionが始まります。
- セッションを終えるには、`close`を使います。

### 起動の段階で死に続けるセッション

checkpointのないセッションも、同じ規則に従います。workerがclaimのあと、入力を一度も求めずに終わると、失敗1回です。workspaceの準備(git clone・fetch)やengineの起動で死んだ場合です。2回目までは30秒、60秒待ち、3回目には`recovery_required`で止まります。attentionは`STARTUP_FAILED`で、`reason`・`failures`・`retry_at`は上と同じです。イベントストリームには、失敗のたびにsystemの`startup_failed`が残ります。
- よくある原因は、リポジトリのURL・branchがなくなった、リポジトリの認証情報が拒否された、そしてworkerのobject store・proxyの設定ミスです。workerログの`worker.stopping kind=failed`、`worker.failed`で確認します。
- 原因を直したあと、`start_fresh`で起動し直します。このセッションには捨てるcheckpointがないので、失うものはありません。セッションを終えるには、`close`を使います。
- pause、terminate、close、実行権限の取り消しで終わったworkerは、数えません。
- SIGTERMでdrainされたworkerも、数えません。workerはreleaseに`stop_kind: "drain"`を載せます。このフィールドを知らない古いAPIは、strict schemaなので400 `BAD_REQUEST`で拒否します。すると、workerは`worker.release.stop_kind_refused`をログに残し、フィールドなしでもう一度releaseします。セッションは、lease期限切れを待たず、すぐに戻ります。ただし、古いAPIはその終了を以前の規則で数えます。復元が掛かったclaimなら、失敗1回です。
- **デプロイ順序:** 制御ホストのイメージ(`API_IMAGE`、apiとschedulerで共通)を先に上げ、`WORKER_IMAGE`はそのあとで変えます。worker protocolの要求schemaはstrictなので、新しいworkerが送った新しいフィールドを、古いAPIは400で拒否します。release以外には、このような代替経路がありません。

### interruptのあと結果が分からないturn

interruptしたturnが`interrupted`で終わるには、engineが止まったという応答と、そのturnまでを覆うcheckpointが両方必要です。どちらか1つでもなければ、transcriptに何が残ったのか、誰も言えません。そのため、turnは`outcome_unknown`になり、turn取得(`GET /v1/sessions/{id}/turns/{turn_id}`)の`terminal_reason`が原因を示します。
- `interrupt_checkpoint_unavailable`: engineは止まったが、checkpointをコミットできませんでした。workerはdrainで降ります。
- `interrupt_unanswered`: engineがinterruptに時間内に答えませんでした。workerログに`gave no terminal within …ms of its interrupt`または`ended before its interrupt was answered`が残り、workerは失敗で終わります。

workerログの`worker.turn.interrupt.stage`を、同じ`session_id`・`turn_id`・`control_id`で集めると、`control_received` → `sdk_interrupt_called` → `sdk_interrupt_answered` → `engine_terminal` → `capture_started` → `capture_finished` → `finalize_started` → `finalize_finished`の順序と、interrupt受信後の`elapsed_ms`が見えます。最終finalizeのあとには、`control.result`が`operation=interrupt`、最終的なturnの`outcome`、安定した`reason_code`、durableな受理時刻からturn terminalまでの`effect_ms`(`duration_ms`と同じ)を残します。すでに終わったturnに対するno-opは、受理transactionの直後に`effect_ms=0`で、期限までに終わらなかったreceiptは`outcome=unknown`・`reason_code=deadline_exceeded`で、同じeventを残します。SDKの応答がengine terminalのあとに届いたら、正常な順序に挟まず、`late_sdk_interrupt_answered`として記録します。`engine_terminal outcome=timeout`は、5秒のgraceのあいだにSDK/engine terminalが来なかった場合です。`capture_finished outcome=timeout`と`budget_ms=30000`は、checkpointのcapture予算を使い切った場合で、`outcome=failed`の`reason`は、ストレージ要求のような、captureそのものの失敗です。captureが終わっていても、`finalize_finished outcome=failed`に`CHECKPOINT_UNAVAILABLE`があれば、APIがmanifestやそのrefを拒否した場合なので、captureの時間切れやS3要求の失敗には分類しません。5秒のgraceは変えません。timeoutなら、次の入力を同じengineに渡さず、workerを失敗で降ろして、復旧の決定を求めます。

どちらの場合も、セッションは`status: failed`、`admission_state: recovery_required`になり、queuedの入力はdispatchされません。interrupt receiptは`unknown`で、errorは`RECOVERY_REQUIRED`です。復旧は`sessions:recover` scopeで行います。
ストレージがもう一度正常になっても、`outcome_unknown`のturnは自動では再実行しません。ストレージの復旧は、次のworkerがcheckpointを読めるようにするだけで、すでに実行されたturnの外部への効果を判定できないからです。下の`abandon`・`confirm_completed`・`close`のうち、運営者が選んだ決定だけが、queue headを片付けます。
1. `abandon`・`confirm_completed`は、workerが消えたことが確認されたあとにだけ受け付けます。その前は409 `RECOVERY_REQUIRED`(`The previous execution has not been confirmed gone`)です。次のscheduler passがコンテナの不在を確認すれば、受け付けます。`close`は待ちません。残っているexecutionに終了を要求して、すぐに受け付けます。
2. そのturnのツールが外部に行ったことを確認します。ファイルの書き込み、push、外部呼び出しは、元に戻せません。
3. 決定を送ります。

```sh
# KEY: an API key with the sessions:recover scope
curl -X POST "$API/v1/sessions/$SESSION/recovery-decisions" \
  -H "Authorization: Bearer $KEY" -H "Idempotency-Key: $(uuidgen)" \
  -H 'Content-Type: application/json' \
  -d '{"decision":"abandon","expected_revision":<revision>,"reason":"interrupt had no confirmed effect","target_turn_id":"<turn_id>"}'
```

- `abandon`: turnを`cancelled`で閉じます。
- `confirm_completed`: コミットされたcheckpointがそのturnまでを覆うときだけ受け付けます(`evidence_ref`が必須)。`interrupt_checkpoint_unavailable`は、たいていそのようなcheckpointがないので、409 `CHECKPOINT_UNAVAILABLE`です。
- `close`: セッションを終えます。元に戻せません。

4. `abandon`・`confirm_completed`のあと、セッションは`stopped`です。決定receiptの`result.resumable`が`true`ならresumeします。`false`は、引き継げるcheckpointがない、または最後のcheckpointのあとに動いたturnがあって、そのcontextを引き継げない、という意味です(セッション詳細のattention `CONTEXT_GAP`)。`start_fresh`でそのcontextなしで続けるか、`close`します。

## workerのworkspaceの上限と回収

セッションごとに、`ap-ws-<installationId>-<sessionId>-<suffix>`のvolumeが1つ`/workspace`につながります。このvolumeは世代(generation)をまたいで生き残ります。コンテナを入れ替えても、セッションの作業ツリーはそのままでなければならないからです。そのため、**コンテナを消す`terminate`はvolumeに触れず**、回収はpassの④段階が別に行います。

volumeがなくなっても、セッションは最後にコミットされたcheckpointから続けます。何が残り、何が消えるかは、[workspace volumeを失ったときに残るもの](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md#workspace-volume을-잃었을-때-남는-것)にあります。

volumeは、今はbackendが`POST /volumes/create`で**明示的に**作ります。mount specに名前だけを書くと、Dockerがlabelも上限もないvolumeを勝手に作ってしまうからです。作るときに`agent-platform.managed`・`.installation`・`.session-id`・`.workspace-quota` labelを刻み、GCは名前を解析せず、このlabelだけを見ます。

**volume名は使い捨てです。**`local`ドライバは、すでにquotaを掛けた名前をもう一度作ると、`Options.size`はそのまま返すのに、実際のproject quotaは掛けません。xfs+prjquota(Docker 27.5.1)で測った結果です。最初に作った名前は、コンテナ内の`df`の総量が設定値(64MiB)ですが、同じ名前を消してもう一度作ると、`Options.size`が同じでも、`df`はファイルシステム全体(8GiB)を報告します。Engine APIでは両者を区別できないので、セッションのworkspaceは、名前から導かず、ランダムな接尾辞を付けて作ったあと、**labelで引きます。**GCや運営者がvolumeを消しても、次のものは新しい名前を受けるので、上限がもう一度掛かります。1つのセッションにworkspaceが2つ見えたら、どちらが作業ツリーかを判断せず、報告だけをします。preflight probeも同じ理由で毎回新しい名前を使い、前の実行が残したprobeはlabelで回収しますが、作ってから10分と`EXECUTION_DOCKER_REQUEST_TIMEOUT_SEC`の20倍のうち長いほうが過ぎたものだけを消します。preflightはpass lockの外で動くので、それより若いprobeは、同時に動くほかのpreflight(ループの横の単独の`--once`、scheduler 2つ)が使用中のことがあります。

CPU・メモリ・PID・tmpfsと違い、`/workspace`には上限がありませんでした。`EXECUTION_WORKSPACE_QUOTA_MB`(既定4096)が、`local`ドライバの`size` driver optionとして、その上限になります。ただし、このオプションは**daemonのストレージがproject quotaに耐えられるときだけ**(xfs + `prjquota`)動作し、そうでなければdaemonがcreateを`400 quota size requested but no quota support`で拒否します。schedulerは、passの前にprobe volumeを1つ作ってみることでこの能力を確認し(`verifyWorkspaceQuota`)、耐えられないdaemonでは**何も起動せずに終了します。**probeはvolumeを1つ作り、CAP_SYS_ADMIN helperを起動する作業なので、passのたびには繰り返しません。監督ループのpassは、probeを通ると、backend設定の全体(`DOCKER_HOST`・`EXECUTION_*`など)のハッシュを、status fileの隣の`<SCHEDULER_STATUS_FILE>.quota-verified`に書きます。以降のpassは、ハッシュが同じならprobeを飛ばします。監督ループは起動するときにこのファイルを消します。そのため、ループが再び起動すると(コンテナの再起動、連続失敗のあとの再起動)、最初のpassがもう一度確認します。失敗したprobeは何も書かないので、次のpassがまた確認します。ループの外で単独で動かしたpass(`main.ts scheduler --once`)は、この記録を書きも信じもせず、毎回probeします。ループは、記録の場所を`SCHEDULER_QUOTA_PREFLIGHT_MARKER`で自分のpassにだけ渡します。静かに無制限に落ちる経路はなく、無制限を受け入れるなら、`EXECUTION_WORKSPACE_QUOTA=off`を明示する必要があります。その場合、schedulerのpassごとに警告が1件残ります。`on`・`off`以外の値(`false`、`0`、`no`)は、誤字と見て拒否します。

**quotaの最小値は1024 MiBです。**これより小さい`EXECUTION_WORKSPACE_QUOTA_MB`は、起動時に拒否されます。checkpointの復元が、workspace volumeを一時的にこれだけ使うからです。復元は、rootを空にしたあと、次の順序で進みます。表の記号は次のとおりです。

- B: bundleチェーンの合計。control planeの上限は256 MiBです。
- U: untrackedファイル。captureの上限は256 MiBです。
- W: workspaceの`.git`が受け取ったオブジェクト。おおよそBです。
- I: instructions commitが届くオブジェクト。W以下です。
- T: checkoutされた作業ツリーとindex。

| 段階 | 同時に占めるもの | 最大 |
| --- | --- | --- |
| ダウンロード | bundleファイルB、U | 512 MiB |
| staging | bundleファイルB、staged リポジトリ ≈B、U | ≈768 MiB |
| workspace fetch | staged リポジトリ ≈B、W、U (bundleファイルはstagingの直後に消す) | ≈768 MiB |
| staged リポジトリの縮小 | W、I、U (staged リポジトリを先に消す) | ≤768 MiB |
| checkoutのあと、セッションのあいだずっと | W、I、T、U | 2B + T + U |

checkoutの前の固定費用は、bundle上限の2倍 + untracked上限、つまり768 MiBです。1024 MiBは、これにpack indexと余裕を足した値です。incremental thin packを埋めるdelta baseのコピーも、この余裕に入ります。checkoutのあとのTは、セッションの作業ツリーそのものなので、上限がありません。そのため、最小値は、セッションと無関係なcheckoutの前の費用だけを保証します。checkoutのあとのW + I + T + Uは、同じquotaの中でcaptureするとき、そのセッションがすでに使っていた量と同じくらいです。captureのときは、workspaceの`.git`、作業ツリー、untracked、scratchリポジトリのsnapshotオブジェクト、bundleファイル(≤B)が一緒にありました。IはB以下です。quotaを下げたあとで新しいvolumeに復元する場合は、この保証の外です。このときは、復元がcheckoutの最中にENOSPCで失敗することがあります。

既存のworkspaceを再利用するfresh fetch(checkpointなしで再開するreuse)は、復元と違い、rootを空にしません。workerは、originの全体をbare mirrorとして受け取り、そこからbranchをコピーします。mirrorは`.git/werft-fetch-*`の下に作り、fetchが終わったら消します。`/tmp`とHOMEはtmpfsで、コンテナのメモリを使うからです。表の記号に加えて、Mは、mirrorがディスクで占める最大値です。originリポジトリのpack全体に、indexとref、受け取っているあいだの一時packファイルが加わります。Δは、workspaceの`.git`に新しく入るオブジェクトです。下の最大値は、この見積もりを加えた値です。

| 段階 | 同時に占めるもの | 最大 |
| --- | --- | --- |
| mirror cloneとローカルfetch | 既存のW、I、T、U + mirror M + Δ | セッションの使用量 + M + Δ |
| fetchのあと | W + Δ、I、T、U (mirrorは消す) | セッションの使用量 + Δ |

Mには上限がありません。Mだけのquota余裕がなければreuseは成功せず、足りなければfetchがENOSPCで失敗します。最初のclone(`clone`・`recreate`)は、mirrorなしでrootに直接受け取るので、W + Tだけを使います。workerが途中で死んで残したscratch(fetch・capture・publishの`.git/werft-<purpose>-XXXXXX`)は、次のreuseがfetchの前に消します。`werft-checkpoint`は残します。checkoutがほかの場所のオブジェクトを借りている場合(`objects/info/alternates`、`commondir`、リンクの`objects`)、その対象かもしれないので、消しません。

復元のあと、`.git/werft-checkpoint/checkpoint.git`には、instructions commitが届くオブジェクト(I)だけが残ります。engineがそのcommitをpruneしても、次のcaptureがbundleできるようにするためのリポジトリです。そのあとのcommit、コミットしていない変更のsnapshot、チェーンの以前のsnapshotは残しません。ただし、instructions commitがHEADと同じなら、Iはcommittedの履歴の全体です。engineがコミットしないセッションがそうです。このとき減るのは、snapshotの分だけです。

この縮小には代償があります。次のincremental captureは、チェーンのtipのうち、まだあるものだけを除外の対象にします。以前のbase bundleだけにあるsnapshot commitは、もう残りません。最後のbundleのsnapshotも、workspaceの`.git`に参照なしで入っているだけです。普通の`git gc`は、2週間はこれを消しません。ただし、engineが`git gc --prune=now`を実行すると、なくなります。すると、残ったtip(履歴に残ったHEAD commit、instructions commit)を基準にbundleを作ります。その結果、bundleが大きくなったり、完全なbundleに戻ったりすることがあります。正しさは変わりません。完全なbundleが上限を超えるリポジトリは、チェーンが32個になるか上限に届いて再開するときにも、どのみち拒否されます。

**inodeの上限も、同じprojectに掛けます。**byteの上限だけでは、空のファイルを数百万個作ってinodeを使い果たす経路が残ります。xfsはinodeをprojectのblock使用量に数えないので、4GiBの範囲でも可能です。すると、同じdaemonのほかのセッションとPostgresがファイルを作れなくなります。`local`ドライバにはinodeのオプションがなく、`o=loop`でセッションごとにファイルシステムを作る道も塞がれています。ドライバが`mount(8)`ではなくmount syscallを呼ぶからです(`data: loop: invalid argument`)。そのため、Dockerが`size`で作ったxfs projectに、私たちが`ihard`・`isoft`(`EXECUTION_WORKSPACE_QUOTA_INODES`、既定1,000,000)を直接掛けます。

- 掛ける主体は、短く動くhelperコンテナ(`workspace-inodes.ts`)です。設定は`CapDrop ALL` + `CapAdd SYS_ADMIN, MKNOD`、`NetworkMode none`、read-onlyのrootfsで、privilegedではありません。
- helperは、volumeのproject idを読みます。project 0(= projectなし)なら拒否します。0に上限を掛けると、ファイルシステム全体が縛られるからです。
- helperは、マウントソースのblock deviceノードを、自分専用の`/dev`に`mknod`で作ったあと、`xfs_quota`を呼びます。
- `xfs_quota`は、失敗しても0で終わります。そのため、成功したかどうかは、quota報告のhard・soft limitとstatfsの`f_files`を読むことでだけ判定します。
- Dockerの`SetQuota`はBHARD/BSOFTだけを書くので、この値を上書きしません。
- イメージはschedulerの`WORKER_IMAGE`です。workerイメージに`xfsprogs`が入っています。launchごとに違うイメージを選ばせません。CAP_SYS_ADMINを受けるイメージは、カタログではなく運営者が決めます。

適用の時点は3つです。

- preflight probe(`verifyWorkspaceQuota`、ループが起動してから最初に通るまで、そして設定が変わるときだけ): 掛けられなければ、byte上限と同じ規則で起動を拒否し、opt-outは同じ`EXECUTION_WORKSPACE_QUOTA=off`の1つだけです。
- 毎回のlaunchの`ensureWorkspaceVolume`: 新しいvolumeも既存のvolumeも対象です。project idはdaemonの再起動のあとに再利用されることがあるので、キャッシュせず、掛け直すことは冪等です。
- 入れ替え前の`assertReplaceable`: 上限を掛けられないvolumeなら、既存のworkerを降ろす前に、入れ替えを拒否します。
- `migrate-workspace`のコピー前: 上限より多くのファイルがあるツリーは、コピーが失敗して、元が残ります。

inodeの上限は、その場で変えられるので、volume label(`workspace-quota`)には入れません。inode上限なしで作ったvolumeも、拒否されず、次のlaunchで上限を受けます。その代わり、`isolationStampFor`のfingerprintに入れ、`ISOLATION_CONTRACT`を7に上げます。このバージョンより前にロールバックしたhostは、これらのworkerをnewerと見て、触りません。そのため、上限ができたり変わったりすると、実行中のworkerはstaleとして入れ替えられ、入れ替え経路のensureが上限を掛けます。

Docker Desktopは、カーネル自体がXFS quotaなしでビルドされていて(`XFS (loopN): quota support not available in this kernel`)、ローカルでは`off`が事実上唯一の選択肢です。GitHub Actionsランナーのdaemonも、data rootがext4なので同じです。そのため、実際に上限が効くかどうかは、CIの`workspace-quota` jobが、xfs + prjquotaのloopファイルをdata rootに使うdaemonを別に立てて確認します。

上限は、volume 1つにだけ掛けるのでは足りません。Dockerは、イメージが宣言した`VOLUME`パスごとに**書き込み可能な匿名volume**を自動的につなぎますが、そこには上限もlabelもありません。そのため、launchの前にイメージを調べて、`/workspace`以外の`VOLUME`宣言があれば拒否し(`ImageVolumeError`)、コンテナを消すときは`v=true`で匿名volumeも一緒に消します(named volumeであるworkspaceは影響を受けません)。まだpullされていないイメージは、調べると404なので、そのままにして、createに同じ404を出させます。

確認したものと実際に起動するものの間にも、隔たりが生じることがあります。タグは可変なので、コンテナは**調べたイメージのid**(`sha256:…`)で作り、volumeはcreateの直後、startの前にもう一度確認します。その間に`docker volume prune`が通ると、Dockerがmount用にlabelも上限もないvolumeを新しく作ってしまうからです。食い違ったら、まだ何も実行されていないコンテナを消して、失敗させます。

quota preflightが失敗したら、**何も起動しませんが、回収は1回動かします。**probeもディスクを少し使うので、すでに満杯のdaemonはpreflightから失敗しますが、その瞬間こそ、終わったセッションのworkspaceを回収すべきときです。そのまま終了すると、回収する方法が永遠になくなります。このとき動くのはpassではなく`reclaimWorkspaces`で、同じadvisory lockの下で④段階だけを実行します。slot limit 0のpassでは足りません。新しい予約を止めるだけで、消えたコンテナの再作成やstaleコンテナの入れ替えは、そのまま行うからです。回収が終わったら、元のエラーを再び投げて、非ゼロで終わります。

volumeのquota labelが今の設定と異なる場合、つまり、以前に暗黙に作られたlabelのないvolumeや、別のbyte上限で作られたvolumeの場合、起動を拒否します(`WorkspaceQuotaError`)。名前を導いていた時代の`ap-ws-<installationId>-<sessionId>` volumeも、引き続き探します。labelがないので検索には掛かりませんが、見なかったことにして新しいworkspaceを作ると、そのセッションが空のツリーで始まり、以前のツリーが埋もれるからです。volumeのbyte quotaは後から変えられず(inode上限は、上に書いたとおり、その場で変わります)、変えるつもりで消すと、そのセッションの作業ツリーが失われるからです。作業ツリーを残したまま新しい契約に移すには、下の[legacy workspaceのマイグレーション](#legacy-workspaceのマイグレーション)の手順を使います。以前の設定に戻すのも方法です。同じ理由で、quotaの設定は`agent-platform.isolation`のfingerprintにも入ります。そうしないと、すでに起動しているコンテナが、以前の上限を持ったまま生き続けるからです。

この拒否は、**すでに動いているworkerを殺す前に**起こらなければなりません。fingerprintが変わると、stale判定 → `terminate` → 再作成の順序ですが、再作成がvolumeに拒否されると、そのセッションは、workerもなく、戻る道もない状態で残ります。そのため、`inspect`は、staleを報告する前に、そのセッションのvolumeを読み取り専用で確認し、使えないvolumeなら、staleの代わりに例外を投げます。コンテナは以前の上限のまま動き続け、passは`reconcileFailed`で非ゼロを出し、運営者がvolumeを移すまで、その状態が続きます。移す方法は、下の[legacy workspaceのマイグレーション](#legacy-workspaceのマイグレーション)にあります。inodeの上限は、この読み取り専用の確認ではなく、入れ替えの直前の`assertReplaceable`が実際に掛けてみて、掛けられなければ、既存のworkerを降ろす前に入れ替えを拒否します。

④段階のGCは、fail-safeの方向です。**volumeを先に列挙し、そのあとでDBに尋ねます。**順序を逆にすると、2回の呼び出しの間にできたセッションのvolumeを消してしまいます。残す条件は、session rowがあり、admission stateが`closed`ではないか、生きているexecution rowがあることです。`stopped`は例外で、下の期限切れの規則に従います。session id labelがない、またはsession idの形ではないvolume、まだコンテナが掴んでいるvolume(409)、ほかのインストールのvolumeは、すべて**残して、ログだけを残します。**例外は、名前を導いていた時代のlabelのない`ap-ws-<installationId>-<sessionId>` volumeです。名前から読んだsession idは候補にすぎず、**そのidのrowがあって`closed`で、slotを持つlaunchがないときだけ**回収します(`filterClosedLegacySessions`)。rowがない場合は残します。labelのあるvolumeと違い、名前が合っているというだけでは、私たちのセッションのものだという証拠にならないからです。legacy volumeには、`stopped` TTLも適用しません。先にマイグレーションすると、期限切れの規則に乗ります。`EXECUTION_WORKSPACE_GC_MIN_AGE_SEC`(既定3600)より若いvolumeは、そもそも候補ではありません。volumeはコンテナより先に作られるので、その間に回収してしまうと、進行中のlaunchを壊すからです。**判断で残したものと失敗で残ったものは、exit codeが違います。**まだマウントされている(409)、またはほかのインストールのものなので残したvolumeは、正常な状態なので、exit codeを変えません(`workspacesUnresolved`)。一方、一覧を読めなかった、DBが答えなかった(`workspaceScanFailed`)、または削除呼び出しが例外を投げた(`workspacesFailed`)場合は、誰も見ないままディスクが溜まる状態なので、passが非ゼロで終わります。

**`stopped`セッションのworkspaceは期限切れになります。**stopしてから`EXECUTION_WORKSPACE_STOPPED_TTL_SEC`(既定86400、1日)が過ぎると、回収の候補になります。基準時刻は`sessions.updated_at`です。stop遷移がこの値を刻み、回収のclaimと完了の記録はこの値に触れません。すでに`stopped`のセッションに新しいterminateが受理されると、この値が変わり、TTLがそのときから数え直されます。ただし、terminateはworkspaceを掴んでおく手段ではありません。回収のclaimがすでに取られたあとなら、その回収はそのまま進みます。workspaceが必要なら、resumeします。resumeだけがclaimと直列化されます。slotを持つlaunchが残っていれば、候補ではありません。1日あれば、夜のあいだにstopしておいたセッションはそのまま戻り、10-session soakのようにstopが溜まる場合も、ディスクが際限なく増えません。`0`は、次のpassですぐ回収するという意味です。

resumeは、committed checkpointがあるときにだけ受理され、workerは、claimにrestore pointerがあれば、checkpointからworkspaceを復元します(復元は、rootを空にしたあとで満たします)。そのため、TTLが過ぎたstoppedセッションのvolumeは、キャッシュにすぎません。逆に、**checkpointのないstoppedセッションはresumeできず、そのvolumeにだけ残った作業は、TTLが過ぎると消えます。**その作業を残す必要があれば、TTLの範囲内にvolumeから直接取り出す必要があります。

回収とresumeはDBで直列化されます。volumeの一覧から候補が出ると、passは、セッションrowをresumeと同じ順序(launch → session)でロックし、条件をもう一度確認したあと、**claim**(`sessions.workspace_reclaim_id`・`workspace_reclaim_workspace_id`)を記録してcommitします。そのあとでvolumeを消し、同じclaim idで結果を記録します。

* 消えた、またはすでにない場合は、claimを消して`workspace_reclaimed_at`を刻みます。
* マウントされている(409)、またはほかのインストールのものなら、claimだけを解きます。
* 削除呼び出しが例外を投げたら(timeoutを含む)、claimをそのまま置きます。volumeが消えたかどうか分からないからです。次のpassは、volumeの一覧とは別に、終わっていないclaimから処理し直します。消えたvolumeは、一覧にもう出てこないからです。

claimが残っているあいだ、resumeは**503 `BACKEND_UNAVAILABLE`(`retryable: true`)**で拒否されます。このとき、receiptもidempotencyの記録も残さないので、同じ要求をもう一度送れば、回収が終わったあとに正常に処理されます。逆に、resumeが先にcommitされると、セッションが`active`になり、`updated_at`が変わるので、claimが拒否され、volumeは次のlaunchがそのまま使います。再開に成功すると、`workspace_reclaimed_at`は消されます。順序ごとの動作は、`packages/db/src/workspace-reclaim.integration.test.ts`が、実際のPostgreSQLの上で固定します。

#### legacy workspaceのマイグレーション

labelのない古いvolume(`ap-ws-<installationId>-<sessionId>`)や、別のquotaで作られたvolumeを持つセッションは、起動が拒否されます。コンテナを失うと、もう一度起動することもできません。作業ツリーを残したまま、今の設定のquotaに移す手順は次のとおりです。passが自動では行わない、**明示的な運用作業**です。

```sh
# run with the same environment variables as the scheduler (DATABASE_URL, EXECUTION_*, DOCKER_HOST)
bun run --cwd apps/control-host migrate-workspace <session-id> [<session-id>...]
# with compose (apps profile)
docker compose -f infra/compose.yml --profile apps run --rm scheduler \
  bun run apps/control-host/src/scheduler/migrate-workspace.ts <session-id>
```

前提条件:

* **そのvolumeを掴んでいるコンテナがないこと。**停止したコンテナも含みます(再び起動すると、コピー中の元に書き込むからです)。あれば、名前を知らせて拒否します。動いているセッションなら、先にterminateで止め(コンテナが消えます)、移したあとでresumeします。コンテナを`docker rm`で直接消すと、進行中だったturnが切れ、そのセッションは、コンテナを失ったセッションとして扱われます。
* **scheduler pass lockを取ります。**passが動いている最中なら、`A scheduler pass holds the lock`で終わります。終わったら、もう一度実行します。コピーしているあいだはpassが動かないので、GCもlaunchも、2つのvolumeに触れません。
* そのセッションに、終わっていない回収claimがないこと。あれば、次のpassが処理したあとで、もう一度実行します。
* セッションrowがあって、`closed`ではないこと。closedセッションのlegacy volumeは、GCが回収します。rowのないセッションのlegacy volumeは、GCもこのコマンドも触れません。私たちのものだという証拠が名前だけだからです。運営者が確認して、直接消します。
* helperイメージは、**digestで固定**されていて、daemonにすでにあること。既定はbusybox 1.36(`DEFAULT_MIGRATION_HELPER_IMAGE`)です。先に`docker pull busybox@sha256:73aaf090f3d85aa34ee199857f03fa3a95c8ede2ffd4cc2cdb5b94e566b11662`を実行します。変えるには、`--helper-image`または`EXECUTION_WORKSPACE_MIGRATION_IMAGE`を使います。
* quota preflight(`verifyWorkspaceQuota`)を先に通ること。新しいvolumeは、今の設定の上限で作られます。

やること:

1. 新しいvolumeを、今の契約どおりに作ります。labelと`size`を付け、元の名前は`agent-platform.migration-source` labelに、元の作成時刻は`agent-platform.migration-source-created-at` labelに残します。名前は、ほかのworkspaceと同じ使い捨てです。workspaceはlabelで探すので、名前を変える必要はありません。
2. 起動しないpinコンテナ(`ap-ws-migrate-pin-`接頭辞)が、元を読み取り専用で掴みます。Dockerは、コンテナが参照しているvolumeを消しません。そのため、pass lockを失った間にGCが割り込んでも、この実行が終わるまで元は残ります。pin名は実行ごとに違い、各実行は自分のpinだけを消します。続いて、helperコンテナが、元を読み取り専用で、新しいvolumeを書き込みでつなぎ、`cp -a`でコピーします。helperはrootですが、ネットワークがなく、ファイルのコピーに必要なcapability(`CHOWN`・`DAC_OVERRIDE`・`FOWNER`・`FSETID`)だけを持ちます。
3. 同じhelperが、両側のmanifestを比べます。比較の対象は、パスの集合、種類、mode、uid/gid、symlinkの対象、通常ファイルのサイズ・mtime・SHA-256です。ディレクトリのサイズと時刻、xattrとACLは比べません。busyboxの`cp -a`はhard linkを保存しないので、hard linkは、内容が同じ別のファイルになります。その分ディスクを余計に使うので、quotaに掛かるとコピーが失敗します。mtimeは秒単位までしか比べません。
4. 一致したら、元を消す前に、同じ元の別のコピーがないか、もう一度見ます。あれば、別の実行がまだ作業中です。そのときは、自分のコピーを捨てて失敗します。元がほかのコンテナに掴まれているときも同じです。どちらでもなければ、helperとpinを消して、**元を消します。**その瞬間から、新しいvolumeがそのセッションのworkspaceです。

途中で失敗しても、元はそのままです。コピーの失敗(quota超過、helperが作れないdeviceファイルなど)、不一致、時間切れ(`--deadline-sec`、既定3600)、lockの喪失が、すべてそうです。失敗したhelperは、`docker logs`で見られるように残します。pinも残り、元を掴み続けます。もう一度実行すると、まず新しいpinで元を掴みます。そのあと、残ったhelper、以前のpin、未完成のコピー(`migration-source`が同じ元を指すもの)を消して、最初からコピーします。元とコピーが一緒にあるあいだは、backendがそのセッションの起動を拒否し、GCは両方を候補から外します。そのため、半分だけコピーされたツリーの上でworkerが起動することも、元だけが先に回収されることもありません。終わらせないまま置くと、2つのvolumeがそのまま残るので、もう一度実行するか、直接片付けます。元の名前のvolumeが、コピーを作ったあとにもう一度作られていることもあります。Dockerは、ない名前をmountすると、空のvolumeを作るからです。このときは、作成時刻が合わないので、コマンドは、そのコピーを未完成と見て消しません。代わりに拒否します。コピーが唯一無傷のworkspaceかもしれないので、両者を直接比べて片付けます。元が消えたら、新しいvolumeの上でworkerを起動し直します。起動するのは次のpassで、その前に失敗したlaunchが再試行の待機中なら、待機が終わったあとのpassです。legacy volumeのために失敗するlaunchも、ほかの失敗と同じく回数が溜まります。上限に届くとセッションが`failed`になるので、できるだけ早く移します。

## workerネットワーク: アドレスプール、slot limit、回収

**アドレスプール。**workerネットワーク1つが、daemonの`default-address-pools`からsubnetを1つ持っていきます。Dockerの既定のプールは、合わせて31個です。

* `172.17.0.0/16`〜`172.31.0.0/16`の/16が15個
* `192.168.0.0/16`を/20に分けた16個

このうち、`docker0`とdaemon上のほかのネットワークが先に持っていきます。このリポジトリのcomposeは`default`を1つ使います。そのため、既定値でworkerに残るのは、おおよそ**30個 − (そのdaemonのほかのネットワークの数)**です。

**slot limitとの関係。**executionは、ネットワークを1つだけ持ちます。入れ替え(replace)は、以前のgenerationを消してから新しいものを作ります。そのため、同時に使われるworkerネットワークの数は、おおよそ`EXECUTION_SLOT_LIMIT`(既定10)です。ただし、プールは**daemonグローバル**なので、同じdaemonのほかのインストール・ほかのcomposeプロジェクトと分け合います。回収に失敗して残ったネットワークも、slot limitは数えません。したがって、既定のプールでは、slot limit 10のインストール2つが、1つのdaemonにかろうじて収まります。

**プールを広げる。**それより大きく使うには、daemon.jsonでプールを広げます。例: `{"default-address-pools":[{"base":"10.210.0.0/16","size":24}]}`は/24が256個です。

* LAN・VPNと重ならない帯域を選びます。
* sizeを小さくすると(`/28`なら4096個)、そのdaemonで自動的に割り当てられる**ほかの**ネットワークもすべて小さくなります。/28ならコンテナ13個までです。
* daemonを再起動しないと適用されず、すでにあるネットワークには適用されません。

**枯渇したときの動作。**枯渇は、静かな障害ではありません。ネットワークのcreateが`could not find an available, non-overlapping IPv4 address pool`で失敗します。すると、そのlaunchは`failedLaunches`に記録され、passはexit 1で終わります。intentは残り、次のpassがもう一度試みます。

**回収は2段構えです。**

1. `terminate`: コンテナを消したあと、proxyを切り離し、ネットワークをidで消します(best effort)。
2. passの②段階の終わり、slotを埋める前(`reconcileNetworks`): このインストールのlabelが付いたworkerネットワークをすべて走査します。
   * 名前に対応するコンテナが**なければ**(どの状態でも)、proxyだけを切り離して、ネットワークを消します。コンテナを`docker rm -f`で消した場合が、ここに当たります。launchがまだ生きているexecutionなら、①段階が先にコンテナを作り直したので、そのネットワークはそのまま再利用されます。
   * コンテナが**あれば**、proxyのattachを確認し、外れていればつなぎ直します。`compose up`がproxyを作り直すと、新しいproxyはどのworkerネットワークにもつながっていません。そのため、起動しているworkerのegressは、次のpass(`SCHEDULER_INTERVAL_SEC`、既定5秒)まで切れます。

**回収に失敗したときの動作。**

* 生きているネットワークも、passのたびに同じ基準でもう一度検査します。対象は、ネットワークの形、名前に対応するコンテナがこのインストールのそのworkerか、worker・proxy以外のメンバー、workerがほかのネットワークにもつながっていないか、です。入れ替えを控えて前もって作っておいたネットワーク(まだ古いコンテナがつながっていないもの)は、問題として見ません。
* メンバーは、network inspectが示す実行中のendpointだけではありません。停止した、または一度も起動していないコンテナも、起動する瞬間につながるので、一緒に数えます(`network`フィルターでコンテナを調べる)。
* 生きているネットワークに残ってよいproxyは、**今実行中の1つ**だけです。labelが付いたほかのproxy(停止した以前のproxyなど)は、切り離して`networksRepaired`で数えます。起動する瞬間に、同じaliasでworkerの前にもう一度立ち得るからです。実行中のproxyが2つ以上あれば、どちらも信頼できないので、labelが付いたproxyをすべて切り離して`networksFailed`として報告します。1つも実行中でなければ、報告だけをして、そのままにします。単独で起動したproxyが信頼する対象だからです。execution labelのないworkerネットワークも、proxyを切り離して報告します。
* 知らないメンバーがつながったネットワークでは、そのメンバーを切り離しません。強制的に切り離すと、痕跡が消えるからです。代わりに、**このインストールのproxyを切り離します。**知らないコンテナが、このインストールのallowlistを使えないようにするためです。そのネットワークのworkerもegressを失います。このようなネットワークは、そのままにして`networksFailed`として報告し、passはexit 1で終わります。
* 一覧の取得そのものが失敗しても(`networkScanFailed`)、やはりexit 1です。
* 残ったネットワークは、アドレスプールを占め続けます。運営者が`docker network inspect <name>`でメンバーを確認して、片付けます。
* proxyがなければpreflightで終了するので、この回収も動きません。代わりに新しいネットワークもできないので、リークは増えず、proxyが戻ったあとの最初のpassが回収します。

同じdaemonを複数のインストールが共有する場合は、`EXECUTION_INSTALLATION_ID`をインストールごとに変えて渡し、egress proxyもインストールごとに別に置いて、それぞれのidでlabelを付けます。workerネットワークの名前・labelにインストールidが入るので、インストールAのworkerネットワークには、Aのproxyだけがつながります。1つのproxyを2つのインストールが使うと、2つのインストールのworkerが同じallowlistを使うことになります。

composeのproxyは、`apps/egress-proxy/Dockerfile`でビルドしたイメージで動きます。ソースがイメージに入っているので、checkoutを移しても起動しているproxyは変わらず、新しいコードは`up -d --build egress-proxy`でビルドし直さないと反映されません。
- proxyは、起動するときに、自分のソース(`src`のテストではない`.ts`)のsha256を、ログ(`Egress proxy listening`の`source`)と`/healthz`(`ok source=<hex>`)で知らせます。どのコードが動いているかは、この値で確認します。
- compose healthcheck(`src/healthcheck.ts`)は、この値を`/app/src`の現在のソースと比べ、異なればunhealthyに落ちます。イメージで動くときは、両者はいつも同じです。誰かがソースツリーをmountして上書きしたあとで、そのcheckoutを移したときにだけ、この検査が発動します。ただし、Dockerは連続失敗12回(約60秒)が溜まって初めて状態を変えます。

```bash
docker compose -f infra/compose.yml up -d --wait --build egress-proxy   # after moving the checkout
docker compose -f infra/compose.yml exec -T egress-proxy bun run /app/src/healthcheck.ts
docker network ls --filter label=agent-platform.worker-network=true \
  --format '{{.Name}} {{.Labels}}'
```
