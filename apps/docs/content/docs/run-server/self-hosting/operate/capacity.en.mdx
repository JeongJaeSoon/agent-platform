title: "Capacity"
description: How the transcript limit, worker memory and sessions per node relate, and how to change them
---

The transcript size one session may use and the worker memory are tied together. On Kubernetes the requests of a worker Pod equal its limits, so these two values also decide how many sessions one node can hold at the same time. This page puts the relation of the three values, the measurements behind them, and how to change them and at what cost in one place.

## At a glance

| Value | Default | Defined in |
|---|---|---|
| Transcript total limit `MAX_TRANSCRIPT_BYTES` | 512 MiB | `packages/runtime-core/src/checkpoint-manifest.ts` |
| Transcript part limit `MAX_TRANSCRIPT_PART_BYTES` | 16 MiB | The same file |
| Warning threshold `transcriptWarnBytes` | 80% of the limit, 409.6 MiB | The same file. See "80% warning" below |
| Worker memory `WORKER_MEMORY_MB` / helm `worker.memoryMb` | 4608 MiB | `apps/control-host/src/scheduler/config.ts`, `deploy/helm/agent-platform/values.yaml`, `infra/compose.core.yml` |
| Workspace limit `EXECUTION_WORKSPACE_QUOTA_MB` / helm `worker.workspace.quotaMb` | 4096 MiB (minimum 1024) | `packages/adapters/execution/kubernetes/src/config.ts`, `packages/adapters/execution/local-docker/src/config.ts`, `deploy/helm/agent-platform/values.yaml` |

`.env.example` sets `WORKER_MEMORY_MB=2048` for local development. With that value the half-of-the-limit rule below does not hold. In a local test that resumes a large transcript, delete that line or change it to 4608.

## Transcript limit

The transcript in one checkpoint (the root and all subagents together) must not exceed 512 MiB. One part must not exceed 16 MiB. Three places check with the same values.

1. Before the worker uploads the checkpoint (`captureTranscripts`, before the manifest is uploaded and committed).
2. Before the API's finalize reads the parts. This check is the authority.
3. Before restore downloads the parts (`#checkManifest`).

The size is the whole JSONL that remains after compaction. The engine (the Claude Code CLI) does not re-read what came before the last compaction when it resumes, but the platform stores and restores the whole file. So the limit applies to the size of the whole file.

### 80% warning

- The first time the transcript of a committed checkpoint reaches 80% of the limit (409.6 MiB), the platform sends one SSE `system` event (`transcript_near_limit`) and sets the session detail `attention` to `TRANSCRIPT_LIMIT`. It does not block anything.

### When the limit is exceeded

- The worker's pre-check (before the workspace is uploaded) or finalize (before the parts are read) records `transcript_too_large` (`transcript_part_too_large` when one part is over) in the session's `durability.checkpoint_pending_reason`. The first time it is recorded, one SSE `system` event (`transcript_limit_reached`) is sent.
- A turn that went over the limit ends as `completed`, as it ran, but its checkpoint is not committed.
- After that, a new message is refused with 409 `CHECKPOINT_UNAVAILABLE`, and turns already in the queue do not run. To go on, create a new session or use `start_fresh` on the recovery path. Close is also 409 `CHECKPOINT_UNAVAILABLE`. Terminate and then close with recovery close.
- An interrupted turn is different. If its checkpoint is refused, the turn ends as `outcome_unknown` (`interrupt_checkpoint_unavailable`) and the session goes to `recovery_required`.
- The last committed checkpoint remains as the restore point. The one turn that went over the limit has no checkpoint, so after the worker changes, its context is not carried over (session detail attention `CONTEXT_GAP`).

## Worker memory and transcript size (measured)

The rule (set on 2026-10-21): **the worst-case peak when resuming a transcript with no compaction must be at most half of the worker memory limit.** The other half is margin for the work of the first turn, transcript shapes that were not measured, and differences between engine versions.

### How it was measured

We measured on a dedicated compose stack (fake model, cgroup v2). The source worker put a synthetic transcript into the mirror, checkpointed, and paused. Then a new worker restored that checkpoint and ran the first resume turn. Throughout, every 0.5 seconds, we recorded the cgroup of the worker container (`memory.peak`, anon, file, shmem, swap, oom_kill) and the VmHWM of each process. `memory.peak` includes reclaimable page cache (file). We counted it toward the rule anyway. The worker image has claude-agent-sdk 0.3.270 and Claude Code CLI 2.1.270.

### 4608 MiB limit (the current default)

| transcript | compaction | first resume turn | memory.peak MiB (of limit) | anon | file | swap | OOM | worker (bun) VmHWM | CLI VmHWM |
|---|---|---|---|---|---|---|---|---|---|
| 511 MiB | none | succeeded | **1970 (43%)** | 1054 | 710 | 0 | 0 | 546 | 1129 |
| 511 MiB | yes | succeeded | 1338 (29%) | 533 | 716 | 0 | 0 | 588 | 237 |
| 64 MiB | none | succeeded | 726 (16%) | 558 | 75 | 0 | 0 | 504 | 329 |

### 6144 MiB limit (measured for comparison)

| transcript | compaction | first resume turn | memory.peak MiB (of limit) | anon | file | swap | worker (bun) VmHWM | CLI VmHWM |
|---|---|---|---|---|---|---|---|---|
| 600.0 MiB | none | succeeded | 2178 (35%) | 1301 | 745 | 0 | 626 | 1308 |
| 600.1 MiB | yes | succeeded | 1029 (17%) | 453 | 609 | 0 | 497 | 236 |
| 799.4 MiB | none | succeeded | 2785 (45%) | 1669 | 852 | 0 | 597 | 1727 |
| 799.1 MiB | yes | succeeded | 1392 (23%) | 671 | 996 | 0 | 716 | 234 |
| 64.9 MiB | none | succeeded | 839 (14%) | 508 | 279 | 0 | 437 | 326 |
| 150.2 MiB | none | succeeded | 828 (13%) | 501 | 151 | 0 | 487 | 492 |

### How to read it

- The worker (bun) uses 440 to 720 MiB whatever the transcript size, because restore streams part by part.
- The share that grows with size is the engine (the CLI). Without compaction the engine uses about **210 + 1.85 × T MiB** (T is the transcript in MiB). At 511 MiB the formula gives 1155 MiB and the measurement was 1129 MiB. With compaction, the engine's share is about 235 MiB whatever the size.
- The total peak, with page cache added, grows by about 3 MiB per 1 MiB of transcript in the 150 to 800 MiB range (828 MiB at 150.2 MiB, 2178 MiB at 600 MiB, 2785 MiB at 800 MiB). The 256 and 400 MiB values in the table below are **estimates** interpolated on this line.

## Why 512 MiB / 4608 MiB

For each candidate limit we compared the memory needed and the sessions per node. The memory is 2 × peak rounded up to a multiple of 512 MiB. The session count assumes a node with 30 GiB (30720 MiB) allocatable. The distribution is 12 real transcripts measured on two development machines on 2026-10-21. The top 10 on one machine are 400.1, 217.2, 113.4, 102.0, 96.3, 86.0, 85.2, 78.8, 70.4 and 68.5 MiB, and the top 2 on the other machine are 591.8 and 150 MiB. The sample collects only the top values, so it does not represent the whole distribution.

| Limit | Peak without compaction | Memory by the half rule | Sessions per node | Within the limit in the distribution | 80% warning |
|---|---|---|---|---|---|
| 256 MiB | 1146 MiB (estimate) | 2560 MiB | 12 | 10/12 | 204.8 MiB |
| 400 MiB | 1578 MiB (estimate) | 3584 MiB | 8 | 10/12 | 320 MiB |
| **512 MiB** | **1970 MiB (measured)** | 4096 MiB → **4608 MiB** | **6** | **11/12** | **409.6 MiB** |
| 600 MiB | 2178 MiB (measured) | 4608 MiB | 6 | 12/12 | 480 MiB |
| 800 MiB | 2785 MiB (measured) | 5632 MiB | 5 | 12/12 | 640 MiB |

- 512 MiB holds 11 of the 12 observed. Even the second largest, the 400.1 MiB session, does not trigger the warning. The one over is the 591.8 MiB session. Such a session gets the warning at 409.6 MiB and moves to a new session.
- At 400 MiB, the checkpoint of the 400.1 MiB session would be refused at once. At 256 MiB, even the 217 MiB session would fall in the warning zone.
- Other published systems also keep the active record small. Temporal ends an execution when its event history reaches 50 MB ([defaults](https://docs.temporal.io/self-hosted-guide/defaults)). Inngest caps run state at 32 MiB ([usage limits](https://www.inngest.com/docs/usage-limits/inngest)). The optional `CLAUDE_CODE_TRANSCRIPT_LOCAL_GC` of Claude Code deletes what came before the compaction when the file passes 5 MB ([env vars](https://code.claude.com/docs/en/env-vars)). We found no case that restores hundreds of MiB whole (surveyed 2026-10-21).
- The memory is 4608 MiB, not 4096 MiB. The measured peak of 1970 MiB at 512 MiB leaves only 78 MiB under half of 4096 MiB (2048). At 4608 MiB the margin is 334 MiB.

## Concurrent sessions per node

A worker Pod has requests equal to limits (Guaranteed QoS). So the number of workers on one node is:

```text
sessions per node = floor((node allocatable memory - sum of other Pod requests on the node) / worker.memoryMb)
```

With a dedicated worker node group (`worker.nodeSelector`, `worker.tolerations`), the share of other Pods is about the DaemonSets. On a node with 30 GiB allocatable, taking the DaemonSet share as 0:

| `worker.memoryMb` | Sessions per node |
|---|---|
| 2048 | 15 |
| **4608 (current)** | **6** |
| 6144 | 5 |

CPU is counted the same way (`worker.cpus`, default 1). Usually memory fills first. Each session also gets one workspace PVC (`worker.workspace.quotaMb`, 4096 MiB by default). The restored transcript (up to 512 MiB) fits inside it along with the working tree, the git objects and the restore spool.

On the local Docker execution base, `EXECUTION_SLOT_LIMIT` (default 10) workers share one machine's memory. The limit is a cgroup cap, not a reservation, so if they do not all fill at once it can run over. Even so, if slots × 4608 MiB far exceeds the machine's memory, you get OOM.

## How to adjust, and the cost

| Method | What it does | What you gain | Cost |
|---|---|---|---|
| ① Lower `worker.memoryMb` | Change one value (`WORKER_MEMORY_MB`, applied from the next launch) | More sessions per node. For example 3584 MiB gives 8 on a 30 GiB node | The room to resume a large transcript with no compaction shrinks with it. To keep the half rule, lower the limit too (about 400 MiB for 3584 MiB, an estimate). The limit is a code constant, so it needs a build |
| ② (not available today) Overcommit with `requests` below `limits` | Set the worker Pod requests of the chart below its limits | Many more sessions per node when sessions are small. In the measurements, the resume peak of 64 to 150 MiB transcripts was 726 to 839 MiB | Today the chart and the scheduler create Pods only with requests = limits. Changing it needs a code change. QoS drops to Burstable, and when several large sessions resume at once, node memory pressure causes OOM kills or evictions |
| ③ Grow the node group | Add worker nodes or make nodes bigger | More sessions in total, with the per-session guarantee unchanged | Cost goes up. No code change |
| ④ (not available today) Pod size by session size | The scheduler picks the Pod memory from the size of the transcript to restore | Small sessions start small, and only large ones start large | Needs a code change. The scheduler must know the checkpoint size before launch, and it must handle a transcript that grows inside the same Pod while it runs |

We do not recommend raising only the limit (`MAX_TRANSCRIPT_BYTES`) and leaving memory alone. When the resume of a large transcript with no compaction hits the limit, the worker keeps restarting and the session becomes `recovery_required`. When you change the limit, measure again with the method on this page.

## Index limits for results (`out/`)

At each checkpoint the worker indexes the regular files under `out/` in the working directory whatever their git state, puts them in the manifest `outputs`, and uploads one object per file. The limits are `DEFAULT_OUTPUT_LIMITS` in `apps/worker/src/workspace-outputs.ts`.

| Value | Default | When exceeded |
|---|---|---|
| One file `maxFileBytes` | 64 MiB | The file stays only as `{path, bytes, omitted: "too_large"}` and is not uploaded |
| Upload total of one checkpoint `maxTotalBytes` | 256 MiB | From the file that pushes the total over, files become `too_large` |
| File count `maxFiles` | 1,000 | In path order, files after the 1,000th are left out of the list. The count is in `outputs_dropped` of the publish log |

- A checkpoint does not fail when it goes over the index limits. The git bundle limit (256 MiB) and the workspace quota are unchanged, so a large `out/` file that git tracks, or that a session without a repository puts in the bundle, is caught separately by those limits. An untracked `out/` file that git does not ignore is still uploaded as an untracked object for restore, even when it is `too_large` in the index.
- The manifest limits (20,000 objects, 8 MiB) do not fail the checkpoint either. The results list holds only as many as the objects used for restore leave, and files beyond that are counted in `outputs_dropped`. If the list pushes the manifest over 8 MiB, that checkpoint is uploaded without `outputs`, and the reason is in `outputs_refused` of the publish log. In both cases the objects of the dropped files are already uploaded and no manifest points at them, and the next checkpoint uploads those files again.
- Files are read into memory one at a time. What this adds to worker memory is at most the one-file limit (64 MiB).
- Symlinks, anything that is not a regular file, and names the manifest does not accept, such as `.git` or a name that is not UTF-8, are not in the list. If `out` itself is a symlink, the list is empty.
- The same digest is uploaded once. A digest the previous checkpoint already uploaded points at that object and is not uploaded again.
- The objects are at `sessions/<id>/checkpoints/<revision>/<attempt>/<publish>/outputs/<sha256>`. The control plane checks the size and digest at finalize and holds the version. The checkpoint GC does not delete a result object that a retained checkpoint points at.

## Deployment order

A change that alters these values raises the control-host and worker images **in the same release**. The worker (capture, restore) and the API (finalize) check the limit separately. So if only one side has the new value:

- Only the API has the old value (a smaller limit): finalize refuses a large checkpoint and records `transcript_too_large`. The session stops accepting new turns, as above. A session that is within the limit by the worker's measure can stop this way too.
- Only the worker has the old value (a smaller limit): it refuses to restore a large checkpoint, and refuses to capture one with the smaller limit.

A release that carries the migration adding the over-limit reasons (`transcript_too_large`, `transcript_part_too_large`) and the `checkpoints.transcript_bytes` column deploys in the order migration → **all** control-host (api) instances → worker image. An old api rejects the new reason the worker sends with 400, and a new worker fails the capture when that report fails. Roll back only to a build that knows these reasons. An older build throws an exception when it reads, on the worker path, a session that has one of these reasons.

A release that carries the manifest `outputs` deploys **all** control-host (api) instances → worker image. The manifest codec of an old api rejects an unknown field, so a new worker cannot commit a checkpoint it wrote for a session that has `out/`. Roll back only to a build where both api and worker know this field. An older build cannot read a checkpoint that carries `outputs` as a restore point.

`WORKER_MEMORY_MB` (`worker.memoryMb`) applies from the next launch. Running workers are not replaced.
