mainをKubernetesに載せる手順です。chartのソースは`deploy/helm/werft`にあり、`main`のマージと`v*`タグのたびに`oci://ghcr.io/jeongjaesoon/werft`へ公開されます。既定値は一般的なKubernetes(kind含む)で動きます。AWS専用の値(ALB Ingress、IRSA、ECR、External Secrets)はchartの`values-aws.example.yaml`にだけあります。各コンポーネントの動作と環境変数は[Kubernetes実行backend](https://jeongjaesoon.github.io/werft/ja/run-server/self-hosting/operate/kubernetes-backend/)、バックアップは[backup-restore.md § Kubernetesインストール](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/backup-restore.md#kubernetes-설치)にあります。

**現在の状態:** 公式リリース(`v*`タグ)はまだありません。`main`のマージごとに公開されるchartには、そのrunのイメージdigestとworker runtimeが入っているので、リポジトリのcheckoutなしで[公開chartでインストール](#公開chartでインストール)します。リポジトリの`values.yaml`はdigestが空なので、checkoutのパスでインストールするときはdigestを自分で入れます。そのままではrenderが失敗します。

Docker単一サーバーのインストール(`local-docker`実行基盤、compose)は引き続き運用します。その手順は[server-deployment.md](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/server-deployment.md)で、公開イメージでインストールする順序は[単一サーバーの設置](https://jeongjaesoon.github.io/werft/ja/run-server/self-hosting/single-server/)にあります。このページはその隣にある2つ目のインストール経路です。

worker Pod 1つのメモリ(`worker.memoryMb`)はtranscript上限に合わせた値で、requests = limitsなのでノードあたりの同時セッション数を決めます。ノードの大きさを決める前や、この値を変える前に[容量管理](https://jeongjaesoon.github.io/werft/ja/run-server/self-hosting/operate/capacity/)を読んでください。

コマンドごとに、どこで確認したかを書いています。**kind**は`deploy/kind/up.sh`で立ち上げたクラスターで実行したコマンド、**AWS専用**はAWSのリソースが必要でローカルでは実行できないコマンドです。**kind**の表示は、次の2つの場合に限って、ドキュメントのブロックそのままの実行を意味しません。直接インストールのSecretブロックは`up.sh`が作る形と違い、ドキュメントのブロックそのままでは実行していません。「公開chartのアップグレード」のコマンドは、公開chartではなくfixture chartで実行しました。アップグレード前の検査の直前イメージの経路(`lookup`で直前イメージを読む分岐と、直前イメージを外したり変えたりする実際の`helm upgrade`)は、kindでも実行していません。

## 準備

- NetworkPolicyを強制するCNI。強制しないCNIではworkerの隔離がありません。kind v0.33の既定CNI(kindnet)は強制します。EKSではVPC CNIのnetwork policy agentをオンにします。
- PostgreSQL 16とS3 bucket。既定の保護モード`locked`はversioningとObject Lockがオンのbucketを要求し、そうでなければapiが起動を拒否します。
- 公開chartでインストールするときはイメージdigestがchartの中にあるので、この項目は飛ばします。checkoutのchartでインストールするときは、3つのイメージ(control-host、egress-proxy、worker)のdigestを控えておきます。`values.yaml`の既定名が公開先なので、公開イメージのdigestだけを入れれば済みます([公開chartでインストール](#公開chartでインストール)の`helm show values`で読みます)。kindでは`deploy/kind/up.sh`がcheckoutからビルドして代わりにします。公開イメージを使えないときは、イメージを自分でビルドしてregistryにpushし、valuesの`images.registry`と`images.*.repository`をそのregistryに変えます(`values-aws.example.yaml`の形式)。chartはtagを受け取らず、`<registry>/<repository>@<digest>`だけでrenderします。digestがなければrenderが失敗します。schedulerが受け取る`WORKER_IMAGE`も`repository@sha256:<digest>`の形式でなければなりません。
- `secrets.name`(既定`werft`)のSecret。キーは下のとおりです。値はコマンド引数やシェルhistoryに残しません。

| キー | 読む場所 |
|---|---|
| `DATABASE_URL` | api、scheduler、reconciler、slack、migrate、checkpoint GC |
| `EGRESS_AUTHORIZER_TOKEN` | api、egress-proxy(同じ値) |
| `AWS_ACCESS_KEY_ID`、`AWS_SECRET_ACCESS_KEY` | api、checkpoint GC。`secrets.objectStoreKeys: true`のときだけ。`false`ならAWSの既定credential chain(IRSA)で署名します |
| `secrets.catalogEnv`の名前(既定`ANTHROPIC_API_KEY`) | apiだけ。設定ドキュメントが`value_env`で指すproviderとリポジトリの認証情報。slackは受け取りません |
| `PLATFORM_SECRET_KEY` | api、slack。必須。64文字のhex master key。コンソールで保存した認証情報を封印します。Secretになければ、Podは起動しません |

## インストール順序

順序はSecret → イメージdigest → migrate → 制御領域です。chartではSecretとschemaだけが先でなければならず、残りはHelmがhookで整えます。

1. ExternalSecret(使うとき、hook weight -10)がSecretを書きます。
   upgradeでは、その次にupgrade-check Job(hook weight -5)が、再開できなくなるセッションを検査します。失敗するとHelmが止まり、migrateも走りません([アップグレード前の検査](#アップグレード前の検査))。
2. migrate Job(hook weight 0)がschemaを上げ、ファイルカタログのあったchartから上げる場合は、古いConfigMapを設定として取り込みます(下の「ファイルカタログからのアップグレード」)。失敗するとHelmが止まり、Deploymentは変わりません。
3. api、egress-proxy、reconciler、scheduler、slackのDeploymentがまとめて適用されます。互いに待たず、それぞれprobeを通ればreadyになります。scheduler・reconciler・slackは最初のpassが終わるまでreadyになりません。

### kind(ローカル)

`deploy/kind/up.sh`が上の順序を一度に行います。クラスターとregistryの作成、イメージのビルドとpush(digestの確保)、namespace・PostgreSQL・LocalStack・Secretの作成、`helm upgrade --install`、rolloutと`/readyz`・`/docs`の確認までです。kubeconfigは`~/.kube/config`ではなく`~/.cache/agent-platform/kind/<cluster>/kubeconfig`に書きます。**kind**

```bash
CLUSTER_NAME=<cluster> REGISTRY_PORT=<port> deploy/kind/up.sh
export KUBECONFIG=~/.cache/agent-platform/kind/<cluster>/kubeconfig
```

`CLUSTER_NAME`(既定`agent-platform-dev`)と`REGISTRY_PORT`(既定5001)は省略できます。ほかのクラスターやregistryと衝突するときに変えます。削除するコマンドは`CLUSTER_NAME=… deploy/kind/up.sh down`です(クラスターとregistryコンテナだけを消します)。

`EXTRA_VALUES=<ファイル>`を渡すと、valuesファイル1つをほかのvaluesファイル(モデル用を含む)の上に最後に重ねます。ノートPCでapiとegress-proxyを1つずつだけ立てるときに使います(`api.replicas: 1`、`egressProxy.replicas: 1`)。

### 公開chartでインストール

リポジトリのcheckoutは要りません。バージョンは必ず`--version`で正確に書きます。リリースはタグから`v`を除いた形(`v1.2.3`なら`1.2.3`)、`main`のマージは`<Chartバージョン>-main-<12>`で、`<12>`はcommit SHAの先頭12文字です。`main`バージョン同士の順序に意味はありません(プレリリースの比較がSHAの文字列を比べるためです)。そのため`--devel`で「最新」を選ばず、[Images run](https://github.com/JeongJaeSoon/werft/actions/workflows/images.yml)でマージしたcommitを探して書きます。パッケージは匿名で取得します。

```bash
VERSION=0.1.0-main-<12>
helm show chart oci://ghcr.io/jeongjaesoon/werft --version "$VERSION"
helm show values oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" | sed -n '/^images:/,/^$/p'
```

`images`のdigestと`images.worker.runtime`が、そのrunの公開した値です。パッケージ1つが3つのイメージとruntimeをまとめて持つので、valuesにもう一度書きません。次の節のnamespace、Secret、インストールごとのvaluesファイルを用意したら、chartのパスだけを替えてインストールします。

```bash
helm upgrade --install werft oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
  --namespace werft -f values-<installation>.yaml --timeout 10m
```

インストールごとのvaluesファイルには、`images.worker`・`images.controlHost`・`images.egressProxy`のdigestを書きません。書くと次のchartの値をずっと上書きします。公開されたdigestは`linux/amd64`と`linux/arm64`を持つindexなので、ノードは自分のアーキテクチャを取得します。kindのインストール検査はamd64でだけ動きます。

### 直接インストール

namespaceとSecretを先に作ります。Secretはキーごとにファイル1つのディレクトリ(`0700`、ファイル名がキー)から作ります。値がコマンドラインに現れません。**kind**

```bash
kubectl create namespace werft
kubectl -n werft create secret generic werft --from-file=<secret-dir>
```

インストールごとの値はvaluesファイル1つにまとめます。最低限、3つのイメージのdigestとcheckpoint bucketが入ります。接続・リポジトリ・MCPサーバー・上限はvaluesにありません。インストールの後でコンソールから加えるか、`bun run settings:k8s import --document - < settings.json`で取り込みます([api-server.md](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md#설정-문서-가져오기내보내기))。既定値と説明は`values.yaml`にあります。同じコマンドが最初のインストールとアップグレードの両方を行います。**kind**(`-f deploy/kind/values.yaml -f <digestだけを入れたファイル>`)

```bash
helm upgrade --install werft deploy/helm/werft \
  --namespace werft -f values-<installation>.yaml --timeout 10m
kubectl -n werft get job werft-migrate
for d in api egress-proxy reconciler scheduler; do
  kubectl -n werft rollout status deploy/werft-$d --timeout=600s
done
```

release名に`werft`が入っていなければ、リソース名は`<release>-werft-…`になります。

chart名が`agent-platform`だったときにインストールしたreleaseは、その場でアップグレードできません。リソース名が変わり、upgrade-check Jobが既存のschedulerを見つけられずに止まります。セッションが終わっていることを確認して古い名前で削除し(`helm -n agent-platform uninstall agent-platform`、残るものは[削除](#削除)を見ます)、新しくインストールします。ファイルカタログを使っていたreleaseは、削除する前に[「ファイルカタログからのアップグレード」](#ファイルカタログからのアップグレード)のConfigMapを保存します。

最初のインストールが失敗したら(イメージパスやpull権限のエラーが多い)、値を直して同じコマンドをもう一度実行します。Helmはreleaseが`failed`で残っているのでこれをupgradeとして扱い、そのためupgrade-check Jobが初めて走ります。scheduler Deploymentがなく、DBが空かセッションがなければ、Jobは`proceed`で終わってインストールが続きます([アップグレード前の検査](#アップグレード前の検査))。Deploymentが作られた後で失敗したなら、再試行は通常のupgradeの規則に従います。workerイメージを直した再試行はここで止まるので(`check_failed`、runtimeを入れていたなら`refused`)、セッションを始めていなければ[削除](#削除)してからインストールし直します。

## AWSの値を入れる

`values-aws.example.yaml`をインストールごとのファイルにコピーし、placeholder(account id、ARN、host、digest)を埋めて、`values.yaml`の上に重ねます。下のrenderはローカルで動きますが、その結果を適用するのは**AWS専用**です。

**ALBは内部網専用です。** このインストールは内部網からだけ届く入口を前提にするので、例のIngress annotation `scheme`はすでに`internal`です。インストールごとのファイルでも`internet-facing`に変えません。`render-check`が例のrenderで`internet-facing`を拒否します。適用の後は、ALBが内部網のsubnetにできたことを確認します(**AWS専用**)。

### Webコンソールと`/internal`

Webコンソールはapiが3000番で配信します。`ingress.console.enabled: true`(既定`false`)にすると、Ingressが`/`(Prefix)をapi Serviceへ送ります。同じポートにworker用の`/internal`もあり、`/` Prefixは`/internal`にも一致します。そのためchartは`/`の前に`/internal`(Prefix)のルールを置き、そのルールはapiではなく、annotation `alb.ingress.kubernetes.io/actions.block-internal`のfixed-response(404、`text/plain`)へ送ります。AWS Load Balancer Controllerは長いPrefixを短いPrefixより先に評価するので、`/internal`とその配下のパスはALBが404で答えます。`render-check`が、このルールが`/`より前にあるか、404 actionを指しているか、残りのパスがapi Serviceの`http`(3000)ポートへ行くかを検査します。

このルールが効くのはALBだけです。ほかのcontrollerは`block-internal`というServiceがないパスを飛ばして、`/`で`/internal`を開けてしまうことがあるので、`ingress.className`が`alb`でなければchartはrenderを拒否します。`/internal`のリクエストを404ルールの外へ送れるannotation(`alb.ingress.kubernetes.io/`の`actions.*`・`conditions.*`・`transforms.*`・`group.*`、`kubernetes.io/ingress.class`)が`ingress.annotations`にあるときも、renderを拒否します。IngressClassの`IngressClassParams`がこのIngressをほかのIngressと同じgroupに入れると、先のIngressのルールが先に評価されるので、コンソールをオンにするときは`alb` IngressClassがgroupを強制しないことを確認します(**AWS専用**)。

**オンにする条件。** apiはpercent-encodingをデコードしたパスでrouteします。ALBのpath patternには`%`を使えないので、`/%69nternal/…`のようにエンコードしたパスは`/internal`のルールに掛からず、`/`のルールを通ってapiに届きます。apiはデコードしていないパスが`/internal`で始まるときだけworkerルートへ送り、エンコードした変形には404 `NOT_FOUND`で答えます。この動作の入ったapiイメージを使うときだけ`ingress.console.enabled`をオンにします。

dot segment(`/x/../internal/…`、`/%2e/internal/…`)とバックスラッシュ(`/internal\…`、`/x/..\internal/…`)は、Bunがリクエストをapiに渡す前に`/internal/…`へ整えるので、apiはこれらのパスを普通の`/internal/…`と区別できません。これらのパスを止めるのはALBです。ALBはURIを正規化してからルールを評価しますが、何を正規化するのかはドキュメントに書かれていません。そのため、コンソールをオンにした後は、内部網から下のリクエストを送って確認します(**AWS専用**)。`/%69nternal/x`はapiの404(`application/json`)が期待値です(ALBがこれまで正規化して`text/plain`の404で答えても安全です)。ほかのパスはすべてALBの404(`text/plain`)が期待値です。apiの`/internal`ルートは状態にかかわらず`application/json`で答えます。そのため、dot segmentやバックスラッシュのパスに`application/json`の応答が来たら、ALBがそのパスをapiへ送ったということなので、コンソールをオフに戻します(ALBが400のような自分のエラーで拒否するのは安全です)。

```bash
for p in /internal/x /%69nternal/x /x/../internal/x /%2e/internal/x '/internal\x' '/x/..\internal/x'; do
  curl -s --path-as-is -o /dev/null -w "$p %{http_code} %{content_type}\n" "https://<host>$p"
done
```

オンにするときは、インストールごとのファイルに次を置きます。オフにすると`/`と`/internal`のルールが一緒に消え、`/v1`・`/docs`・`/healthz`・`/readyz`はそのままです。

```yaml
ingress:
  className: alb
  console:
    enabled: true
```

適用の後、内部網から確認します(**AWS専用**)。`curl -s -o /dev/null -w '%{http_code}\n' https://<host>/`は200です。`curl -si -X POST https://<host>/internal/worker/x`は404で、応答ヘッダーが`content-type: text/plain`で、apiが付ける`x-request-id`がないことが必要です。apiの404は`application/json`で`x-request-id`が付くので、ステータスコードだけではALBが止めたかどうかは分かりません。

```bash
helm lint deploy/helm/werft -f deploy/helm/werft/values-aws.example.yaml   # kind 머신에서 확인
helm template werft deploy/helm/werft \
  -f deploy/helm/werft/values-aws.example.yaml >/dev/null                          # kind 머신에서 확인
helm upgrade --install werft deploy/helm/werft \
  --namespace werft -f values-aws-<installation>.yaml --timeout 10m               # AWS 전용
```

| 値 | 何を変えるか |
|---|---|
| `images.registry`、`images.*.digest` | ECRのhostとそのイメージのdigest |
| `secrets.objectStoreKeys: false`、`serviceAccounts.api.annotations` | 静的なAWS keyの代わりにIRSA。apiとcheckpoint GCがこのroleでS3とSecrets Managerに署名します。schedulerとworkerにはS3の権限がありません |
| `secrets.externalSecret` | External Secrets OperatorがSecrets Managerの`remoteKey`(JSON、上のSecretキー全部。IRSAならAWS keyの2つは除く)からSecretを書きます。operatorのCRDが必要です |
| `ingress` | ALB Ingress。`scheme`は`internal`です(上)。`healthcheck-path: /readyz`、SSEのためにidle timeout 300秒。公開パス(`/v1`・`/docs`・`/healthz`・`/readyz`)だけをrouteし、`/internal`とauthorizer(3100)は開けません |
| `ingress.console.enabled` | 既定`false`。オンにするとWebコンソール`/`と`/internal`の404ルールが加わります。オンにする条件は[下](#webコンソールとinternal) |
| `config.egress.credentialAllowlist` | provider hostにcheckpoint bucketのvirtual-hosted endpointを加えます。workerのcheckpointのuploadとrestoreがcredential routeで外へ出ます |
| `worker.storageClass`、`worker.nodeSelector`、`worker.tolerations` | worker専用のnode groupとworkspace PVCのStorageClass(gp3) |
| `networkPolicy.enabled` | VPC CNIのnetwork policy agentがオンのときだけ効果があります |

静的なS3 keyを使う必要があるなら、`secrets.objectStoreKeys: true`のままにして、SecretにAWS keyの2つを入れます。両方あるときは、静的keyがIRSAより優先されます。

## healthの確認

probeはchartが決めます。人が確認するときも同じものを呼びます。

| コンポーネント | readiness | liveness | startup |
|---|---|---|---|
| api | `GET /readyz`(DB、schema、設定) | `GET /healthz`(HTTPだけ) | `GET /healthz`、最大120秒 |
| scheduler | `main.ts scheduler --health` | 同じ | 同じ。`intervalSec + passTimeoutSec + 39`秒まで待ちます |
| reconciler | `main.ts reconciler --health` | 同じ | 同じ |
| egress-proxy | `/app/src/healthcheck.ts` | 同じ | なし |

`/livez`はありません。livenessは`/healthz`です。**kind**

```bash
kubectl -n werft port-forward svc/werft-api 13000:3000 &
curl -fsS -w '\n' http://127.0.0.1:13000/readyz
curl -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:13000/docs
kubectl -n werft exec deploy/werft-scheduler -- bun run apps/control-host/src/main.ts scheduler --health
kubectl -n werft exec deploy/werft-reconciler -- bun run apps/control-host/src/main.ts reconciler --health
kubectl -n werft exec deploy/werft-egress-proxy -- bun run /app/src/healthcheck.ts
```

port-forwardは終わったらそのjobだけを止めます(`kill %1`)。AWSではport-forwardの代わりにIngressのhostで`/readyz`を呼びます(**AWS専用**)。

## API key、実行権限、設定ドキュメント

composeインストールの`bun run keys`・`grants`・`settings`はapiコンテナの中で動きます。Kubernetesインストールでは、`:k8s`が付いた同じ名前のscriptが`scripts/k8s-api.sh`でapi Podの中で同じCLIを動かします。Podがすでに`DATABASE_URL`を持っているので、秘密の値が運用者のシェルを通りません。kubectlの現在のcontextまたは`KUBECONFIG`がクラスターを、`NAMESPACE`・`RELEASE`(既定はどちらも`werft`)がインストールを選びます。**kind**

```bash
bun run keys:k8s create <owner_id> --scopes sessions:read,sessions:write,sessions:approve,sessions:control,sessions:recover
# stdout: 평문 key(한 번만 나온다), stderr: key_id
bun run keys:k8s revoke <key_id>
bun run grants:k8s revoke <session_id> --reason <text>
bun run grants:k8s restore <session_id> --reason <text>
bun run settings:k8s export > settings.json
bun run settings:k8s import --document - --dry-run < settings.json
```

scriptなしで呼ぶと次のようになります。`deploy/…-api`はapi Podを1つ選びます。3つのCLIはDBだけを使うので、どのPodでも同じです。

```bash
kubectl -n werft exec deploy/werft-api -c api -- \
  bun run apps/control-host/src/api/keys.ts create <owner_id> --scopes sessions:read
```

`Session catalog loaded`ログは、api PodがDBから読んだ上限とリポジトリ数を残します。

```bash
kubectl -n werft logs deploy/werft-api | grep 'Session catalog loaded'
```

## アップグレードとロールバック

アップグレードは、checkoutインストールならvaluesファイルのdigestを新しいイメージに変え、公開chartインストールなら[新しいchartバージョンへ上げた後](#公開chartのアップグレード)、インストールと同じ`helm upgrade --install`を実行します。migrate hookが先に走り、失敗するとDeploymentはそのままです。schedulerは`Recreate`なので、古いPodが落ちてから新しいPodが立ち上がります。その間はscheduler passが回りません(新しいworkerのlaunchと回収が止まります)。**kind**

```bash
helm -n werft history werft
helm -n werft rollback werft <revision> --wait --timeout 10m
```

ロールバックはmigrate hookを実行しません(`pre-rollback`ではありません)。DBは新しいschemaのまま残り、古いビルドは自分より先のschemaでもreadyになります(`/readyz`のschema検査は、自分のmigration一覧が適用済み一覧の先頭部分と同じかどうかだけを見ます)。そのため、ロールバックできないmigrationはデプロイしません。workerイメージを戻すときのcheckpoint互換は、先に[images-and-supply-chain.md § worker・control-hostのロールバックとincremental checkpoint](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/images-and-supply-chain.md#workercontrol-host-롤백과-incremental-checkpoint)を読みます。

### デプロイ順序

worker Podのイメージは、schedulerがlaunchするときに決まります。イメージは隔離stampに入らないので、upgradeが`images.worker`を変えても、すでに動いているworker Podは入れ替わらず、終わるまで古いイメージで動きます。入力のないworkerも`WORKER_IDLE_TIMEOUT_SEC`(既定1800秒)の間は残ります。新しいイメージはその後のlaunchから使われます。

- workerが送るprotocolフィールドを加えるリリースや、checkpoint manifestにフィールドを加えるリリースは、`images.controlHost`だけを変えたupgradeを先に行い、`images.worker`は次のupgradeで変えます。1回のupgradeでは、新しいworkerが古いapiより先に立ち上がらない保証がありません。フィールドごとの順序は[images-and-supply-chain.md § worker protocolフィールドを取り除く順序](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/images-and-supply-chain.md#worker-protocol-필드를-걷어내는-순서)にあります。
- DBの変更は[images-and-supply-chain.md § DBスキーマを変える順序](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/images-and-supply-chain.md#db-스키마를-바꾸는-순서)の拡張→切り替え→整理に従います。migrate hookがrolloutより先に走るので、古いapiと古いworkerが新しいschemaの上で動きます。
- 新しいcontrol-hostと直前リリースのworkerイメージの組み合わせは、CIがまだ検査していません。リリースの前に、kindや試用インストールで自分で確認します。`images.controlHost`だけを新しいdigestに、`images.worker`は直前リリースのdigestにしたvaluesでupgradeし、セッション1つがturn 1を終えるかを見ます。そのセッションのworker Podを`kubectl delete pod`で消した後、入力をもう1つ送り、新しいPodがcheckpointから続けてturn 2を終えるかを見ます。apiログにworkerリクエストの400 `BAD_REQUEST`がないことが必要です。`deploy/kind/up.sh`は`images.worker`を`--set`で上書きするので、`EXTRA_VALUES`ではworkerイメージを変えられません。直接`helm upgrade`します。

### 公開chartのアップグレード

公開chartは`images.worker.runtime`を持ち、`images.workerPrevious`は空にしてあります。直前イメージはchartには分からず、インストールごとに違うためです。workerのdigestが変わるupgradeは、対象の`images.workerPrevious`がいまデプロイされているイメージでなければ`refused`で止まり、承認でも越えられません([アップグレード前の検査](#アップグレード前の検査))。そのため、いまのイメージをファイルに保存して一緒に渡します。

```bash
VERSION=<새 버전>
DEPLOYED="$(helm -n werft history werft -o json | jq '[.[] | select(.status == "deployed")] | last.revision')"
CURRENT="$(helm -n werft get values werft --all --revision "$DEPLOYED" -o json | jq -r '.images.worker.digest')"
TARGET="$(helm show values oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
  | awk '/^  worker:/ {found = 1} found && /digest:/ {print $2; exit}')"
echo "deployed ${CURRENT}"
echo "target   ${TARGET}"
PREVIOUS=worker-previous.json
if [ -n "$TARGET" ] && [ "$CURRENT" != "$TARGET" ]; then
  PREVIOUS=worker-previous.next.json
  helm -n werft get values werft --all --revision "$DEPLOYED" -o json \
    | jq '{images: {workerPrevious: .images.worker}}' > "$PREVIOUS"
fi
set -- -f values-<installation>.yaml
if [ -f "$PREVIOUS" ]; then set -- "$@" -f "$PREVIOUS"; fi
if helm upgrade --install werft oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
  --namespace werft "$@" --timeout 10m; then
  if [ "$PREVIOUS" != worker-previous.json ]; then mv "$PREVIOUS" worker-previous.json; fi
fi
```

`--revision`を外すと、失敗したupgradeがあるときにそのrevisionの値、つまり上げようとしたイメージが出ます。workerのdigestが違えば、いまのイメージを候補ファイルに書き、upgradeが成功した後にだけ`worker-previous.json`をそのファイルに替えます。失敗したupgradeは保存ファイルに触れません。digestが同じなら、あるファイルをそのまま渡します。最初のインストールの後、workerが変わらないupgradeには、渡すファイルがまだなく、それで構いません。

- `worker-previous.json`はインストールの横に保管し、次のupgradeにも渡します。workerのdigestが同じupgradeでこのファイルを抜かすと、デプロイされた直前イメージが抜けます。アップグレード前の検査はそのときセッションを比べ、対象イメージ(現在のイメージと、あれば直前イメージ)のどちらとも組み合わせが合わないか、組み合わせが記録されていないセッションがあれば`refused`で止まります(承認できます)。うっかり抜かしたなら、承認せずにファイルを入れてもう一度実行します。選ばれたセッションがなく`upgrade.approvedSessions`が空なら通ります(前のupgradeの承認が残っていれば`refused`です)。検査が見えないセッションは、下の「検査が見ないもの」を読みます。同じ日にマージされた`main`のchartは、workerのdigestが同じことがあります。
- `--reuse-values`は使いません。古いchartの値を既定値として使うので、新しいchartバージョンなのにイメージはそのまま残ります。
- `helm get values --all`の全体をvaluesファイルとして渡しません。古いdigestが新しいchartの値を上書きします。`.images.worker`だけを取り出します。
- `v*`タグから公開したchartも、同じ手順に従います。

### ファイルカタログからのアップグレード

古いchartの`catalog` ConfigMapは、今回のchartにありません。Helmはhookが終わった後に古いリソースを消すので、pre-upgradeのmigrate Jobが同じConfigMapを`/legacy-config`に任意でマウントし、`settings import --from-dir /legacy-config --if-present`で取り込みます。次のupgradeからはConfigMapがなく、何もしません。一部のファイルだけがあるか値が壊れていれば、Jobが失敗してDeploymentは変わりません。

1. `PLATFORM_SECRET_KEY`を先にSecretに入れます。すでにあれば同じ値のままにします。
2. valuesから`catalog`の節を消して`helm upgrade`します。`api.extraEnv`に`PLATFORM_CONFIG_DIR`を置いていたなら消します。
3. 終わったら`bun run settings:k8s export`で加わった項目を見ます。`installation_profiles`にすでに行があれば、ファイルの上限は入れ直しません。手順と戻すときの下限は[api-server.md](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md#설정-문서-가져오기내보내기)にあります。

chart名が`agent-platform`だったreleaseは、削除して新しくインストールするのでConfigMapも一緒に消え、新しいchartは別の名前を探します。古いreleaseを消す前にConfigMapを新しい名前で保存し、`helm install`の前に作っておきます。migrate Jobはインストールのときも走り、そのConfigMapを取り込みます。ConfigMapには参照だけがあり、秘密の値はありません。

```bash
kubectl -n agent-platform get configmap agent-platform-catalog -o json \
  | jq '{apiVersion, kind, data, metadata: {name: "werft-catalog", namespace: "werft"}}' > catalog-configmap.json
# 옛 release를 지우고 namespace를 만든 뒤
kubectl apply -f catalog-configmap.json
```

### 変わるものごとのセッション継続方法

| 変わるもの | 動いているworker Pod | セッションが続く方法 |
|---|---|---|
| workerイメージ(`images.worker`) | 終わるまで古いイメージで動きます | 次のlaunchが、checkpointポインターのengine・SDK・CLI・profile digestの方式と同じイメージを、新しいイメージ(`images.worker`)、直前イメージ(`images.workerPrevious`)の順に選んで復元します。どちらも合わなければlaunchの前に`recovery_required`で止まります。そうしたセッションは下の事前検査がupgradeの前に示します |
| 隔離設定(stampに入る値: egress proxyのアドレス、保存容量、worker ServiceAccount、上限など) | staleになります。claimされたPodはturn境界までdrainしてから落ちます | 最後に終わったturnまでcheckpointが覆っていれば、新しいPodがPostgreSQLのポインターとS3のcheckpointから続けます。checkpointなしで終わったturnがあれば、セッションは`recovery_required`で止まります(`CONTEXT_GAP`)。drainの期限(`MAX_TURN_SECONDS` + 5分)を過ぎたturnは`outcome_unknown`になり、そのセッションは`recovery_required`で止まって運用者の判断を待ちます([execution.md § 契約が上がるときのclaim済みworkerのdrain](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/execution.md#계약이-오를-때-claim된-worker의-drain)) |
| ノードの入れ替え、Kubernetesのアップグレード | Podが消えます。SIGTERMを受ければdrainでreleaseし、受けられなければheartbeatが途切れます | releaseされていればすぐに、そうでなければschedulerがPodの消失を確認するかleaseが切れた後に回収されます。動いていたturnがなく、最後に終わったturnまでcheckpointが覆っていれば、次のlaunchがそのcheckpointから続けます。checkpointが遅れていればセッションは`recovery_required`で止まります(セッション詳細のattention `CONTEXT_GAP`)。確定していないturnがあれば、そのturnは`outcome_unknown`になり、セッションは`recovery_required`で止まります([execution.md](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/execution.md)) |
| checkpoint bucket(`config.checkpoints.bucket`) | bucketがstampにあるので、staleとして入れ替わります | 自動では続きません。古いbucketのオブジェクトは新しいbucketにありません。未回収のcheckpoint行があるのに、新しいbucketにobject versionが1つもなければ、apiは起動しません([api-server.md](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md))。Kubernetesインストールには、checkpointを別のbucketへ移す手順がありません。復元も同じbucketのversionを指します([backup-restore.md § Kubernetesインストール](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/backup-restore.md#kubernetes-설치))。未回収のcheckpointがある間は、bucketを変えません |

### アップグレード前の検査

`helm upgrade`は、migrateより先に(hook weight -5)`upgrade-check` Jobを、対象リリースのapiイメージで動かします。Jobは、回収されていないcheckpointのあるセッションごとにポインターの組み合わせを読み、対象リリースの`images.worker`と`images.workerPrevious`のどちらでも再開できないセッションを選びます。組み合わせを記録する前にコミットされたポインターも選びます。結果はJobログのJSON 1行です。

```bash
kubectl -n werft logs job/werft-upgrade-check
```

| `verdict` | exit | upgrade | 意味 |
|---|---|---|---|
| `proceed` | 0 | 進む | `upgrade.approvedSessions`が`affected`の`sessionId`と完全に同じです。選ばれたセッションがない、またはworkerイメージが同じでデプロイ済みの直前イメージがないか同じ、あるいはデプロイされたことがなければ、承認リストは空でなければなりません |
| `refused` | 2 | 止まる | 承認リストが1つでも違います(前のupgradeの承認がvaluesに残った場合を含む)。workerイメージが同じでも、デプロイ済みの直前イメージが対象から抜けるか変わると、セッションを比べるので、対象イメージ(現在のイメージと、あれば直前イメージ)のどちらとも組み合わせが合わないか、組み合わせが記録されていないセッションがリストに載ります。または、workerイメージが変わるのに対象の`images.workerPrevious`がいまデプロイされているworkerイメージではありません。この場合は承認では越えられません |
| `check_failed` | 1 | 止まる | DBを読めなかった、イメージの組み合わせが読めない、または下の表のとおり必要なのにない、デプロイされたworkerイメージが分からない場合です。デプロイされたworkerイメージがあるのに`UPGRADE_DEPLOYED_WORKER_IMAGE_PREVIOUS`がないときもここです(直前イメージがなければ空の値を渡します)。scheduler Deploymentがないのに、DBにセッションや一部のschemaがあるときもここです。越える設定はありません |

`images.worker.runtime`は最初のインストールではなくても構いません。upgradeで必要かどうかは、デプロイされた状態と対象の値で決まります。

| デプロイされた状態 | 対象 | runtimeがないとき |
|---|---|---|
| scheduler Deploymentがない、DBが空かセッションがない(最初のインストールの再試行) | どのworkerイメージでも、`images.workerPrevious`なし | `proceed` |
| workerイメージ1つ、runtime・直前イメージなし | 同じworkerイメージ、`images.workerPrevious`なし | `proceed` |
| workerイメージ1つ、runtime・直前イメージなし | 違うworkerイメージ | `check_failed`。対象に`images.worker.runtime`と、いまのイメージを入れた`images.workerPrevious`を置きます |
| runtimeか直前イメージがある | `images.worker.runtime`を除いた値 | `check_failed`。組み合わせなしにはセッションを検査できません |

runtimeの値を得る方法は、[設定リファレンス](https://jeongjaesoon.github.io/werft/ja/run-server/self-hosting/operate/configuration/#api設定)のAPI設定にあります。最小のvaluesのインストールはruntimeなしで始め、workerイメージを初めて変えるupgradeで、2つのイメージのruntimeを一緒に入れます。

`images.worker`をそのままにして、デプロイ済みの`images.workerPrevious`を外したり変えたりするupgradeは、セッションを比べます。対象イメージ(現在のイメージと、あれば直前イメージ)のどちらとも組み合わせが合わないか、組み合わせが記録されていないセッションがあれば`refused`で、そのリストを承認すれば通ります。組み合わせが記録されていないセッションは、イメージを変えるupgradeと同じく、どの場合でも選びます。デプロイ済みの直前イメージがなかったか同じなら、セッションを比べず、承認リストが空のとき`proceed`です(残った承認は`refused`です)。イメージだけが違って組み合わせが同じ再ビルドは、直前イメージを外してもセッションが現在のイメージで再開されるので、リストに載りません。

選ばれたセッションが再開できなくてもよければ、そのリストをそのままvaluesに入れて同じupgradeをもう一度実行します。承認はセッションの状態を変えません。`no_image`で選ばれたセッションは、再開するときに`recovery_required`で止まります。`unrecorded`で選ばれたセッションは新しいイメージで立ち上がり、復元の判定で続くか`recovery_required`で止まります。

```bash
helm upgrade --install ... --set-json 'upgrade.approvedSessions=["<sessionId>", ...]'
```

承認リストはrelease valuesに残ります。次のupgradeのたびに`--set-json 'upgrade.approvedSessions=[]'`で空にし、そのupgradeのリストを読み直して承認します。残ったリストは、そのupgradeの`affected`と違えば`refused`で止まりますが、同じでサポート窓の条件も合えば、そのまま通ります。

Jobは承認リストを`UPGRADE_APPROVED_SESSIONS`(JSON配列)、デプロイ済みのworkerイメージを`UPGRADE_DEPLOYED_WORKER_IMAGE`、デプロイ済みの直前イメージを`UPGRADE_DEPLOYED_WORKER_IMAGE_PREVIOUS`(なければ空)として受け取ります。デプロイ済みのイメージは、chartがいまのscheduler Deploymentの`WORKER_IMAGE`と`WORKER_IMAGE_PREVIOUS`を`lookup`で読んで渡します。直前イメージを読む`lookup`の分岐と、直前イメージを外したり変えたりする実際の`helm upgrade`は、クラスターで実行して確認していません。検査のエントリポイントだけを実際のPostgreSQLに対して動かして確認しました。上の表の例外を開けられるのは、chartが一緒に渡す`UPGRADE_DEPLOYED_STATE`だけです。`absent`はscheduler Deploymentがなく、namespaceの`default` ServiceAccountは読めたという意味です(そのため、この経路にはそのServiceAccountの`get`権限が必要です)。`unpinned`はDeploymentがruntime・直前イメージなしで動いている状態です。`helm template`とクライアントの`--dry-run`では`lookup`が何も読まず3つの値が空になるので、そのrenderで動かしたJobは`check_failed`になります。`--dry-run=server`はクラスターを読みますがhookを実行しないので、判定の代わりにはなりません。検査は、`DATABASE_URL`がこのインストールのDBだと信じます。別の空のDBを指していると`absent`の経路が通ります。最初のインストール(`pre-install`)と`scheduler.enabled: false`ではJobを作りません。Jobとschedulerが同じイメージを見るように、`WORKER_IMAGE`・`WORKER_IMAGE_PREVIOUS`・`WORKER_IMAGE_RUNTIME`・`WORKER_IMAGE_PREVIOUS_RUNTIME`は`*.extraEnv`、`config.limits`、`secrets.catalogEnv`では渡せません。渡すとrenderが失敗します。`images.worker`と`images.workerPrevious`で渡します。

**`helm rollback`の前。** rollbackはhookを実行しないので、同じコマンドをapi Podで直接実行します。値は戻すrevisionのもの(`helm get values --revision <revision>`)を入れます。

```bash
kubectl -n werft exec deploy/werft-api -- env \
  UPGRADE_DEPLOYED_WORKER_IMAGE='<지금 scheduler의 WORKER_IMAGE>' \
  UPGRADE_DEPLOYED_WORKER_IMAGE_PREVIOUS='<지금 scheduler의 WORKER_IMAGE_PREVIOUS, 없으면 빈 값>' \
  WORKER_IMAGE='<되돌릴 revision의 worker 이미지>' WORKER_IMAGE_RUNTIME='<그 runtime JSON>' \
  WORKER_IMAGE_PREVIOUS='<그 revision의 workerPrevious>' WORKER_IMAGE_PREVIOUS_RUNTIME='<그 runtime JSON>' \
  bun run apps/control-host/src/api/upgrade-check.ts
```

workerイメージを戻す通常のrollbackは`refused`です。戻すrevisionの`images.workerPrevious`が、いまデプロイされているイメージではないからです(検査は組み合わせではなくイメージ参照を比べます)。設定やDBを読めなければ`check_failed`です。いまのイメージで動いているworkerは、rollbackの後も終わるまでそのイメージの組み合わせでcheckpointを残しますが、検査はそのcheckpointを見られません。出力の`affected`は、検査の時点ですでに選んだセッションです。ロールフォワードが先です。それでも戻すなら、再開するときにschedulerが組み合わせでイメージを選びます。戻したrevisionのworkerイメージと直前イメージ(あれば)のどちらとも組み合わせが合わないセッション(いまのイメージが新しいSDK・CLIを載せていたなら、rollbackの間にいまのイメージでcheckpointを残したセッション)は`recovery_required`で止まります。`images.worker`をそのままにするrollbackは、いまデプロイされている直前イメージが戻すrevisionにもそのままあれば、承認リストが空のとき`proceed`で(残った承認は`refused`)、抜けるか変わるなら上のupgradeのようにセッションを比べます。このコマンドはhookではないので、rollbackを止めてはくれません。`refused`が出たら`affected`を読んで、戻すかどうかを決めます。デプロイされたworkerイメージがあるのに`UPGRADE_DEPLOYED_WORKER_IMAGE_PREVIOUS`を抜くと`check_failed`です。

**検査が見ないもの。** 単一サーバーのアップグレード検査([アップグレード](https://jeongjaesoon.github.io/werft/ja/run-server/self-hosting/upgrade/)を参照)と違い、この検査は対象イメージを実行しません。ポインターに記録された組み合わせ(engine・SDK・CLI・profile digestの方式)だけを比べ、実際のprofile digestは復元のときに判定されます。検査の後にwriterを止めて再検査することもしません。workerイメージが変わるupgradeは、対象の`images.workerPrevious`がいまデプロイされているイメージと同じでなければ通らないので、検査の後にいまのイメージのworkerが残すcheckpointは、対象のサポート窓の中にあります。workerイメージをそのままにして直前イメージを外すupgradeには、この保証がありません。直前イメージで動くworkerは、検査の後もその組み合わせでcheckpointを残せます。最初のcheckpointの前のセッションも同じです。そのため、直前イメージを外す前に、そのworkerが終わったかを先に見ます。それより古いイメージで動くworkerのセッションは、ポインターがすでにその組み合わせならリストに載ります。最初のcheckpointの前のセッションはリストにありません。この限界は、サポート窓から外れるすべてのイメージ、そして直前イメージを変えるupgradeにも同じです。対象イメージをregistryから取得できるかも見ません。取得できなければ、launchの失敗として現れます。

## 単一サーバー10ステップとの対応

[server-deployment.md](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/server-deployment.md)の各ステップが、Kubernetesのどこに行くかです。

| 単一サーバーのステップ | Kubernetesインストール |
|---|---|
| 1. ホストの準備 | クラスターとNetworkPolicyを強制するCNI、worker node group。XFS quotaの代わりにworkspace PVCの大きさ(上の「準備」) |
| 2. ネットワーク経路 | SSH tunnelの代わりに内部網のALB Ingress(**AWS専用**)。authorizer 3100とDBはクラスターの外に開けません |
| 3. 専用S3 | 同じです。静的keyの代わりにIRSA(上の「AWSの値を入れる」) |
| 4. releaseと設定の封印 | イメージdigestをインストールごとのvaluesファイル1つに置き、設定は設定ドキュメントで取り込みます |
| 5. インストールと最初の利用 | 「インストール順序」「healthの確認」「API key」の節 |
| 6. バックアップと復元 | RDSとS3の機能([backup-restore.md § Kubernetesインストール](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/backup-restore.md#kubernetes-설치)) |
| 7. アップグレードとロールバック | 「アップグレードとロールバック」の節 |
| 8. 物理的な再起動 | nodeが替わってもDeploymentが立ち上げ直します。EBS PVCはAZに結び付くので、workerが同じAZのnodeにもう一度付くかはEKSで確認します(**AWS専用**) |
| 9. Day 1運用 | 同じ点検。コマンドは`kubectl exec`・`bun run *:k8s`に替えます |
| 10. 証拠 | 同じです。`helm history`、`kubectl get job,deploy,pods`、`/readyz`の出力を残します |

## 削除

```bash
helm -n werft uninstall werft
```

**kind**。`helm uninstall`が残すものは次のとおりです。

- schedulerが作ったworker Pod、nonce Secret、workspace PVC。消す前に、セッションが終わったか(またはcheckpointされたか)を見ます。PVCを消すと、checkpointされていない作業が消えます。一覧: `kubectl -n werft get pods,secrets,pvc -l app.kubernetes.io/part-of=agent-platform,agent-platform.installation=<installationId>`
- hookで作ったmigrate Jobとupgrade-check Job、ExternalSecretとそれが書いたSecret(`creationPolicy: Orphan`)。手で作ったSecretも残ります。残ったJobは次のインストールを妨げません。同じ名前のhookが走るときにHelmが先に消します。いま消すなら`kubectl -n werft delete job werft-migrate werft-upgrade-check --ignore-not-found`を実行します。
