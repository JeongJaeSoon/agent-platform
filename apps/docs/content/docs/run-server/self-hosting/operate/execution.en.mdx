This page describes how the reconciler and scheduler start and reclaim workers, worker isolation, recovery of stuck sessions, and the limits and reclamation of the worker workspace and the worker network. The table of settings is in the [Configuration reference](/run-server/self-hosting/operate/configuration). The catalog, credentials and authentication are in [API server](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md).

## Reconciler, scheduler and worker isolation

A reconciler pass (`main.ts reconciler --once`, package script `reconciler`) handles one batch and then exits. It does not interpret the lease deadline itself: when the API receives a heartbeat it writes the deadline to `workers.lease_expires_at`, and the reconciler compares that time with the DB clock. Only the API reads `HEARTBEAT_TTL_SEC` (default 30; startup is refused if it is 20 or less, or above 86400, see [API settings](/run-server/self-hosting/operate/configuration#api-settings)), and the reconciler does not start if this value is set. To check only the targets before a real change, state dry-run explicitly. It redelivers automatically only unprocessed rows or `queued` turns. A row that is running, or whose state cannot be proven, moves the session to `failed` and is left as an explicit recovery target.

```bash
DATABASE_URL=postgres://postgres:dev@127.0.0.1:5432/sessions \
RECONCILER_DRY_RUN=true \
  bun run --cwd apps/control-host reconciler

DATABASE_URL=postgres://postgres:dev@127.0.0.1:5432/sessions \
RECONCILER_DRY_RUN=false \
  bun run --cwd apps/control-host reconciler
```

In the `apps` profile of compose, the `reconciler` service repeats this pass by default. `main.ts reconciler`, given only the role name, is the supervision loop (`apps/control-host/src/pass-loop`), and the pass runs in a child process that the loop starts (`main.ts reconciler --serve`). Each time the loop asks over IPC, the child runs one pass and waits for the next request. This is because starting bun anew and reloading the modules for every pass costs several times the CPU of the pass itself, and even on an idle stack one role used tens of percent of a core. The pool is still opened and closed anew on every pass. A failed pass, a pass killed for exceeding the time limit, and a pass that received a termination signal end together with the child, so the next pass runs in a new process. If the child dies between passes, it counts as a failed pass. Passes do not overlap; they run one after another. The healthcheck is `main.ts reconciler --health`. When the loop receives SIGTERM, it starts no new pass, sends SIGTERM to the pass in progress, and sends SIGKILL 10 seconds later. Every write is a transaction, so nothing is lost wherever it is cut off. The compose `stop_grace_period` is 20s. Compose gives `BUN_OPTIONS=--smol` to the three roles that use the supervision loop (reconciler, scheduler, slack). The loop, the child and the healthcheck all inherit this value, so the GC runs more often and the heap stays small. In a local stack measurement on 2026-11-04, memory per container fell by 5 to 23 MiB, and CPU rose by at most 6% over 120 seconds (slack 2.2 seconds to 2.3 seconds).

| Setting | Default | Meaning |
|---|---|---|
| `RECONCILER_INTERVAL_SEC` | 10 | Time to rest after a pass ends before the next pass |
| `RECONCILER_PASS_TIMEOUT_SEC` | 60 | A pass that exceeds this time is ended with SIGTERM and, 10 seconds later, SIGKILL, and counts as a failure. Keep it well above the roughly 45 seconds after which a pass stuck on the DB ends by itself on the pool timeout |
| `RECONCILER_MAX_CONSECUTIVE_FAILURES` | 3 | When failed passes continue this many times, the loop exits with 1 and `restart: unless-stopped` restarts it. With fewer failures, the next pass is the retry |
| `RECONCILER_HEALTH_STALE_SEC` | 90 | The healthcheck is unhealthy if the last finished pass failed, if the pass in progress has exceeded the time limit, or if no pass has succeeded for this long. A pass that hangs right after a success also becomes unhealthy at the time limit. It must be greater than `RECONCILER_INTERVAL_SEC + RECONCILER_PASS_TIMEOUT_SEC`, or startup is refused |
| `RECONCILER_STATUS_FILE` | `/tmp/reconciler-status.json` | The state the loop updates on every pass (`lastSuccessAt`, `lastDegradedAt`, `lastFailureAt`, `lastFailureReason`, `consecutiveFailures`, `lastPassDurationMs`, and `passDeadlineAt` of the pass in progress). The healthcheck reads it |
| `RECONCILER_BATCH_SIZE` | 100 | Upper limit on the rows each stage of a pass handles at one time (reclaiming orphans, leases and interrupts, closing interrupt and terminate receipts past their deadline as `unknown`, and input-waiting notifications). The next pass handles the remaining rows. The scheduler's terminate deadline sweep does not read this value and handles a fixed upper limit of 100 per pass |

Recent successes and failures can be seen with `docker compose -f infra/compose.yml exec reconciler cat /tmp/reconciler-status.json` and the log lines `Reconciler pass completed` and `Reconciler pass failed`. The reconciler service does not read an environment file: it refuses to start when it receives `HEARTBEAT_TTL_SEC`, which environment files commonly contain. Give the values above in the shell that runs `docker compose`. Compose does not pass `RECONCILER_STATUS_FILE` or `RECONCILER_DRY_RUN`, though. So the reconciler in compose writes its state to the default path whatever the shell values are, and it always really fixes things. Check with dry-run by running one pass directly as in the example above. The reconciler container has no Docker socket. The reconciler writes only the epoch fence and `desired_state = terminated` to the DB, and the scheduler removes the container and confirms its absence. Even if two reconcilers overlap or one restarts in the middle of a pass, each write is judged again under a row lock, so the same lease, interrupt or orphan is not handled twice (`apps/control-host/src/reconciler/overlap.integration.test.ts`).

The last stage of a pass is the tool call projection. It pairs the `tool_use` and `tool_result` events that accumulated since the previous pass and writes them to `tool_calls` and to the daily totals `tool_call_days`. The usage API (`GET /v1/usage/tools`) reads only these two tables and does not parse events again. It processes 5,000 events per transaction for 10 seconds per pass, and the next pass continues with what is left. If a batch hits the statement timeout (10 seconds), it cuts the batch to one tenth and processes it again, and commits the reduced size straight to `tool_call_progress.batch_size`. Even if the pass timeout (60 seconds) cuts a pass off, the next pass starts from that size, so a batch eventually gets through. A pass that ends without a timeout restores the size by 10 times (to NULL when it reaches the configured value). Every timeout logs `Tool call batch timed out` right away (`batch_size`, `retry_size`), and `Tool calls projected` at the end of the pass records the count as `timed_out_batches`. The position is `tool_call_progress.applied_through` (an event id). This cursor advances only through events older than 60 seconds, so an event with a lower id that was committed late is not missed. Events newer than that are read again by the next pass, and applying them again gives the same result. So it usually takes about one pass (a little over 10 seconds) for a new call to show up in the API. The first passes after a migration fill in all the existing events from cursor 0 (backfill). On a local PG16, projecting 20 million events without a break took about 26 minutes. Because the pass rests for `RECONCILER_INTERVAL_SEC` between passes, in practice it takes about twice that (around an hour), and during that time the API's tool totals are incomplete. Dry-run does not project.

A scheduler pass is also one-shot (`main.ts scheduler --once`, package script `scheduler`). The compose `scheduler` service repeats this pass with the same supervision loop (`main.ts scheduler`, healthcheck `main.ts scheduler --health`). The settings are `SCHEDULER_INTERVAL_SEC` (5), `SCHEDULER_PASS_TIMEOUT_SEC` (180; it must be greater than `EXECUTION_DOCKER_STOP_TIMEOUT_SEC` + `EXECUTION_DOCKER_REQUEST_TIMEOUT_SEC`, or startup is refused; for the kubernetes backend see [Kubernetes execution backend](/run-server/self-hosting/operate/kubernetes-backend)), `SCHEDULER_MAX_CONSECUTIVE_FAILURES` (3), `SCHEDULER_HEALTH_STALE_SEC` (200; it must be greater than interval + timeout, or startup is refused) and `SCHEDULER_STATUS_FILE` (`/tmp/scheduler-status.json`; compose does not pass it), and their meaning is the same as in the reconciler table above. A pass that was skipped because another pass held the lock ends with exit 75, which is neither a success nor a failure. If only skips continue, there is no success, so it becomes unhealthy after the stale time. A pass that did everything it had to but left sessions it cannot help in this pass ends with exit 76 (degraded). Those are sessions whose launch is in backoff (`launch_backoff_count`), that were just quarantined (`launch_quarantined_count`), or that have used up the replacement limit (`replacement_exhausted_count`). That state is in the DB and a restart does not clear it, so a degraded pass does not count as a consecutive failure and breaks the failure streak. Health treats a recent degraded pass as healthy but writes `completed degraded` in the reason, and the status keeps it as `lastDegradedAt` (`lastSuccessAt` is only for clean passes). If the same pass has even one other failure, it is exit 1 as before. When the loop receives SIGTERM, the pass in progress stops at the next safe point (the same place where it stops when it loses the pass lock) and reserves nothing more, and it is killed if it does not finish within 30 seconds. A worker stop that the pass was waiting for continues in the daemon even if the pass is killed (since Engine 25, a dropped request does not cancel the stop). The compose `stop_grace_period` is 45s. When it carries out a kill intent (terminate, lease expiry, quarantine), the pass does not wait for the worker to drain its turn. It requests the stop, and if that does not finish within 5 seconds, it counts that container in `kills_stopping_count` and moves on, without counting a failure. The daemon sends SIGKILL after `EXECUTION_DOCKER_STOP_TIMEOUT_SEC` has passed since SIGTERM, and the next pass confirms the container is gone and returns the slot. Replacing a claimed worker past its drain deadline and stopping an orphan container with no launch intent work the same way (orphans are counted in `orphan_stopping_count` and hold their slot until they are gone). Replacing an unclaimed worker waits. It has no turn, so it ends soon, and every replacement attempt uses up the replacement limit. Even so, on the path that deletes and recreates an unclaimed container, a pass may wait for one stop to the end. That is why the scheduler refuses to start when the pass timeout is smaller than the stop timeout + request timeout. If a container create or start request gets no answer within `EXECUTION_DOCKER_REQUEST_TIMEOUT_SEC`, it is not known whether the container was created, so it is not counted as a launch failure. It does not discard the nonce and sets no backoff. That pass ends as a failure (exit 1). The next pass inspects, and adopts the container if it exists (and starts it if it was only created). If it does not exist, only then is it counted as a launch failure. At that point it discards the nonce and sets backoff, so a create that never materializes does not hold the slot forever and is quarantined at the failure limit. A container that appears late after the discard is seen as a failed attempt and is deleted. When the daemon answers with a refusal (4xx, 5xx), it is counted as a launch failure as before. Stopping the scheduler does not end the workers. The slot is returned only after the pass confirms the worker is absent. A pass proceeds in this order: (1) compare the live `executions` rows against Docker (recreate with the same intent if the container is missing; if it exited, record `terminated` and remove it); (2) stop managed containers that have no launch intent after logging them, and delete worker networks whose container is gone or reattach the proxy to a network it dropped off; (3) for each unassigned session within `EXECUTION_SLOT_LIMIT`, commit the intent and then create the container; (4) reclaim the workspace volumes of ended sessions. The worker container does not receive the Docker socket or the host HOME. Its env is `WORKER_EXECUTION_ID`, `WORKER_EXECUTION_GENERATION`, `WORKER_BOOTSTRAP_NONCE` and `WORKER_GATEWAY_URL`, which are needed for the bootstrap claim; `HOME` pointing at a tmpfs; `HTTP_PROXY`, `HTTPS_PROXY` and `NO_PROXY` pointing at the egress proxy (both upper-case and lower-case spellings; `NO_PROXY` contains the proxy's own name); `WORKER_EGRESS_CREDENTIAL_URL` pointing at the proxy's credential route ([the credential route section of API server](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md#provider-키와-저장소-자격-증명은-worker에-가지-않는다)); and the names of the object store: `S3_BUCKET`, `AWS_REGION` and the session prefix `WORKER_OBJECT_PREFIX` (`sessions/<sessionId>/`). The scheduler does not start without the bucket and region. It does not receive the object store credentials or endpoint. The worker reaches the object store only through the proxy's object store route, and the boundary is that route (same section). The worker-side `scopedCheckpointObjectStore` (`packages/storage`) is only a fast failure that rejects a key outside the prefix before the request. The only file in the worker that imports `@werft-ai/storage` is `apps/worker/src/object-store.ts`, and `tests/architecture.test.ts` enforces this. In case the Docker daemon response echoes the body of the create request, the backend strips the nonce from error messages. The `/tmp` and HOME tmpfs are mounted owned by the worker uid/gid. Docker initializes the `/workspace` named volume from the same path in the image, so the worker image must pre-create `/workspace` owned by the worker uid (an image contract). The worker image (`apps/worker/Dockerfile`) is given by `WORKER_IMAGE`. The whole pass is serialized by a Postgres session advisory lock (`scheduler:pass`), and an overlapping run only logs and skips. When several installations share one Docker daemon, give each installation a different `EXECUTION_INSTALLATION_ID`. The scheduler does not start without this value (only the adapter has a default `local`, for tests). If two installations that use the same value share a daemon, they reclaim each other's containers as orphans.

```bash
DATABASE_URL=postgres://postgres:dev@127.0.0.1:5432/sessions \
WORKER_IMAGE=werft-worker:dev \
WORKER_GATEWAY_URL=http://host.docker.internal:3000 \
EXECUTION_SLOT_LIMIT=10 \
QUEUED_INPUT_LIMIT_PER_SESSION=20 \
STORAGE_LIMIT_BYTES=1073741824 \
MAX_TURN_SECONDS=3600 \
SESSION_COST_LIMIT_USD=25 \
PROVIDER_MAX_RETRIES=2 \
EXECUTION_INSTALLATION_ID=local \
EXECUTION_EGRESS_PROXY_URL=http://egress-proxy:3128 \
EXECUTION_WORKSPACE_QUOTA=off \
  bun run --cwd apps/control-host scheduler
```

A worker container attaches to only one **dedicated network**, `ap-net-<installationId>-<executionId>-g<generation>`, which the scheduler creates for each execution. This network is created with the bridge driver, `internal: true`, `EnableIPv6: false` and `com.docker.network.bridge.gateway_mode_ipv4=isolated`. Docker builds no route out of this network and keeps no host-side bridge address (IPAM gateway) in it. So the worker cannot directly reach the host, processes running on the host, the LAN, the instance metadata (`169.254.169.254`), other compose services or other workers. The only members of this network are the worker itself and the egress proxy. The scheduler treats **exactly one running container** with the label `agent-platform.egress-proxy=<installationId>` as that installation's proxy, and connects it to each network with the host name of `EXECUTION_EGRESS_PROXY_URL` as an alias. The worker points at that name through `HTTP_PROXY` and `HTTPS_PROXY`. The proxy address differs per network, so the host of `EXECUTION_EGRESS_PROXY_URL` must be a name, and IP literals and `localhost` are rejected. The `egress-proxy` service in compose carries this label. The worker has no `host.docker.internal:host-gateway` mapping: the gateway also goes through the proxy.

The blocking policy is versioned through the proxy's two lists. `EGRESS_ALLOWLIST` holds public destinations (`host:port`), and a destination passes only if all its resolved addresses are public unicast. `EGRESS_PRIVATE_ALLOWLIST` holds destinations that are known to be in a private range and allowed (the gateway). In the compose defaults, `EGRESS_ALLOWLIST` is empty and `EGRESS_PRIVATE_ALLOWLIST` is `api:3000,host.docker.internal:3000`. The provider, repositories and the object store are in neither list. Reaching them through the forward proxy would bypass each one's credential route. The provider would be reached with any key the worker holds, outside cost metering; a public repository would be readable without a token; and the object store must go through the route where the API verifies and signs each request. The local SeaweedFS also checks SigV4, but storage authentication alone cannot replace the per-session prefix permission. These go in the lists that only the credential route reaches: `EGRESS_CREDENTIAL_ALLOWLIST` (compose default `api.anthropic.com:443`; add `github.com:443` if you use GitHub repositories) and `EGRESS_CREDENTIAL_PRIVATE_ALLOWLIST` (local stack default `fake-git:3000,fake-messages:4010,fake-mcp:4020,localstack:4566`, `infra/compose.local.yml`). If a destination of the credential list is also in the forward list, the proxy refuses to start. So if such a value remains in the forward list of an environment file, you must delete it before the proxy comes up. The comparison is on the `host:port` exactly as written, so writing the same upstream under another name or IP is not caught. `.env.example` has the same values (`tests/images.test.ts` ties the two together). Both lists reject a name that resolves to link-local (`169.254.0.0/16`, `fe80::/10`), multicast or reserved addresses, so rebinding where a name on the allowlist resolves to a metadata address is also blocked. A host or port not in the list gets `403` for both CONNECT and absolute-form, and a request that is not absolute-form gets `400` except `/healthz`. If a name in the list cannot be looked up (when a restarting `api` container briefly drops out of Docker DNS), it is `502` rather than a policy denial, and if the lookup does not finish in time, it is `504`. The worker retries both.

The public package registries (npm, RubyGems, the Go module proxy and the Go checksum DB) are opened through the `packages` route of the credential route, not through the forward list. This is because a forward allowance that looks only at the SNI cannot stop leaking to another destination behind a CDN. The worker sends `GET` and `HEAD /packages/<registry>/<path>` to `WORKER_EGRESS_CREDENTIAL_URL`. `<registry>` is one of four: `npm` (`https://registry.npmjs.org`), `rubygems` (`https://rubygems.org`), `go` (`https://proxy.golang.org`) and `gosum` (`https://sum.golang.org`). `proxy.golang.org` answers 404 to `/sumdb/` proxy requests, so the checksum DB is kept separate. The request carries the egress token for `packages` only (prefix `wek_`), issued per attempt, as `Authorization: Bearer`, as the password in the URL userinfo (Basic), or in the path segment `/packages/<registry>/_token/<token>/<path>`. Go does not send credentials with the userinfo of an http proxy URL (`refusing to pass credentials to insecure URL`), so it uses the path segment. The proxy sends only the path with this segment removed to the upstream and does not write it to the log either. If the token comes in both the header and the path, it is `401`. Within a session, this token is visible to the same extent as the config files of the other package managers, and if Go prints a URL in an error message, the token may be printed with it (the worker's output scrubber masks it). Bundler and Go cannot send a bearer, so Basic is also accepted. The authorizer only looks at whether the token's attempt still has its session and returns the registry address. It attaches no credentials. Other methods (`PUT`, `POST`, `DELETE` and so on, that is, publish and unpublish) have no route, so they get `404` and the authorizer is not even asked. A path with a segment that resolves to `.` or `..` is also `404`.

Which registries are open is decided by the proxy's global setting. Putting the four hosts in `EGRESS_CREDENTIAL_ALLOWLIST` opens them, and removing them closes them in every session. The defaults of compose, helm and `.env.example` are `api.anthropic.com:443,registry.npmjs.org:443,rubygems.org:443,proxy.golang.org:443,sum.golang.org:443`. A request to a registry not in the list is `403 egress denied`. If you put these hosts in `EGRESS_ALLOWLIST` until now to open the registries, delete that value when you upgrade. If it overlaps the new defaults, the proxy refuses to start. There is not yet a feature to open them differently per profile or agent. When a registry redirects to another host, only for the `packages` route and only for hosts in `EGRESS_PACKAGES_REDIRECT_ALLOWLIST` (`host:port`, comma separated, public addresses only, empty by default) does the proxy follow it on the server side (at most 5 times per request). When following, it carries neither the `Authorization` the worker sent nor the header the authorizer attached to the registry request. A host outside the list, a location that is not `http` or `https`, a location with userinfo, and a redirect beyond five are `502`. A redirect that only changes the path within the same registry host is also followed only if that host is in the redirect list. A `304` for cache revalidation is not a redirect, so it goes back to the worker as is. Redirects on other routes are not followed, as before, and are `502`. Git LFS objects of the repository route are likewise fetched without credentials only from hosts in this list. To use LFS of a GitHub repository, add `github-cloud.githubusercontent.com:443` (the LFS item of [API server](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md)). If a host of the redirect list is also in the forward list, the proxy refuses to start. On 2026-11-01 we actually fetched npm metadata and tarballs, RubyGems `versions`, `info` and `.gem`, and Go proxy `list`, `.mod` and `.zip`, and saw no redirect. So the default is empty.

The `Credential route` line of the proxy log records `purpose: packages`, `registry`, `session_id`, `attempt_id`, and the upstream host and status. A redirect that was followed is logged as `Credential route redirect followed` (`to_host`, `to_port`), and a refused redirect as `Credential route redirect refused` or `Credential route denied`.

#### GitHub Packages (private npm and gem)

An organization's private npm and gem packages are fetched with `<registry>` set to `github-npm` (`https://npm.pkg.github.com`) and `github-rubygems` (`https://rubygems.pkg.github.com`). Unlike the public registries, the authorizer attaches the bot classic PAT that a workspace administrator registered as `Authorization: Bearer`. This value does not go to the worker. The design of registration, the allow list and the audit is in [Decision: GitHub Packages bot token](https://github.com/JeongJaeSoon/werft/blob/main/docs/contributing/decisions/github-packages-bot-token.md). The operator has three things to do.

1. Add `npm.pkg.github.com:443,rubygems.pkg.github.com:443` to `EGRESS_CREDENTIAL_ALLOWLIST`. If they are missing, requests are `403 egress denied` even when a token is registered.
2. Add `pkg-npm.githubusercontent.com:443,rubygemsregistryv2prod.blob.core.windows.net:443` to `EGRESS_PACKAGES_REDIRECT_ALLOWLIST`. GitHub redirects tarballs and `.gem` files to these hosts with 302 (measured on 2026-10-31). The proxy follows this redirect without the token.
3. For GitHub Enterprise Server, set `GITHUB_PACKAGES_*_URL` ([Configuration reference](/run-server/self-hosting/operate/configuration#api-settings)).

The authorizer judges a GitHub request by its path. A package not in the allow list, an unrecognizable path, and a missing or expired token get `403`, and the `fetch_github_package` receipt is recorded as `failed` with a `reason_code`. An allowed request is also recorded in the same receipt as `succeeded`. If the receipt cannot be written, the request fails. The proxy log for this path is the same as for other packages requests.

npm 11 rewrites the GitHub tarball location relative to the default registry (`replace-registry-host=always`), so tarball requests come to the `npm` route. The authorizer judges an `npm` path shaped like `/download/@owner/<name>/<version>/<digest>` to be a GitHub request. Public npm has no path of this shape.

Every time it receives a claim, the worker writes only user-level settings into the engine's HOME (tmpfs). It does not change the repository files (`.npmrc`, `Gemfile`, `.bundle/config`, `go.mod`).

| Tool | File (relative to HOME) | Content |
|---|---|---|
| npm (also read by pnpm and Bun) | `.npmrc` | `registry=<route>/packages/npm/`, `//<route host>/packages/npm/:_authToken=<token>` |
| Bundler | `.bundle/config` | `BUNDLE_MIRROR__HTTPS://RUBYGEMS__ORG/` set to `<route, token in userinfo>/packages/rubygems` |
| Go | `.config/go/env` | `GOPROXY=<route>/packages/go/_token/<token>` (no `direct`), `GOSUMDB=sum.golang.org <route>/packages/gosum/_token/<token>`, `GOFLAGS=-mod=readonly` |

If the allow list has a GitHub owner, only the owner name comes in the claim's `packages.github` (there is no token), and the worker adds the following to the files above. `.npmrc` gets `replace-registry-host=always`, `@<owner>:registry=<route>/packages/github-npm/` for each owner, and `//<route host>/packages/github-npm/:_authToken=<token>`. `.bundle/config` gets, for each owner, a mirror that turns `https://rubygems.pkg.github.com/<owner>/` into `<route>/packages/github-rubygems/<owner>`. Bundler reads mirror keys in lower case, so the `source` in the `Gemfile` must also write the owner in lower case to use the mirror. If the repository's `.npmrc` pins `@<owner>:registry=https://npm.pkg.github.com`, that setting beats the HOME setting, the request goes to the forward proxy instead of the credential route, and it is rejected there. Remove that line from the repository.

Because `GOPROXY` has no `direct`, Go does not go out directly to the VCS host. `GONOSUMDB`, `GOPRIVATE` and `GONOSUMCHECK` are not set, so every module goes through checksum DB verification. This file contains a token, so it is 0600, and it is deleted if the worker meets an old API whose claim has no `packages`. A user can change it inside the session with `go env -w` or `npm config set`, but the boundary is the proxy, so a change reaches nowhere else.

The proxy does not block versions outside the lockfile. The proxy does not know the lockfile. In a session, use frozen installs (`npm ci`, `bundle install --deployment` or `BUNDLE_FROZEN=true`, `go mod download` with `-mod=readonly`). The behavior when the repository's npm settings pin the registry, and the E2E results, are in [Images and supply chain § Package tools inside the worker](/run-server/self-hosting/operate/images-and-supply-chain#package-tools-inside-the-worker).

A CONNECT tunnel carries only TLS. After writing `200 Connection Established`, and before passing the client's first bytes on to the upstream, the proxy reads them as a TLS ClientHello. If the authority is a DNS name, `server_name` must equal that authority (ignoring only case); if it is an IP literal authority named in the allowlist, `server_name` must be absent. It rejects `encrypted_client_hello` (0xfe0d) whether or not it is GREASE: the proxy cannot tell the two apart, and a real ECH hides the name that is to be checked. A first record that is not a handshake, a hello with two host_names, and a hello that is not complete within the first 16 KiB (record header included) or within 15 seconds (`handshakeTimeoutMs`) all drop the connection. The rejection happens after the 200, so the client sees the connection closed in the middle of the handshake.

Limits of this gate:

* What is checked is the SNI of the **outer** ClientHello that is visible in plain text. TLS is not terminated, so the HTTP `Host`, the path and the body inside it, and where an allowed service relays onward, are not seen. Blocking domain fronting on the CDN side is a separate control.
* An IP literal allowlist is permission for `IP:port` access, not a hostname guarantee. Do not put the address of a shared CDN edge in the allowlist as an IP.
* **`fetch` and `node:https` of Bun 1.3.10 to 1.3.13 send GREASE ECH, so they are rejected when they CONNECT to this proxy.** 1.3.14 does not send it (measured 2026-09-25). "Bun's own fetch handshakes through the tunnel" in `egress.integration.test.ts` pins this. Bun `node:tls`, `Bun.connect({tls})`, Node, curl, and the Claude Code binary that the worker's SDK spawns do not send it either (measured 2026-09-23). The worker's object store does not use CONNECT: it sends plain http to the proxy's object store route inside the worker network, and the proxy makes the upstream TLS connection. On AWS the route calls a virtual-hosted name, so `<bucket>.s3.<region>.amazonaws.com:443` must be in `EGRESS_CREDENTIAL_ALLOWLIST` (for a bucket name containing dots, path-style `s3.<region>.amazonaws.com:443`). Code that calls an https upstream with CONNECT from the worker's Bun HTTP client is not supported. Measure again when you raise the runtime or client version.

**Workers cannot reach one another.** They are not on the same network as another worker, so there is no route to its address, and the container name does not resolve either. Even if one tries to go through the proxy, a private address is rejected unless it is in `EGRESS_PRIVATE_ALLOWLIST`. They cannot reach the workers and proxy of another installation either: both the network and the proxy selection are per installation. An integration test ("workers do not reach one another" in `egress.integration.test.ts`) confirms this. It is confirmed together with a positive control: a sibling container on the same network can reach an open port. Remaining limits:

* The proxy is a trusted component attached to every worker network. If the proxy is compromised, every worker of that installation can be reached. Do not put a name that can resolve to a worker in `EGRESS_PRIVATE_ALLOWLIST`.

**Host processes cannot be reached either.** An internal bridge in the default gateway mode (`nat`) gives the host the first address of the subnet. Then a worker can reach, without the proxy, a **host process** (a process started directly on the host, not a published port) that the daemon host has listening on that address or on a wildcard. So the worker network is created with `gateway_mode_ipv4=isolated`, so that the host holds no address on that network. This mode exists only in **Docker 28 (API 1.48) or later**. In its startup preflight (`verifyNetworkIsolation`), the scheduler does not pass this with a warning but refuses (`GatewayModeUnsupportedError`) when the daemon's API version is below 1.48. There is no setting to turn this off. An integration test ("a host process on a wildcard address" in `egress.integration.test.ts`) confirms two things together. On an internal network without the mode, the host listener is reachable (a positive control). On the worker network, it is not. On native Linux (CI), the test process itself is the `0.0.0.0` listener. On Docker Desktop the daemon is inside a VM, so a `--network host` container that uses the VM's network namespace stands in as the listener. IPv6 is off on the worker network, so it does not apply.

Before a pass, the scheduler confirms that exactly one proxy of that installation is up (`verifyNetworkIsolation`). If there is none or more than one, it takes the pass lock and runs only the worker network reconcile (reclaiming orphans, detaching the proxy if there are two or more). Then it exits non-zero without starting anything. The worker network is checked on every launch. If a network with the same name already exists, it is not created again and the following are confirmed. If any one of them is off, the launch is refused with `NetworkIsolationError` (fail closed).

* Do the bridge, internal, IPv6 off and owner labels (installation, execution, generation) match?
* Does the host hold no address on the network? `gateway_mode_ipv4` in `Options` must be `isolated` and the IPAM must have no gateway. Some old daemons only record an option they do not know and still give a gateway, so both conditions are checked
* Is there no member other than the worker and the proxy?

The result of the proxy attach is judged not by the response code but by the attach and alias that the proxy container reports. If it is already attached, 403 comes back, and if it is attached without an alias, DNS does not resolve. When adopting an existing container, that container must be attached to **only one** network, its own (the same id). The container is created by the network id, not by the network name. So a network recreated under the same name cannot take the place of the network that was checked.

The old settings `EXECUTION_DOCKER_NETWORK` and `EXECUTION_DOCKER_NETWORK_ALLOWLIST` are no longer read. If a value remains, startup is refused rather than silently ignored. Delete them from the environment file and put the label on the proxy container.

The isolation contract at creation time is stamped on a container with the label `agent-platform.isolation`, in the form `<version>:<fingerprint>`. The fingerprint is a hash of the proxy URL, the credential route port, the `NO_PROXY` value, the user, the workspace and HOME paths, the tmpfs sizes, the workspace quota setting and inode limit, the stop timeout, the worker limits (turn time, provider retries), and the object store's bucket and region, so the value changes even if you change only `EXECUTION_EGRESS_PROXY_URL` or `S3_BUCKET` without changing code. The object store endpoint and credentials are not in the fingerprint. The worker receives neither, goes through the proxy's object store route, and the API signs that request. So changing `AWS_ENDPOINT_URL` or a key does not replace the worker, and once the API is restarted the new value is used from the next request. The CPU, memory and pids limits are also deliberately kept outside the fingerprint. The limits belong to the launch, so they are fixed in `worker_launches.resources` at reserve time and checked against the `agent-platform.launch-spec` label. So lowering a limit does not replace running workers all at once and applies from the next launch. A container without the `agent-platform.launch-spec` label, however, is adopted without that check. The isolation of a running container does not change when the control host is upgraded, so the scheduler sees a container whose label differs from the current value as `stale`, stops and removes it, and recreates it from the stored intent (`ensureExecution` does not adopt such a container either). A container with a **higher** version was made by a newer control host that is being rolled back. It cannot be known whether that boundary is the same as what is required now, so it is neither adopted nor replaced, and it is refused with `IsolationContractError`: the row stays alive and the pass ends non-zero, so the operator has to roll forward or remove it by hand. When the shape of the isolation itself changes, `ISOLATION_CONTRACT` is raised. From contract 5, the worker network is per execution. So upgrading from contract 4 or below replaces every existing container on the shared network as stale. If the check before replacement (`assertReplaceable`: image, workspace, proxy, new network) fails, normally the old container is left as it is and retried on the next pass. But a container below contract 5 may reach neighboring workers on the shared network. So that container, if it has not been claimed yet, is left **detached from every network**. It is not claimed yet, so there is no turn in progress. It is replaced normally in the pass where the check passes. The result is appended at the end of the error message in the replacement failure log. A claimed worker below contract 5 is torn down without this check, so it is not touched here. There is no fence that bundles the check and the disconnect. So after the disconnect, whether it was claimed is checked once more, and if it was claimed in the meantime, the network is reattached and the scheduler's teardown (drain by SIGTERM) is left to handle it. A worker whose claim requests were going back and forth during the short time the disconnect continued may have its requests cut.

From contract 6, the worker network has no host address. A contract 5 container's network has the same name, but the gateway mode cannot be changed in place, so replacement takes the following order.

* **Check before replacement (`assertReplaceable`):** if the contract 5 worker of the same launch is actually attached to that network and the only defect is the host address, the old network is let through. The teardown that follows deletes the network together with the container. Then `ensureExecution` creates a new one as `isolated`.
* **Ordinary launch path:** an old network left without a worker (when the network removal of a teardown failed) is deleted and recreated if only the proxy is attached. If there is another member, it is refused. A new container is never put up on an old network to which the old worker is still attached.
* **`reconcileNetworks`:** it does not detach the proxy from an old network to which a contract 5 worker is attached. A claimed worker is drained and torn down without a check, so this is so as not to cut its egress before that. If a contract 6 worker is on a network that has a host address, it is treated as a defect and the proxy is detached.

This replacement also follows the rule that a claimed worker is closed after the turn-boundary drain below. **Deployment order:** raise the daemon to Docker 28 or later first. On an old daemon, the preflight blocks the whole pass. Then contract 5 workers are not replaced either and keep running as they are (only new admission is fail-closed).

After the upgrade, the old shared network (`agent-platform-worker`, or the name you changed it to with `EXECUTION_DOCKER_NETWORK`) is no longer declared by compose. Even so, it is not deleted by itself and keeps holding one subnet of the address pool. After all contract 4 containers have been replaced, delete it with `docker network rm agent-platform-worker`. If a running container is attached, Docker refuses the deletion (403), so you cannot delete a network in use by mistake. **A worker that is already claimed cannot be recreated, so it is torn down after being drained to the turn boundary.** Follow the section below.

#### Draining claimed workers when the contract is raised

When a claimed container is stale, the scheduler does not break it at once.
1. The first pass records `worker_launches.drain_requested_at` with the DB clock. From then on that worker accepts no new turn. A turn it already took runs to the end, and input that arrives later stays queued.
2. If there is a running turn (`running`, `needs_input`), or the worker has not yet asked for its first input (preparing the workspace or restoring a checkpoint; cutting it then counts as a failed startup), the container is left as it is and put in the pass summary's `draining` (log `draining_count`, `Claimed execution draining before its replacement`).
3. The first pass after the turn ends tears down the container. The turn's checkpoint was already finalized in that finalize. The worker that received SIGTERM releases by idle drain, and a new launch (the current contract) takes the queued input and continues from the checkpoint.
4. If the turn is still open or the startup is not finished when the drain deadline passes, it is torn down as it is. Then that turn becomes `outcome_unknown` as before. An unfinished startup is not counted if the worker releases by drain on SIGTERM, and counts as one failure if it dies without a release. The pass summary's `drainsOverdue` (log `drain_overdue_count`) and one warning line `Drain deadline passed with the worker still busy; replacing anyway` are left. The deadline is `MAX_TURN_SECONDS` + 5 minutes. No turn can exceed `MAX_TURN_SECONDS`, and the 5 minutes is the share for the finalize and checkpoint that end that turn.

A stale container that is not claimed is replaced immediately as before.

**Rollout procedure:** in a deployment that raises the contract, the replacement of claimed workers is delayed by up to the drain deadline. Meanwhile the old-contract container stays alive, and no new turn starts in that session. For an isolation defect that must be cut off immediately, terminate the session instead of waiting. If a rollback makes the container current again, the drain request remains. That worker, with no new turn, ends by itself after the idle time, and the session continues on the next launch.

### Sessions whose checkpoint restore keeps failing

If a worker that took over the restore ends before it reports ready, the scheduler does not start it again right away. For such endings it waits 30 seconds and then 60 seconds up to the second one. At the third, the session stops at `recovery_required` and no new generation is made. The session detail attention, while waiting and after the stop, is `RESTORE_FAILED`.
- `reason`: the error the last worker left. If it died without a release, it is `execution_gone`.
- `failures`: the number of consecutive failures.
- `retry_at`: the time of the next attempt. It is null after the stop.

`INCOMPATIBLE_CHECKPOINT` is a deterministic failure that cannot succeed on the same worker runtime and profile even if retried. In this case the session stops at `recovery_required` right after the first launch, and the attention and the `reason` of the `checkpoint_restore_failed` event are `incompatible_checkpoint`, `failures` is 1, and `retry_at` is null. The operator rolls back to a compatible runtime and profile and then chooses `retry_restore` to try the same checkpoint again, chooses `start_fresh` if the earlier context may be dropped, or chooses `close` to end the session.

A system `checkpoint_restore_failed` is left in the event stream for each failure. Find the cause in `worker.checkpoint.restore_refused` and `worker.failed` in the worker log. A checksum mismatch in the storage response (corruption in transit) is also classified as `CHECKPOINT_UNAVAILABLE`.
- A moment when the storage or the egress-proxy `/object-store` path could not answer is not counted as a failure. Connection failure, DNS failure, request or body timeout, a truncated body, and HTTP 408, 429 and 5xx are transient failures. Checkpoint restore logs the warning `worker.checkpoint.restore_unavailable`, and the transcript store check of a new generation that has no checkpoint yet logs `worker.checkpoint.store_unavailable`. Both retry within the same worker, starting at 1 second and doubling, at intervals of at most 30 seconds, up to `WORKER_STARTUP_TIMEOUT_SEC` (default 3600 seconds). When the storage comes back, that worker continues, so no new generation is made.
- If the failure continues until the startup budget ends, that worker's exit counts as one startup failure. The next generation comes up only after the session backoff of 30 seconds and 60 seconds, and at the third failure it stops at `recovery_required`. So a storage outage does not turn into unlimited immediate worker restarts. The scheduler passes no separate value of `WORKER_STARTUP_TIMEOUT_SEC` to the worker, so in the current deployment it is fixed at the code default.
- Cases where the object is really missing (404 or `NoSuchKey`), is refused with 401 or 403, or fails a checksum or digest are not transient failures. If the manifest or an object the manifest points to is missing, it is `CHECKPOINT_UNAVAILABLE`, and it is not assumed to be fixed by a restart. When the whole bucket is empty but the DB pointer remains, the API's startup check stops it first. `restore_refused` is a sign to investigate permanent corruption or mismatch of the checkpoint, not the storage path.
- If the cause was outside the session (corruption in transit by the proxy, a wrong storage path setting), fix that and then restore the same checkpoint again with `retry_restore`. The count returns to 0 and the queued input is signaled again. The next worker gets a restore plan again from the same pointer as the failing worker.
```sh
# KEY: an API key with the sessions:recover scope
curl -X POST "$API/v1/sessions/$SESSION/recovery-decisions" \
  -H "Authorization: Bearer $KEY" -H "Idempotency-Key: $(uuidgen)" \
  -H 'Content-Type: application/json' \
  -d '{"decision":"retry_restore","expected_revision":<revision>,"reason":"proxy fixed"}'
```

It is accepted only for a session that stopped by reaching the limit. A session that is in backoff or stopped for another reason (context gap, unknown turn, `STARTUP_FAILED` without a restore) gets 409 `REQUEST_STALE`.
- If the checkpoint may be given up, continue with `start_fresh`. A new engine session starts without a checkpoint.
- To end the session, use `close`.

### Sessions that keep dying at startup

A session without a checkpoint follows the same rule. If the worker ends without ever asking for input after the claim, it is one failure. This is the case of dying in workspace preparation (git clone, fetch) or engine startup. It waits 30 seconds and then 60 seconds up to the second, and at the third it stops at `recovery_required`. The attention is `STARTUP_FAILED`, and `reason`, `failures` and `retry_at` are as above. A system `startup_failed` is left in the event stream for each failure.
- Common causes are that the repository URL or branch is gone, that the repository credentials were refused, and an error in the worker's object store or proxy settings. Check `worker.stopping kind=failed` and `worker.failed` in the worker log.
- After fixing the cause, bring it up again with `start_fresh`. This session has no checkpoint to discard, so nothing is lost. To end the session, use `close`.
- A worker that ended by pause, terminate, close or revocation of the execution permission is not counted.
- A worker drained by SIGTERM is not counted either. The worker puts `stop_kind: "drain"` in the release. An old API that does not know this field has a strict schema and rejects it with 400 `BAD_REQUEST`. Then the worker logs `worker.release.stop_kind_refused` and releases once more without the field. The session comes back at once without waiting for the lease to expire. But the old API counts that ending by the old rule. If it is a claim with a restore pending, that is one failure.
- **Deployment order:** raise the control host image (`API_IMAGE`, shared by api and scheduler) first, and change `WORKER_IMAGE` after that. The request schema of the worker protocol is strict, so an old API rejects a new field sent by a new worker with 400. There is no such fallback path except for release.

### A turn whose outcome is unknown after an interrupt

For an interrupted turn to end as `interrupted`, there must be both a response that the engine stopped and a checkpoint that covers up to that turn. If either is missing, no one can say what remained in the transcript. So the turn becomes `outcome_unknown`, and the `terminal_reason` of the turn lookup (`GET /v1/sessions/{id}/turns/{turn_id}`) tells the cause.
- `interrupt_checkpoint_unavailable`: the engine stopped but the checkpoint could not be committed. The worker goes down by drain.
- `interrupt_unanswered`: the engine did not answer the interrupt in time. `gave no terminal within …ms of its interrupt` or `ended before its interrupt was answered` is left in the worker log, and the worker ends as a failure.

If you gather `worker.turn.interrupt.stage` of the worker log by the same `session_id`, `turn_id` and `control_id`, you can see the order `control_received` → `sdk_interrupt_called` → `sdk_interrupt_answered` → `engine_terminal` → `capture_started` → `capture_finished` → `finalize_started` → `finalize_finished`, and `elapsed_ms` since the interrupt was received. After the final finalize, `control.result` leaves `operation=interrupt`, the final turn `outcome`, a stable `reason_code`, and `effect_ms` from the durable acceptance time to the turn terminal (the same as `duration_ms`). A no-op for a turn that has already ended leaves the same event right after the acceptance transaction with `effect_ms=0`, and a receipt that did not end by the deadline leaves it with `outcome=unknown` and `reason_code=deadline_exceeded`. If the SDK response arrives after the engine terminal, it is not inserted into the normal order but recorded as `late_sdk_interrupt_answered`. `engine_terminal outcome=timeout` is the case where no SDK or engine terminal came within the 5-second grace. `capture_finished outcome=timeout` with `budget_ms=30000` is the case where the checkpoint capture budget was used up, and the `reason` of `outcome=failed` is a failure of the capture itself, such as a storage request. Even if the capture ended, `CHECKPOINT_UNAVAILABLE` in `finalize_finished outcome=failed` means the API rejected the manifest or its ref, so it is not classified as a capture timeout or an S3 request failure. The 5-second grace is not changed. On a timeout, the next input is not given to the same engine; the worker is taken down as a failure and a recovery decision is required.

Either way, the session becomes `status: failed`, `admission_state: recovery_required`, and queued input is not dispatched. The interrupt receipt is `unknown` and the error is `RECOVERY_REQUIRED`. Recovery is done with the `sessions:recover` scope.
Even if the storage is healthy again, an `outcome_unknown` turn is not rerun automatically. Storage recovery only lets the next worker read the checkpoint, and it cannot judge the external effects of a turn that already ran. Only a decision that the operator chooses from `abandon`, `confirm_completed` and `close` below clears the queue head.
1. `abandon` and `confirm_completed` are accepted only after the worker is confirmed gone. Before that, it is 409 `RECOVERY_REQUIRED` (`The previous execution has not been confirmed gone`). They are accepted when the next scheduler pass confirms the container is absent. `close` does not wait. It requests termination of the remaining execution and is accepted at once.
2. Check what the tools of that turn did outside. File writes, pushes and external calls cannot be undone.
3. Send the decision.

```sh
# KEY: an API key with the sessions:recover scope
curl -X POST "$API/v1/sessions/$SESSION/recovery-decisions" \
  -H "Authorization: Bearer $KEY" -H "Idempotency-Key: $(uuidgen)" \
  -H 'Content-Type: application/json' \
  -d '{"decision":"abandon","expected_revision":<revision>,"reason":"interrupt had no confirmed effect","target_turn_id":"<turn_id>"}'
```

- `abandon`: closes the turn as `cancelled`.
- `confirm_completed`: accepted only when a committed checkpoint covers up to that turn (`evidence_ref` is required). `interrupt_checkpoint_unavailable` usually has no such checkpoint, so it is 409 `CHECKPOINT_UNAVAILABLE`.
- `close`: ends the session. It cannot be undone.

4. After `abandon` and `confirm_completed`, the session is `stopped`. If `result.resumable` of the decision receipt is `true`, resume it. If `false`, it means there is no checkpoint to take over, or a turn ran after the last checkpoint so that context cannot be taken over (session detail attention `CONTEXT_GAP`). Continue without that context with `start_fresh`, or `close`.

## Worker workspace limit and reclamation

One volume `ap-ws-<installationId>-<sessionId>-<suffix>` per session is attached at `/workspace`. This volume survives across generations: even if the container is replaced, the session's working tree must stay as it is. So **`terminate`, which deletes the container, does not touch the volume**, and reclamation is done separately by stage (4) of the pass.

Even if the volume is gone, the session continues from the last committed checkpoint. What remains and what disappears is in [What remains when the workspace volume is lost](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md#workspace-volume을-잃었을-때-남는-것).

The backend now creates the volume **explicitly** with `POST /volumes/create`. This is because if only a name is written in the mount spec, Docker creates a volume with neither label nor limit on its own. At creation it stamps the labels `agent-platform.managed`, `.installation`, `.session-id` and `.workspace-quota`, and the GC does not parse names and looks only at these labels.

**A volume name is single-use.** If you create again a name on which the `local` driver once applied a quota, it returns `Options.size` as it was but does not apply the real project quota. The result measured on xfs+prjquota (Docker 27.5.1): a name created for the first time shows the total of `df` in the container as the configured value (64MiB), but if you delete the same name and create it again, `df` reports the whole filesystem (8GiB) even though `Options.size` is the same. The Engine API cannot tell the two apart, so a session's workspace is created not by deriving a name but with a random suffix, and then **looked up by label.** Even if the GC or an operator deletes a volume, the next one gets a new name, so the limit stands again. If two workspaces are seen for one session, it does not judge which is the working tree and only reports. The preflight probe also uses a new name every time for the same reason, and a probe left by a previous run is reclaimed by label, but only one that is older than the longer of 10 minutes and 20 times `EXECUTION_DOCKER_REQUEST_TIMEOUT_SEC`. The preflight runs outside the pass lock, so a younger probe may be in use by another preflight running at the same time (a standalone `--once` next to the loop, two schedulers).

Unlike CPU, memory, PID and tmpfs, `/workspace` had no limit. `EXECUTION_WORKSPACE_QUOTA_MB` (default 4096) becomes that limit as the `size` driver option of the `local` driver. This option, however, works **only when the daemon's storage can bear project quotas** (xfs + `prjquota`); otherwise the daemon rejects the create with `400 quota size requested but no quota support`. The scheduler checks this capability before a pass by trying to create a probe volume (`verifyWorkspaceQuota`), and on a daemon that cannot bear it, it **exits without starting anything.** The probe creates a volume and starts a CAP_SYS_ADMIN helper, so it is not repeated on every pass. A pass of the supervision loop, once it passes the probe, writes the hash of the whole backend configuration (`DOCKER_HOST`, `EXECUTION_*` and so on) to `<SCHEDULER_STATUS_FILE>.quota-verified` next to the status file. Later passes skip the probe if the hash is the same. The supervision loop deletes this file at startup. So when the loop comes up again (a container restart, a restart after consecutive failures), the first pass checks again. A failed probe writes nothing, so the next pass checks again. A pass run standalone outside the loop (`main.ts scheduler --once`) neither writes nor trusts this record and probes every time. The loop passes the record location only to its own passes, as `SCHEDULER_QUOTA_PREFLIGHT_MARKER`. There is no path that silently falls to unlimited, and to accept unlimited you must state `EXECUTION_WORKSPACE_QUOTA=off` explicitly; in that case one warning is left on every scheduler pass. A value other than `on` and `off` (`false`, `0`, `no`) is treated as a typo and rejected.

**The quota minimum is 1024 MiB.** An `EXECUTION_WORKSPACE_QUOTA_MB` smaller than this is rejected at startup. This is because checkpoint restore at one point uses this much of the workspace volume. Restore proceeds in the order below after emptying the root. The symbols in the table are as follows.

- B: the sum of the bundle chain. The control plane limit is 256 MiB.
- U: untracked files. The capture limit is 256 MiB.
- W: the objects the workspace `.git` received. About B.
- I: the objects the instructions commit reaches. W or less.
- T: the checked-out working tree and index.

| Stage | What it occupies at the same time | Maximum |
| --- | --- | --- |
| Download | bundle files B, U | 512 MiB |
| Staging | bundle files B, staged repository ≈B, U | ≈768 MiB |
| Workspace fetch | staged repository ≈B, W, U (the bundle files are deleted right after staging) | ≈768 MiB |
| Shrinking the staged repository | W, I, U (the staged repository is deleted first) | ≤768 MiB |
| After checkout, throughout the session | W, I, T, U | 2B + T + U |

The fixed cost before checkout is twice the bundle limit plus the untracked limit, that is, 768 MiB. 1024 MiB is this plus the pack index and some margin. The copy of the delta base that fills an incremental thin pack also fits in this margin. T after checkout is the session's working tree itself and has no limit. So the minimum guarantees only the cost before checkout, which is independent of the session. W + I + T + U after checkout is similar to what that session was already using when it captured within the same quota. At capture time, the workspace `.git`, the working tree, the untracked files, the snapshot objects of the scratch repository, and the bundle file (≤B) were present together. I is B or less. Restoring into a new volume after lowering the quota is outside this guarantee. Then the restore may fail with ENOSPC during checkout.

A fresh fetch that reuses an existing workspace (resuming without a checkpoint, reuse) does not empty the root, unlike restore. The worker receives the whole origin as a bare mirror and copies the branch from it. The mirror is made under `.git/werft-fetch-*` and deleted when the fetch ends. This is because `/tmp` and HOME are tmpfs and use container memory. In addition to the symbols in the table, M is the maximum the mirror occupies on disk. It is the whole pack of the origin repository plus the index and refs, plus the temporary pack file while receiving. Δ is the objects newly entering the workspace `.git`. The maxima below add these estimates.

| Stage | What it occupies at the same time | Maximum |
| --- | --- | --- |
| Mirror clone and local fetch | existing W, I, T, U + mirror M + Δ | session usage + M + Δ |
| After the fetch | W + Δ, I, T, U (the mirror is deleted) | session usage + Δ |

M has no limit. There must be quota room of M for reuse to succeed, and if short, the fetch fails with ENOSPC. The first clone (`clone`, `recreate`) receives directly into the root without a mirror, so it uses only W + T. A scratch left by a worker that died midway (`.git/werft-<purpose>-XXXXXX` of fetch, capture and publish) is deleted by the next reuse before the fetch. `werft-checkpoint` is kept. If the checkout borrows objects from somewhere else (`objects/info/alternates`, `commondir`, a linked `objects`), it may be the target, so it is not deleted.

After restore, only the objects the instructions commit reaches (I) remain in `.git/werft-checkpoint/checkpoint.git`. This repository is there so that the next capture can bundle even if the engine prunes that commit. The commits after it, the snapshot of uncommitted changes, and the earlier snapshots of the chain are not kept. But if the instructions commit equals HEAD, I is the whole committed history. That is the case for a session in which the engine did not commit. Then only the share of the snapshot shrinks.

This shrinking has a cost. The next incremental capture excludes only those chain tips that still exist. A snapshot commit that was only in the earlier base bundle no longer remains. The snapshot of the last bundle is also just in the workspace `.git` without a reference. An ordinary `git gc` does not delete this for 2 weeks. But if the engine runs `git gc --prune=now`, it disappears. Then the bundle is made against the remaining tips (the HEAD commit left in history, the instructions commit). As a result the bundle may grow or fall back to a full bundle. Correctness stays the same. A repository whose full bundle exceeds the limit is rejected anyway on a restart too, when the chain reaches 32 or the limit.

**An inode limit is also applied to the same project.** With the byte limit alone, there remains a path to exhaust inodes with millions of empty files. xfs does not charge inodes to the project's block usage, so it is possible even within 4GiB. Then other sessions on the same daemon and Postgres cannot create files. The `local` driver has no inode option, and the way of making a filesystem per session with `o=loop` is also closed. The driver calls the mount syscall, not `mount(8)` (`data: loop: invalid argument`). So we apply `ihard` and `isoft` (`EXECUTION_WORKSPACE_QUOTA_INODES`, default 1,000,000) ourselves to the xfs project that Docker made with `size`.

- The one that applies it is a short-lived helper container (`workspace-inodes.ts`). Its configuration is `CapDrop ALL` + `CapAdd SYS_ADMIN, MKNOD`, `NetworkMode none` and a read-only rootfs, and it is not privileged.
- The helper reads the volume's project id. It refuses project 0 (= no project). If a limit were applied to 0, the whole filesystem would be bound.
- The helper makes the block device node of the mount source in its own `/dev` with `mknod` and then calls `xfs_quota`.
- `xfs_quota` ends with 0 even when it fails. So success is judged only by reading the hard and soft limits of the quota report and the statfs `f_files`.
- Docker's `SetQuota` writes only BHARD and BSOFT, so it does not overwrite this value.
- The image is the scheduler's `WORKER_IMAGE`. The worker image contains `xfsprogs`. A different image is not left to be chosen per launch. The image that receives CAP_SYS_ADMIN is decided by the operator, not the catalog.

It is applied at four points.

- The preflight probe (`verifyWorkspaceQuota`, from when the loop is up until the first pass, and again only when the configuration changes): if it cannot be applied, startup is refused by the same rule as the byte limit, and the opt-out is the same single `EXECUTION_WORKSPACE_QUOTA=off`.
- `ensureWorkspaceVolume` on every launch: both new and existing volumes. The project id can be reused after a daemon restart, so it is not cached, and applying it again is idempotent.
- `assertReplaceable` before replacement: for a volume to which the limit cannot be applied, the replacement is refused before the existing worker is taken down.
- Before the copy of `migrate-workspace`: a tree with more files than the limit fails to copy and the original remains.

The inode limit can be changed in place, so it is not put in the volume label (`workspace-quota`). A volume made without an inode limit is not rejected either and receives the limit on the next launch. Instead it goes into the `isolationStampFor` fingerprint and `ISOLATION_CONTRACT` is raised to 7. A host rolled back to before this version sees these workers as newer and does not touch them. So when the limit appears or changes, running workers are replaced as stale, and the ensure on the replacement path applies the limit.

Docker Desktop has a kernel built without XFS quota (`XFS (loopN): quota support not available in this kernel`), so locally `off` is practically the only choice. The daemon of a GitHub Actions runner is the same, since its data root is ext4. So whether the real limit bites is confirmed by the CI `workspace-quota` job, which starts a separate daemon that uses an xfs + prjquota loop file as its data root.

Applying the limit to a single volume is not enough. Docker automatically attaches a **writable anonymous volume** for every `VOLUME` path an image declares, and that has neither limit nor label. So before a launch it inspects the image and refuses if there is a `VOLUME` declaration other than `/workspace` (`ImageVolumeError`), and when it deletes the container it deletes the anonymous volumes together with `v=true` (the named workspace volume is not affected). For an image not yet pulled, the inspection is 404, so it leaves it as is and lets the create produce the same 404.

A gap can also open between what was checked and what is actually started. Tags are mutable, so the container is created from the **id of the inspected image** (`sha256:…`), and the volume is checked once more after the create and before the start, because if a `docker volume prune` passed in between, Docker would newly create a volume with neither label nor limit for the mount. If it does not match, the container, in which nothing has run yet, is deleted and the launch fails.

If the quota preflight fails, **nothing is started but reclamation is run once.** The probe also uses a little disk, so a daemon that is already full fails from the preflight, and that moment is exactly when the workspaces of ended sessions must be reclaimed. If it simply exited, there would be no way to reclaim ever. What runs then is not a pass but `reclaimWorkspaces`, which performs only stage (4) under the same advisory lock. A pass with slot limit 0 is not enough. It only blocks new reservations, and it still recreates vanished containers and replaces stale containers. When the reclamation is done, the original error is thrown again and it ends non-zero.

If the quota label of a volume differs from the current setting, whether it is a volume without a label that was created implicitly in the past or one made with a different byte limit, startup is refused (`WorkspaceQuotaError`). It keeps looking for the volume `ap-ws-<installationId>-<sessionId>` of the time when names were derived. It has no label and so does not show up in the lookup, but if it pretended not to see it and made a new workspace, that session would start with an empty tree and the old tree would be buried. The byte quota of a volume cannot be changed later (the inode limit changes in place, as written above), and deleting it to change it would throw away that session's working tree. To move to the new contract while keeping the working tree, use the procedure in [Legacy workspace migration](#legacy-workspace-migration) below. Going back to the previous setting is also a way. For the same reason the quota setting also goes into the `agent-platform.isolation` fingerprint: otherwise a container that is already up would keep living with the old limit.

This refusal must happen **before killing a worker that is already running.** When the fingerprint changes, the order is stale judgment → `terminate` → recreate, and if the recreate is refused by the volume, that session is left with no worker and no way back. So before it reports stale, `inspect` checks that session's volume read-only, and for a volume that cannot be used, it throws instead of reporting stale: the container keeps running with the old limit as it was, the pass ends non-zero with `reconcileFailed`, and that state stays until the operator moves the volume. How to move it is in [Legacy workspace migration](#legacy-workspace-migration) below. The inode limit is not this read-only check but is actually tried by `assertReplaceable` just before replacement, and if it cannot be applied, the replacement is refused before the existing worker is taken down.

The GC of stage (4) leans toward fail-safe. **It lists the volumes first and then asks the DB.** If the order were reversed, it would delete the volume of a session created between the two calls. The conditions to keep are that the session row exists and the admission state is not `closed`, or that a live execution row exists. `stopped` is an exception and follows the expiry rule below. A volume with no session id label or with a session id that is not shaped like one, a volume a container still holds (409), and a volume of another installation are all **kept, with only a log line.** The exception is the label-less `ap-ws-<installationId>-<sessionId>` volume of the time when names were derived. The session id read from the name is only a candidate, and it is reclaimed **only when the row of that id exists, is `closed`, and no launch holds a slot** (`filterClosedLegacySessions`). If there is no row, it is kept. Unlike a labeled volume, a matching name alone is not evidence that it belongs to our session. The `stopped` TTL is not applied to a legacy volume either. It must be migrated first before it follows the expiry rule. A volume younger than `EXECUTION_WORKSPACE_GC_MIN_AGE_SEC` (default 3600) is not a candidate at all, because a volume is created before the container, and reclaiming it in between would break a launch in progress. **What was left by judgment and what was left by failure have different exit codes.** A volume left because it is still mounted (409) or belongs to another installation is a normal state, so the exit code does not change (`workspacesUnresolved`). On the other hand, when the list could not be read, the DB did not answer (`workspaceScanFailed`), or the delete call threw (`workspacesFailed`), disk piles up with no one looking, so the pass ends non-zero.

**The workspace of a `stopped` session expires.** After `EXECUTION_WORKSPACE_STOPPED_TTL_SEC` (default 86400, one day) has passed since the stop, it becomes a reclamation candidate. The reference time is `sessions.updated_at`. The stop transition stamps this value, and the reclaim claim and the completion record do not touch it. When a new terminate is accepted for a session that is already `stopped`, this value changes and the TTL is counted again from then. But terminate is not a means to hold the workspace. If a reclaim claim has already been taken, that reclamation goes on as it is. If you need the workspace, resume. Only resume is serialized with the claim. If a launch holding a slot remains, it is not a candidate. With one day, a session stopped overnight comes back as it was, and even when stops pile up as in a 10-session soak, the disk does not grow without end. `0` means reclaim at the next pass.

Resume is accepted only when a committed checkpoint exists, and when the claim has a restore pointer, the worker restores the workspace from the checkpoint (restore empties the root and then fills it). So the volume of a stopped session past the TTL is just a cache. Conversely, **a stopped session without a checkpoint cannot be resumed, and the work that remains only in its volume disappears after the TTL.** If that work must be saved, take it out of the volume directly within the TTL.

Reclamation and resume are serialized in the DB. When a candidate comes out of the volume list, the pass locks the session row in the same order as resume (launch → session), checks the conditions again, then records and commits a **claim** (`sessions.workspace_reclaim_id`, `workspace_reclaim_workspace_id`). After that it deletes the volume and records the result with the same claim id.

* If it was deleted or is already absent, it clears the claim and stamps `workspace_reclaimed_at`.
* If it is mounted (409) or belongs to another installation, it only releases the claim.
* If the delete call throws (a timeout included), it leaves the claim as it is, because it is not known whether the volume was deleted. The next pass first handles claims that have not finished, separately from the volume list, because a deleted volume does not appear in the list again.

While a claim remains, resume is rejected with **503 `BACKEND_UNAVAILABLE` (`retryable: true`)**. Then neither a receipt nor an idempotency record is left, so sending the same request again is handled normally after the reclamation ends. Conversely, if the resume commits first, the session becomes `active` and `updated_at` changes, so the claim is rejected and the next launch uses the volume as it is. When the resume succeeds, `workspace_reclaimed_at` is cleared. The behavior in each order is pinned on a real PostgreSQL by `packages/db/src/workspace-reclaim.integration.test.ts`.

#### Legacy workspace migration

A session with an old volume without a label (`ap-ws-<installationId>-<sessionId>`) or a volume made with a different quota is refused at startup. If it loses its container, it cannot even come up again. The procedure to move it to the current setting's quota while keeping the working tree is as follows. It is an **explicit operator task** that a pass does not do automatically.

```sh
# run with the same environment variables as the scheduler (DATABASE_URL, EXECUTION_*, DOCKER_HOST)
bun run --cwd apps/control-host migrate-workspace <session-id> [<session-id>...]
# with compose (apps profile)
docker compose -f infra/compose.yml --profile apps run --rm scheduler \
  bun run apps/control-host/src/scheduler/migrate-workspace.ts <session-id>
```

Preconditions:

* **No container may hold that volume.** A stopped container counts too (if it starts again, it writes to the original being copied). If there is one, it names it and refuses. For a running session, first stop it with terminate (the container is deleted), move it, and then resume. If you delete the container directly with `docker rm`, the turn in progress is cut off, and that session is handled as a session that lost its container.
* **It takes the scheduler pass lock.** If a pass is running, it ends with `A scheduler pass holds the lock`. Run it again when that is over. While copying, no pass runs, so neither the GC nor a launch touches the two volumes.
* That session must have no unfinished reclaim claim. If there is one, run it again after the next pass handles it.
* The session row must exist and must not be `closed`. The legacy volume of a closed session is reclaimed by the GC. The legacy volume of a session without a row is touched by neither the GC nor this command, because the only evidence that it is ours is the name. The operator checks and deletes it directly.
* The helper image must be **pinned by digest** and must already be on the daemon. The default is busybox 1.36 (`DEFAULT_MIGRATION_HELPER_IMAGE`). Run `docker pull busybox@sha256:73aaf090f3d85aa34ee199857f03fa3a95c8ede2ffd4cc2cdb5b94e566b11662` first. To change it, use `--helper-image` or `EXECUTION_WORKSPACE_MIGRATION_IMAGE`.
* It must pass the quota preflight (`verifyWorkspaceQuota`) first. The new volume is made with the current setting's limit.

What it does:

1. It creates the new volume under the current contract. It attaches the label and `size`, and leaves the original name as the label `agent-platform.migration-source` and the original's creation time as the label `agent-platform.migration-source-created-at`. The name is single-use like other workspaces. The workspace is found by label, so there is no need to rename it.
2. A pin container that is never started (prefix `ap-ws-migrate-pin-`) holds the original read-only. Docker does not delete a volume that a container references. So even if the GC steps in while the pass lock is lost, the original remains until this run ends. The pin name differs per run, and each run deletes only its own pin. Then a helper container attaches the original read-only and the new volume for writing and copies with `cp -a`. The helper is root but has no network and has only the capabilities needed for copying files (`CHOWN`, `DAC_OVERRIDE`, `FOWNER`, `FSETID`).
3. The same helper compares the manifests of both sides. The comparison covers the set of paths, the kind, mode, uid/gid, symlink targets, and for regular files the size, mtime and SHA-256. The size and time of directories, xattrs and ACLs are not compared. Busybox `cp -a` does not preserve hard links, so a hard link becomes a separate file with the same content. That uses that much more disk, so if it hits the quota the copy fails. mtime is compared only to the second.
4. If they match, before deleting the original it checks again whether another copy of the same original exists. If so, another run is still working. Then it discards its own copy and fails. The same applies when the original is held by another container. If neither is the case, it deletes the helper and the pin and **deletes the original.** From that moment the new volume is that session's workspace.

If it fails midway, the original stays as it is. This holds for a copy failure (quota exceeded, a device file the helper cannot make and so on), a mismatch, a timeout (`--deadline-sec`, default 3600) and a lost lock. A failed helper is left so that it can be seen with `docker logs`. The pin is also left and keeps holding the original. When you run it again, it first holds the original with a new pin. Then it deletes the leftover helper, the earlier pin, and the incomplete copy (the one whose `migration-source` points at the same original), and copies from the start. While the original and the copy exist together, the backend refuses to start that session, and the GC leaves both out of the candidates. So a worker never comes up on a half-copied tree, and the original is never reclaimed alone first. If you leave it unfinished, both volumes remain, so run it again or clean up by hand. A volume with the original's name may also have been recreated after the copy was made. This is because Docker creates an empty volume when you mount a name that does not exist. In that case the creation time does not match, so the command treats that copy as incomplete and does not delete it. It refuses instead. The copy may be the only intact workspace, so compare the two directly and clean up. When the original is deleted, a worker is brought up again on the new volume. It is the next pass that brings it up, and if a failed launch is waiting to retry before that, the pass after the wait ends. A launch that fails because of the legacy volume also accumulates its count like other failures. When it reaches the limit, the session becomes `failed`, so move it as early as you can.

## Worker network: address pool, slot limit, reclamation

**Address pool.** One worker network takes one subnet from the daemon's `default-address-pools`. Docker's default pools total 31.

* 15 /16 blocks, `172.17.0.0/16` to `172.31.0.0/16`
* 16 blocks made by dividing `192.168.0.0/16` into /20

Of these, `docker0` and the other networks on the daemon take theirs first. The compose in this repository uses one `default`. So what is left for workers under the defaults is about **30 − (the number of other networks on that daemon)**.

**Relation to the slot limit.** One execution holds only one network. A replace deletes the previous generation and then creates the new one. So the number of worker networks in use at the same time is roughly `EXECUTION_SLOT_LIMIT` (default 10). But the pool is **daemon-wide**, so it is shared with other installations and other compose projects on the same daemon. A network left over because its reclamation failed is not counted by the slot limit either. So with the default pool, two installations with slot limit 10 barely fit on one daemon.

**Widening the pool.** To use more than that, widen the pool in daemon.json. Example: `{"default-address-pools":[{"base":"10.210.0.0/16","size":24}]}` gives 256 /24 blocks.

* Pick a range that does not overlap the LAN or VPN.
* If you reduce the size (4096 blocks with `/28`), **every other** network automatically allocated on that daemon also becomes small. With /28 it holds up to 13 containers.
* It applies only after a daemon restart, and does not apply to networks that already exist.

**Behavior on exhaustion.** Exhaustion is not a silent failure. The network create fails with `could not find an available, non-overlapping IPv4 address pool`. Then that launch is recorded in `failedLaunches` and the pass ends with exit 1. The intent remains and the next pass tries again.

**Reclamation has two layers.**

1. `terminate`: after deleting the container, it detaches the proxy and deletes the network by id (best effort).
2. At the end of stage (2) of the pass, before filling the slots (`reconcileNetworks`): it sweeps all the worker networks that carry this installation's label.
   * If there is **no** container that corresponds to the name (in any state), it only detaches the proxy and deletes the network. The case where a container was deleted with `docker rm -f` falls here. If the launch is an execution that is still alive, stage (1) recreated the container first, so that network is reused as it is.
   * If the container **exists**, it checks the proxy attach and reattaches it if it has dropped off. When `compose up` recreates the proxy, the new proxy is not attached to any worker network. So the egress of workers that are up is cut until the next pass (`SCHEDULER_INTERVAL_SEC`, default 5 seconds).

**Behavior when reclamation fails.**

* A live network is also inspected again by the same criteria on every pass. The targets are the shape of the network, whether the container that corresponds to the name is that worker of this installation, members other than the worker and proxy, and whether the worker is also attached to another network. A network made in advance ahead of a replacement (one to which the old container is not yet attached) is not treated as a problem.
* Members are not only the running endpoints that network inspect shows. A container that is stopped or has never been started also attaches the moment it starts, so it is counted too (containers are looked up with the `network` filter).
* The only proxy allowed to remain on a live network is **the one running now.** Other proxies carrying the label (a stopped earlier proxy and so on) are detached and counted in `networksRepaired`. This is because the moment one starts, it can stand in front of the worker again with the same alias. If two or more proxies are running, neither can be trusted, so all proxies carrying the label are detached and it is reported in `networksFailed`. If none is running, it only reports and leaves things as they are. A proxy that started on its own is the one to be trusted. A worker network with no execution label also has its proxy detached and is reported.
* On a network with an unknown member attached, that member is not detached. Detaching it by force would erase the trace. Instead, it **detaches this installation's proxy.** This is so that the unknown container cannot use this installation's allowlist. The worker of that network also loses egress. Such a network is left as it is and reported in `networksFailed`, and the pass ends with exit 1.
* If the list lookup itself fails (`networkScanFailed`), it is also exit 1.
* A remaining network keeps occupying the address pool. The operator checks the members with `docker network inspect <name>` and cleans up.
* If there is no proxy, the preflight exits, so this reclamation does not run either. In return, no new network is made, so the leak does not grow, and the first pass after the proxy returns reclaims.

When several installations share the same daemon, give each installation a different `EXECUTION_INSTALLATION_ID`, and keep a separate egress proxy per installation, each labeled with its own id. The installation id is in the worker network name and label, so only installation A's proxy attaches to the worker networks of installation A. If two installations use one proxy, the workers of the two installations end up using the same allowlist.

The proxy in compose runs from an image built from `apps/egress-proxy/Dockerfile`. The source is inside the image, so moving the checkout does not change a running proxy, and new code is reflected only by rebuilding with `up -d --build egress-proxy`.
- At startup the proxy reports the sha256 of its own source (the non-test `.ts` files in `src`) in the log (`source` of `Egress proxy listening`) and in `/healthz` (`ok source=<hex>`). Use this value to confirm which code is running.
- The compose healthcheck (`src/healthcheck.ts`) compares this value with the current source in `/app/src`, and if they differ it falls to `unhealthy`. When running from the image the two are always the same. This check fires only when someone mounted and overwrote the source tree and then moved that checkout. But Docker changes the state only after 12 consecutive failures (about 60 seconds) accumulate.

```bash
docker compose -f infra/compose.yml up -d --wait --build egress-proxy   # after moving the checkout
docker compose -f infra/compose.yml exec -T egress-proxy bun run /app/src/healthcheck.ts
docker network ls --filter label=agent-platform.worker-network=true \
  --format '{{.Name}} {{.Labels}}'
```
