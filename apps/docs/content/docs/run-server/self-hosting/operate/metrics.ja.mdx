---

Helmインストールで`metrics.enabled: true`を有効にすると、プラットフォームが、インストール全体のセッション状態、turn数と所要時間、ツール呼び出し、providerトークンと推定コスト、待機キューをメトリクスとして出します。運用者のコレクター(Prometheus、Datadog Agent、OpenTelemetry Collector)が、Prometheusのテキスト形式(0.0.4)で読みます。ダッシュボードとアラート規則は運用者が作ります。PodのCPU・メモリ・再起動・ログはクラスターのコレクターが集めるので、ここにはありません。

## 有効にする

```yaml
metrics:
  enabled: true
  podAnnotations:          # how the collector finds the Pod; the install chooses
    prometheus.io/scrape: "true"
    prometheus.io/port: "9464"
networkPolicy:
  metrics:
    ingressFrom: []        # empty: reachable on 9464 from anywhere; narrow it to the collector namespace
```

有効にすると、chartが`<release>-metrics` Deployment(replica 1、`Recreate`)、同じ名前のClusterIP Service(9464)、9464だけを開くNetworkPolicyを作ります。無効なら(既定)何も作らないので、既定のインストールのレンダリング結果は変わりません。値の全一覧は、`deploy/helm/werft/values.yaml`の`metrics`ブロックです。

`metrics`ロールが読む設定:

| 設定 | 既定値 | 意味 |
|---|---|---|
| `METRICS_PORT` | `9464` | `/metrics`と`/healthz`を受けるポート。chartは`metrics.port`から入れます |
| `DATABASE_URL` | なし(必須) | 読み取り専用で開くDBのアドレス。chartはほかのロールと同じSecretのkeyを入れます |
| `config.limits`の上限 | [設定リファレンス](/run-server/self-hosting/operate/configuration) | launchの待機キューを、schedulerと同じコスト・token上限で数えます。chartはschedulerと同じ値を入れます |
| `LOG_LEVEL` | `info` | 読み取りの失敗を記録するログレベル |

確認:

```sh
kubectl -n <namespace> port-forward deploy/<release>-metrics 9464
curl -s localhost:9464/metrics
```

## コレクターの読み方

| コレクター | 方法 |
|---|---|
| Prometheus | `metrics.podAnnotations`の`prometheus.io/*` annotation、または運用者のServiceMonitorがService `<release>-metrics`の`metrics`ポートを指す |
| Datadog Agent(Helm) | Autodiscoveryの`openmetrics`チェック。`metrics.podAnnotations`に`ad.datadoghq.com/metrics.checks`を入れます。Datadogにどんな名前(ドット表記など)で保存するかは、コレクター側の設定です |
| OpenTelemetry Collector | `prometheus` receiverで同じエンドポイントをscrapeし、OTLPで送る |

プラットフォームがOTLPでメトリクスを押し出すことはありません。pullのエンドポイントを1つ置けば、コレクターの種類に関係なく同じ定義を読め、アプリにコレクターのアドレスやSDK設定は要りません。セッショントレースはまだエクスポートしません。[オブザーバビリティ (OTel)](/observability)を参照してください。

## 値の作り方

- **scrapeのときにDBから計算します。** `metrics`ロール(`bun run apps/control-host/src/main.ts metrics`)は状態を持ちません。リクエストごとに`packages/db/src/metrics-reader.ts`のクエリでDBを読み、`apps/control-host/src/metrics/families.ts`がメトリクスに変換します。そのため、Podが再起動してもcounterは0に戻りません。
- **targetは1つです。** 値はインストール全体の合計なので、replicaが2つなら同じ値を2回出します。chartはreplicaを1に固定し、`Recreate`にします。
- **読み取り専用の接続です。** DB接続は`default_transaction_read_only=on`で開くので、誤って送った書き込みはDBが拒否します。これはセッション設定であって、DBの権限ではありません。`DATABASE_URL`のアカウントはほかのロールと同じで書き込み権限があり、接続の中で設定を戻せば書けます。この設定は接続開始パラメーターの`options`として送るので、`options`を拒否する接続プーラー(`ignore_startup_parameters`に`options`がないPgBouncerなど)を経由すると、metricsロールだけが接続できません。
- **同時のscrapeは1回だけ読みます。** 読んでいる間に来たリクエストは、同じ結果を受け取ります。読み取りが失敗したら503を返し、前の値は出しません(コレクターではscrapeの失敗、Prometheusでは`up` = 0)。
- **`/healthz`** は、プロセスが応答するかだけを見ます。probeはDBを読みません。

scrapeのたびにDBを読んで値を集計します。scrapeの間隔を短くするほどDBの負荷が増えます。収集時間がscrape間隔の半分を超えたら、scrapeの間隔を長くすることを検討します。

## メトリクス

接頭辞は`werft_`です。コードでは`apps/control-host/src/metrics/families.ts`の`METRIC_PREFIX`の1か所で決めます。

| 名前 | タイプ | ラベル | 意味 |
|---|---|---|---|
| `werft_sessions` | gauge | `state`、`status`、`admission` | セッション数。`state`は下の状態表で決めます。`status`はAPIが見せる状態(`needs_input`を含む)、`admission`は`sessions.admission_state`です |
| `werft_turns_total` | counter | `status` | `completed`・`failed`・`interrupted`・`cancelled`で終わったturn数 |
| `werft_turn_duration_seconds` | histogram | `status`、`le` | 上のturnのうち開始したものの、開始から終了までにかかった時間。bucketは1、5、15、30、60、120、300、600、1800、3600秒 |
| `werft_turns_outcome_unknown` | gauge | なし | 実行が消えて結果が分からないturn数。運用者の復旧判断を待ちます |
| `werft_tool_calls_total` | counter | `tool` | エンジンが呼んだツール呼び出し数 |
| `werft_tool_calls` | gauge | `tool`、`outcome` | ツール呼び出し数を、現在の結果別に。`ok`、`failed`、`denied`、`unknown`(結果がまだない) |
| `werft_provider_tokens_total` | counter | `model`、`priced_by`、`kind` | providerの呼び出しで測ったトークン数。`kind`は`input`・`output`・`cache_read`・`cache_creation` |
| `werft_provider_cost_usd_total` | counter | `model`、`priced_by` | providerの推定コスト(USD)。Kubernetesのインフラコストではありません |
| `werft_launch_queue_sessions` | gauge | なし | workerのlaunchを待つセッション数 |
| `werft_launch_queue_oldest_wait_seconds` | gauge | なし | launch待機キューで最も長く待っているセッションの待ち時間。空なら0 |
| `werft_input_queue_oldest_age_seconds` | gauge | なし | workerがまだ取りに行っていない入力のうち、最も古いものの経過時間。空なら0 |

`tool_calls`がcounterではなくgaugeである理由: ツールの結果は後から変わることがあります。結果イベントが遅れて届くと`unknown`が`ok`や`failed`になり、より早い結果が後から届くと既存の結果を置き換えます(`packages/db/src/tool-calls.ts`のprojection)。counterの値が減ると、コレクターはresetと読んで増加量が跳ねます。呼び出し数の増加量は`tool_calls_total`で、結果別の割合は`tool_calls`で見ます。

`outcome_unknown`のturnを`turns_total`に入れない理由も同じです。運用者が復旧すると`completed`や`cancelled`に変わり、終了時刻もそのときに変わります。変わったturnは、そのとき`turns_total`とhistogramに入ります。

### セッション状態表

上から最初に合う行が`state`です。すべてのセッションがちょうど1行に入るので、`state`ごとの合計は全セッション数に等しくなります。

| `state` | 条件 | ユーザーに見える状態 |
|---|---|---|
| `ended` | `admission`が`stopping`・`stopped`・`closing`・`closed`、または保存されたstatusが`stopped` | 終了 |
| `paused` | `admission`が`pausing`・`paused` | 一時停止 |
| `recovery_required` | `admission`が`recovery_required` | — |
| `awaiting_approval` | API statusが`needs_input`で、人が答えられるpermissionリクエストがある | 承認待ち |
| `awaiting_answer` | API statusが`needs_input`で、人が答えられるリクエストがquestionだけ | — |
| `running`・`queued`・`idle`・`failed` | API statusそのまま | 実行中は`running` |

`needs_input`はDBに保存されません。実行中のセッションや、turnを止めて置いた(parked)セッションに、人が答えられるリクエストがあると、読むときに`needs_input`になります(`packages/db/src/pending-requests.ts`の`publicStatus`)。メトリクスも同じ規則(`actionableOfSession`)を使います。`ended`は、閉じたセッションが消えないので増え続けます。現在の負荷は、`ended`を除いた合計で見ます。

### ツールの結果と拒否

- `ok`・`failed`・`unknown`は`tool_calls.outcome`(ツール結果ブロックの`is_error`)です。
- `denied`は、人がpermissionリクエストに`deny`で答えた呼び出しです。`pending_requests`(`kind = 'permission'`、`answer.decision = 'deny'`)と`tool_calls`を`(session_id, tool_use_id)`で結びます。tool_use idはproviderが与える一意の値なので、止めて置いたリクエストに次のattemptが答えた場合も、同じ呼び出しに結びます。同じtool_useに`deny`の答えが1つでもあれば、その後に再び許可されて実行されても`denied`として数えます。
- エージェントのツールポリシーの`deny`、期限切れや取り消されたリクエスト、`tool_use_id`を送らない古いworkerの拒否は、`denied`ではなく結果ブロックのとおり(`failed`など)に数えます。

### コストとトークン

- コストは`provider_usage.cost_usd`の合計です。この値は呼び出しを記録するときに、プラットフォームの価格表(`packages/platform/src/limits/model-prices.ts`の`priceProviderUsage`、`MODEL_PRICES`)が計算しました。メトリクスは単価を再計算せず、単価の設定も別に持ちません。
- `priced_by`は、その呼び出しの価格の根拠です。`table`(価格表にあるモデル)、`fallback`(価格表にないモデルなので最も高い単価で計算)、`unmetered`(profileが`billing: none`なのでコスト0)。自己ホストのモデルのようにコストが0の呼び出しは、`priced_by="unmetered"`のトークン数で使用量を見ます。
- **期間の基準は、呼び出しを記録した時刻(`provider_usage.recorded_at`)です。** 期間のコストは、`increase(werft_provider_cost_usd_total[1h])`のように、counterの増加量で見ます。
- `GET /v1/usage/summary`とは3点違います。期間内に作成して期間内に課金されたセッションだけなら、2つは一致します(`packages/db/src/metrics-reader.test.ts`)。
  - summaryは、期間内に**作成した**セッション(`sessions.created_at`)を選んで、そのセッションのコスト全体を足します。期間より前に作成したセッションが期間内に使ったコストは、メトリクスにだけあります。
  - summaryは`sessions.cost_usd`を足します。この値はセッションのコスト上限の桁(99,999,999.999999 USD)で止まりますが、呼び出しごとのコストは止まりません。
  - summaryには、呼び出し単位の記録ができる前(マイグレーション0169より前)のセッションコスト(`session_pre_metering_cost`)が入っていて、メトリクスにはありません。
- トークンは、`provider_usage`の呼び出しごとの値を足します。`cache_creation`は、1時間cacheの書き込みを含む、cache書き込み全体です。

### 待機キュー

- **launch待機キュー**: schedulerが次のpassでworkerを起動できるセッションです。schedulerと同じSQL条件(`packages/db/src/scheduler-store.ts`の`awaitingLaunch`)で数えます。launchできるadmission、実行の回収・takeoverがない、コスト・token上限の範囲内、restoreの再試行時刻を過ぎている、スロットを持つlaunchがない。上限は、schedulerと同じ`config.limits`から読みます。待ち時間は`unassigned_sessions.signaled_at`から測ります。
- **入力待機キュー**: `queue_messages`のうち、どのworkerも取っておらず、見える時刻を過ぎた入力です。composeの`werft.queue.oldest_age_seconds`と意味が同じです。

## ラベルの規則

- セッションid、turn id、ユーザーid、API key id、エージェントid、attempt idは、ラベルに使いません。エージェント別のコストは`GET /v1/usage/*`で見ます。
- `state`・`status`・`admission`・`outcome`・`priced_by`・`kind`・`le`には、決まった値だけが出ます。
- `tool`と`model`はデータから来ます。MCPツール`mcp__<server>__<tool>`は`mcp__<server>`に畳みます。そのあと、最初に現れた順に、`tool`は100個、`model`は50個までだけ名前を置き、残りは`other`にまとめます。行を消さないので、名前を得た値は、通常そのまま残ります。ただし、上限が埋まった後で、projectionが遅れて入れた行(`tool`)や遅れてコミットされた行(`model`。`recorded_at`はトランザクションの開始時刻)がより早い時刻を持つと、名前1つが`other`と入れ替わることがあります。そのとき押し出された名前のseriesは途切れ、入ってきた名前は新しいseriesとして始まり、`other`は1回跳ねるか、resetとして読まれます。
- テスト: `apps/control-host/src/metrics/families.test.ts`のcardinalityの節が、ラベル名の一覧、id形の値がないこと、上限を確認します。

## composeのメトリクスとの対応

composeのDatadog overlayは、PostgreSQLのcustom queryで似た値を出します([Datadog監視基準](/run-server/self-hosting/operate/monitoring-datadog)、`infra/datadog/conf.d/postgres.d/conf.yaml`)。Kubernetesのインストールでは、このメトリクスを読みます。

| compose(DB query) | このメトリクス |
|---|---|
| `werft.queue.oldest_age_seconds` | `werft_input_queue_oldest_age_seconds`(同じ意味) |
| `werft.provider.cost_usd_1h` | `increase(werft_provider_cost_usd_total[1h])` |
| `werft.provider.unmetered_tokens_1h` | `increase(werft_provider_tokens_total{priced_by="unmetered"}[1h])`の合計 |
| `werft.provider.fallback_pricing_count_1h` | 対応なし(呼び出し数の代わりに`priced_by="fallback"`のコストとトークンを見ます) |
| `werft.turn.outcome_unknown_count` | 対応なし。`werft_turns_outcome_unknown`は、直近5分に生じた数ではなく、今残っている数です |
| `werft.checkpoint.pending_age_seconds`、`werft.lease.stale_count` | 対応なし |
