## 계약

`WERFT_API_KEY`와 `WERFT_BASE_URL`은 서버 설정이 아니라 SDK 호출자의 설정이다. [SDK 클라이언트 설정](/getting-started/client)을 따른다.

설정값의 형식·필수성·반영 시점을 찾는 문서다. 실행 전 활성화·롤백 게이트는 [Compose 업그레이드](/run-server/self-hosting/upgrade-compose)와 [Kubernetes 업그레이드](/run-server/self-hosting/upgrade-kubernetes)를 먼저 읽는다.

## 설치 상한

API와 scheduler는 아래 값 중 `SESSION_TOKEN_LIMIT`를 뺀 여섯 값이 없거나, 어느 값이든 형식이 틀리면 문제를 한 줄에 모두 로그로 남기고 기동하지 않는다. `SESSION_TOKEN_LIMIT`는 없으면 0(상한 없음)으로 읽는다. 두 프로세스는 같은 parser(`packages/platform/src/limits/installation-limits.ts`)를 쓴다. `SESSION_TOKEN_LIMIT`의 0 말고는 코드에 기본값이 없고, compose의 `x-installation-limits` 블록이 로컬 기본값을 준다. 떠 있는 API의 `/readyz`는 같은 검증을 `config` 체크로 다시 수행한다.

| 변수 | 의미 | 넘었을 때 |
|---|---|---|
| `EXECUTION_SLOT_LIMIT` | 동시에 슬롯을 잡는 worker 수. 0이면 접수만 받고 아무것도 띄우지 않는다 | 입력은 거부하지 않고 `queued`로 둔다 |
| `QUEUED_INPUT_LIMIT_PER_SESSION` | 세션 하나가 쌓아 둘 수 있는 `queued` turn 수 | `429 RATE_LIMITED`, `retryable:true`, `Retry-After: 5` |
| `STORAGE_LIMIT_BYTES` | 설치 전체가 보존하는 입력 message의 UTF-8 bytes. event·checkpoint object·worker 디스크는 세지 않는다(디스크는 workspace quota가 맡는다) | `413 STORAGE_LIMIT_EXCEEDED`, `retryable:false` |
| `MAX_TURN_SECONDS` | turn 하나의 벽시계 상한. 승인 대기도 포함한다. worker env `WORKER_MAX_TURN_SEC`로 전달된다 | turn `failed(turn_timeout)`. 엔진이 응답하지 않으면 `outcome_unknown(turn_timeout)` |
| `SESSION_COST_LIMIT_USD` | 세션 누적 비용(egress proxy가 계측한 Messages 호출별 usage를 플랫폼 가격표로 환산한 합, 추정치) | 새 turn을 dispatch하지 않는다. 세션 상세 `attention.code=BUDGET_EXCEEDED`가 뜨고 worker는 슬롯을 반납한다. 입력은 계속 `queued`로 받는다 |
| `SESSION_TOKEN_LIMIT` | 세션 누적 provider token 수. 비용 상한과 같은 호출을 세되 단가와 무관하다. 0이면 상한이 없다(기본) | `SESSION_COST_LIMIT_USD`와 같다. 두 상한은 같은 판정(`budgetExceeded`)을 지나며 어느 쪽이 먼저 닿아도 `BUDGET_EXCEEDED`다. `attention.reason`은 닿은 상한만 적는다 |
| `PROVIDER_MAX_RETRIES` | 실패한 Messages 요청을 다시 보내는 횟수. worker env `WORKER_PROVIDER_MAX_RETRIES`를 거쳐 SDK `CLAUDE_CODE_MAX_RETRIES`로 전달된다. 0이면 첫 실패에서 turn이 끝난다 | turn `failed(api_error)`. turn 상세 `result`에 `api_error_status`·`provider_error`·`last_retry_status`가 남는다 |

## API 설정

API는 설치 상한 말고도 아래 값을 기동 때 한 parser(`apps/control-host/src/api/api-settings.ts`)로 읽는다. 설정하지 않으면 기본값을 쓴다. 설정했는데 틀린 값이면(빈 문자열 포함) 기본값으로 돌아가지 않는다. 숫자 설정은 API·scheduler·reconciler·worker와 설치 상한이 모두 이 규칙을 따른다(`packages/contracts/src/shared/settings.ts`). 기본값이 없는 값은 설정하지 않으면 `X is required`로, 틀린 값은 `X must be a positive integer`처럼 기대한 범위를 적어 거부한다. 받은 값은 적지 않는다. 로그에 남고, 다른 변수에 잘못 넣은 비밀일 수 있어서다. 이때 `Refusing to start: API settings are invalid` 한 줄에 문제를 모두 남기고 기동하지 않는다. 떠 있는 API의 `/readyz`도 같은 검증을 `config` 체크로 다시 수행한다.

| 변수 | 기본값 | 허용 범위 |
|---|---|---|
| `HEARTBEAT_TTL_SEC` | 30 | 20 초과 86400 이하. worker는 lease가 끝나기 10초 전에 lease를 내려놓고(`WORKER_LEASE_SAFETY_MARGIN_SEC`), 5초마다 heartbeat를 보낸다(`WORKER_HEARTBEAT_INTERVAL_SEC`, 이전 버전 worker는 10초). 마진과 10초의 합 이하이면 이전 버전 worker의 attempt가 첫 heartbeat 무렵 lease를 잃는다. launcher는 두 worker 값을 넘기지 않으므로 기본값을 기준으로 판정한다 |
| `PENDING_REQUEST_TTL_SEC` | 1800 | 정수 1–604800. 승인·질문 요청을 받는 기간이다. 등록된 요청은 worker가 이 값만큼 기다린다. worker의 `QUESTION_TIMEOUT_SEC`는 gateway가 등록을 확인하기 전에만 적용된다. turn 벽시계 `MAX_TURN_SECONDS`에는 대기 시간도 들어가므로, 대기는 그 상한을 넘지 못한다 |
| `SSE_MAX_STREAMS` · `SSE_MAX_STREAMS_PER_OWNER` · `SSE_REPLAY_MAX_BYTES` | 256 · 8 · 1 MiB | 양의 정수 |
| `AGENT_ACTION_FLOWS` | `false` | `true`·`false`·`1`·`0`(그 밖의 값은 기동을 거부한다). 켜면 실행 중인 turn의 `request_push`가 요청 대신 "turn이 끝날 때 push" 의도를 남기고, 이어 가는 turn 없이 그 turn의 마지막 checkpoint를 push 요청으로 만든다. 끄면 새 의도를 만들지 않고 옛 흐름으로 돌아간다. 이미 남은 의도는 계속 처리된다. 활성화·rollback은 [업그레이드 게이트](/run-server/self-hosting/upgrade-compose#실행-전-게이트)를 먼저 따른다 |
| `LOG_LEVEL` | `info` | `debug`·`info`·`warn`·`error`(대소문자 무관, 빈 값은 `info`). scheduler·reconciler loop와 egress-proxy도 같은 규칙으로 기동을 거부한다. worker는 scheduler의 값을 받는다 |
| `WEB_DIST_DIR` | 없음(웹 콘솔을 서빙하지 않음). control-host 이미지는 `/app/apps/web/dist` | `index.html`이 있는 절대 경로. 웹 콘솔(`apps/web`)의 빌드 결과다 |

모든 `/v1` 응답은 `api.request.completed`를 남긴다. 실제 id가 없는 Hono `route_template`, `method`, `status`, 인증과 route 처리를 포함한 `duration_ms`, `operation=api_request`, `outcome`, `reason_code`가 있고 `request_id`는 log context에 있다. request body·credential·provider key는 넣지 않는다. terminate 요청은 같은 `request_id`의 `Terminate control transaction completed`도 남기며, 여기에는 pool checkout, binding·launch·session lock, 각 SQL, commit 또는 rollback, control transaction 전체의 millisecond 계측이 들어간다. 배포 환경에서 수락 지연을 조사할 때는 두 로그를 `request_id`로 묶어 어느 단계가 느렸는지 판단한다.

terminate가 이미 사라진 execution에서 즉시 끝나거나 scheduler/reconciler가 execution 부재를 확인하면 `control.result`가 `operation=terminate`, receipt id인 `control_id`, `outcome`, `reason_code`, durable 수락부터 확인까지의 `effect_ms`(`duration_ms`와 같음)를 남긴다. 기한을 넘긴 receipt는 먼저 `outcome=unknown`·`reason_code=deadline_exceeded`를 남기며, 이후 execution 부재를 확인해 receipt를 성공으로 올리면 `outcome=succeeded`·`reason_code=execution_gone` 결과를 추가로 남긴다.

`WEB_DIST_DIR`가 있으면 API가 웹 콘솔을 같은 origin에서 서빙한다. `/v1`·`/internal` 밖의 GET·HEAD는 그 디렉터리의 파일을 돌려주고, 파일이 없으면 `index.html`을 돌려준다(SPA fallback). 그래서 `/login`·`/bootstrap`을 새로고침해도 화면이 열린다. `/v1`·`/internal` 아래는 fallback하지 않는다. 인증된 `/v1/nope`는 JSON `404 NOT_FOUND`다. `/assets/` 아래 파일은 content hash가 붙은 이름이라 `immutable`로 캐시하고, 없는 asset은 페이지 대신 404를 준다. `index.html`은 `no-cache`이며 inline script를 허용하지 않는 CSP(`script-src 'self'`)를 붙인다. control-host 이미지는 `web` build stage에서 `apps/web`을 빌드하고 `dist/`만 담는다. 별도 web 이미지는 없다. 로컬에서 웹만 고칠 때는 `bun run --cwd apps/web dev`(Vite, `/v1`을 `VITE_API_TARGET` 기본 `http://127.0.0.1:3000`으로 proxy)를 쓴다.

`AUTH_MODE=none`은 egress authorizer(`EGRESS_AUTHORIZER_PORT`)와 함께 쓸 수 없다. authorizer가 켜져 있다는 것은 worker가 proxy를 거쳐 이 API에 닿는다는 뜻이다. `none` 모드에서는 worker 안의 코드가 `X-Owner-Id`로 아무 owner나 행세할 수 있으므로 기동을 거부한다. `AUTH_MODE` 값 자체(`none`|`api-key`)는 readiness가 판정한다.

worker도 기동 때 교차 검사를 한다. `WORKER_PROVIDER_MAX_RETRIES`가 없으면 기동하지 않는다. 코드 기본값이 없는 설치 상한이고, scheduler가 항상 넘긴다. `WORKER_NEXT_INPUT_WAIT_SEC`가 `WORKER_REQUEST_TIMEOUT_SEC` 이상이어도 기동하지 않는다. 그 설정에서는 모든 long poll이 요청 timeout에 잘린다. scheduler와 reconciler는 빈 `DATABASE_URL`을 설정하지 않은 것으로 보고 `QUEUE_DATABASE_URL`을 쓴다.

API와 slack role은 `WORKER_IMAGE_RUNTIME`과 `WORKER_IMAGE_PREVIOUS_RUNTIME`으로 현재·직전 worker 이미지의 런타임 조합을 읽는다. 값은 손으로 적지 않고, images.yml이 남긴 worker digest JSON의 `runtime` 필드를 그대로 넣는다(`{"engine":…,"sdkVersion":…,"cliVersion":…,"profileDigestScheme":…}`). `engine`은 지금 `claude`뿐이고, chart는 다른 이름을 렌더링 때 `images.worker.runtime.engine must be one of: claude`로 거절한다. 직접 빌드한 이미지에는 그 JSON이 없다. images.yml과 같은 명령으로 이미지에서 읽는다.

```bash
docker run --rm -i --network none --entrypoint bun <worker-image> \
  run apps/worker/src/image-runtime.ts <<<'{}' | jq -c 'del(.profiles)'
```

둘 다 없으면 런타임 조합을 읽지 않으므로 아래 pin 유지도 적용되지 않는다. `WORKER_IMAGE_PREVIOUS_RUNTIME`만 있거나 값을 읽을 수 없으면 기동하지 않는다. 설정하면 profile의 `runtime_version`을 다음 이미지 버전으로 올려도, 직전 이미지 버전으로 만들어진 열린 세션의 profile pin이 유지된다. 현재 이미지가 싣지 않은 `runtime_version`의 profile은 새 세션을 받지 않는다. 그래서 SDK를 올리는 릴리스는 상한마다 `runtime_version`을 올린 새 버전을 함께 만든다(콘솔 또는 `POST /v1/installation-profiles`).

API와 slack role은 `SESSION_PROMPT_REVISION`(기본 0, 허용 값 0·1, 틀린 값이면 기동하지 않음)으로 에이전트 release 세션의 system prompt 앞머리 문단을 정한다. 1이면 새 세션은 만들 때 에이전트 이름·설명, 시작한 곳(Slack 채널·DM, 웹 콘솔, API), 에이전트의 언어, 세션 저장소의 GitHub 이름(`owner/repo`)을 `sessions.platform_prompt`에 남기고, worker가 그것으로 문단을 만든다. 문단에는 역할 문장이 없다. 역할은 에이전트 작성자가 지시문에 쓴다. GitHub 안내는 설정 유무와 관계없이 한 문단이다. GitHub 일은 내장 `mcp__github__` 도구로 하고 쓸 수 있는 저장소는 `list_repositories`가 답한다고 알린다. `git push`는 GitHub에 닿지 않는다는 것도 알린다. 그 도구가 없거나 GitHub를 쓸 수 없다고 답하면 "이 세션에서는 GitHub 작업을 할 수 없고, 관리자가 콘솔 에이전트 GitHub 탭에서 설정하며 새 세션이 필요할 수 있다"고 답하게 한다. GitHub 설정 없는 release로 시작한 세션에는 나중에 설정해도 도구가 붙지 않기 때문이다. 0이면 새 세션도 문단이 없다. 저장한 값은 세션이 끝날 때까지 바뀌지 않는다. 문단은 checkpoint fingerprint에 들어가므로 에이전트 이름·설명이나 release를 바꿔도 진행 중인 세션은 그대로 재개된다.

`SESSION_PROMPT_REVISION`의 배포·활성화·rollback 순서는 [Compose 게이트](/run-server/self-hosting/upgrade-compose#실행-전-게이트) 또는 [Kubernetes 게이트](/run-server/self-hosting/upgrade-kubernetes#실행-전-게이트)를 따른다. 0으로 되돌려도 이미 1로 만든 세션의 저장된 문단은 바뀌지 않는다. 로컬 compose는 API·slack·worker를 한 tree에서 빌드하므로 1을 기본으로 둔다.

GitHub Packages bot token([결정](https://github.com/JeongJaeSoon/werft/blob/main/docs/contributing/decisions/github-packages-bot-token.md))을 다른 host로 보내야 할 때만 아래 값을 둔다. GitHub Enterprise Server나 테스트용 가짜 레지스트리가 그런 경우다. 값은 http(s) URL이고 userinfo·query·fragment가 있으면 API가 기동하지 않는다. 레지스트리 host는 proxy의 `EGRESS_CREDENTIAL_ALLOWLIST`(사설 주소면 `EGRESS_CREDENTIAL_PRIVATE_ALLOWLIST`)에도 있어야 한다.

| 변수 | 기본값 | 의미 |
|---|---|---|
| `GITHUB_PACKAGES_API_URL` | `https://api.github.com` | 등록하는 token의 scope를 묻는 곳(`GET /user`) |
| `GITHUB_PACKAGES_NPM_URL` | `https://npm.pkg.github.com` | `github-npm` route의 upstream |
| `GITHUB_PACKAGES_RUBYGEMS_URL` | `https://rubygems.pkg.github.com` | `github-rubygems` route의 upstream |

## scheduler·worker 컨테이너·egress 설정

scheduler가 worker 컨테이너를 만들 때 읽는 값이다. 없으면 기본값을 쓰고, 형식이 틀리면 기동하지 않는다. user, HOME·workspace 경로, tmpfs 크기, credential 포트, stop timeout은 `werft.isolation` 지문에 들어간다([실행 기반과 worker 격리](/run-server/self-hosting/explanation/isolation)). 그래서 바꾸면 실행 중인 worker가 교체된다. CPU·메모리·PID 한도는 다음 launch부터 적용된다.

`WORKER_MEMORY_MB`는 transcript 상한(`MAX_TRANSCRIPT_BYTES`)과 함께 정한 값이다. 둘의 관계, 실측, 노드당 세션 수, 바꾸는 방법은 [용량 관리](/run-server/self-hosting/reference/storage)에 있다.

scheduler는 `WORKER_IMAGE`와 `WORKER_IMAGE_RUNTIME`으로 현재 이미지를, `WORKER_IMAGE_PREVIOUS`와 `WORKER_IMAGE_PREVIOUS_RUNTIME`으로 직전 릴리스 이미지를 받는다. 런타임 값은 API와 같은 값이다(위 API 설정). 직전 이미지는 두 값을 함께 설정하고, 하나만 있으면 기동하지 않는다. `WORKER_IMAGE_RUNTIME`이 없으면 모든 launch가 `WORKER_IMAGE`로 뜬다. 설정하면 launch마다 세션의 checkpoint 포인터가 기록한 조합(engine·SDK·CLI·profile digest scheme)과 같은 이미지를 고르고, 둘 다 맞으면 현재 이미지를 쓴다. 새 세션, checkpoint가 없는 세션, 조합을 기록하지 않은 옛 checkpoint는 현재 이미지로 뜬다. 어느 이미지와도 맞지 않는 세션은 worker를 띄우지 않고 `recovery_required`(`incompatible_checkpoint`)로 멈추며, 세션 이벤트 `checkpoint_restore_failed`에 `detected_at: "launch"`가 남는다. `retry_restore`로 다시 시도할 수 있다.

worker는 claim 때 자기 이미지가 실제로 싣는 조합을 보낸다. 설정한 조합과 다르면 API가 claim을 거절하고(`LAUNCH_FAILED`, `reason_code` `worker_image_mismatch`), 그 이미지를 그 설정값에 대해 거부한 것으로 기록한다. 이후 그 이미지로 뜰 세션은 launch되지 않고 기다리며, scheduler pass는 `images_refused`를 error 로그로 남기고 exit 1로 끝난다. 이미지 설정을 바로잡으면(값이 달라지면) 다음 pass부터 다시 launch한다. 세션 자체는 실패로 바뀌지 않는다.

배포 순서: 새 worker는 claim에 `image_runtime`을 싣는다. 이 필드를 모르는 옛 API는 요청을 거절하므로, API를 먼저 올린 뒤 scheduler의 `WORKER_IMAGE`를 새 이미지로 바꾼다.

| 변수 | 기본값 | 의미 |
|---|---|---|
| `WORKER_CPUS` | 1 | worker 하나의 CPU 몫. 0.01 이상 |
| `WORKER_MEMORY_MB` | 4608 | worker 하나의 메모리 한도(MiB). 압축 없는 512MiB transcript를 resume한 엔진이 한도의 절반 아래에 들도록 잡은 값이다 |
| `WORKER_PIDS_LIMIT` | 512 | worker 하나의 PID 한도. compose는 넘기지 않는다 |
| `EXECUTION_DOCKER_USER` | `1000:1000` | worker의 숫자 `uid[:gid]`. uid나 gid가 0이면 기동을 거부한다. worker 이미지의 `/workspace` 소유자와 같아야 한다 |
| `EXECUTION_DOCKER_HOME_DIR` | `/home/worker` | tmpfs로 마운트하는 HOME. 절대 경로 |
| `EXECUTION_DOCKER_WORKSPACE_DIR` | `/workspace` | 세션 volume을 마운트하는 곳. 절대 경로이고 HOME과 달라야 하며 공백·역슬래시를 쓸 수 없다. worker에는 `WORKER_WORKSPACE_DIR`로 간다 |
| `EXECUTION_DOCKER_TMPFS_SIZE_MB` | 256 | HOME과 `/tmp` tmpfs 각각의 크기(MiB) |
| `EXECUTION_DOCKER_STOP_TIMEOUT_SEC` | 120 | SIGTERM에서 SIGKILL까지의 유예. 30 미만이면 기동을 거부한다. worker에는 `WORKER_STOP_GRACE_SEC`로 가고, worker는 drain을 그 안에 맞춘다 |
| `EXECUTION_DOCKER_REQUEST_TIMEOUT_SEC` | 30 | Docker Engine API 요청 하나의 기한 |
| `EXECUTION_DOCKER_COMMAND` | 없음 | 이미지 entrypoint 대신 돌릴 명령(공백으로 나눈다). 테스트용이다 |
| `DOCKER_HOST` | `unix:///var/run/docker.sock` | Docker daemon 주소 |
| `DOCKER_API_VERSION` | `v1.44` | 요청에 쓰는 Engine API 버전 |
| `EXECUTION_EGRESS_CREDENTIAL_PORT` | 3129 | proxy credential route의 포트. proxy의 `EGRESS_CREDENTIAL_PORT`와 같아야 하고, `EXECUTION_EGRESS_PROXY_URL`의 포트와는 달라야 한다 |

`EXECUTION_DOCKER_NETWORK`·`EXECUTION_DOCKER_NETWORK_ALLOWLIST`는 더 이상 읽지 않는다. 값이 있으면 기동을 거부한다.

egress-proxy와 API의 authorizer listener는 아래 값을 읽는다.

| 변수 | 기본값 | 의미 |
|---|---|---|
| `EGRESS_PROXY_HOST` | `0.0.0.0` | proxy의 두 listener(forward, credential route)가 여는 주소 |
| `EGRESS_PROXY_PORT` | 3128 | forward proxy 포트 |
| `EGRESS_CREDENTIAL_PORT` | 3129 | credential route 포트 |
| `LOG_LEVEL` | `info` | proxy 로그 수준. 규칙은 위 API 설정과 같다 |
| `EGRESS_AUTHORIZER_HOST` | `0.0.0.0` | API의 authorizer listener(`EGRESS_AUTHORIZER_PORT`)가 여는 주소 |

compose의 세 포트와 두 내부 URL은 `infra/compose.core.yml` 상단의 `x-egress-ports` 한 곳에서 정한다. proxy의 `EGRESS_PROXY_PORT`·`EGRESS_CREDENTIAL_PORT`·`EGRESS_AUTHORIZER_URL`, api의 `EGRESS_AUTHORIZER_PORT`, scheduler의 `EXECUTION_EGRESS_PROXY_URL`·`EXECUTION_EGRESS_CREDENTIAL_PORT`는 모두 그 anchor를 쓴다. 포트를 바꿀 때는 같은 블록의 listener와 URL 짝을 함께 바꾼다. `tests/images.test.ts`가 `docker compose config` 결과에서 두 URL의 포트와 세 listener가 맞는지 확인한다.

API 컨테이너의 메모리는 checkpoint bundle 검증이 정한다. 검증은 동시에 두 개까지 돌고, 검증마다 git fetch와 index-pack이 각자 `CHECKPOINT_GIT_MEMORY_MB`의 주소 공간 상한 아래에서 함께 돈다. 두 값은 함께 바꾼다. 상한만 올리면 OOM killer가 무엇을 죽일지 정하게 된다. 계산은 `infra/compose.core.yml`의 api 서비스 주석에 있다.

| 변수 | 기본값 | 의미 |
|---|---|---|
| `API_MEMORY_MB` | 7168 | compose api 컨테이너의 `mem_limit`(MiB) |
| `CHECKPOINT_GIT_MEMORY_MB` | 1536 | bundle 검증 git 프로세스 하나의 주소 공간 상한(MiB). 512 미만이면 기동을 거부한다 |

compose의 Postgres는 `POSTGRES_USER`(`postgres`)·`POSTGRES_PASSWORD`(`dev`)·`POSTGRES_DB`(`sessions`)로 만들고, 모든 서비스가 같은 값으로 DSN을 만든다.

worker는 아래 값도 env로 읽는다. 하지만 scheduler가 넘기지 않으므로 운영에서는 코드 기본값으로 고정이다. `WORKER_ANSWER_POLL_SEC`(1), `WORKER_ATTACH_FETCH_TIMEOUT_SEC`(300, 세션 도중 붙인 저장소 하나를 받아 오는 시간), `WORKER_ATTACH_FETCH_MAX_MB`(2048, 그 저장소를 받은 scratch mirror의 크기), `WORKER_CLAIM_TIMEOUT_SEC`(60), `WORKER_DRAIN_TIMEOUT_SEC`(100, stop 유예 안으로 줄어든다), `WORKER_HEARTBEAT_INTERVAL_SEC`(5), `WORKER_IDLE_TIMEOUT_SEC`(1800), `WORKER_LEASE_SAFETY_MARGIN_SEC`(10), `WORKER_NEXT_INPUT_RETRY_SEC`(60), `WORKER_NEXT_INPUT_WAIT_SEC`(20), `WORKER_REQUEST_TIMEOUT_SEC`(30), `WORKER_STARTUP_TIMEOUT_SEC`(3600), `QUESTION_TIMEOUT_SEC`(1800), `WORKER_CLAUDE_CONFIG_DIR`(`$HOME/.claude`).

## 감독 루프

| 설정 | 기본 | 의미 |
|---|---|---|
| `RECONCILER_INTERVAL_SEC` | 10 | pass가 끝난 뒤 다음 pass까지 쉬는 시간 |
| `RECONCILER_PASS_TIMEOUT_SEC` | 60 | 이 시간을 넘긴 pass는 SIGTERM, 10초 뒤 SIGKILL로 끝내고 실패로 센다. DB가 멈춘 pass가 pool timeout으로 스스로 끝나는 약 45초보다 크게 둔다 |
| `RECONCILER_MAX_CONSECUTIVE_FAILURES` | 3 | 실패 pass가 이만큼 이어지면 루프가 exit 1 하고 `restart: unless-stopped`가 재시작한다. 그보다 적으면 다음 pass가 곧 재시도다 |
| `RECONCILER_HEALTH_STALE_SEC` | 90 | healthcheck는 마지막으로 끝난 pass가 실패했거나, 진행 중인 pass가 제한 시간을 넘겼거나, 이 시간 동안 성공한 pass가 없으면 unhealthy다. 성공 직후 멈춘 pass도 제한 시간에서 바로 unhealthy가 된다. `RECONCILER_INTERVAL_SEC + RECONCILER_PASS_TIMEOUT_SEC`보다 커야 기동한다 |
| `RECONCILER_STATUS_FILE` | `/tmp/reconciler-status.json` | 루프가 pass마다 갱신하는 상태(`lastSuccessAt`·`lastDegradedAt`·`lastFailureAt`·`lastFailureReason`·`consecutiveFailures`·`lastPassDurationMs`, 진행 중인 pass의 `passDeadlineAt`). healthcheck가 읽는다 |
| `RECONCILER_BATCH_SIZE` | 100 | pass의 각 단계(orphan·lease·interrupt 회수, 기한을 넘긴 interrupt·terminate receipt의 `unknown` 마감, 입력 대기 알림)가 한 번에 처리하는 row 수 상한. 남은 row는 다음 pass가 처리한다. scheduler의 terminate 기한 sweep은 이 값을 읽지 않고 pass마다 고정 상한 100개씩 처리한다 |

| scheduler 설정 | 기본 | 제약 |
| --- | --- | --- |
| `SCHEDULER_INTERVAL_SEC` | 5 | pass 종료 뒤 대기 |
| `SCHEDULER_PASS_TIMEOUT_SEC` | 180 | Docker stop+request timeout보다 큼. Kubernetes는 150초 초과 |
| `SCHEDULER_MAX_CONSECUTIVE_FAILURES` | 3 | 연속 실패 뒤 loop 종료 |
| `SCHEDULER_HEALTH_STALE_SEC` | 200 | interval+timeout보다 큼 |
| `SCHEDULER_STATUS_FILE` | `/tmp/scheduler-status.json` | 디렉터리 전체가 쓰기 가능해야 함 |

compose는 `RECONCILER_STATUS_FILE`, `SCHEDULER_STATUS_FILE`, `RECONCILER_DRY_RUN`을 전달하지 않는다. 상태 확인은 각 status file과 `--health`를 사용한다. reconciler dry-run은 [복구 작업](/run-server/self-hosting/recover-sessions)에서 직접 1회 실행한다. `HEARTBEAT_TTL_SEC`는 API만 읽으며 reconciler에 넣으면 기동을 거부한다.

## Kubernetes env와 values

scheduler는 `EXECUTION_BACKEND`로 backend를 고른다. 값은 `local_docker`(기본값, 비워 둬도 같다)와 `kubernetes` 둘이고, 그 밖의 값이면 그 값을 적은 오류로 기동을 거부한다. `kubernetes`이면 Docker 설정(`DOCKER_HOST`, `EXECUTION_DOCKER_*`, `EXECUTION_WORKSPACE_QUOTA`)을 읽지 않고 Docker socket도 쓰지 않는다. Docker 전용 preflight인 egress proxy 격리 확인과 workspace quota probe도 돌지 않는다. kubernetes에서 worker 격리는 chart의 NetworkPolicy가 맡고, workspace 상한은 PVC 크기다. 정지·요청 timeout은 고정값(120s + 30s)이어서 `SCHEDULER_PASS_TIMEOUT_SEC`는 150보다 커야 한다. `migrate-workspace`는 Docker volume을 옮기는 도구라서 `local_docker`에서만 돈다.

readOnlyRootFilesystem인 Pod에서는 status file을 쓰기 가능한 경로에 둔다. 기본 경로 `/tmp/scheduler-status.json`·`/tmp/reconciler-status.json`은 `/tmp`에 emptyDir를 마운트하면 그대로 쓸 수 있다. 다른 경로라면 `SCHEDULER_STATUS_FILE`·`RECONCILER_STATUS_FILE`로 바꾼다. 루프는 status file과 같은 디렉터리에 임시 파일(`<status file>.<pid>.tmp`)을 쓴 뒤 rename한다. scheduler는 그 옆에 `.quota-verified` 기록도 둔다. 그래서 파일 하나가 아니라 디렉터리 전체가 쓰기 가능해야 한다.

공유 env(`WORKER_IMAGE`, `WORKER_GATEWAY_URL`, `EXECUTION_EGRESS_PROXY_URL`, `EXECUTION_EGRESS_CREDENTIAL_PORT`, `EXECUTION_INSTALLATION_ID`, `EXECUTION_WORKSPACE_QUOTA_MB`, `EXECUTION_WORKSPACE_GC_MIN_AGE_SEC`, `S3_BUCKET`, `AWS_REGION`)는 Docker backend와 같다. kubernetes 모드에서는 다음 두 값에 제약이 더 붙는다.

- `WORKER_IMAGE`는 `repository@sha256:<digest>` 형식이어야 한다.
- `EXECUTION_INSTALLATION_ID`는 32자 이하의 소문자 DNS label이어야 한다.

kubernetes 모드에서만 읽는 설정은 다음과 같다.

| 변수 | 뜻 |
| --- | --- |
| `EXECUTION_K8S_NAMESPACE` | worker Pod·Secret·PVC를 두는 namespace. 기본값은 scheduler 자신의 namespace다. 클러스터 밖에서 돌리면 반드시 줘야 한다. |
| `EXECUTION_K8S_WORKER_SERVICE_ACCOUNT` | worker Pod의 ServiceAccount. token은 늘 마운트하지 않는다. |
| `EXECUTION_K8S_STORAGE_CLASS` | workspace PVC의 StorageClass. 비우면 클러스터 기본값을 쓴다. |
| `EXECUTION_K8S_IMAGE_PULL_SECRETS` | 선택. 쉼표로 구분한 Secret 이름. |
| `EXECUTION_K8S_WORKER_NODE_SELECTOR` | 선택. JSON object. |
| `EXECUTION_K8S_WORKER_TOLERATIONS` | 선택. JSON array. |
| `EXECUTION_K8S_WORKER_EPHEMERAL_STORAGE_MB` | worker 컨테이너의 ephemeral-storage requests·limits(MB). 기본 1024. 넘으면 kubelet이 Pod를 evict한다. |

실패한 worker의 종료 사유와 로그 tail(마지막 8 KiB)은 scheduler 로그의 `Execution resource failed; log tail kept` 줄에 남는다. 저장 위치와 보존 기간은 저장소의 `packages/adapters/execution/kubernetes/README.md`(종료 사유와 로그 tail 절)에 있다.

## chart가 넣는 값

Helm chart(`deploy/helm/werft`, 설치 절차는 [Kubernetes 설치 (Helm chart)](/run-server/self-hosting/reference/configuration))로 설치하면 위 env를 직접 적지 않는다. chart가 values에서 만든다.

| env | values | 비고 |
| --- | --- | --- |
| `EXECUTION_BACKEND` | 없음 | 늘 `kubernetes` |
| `EXECUTION_K8S_WORKER_SERVICE_ACCOUNT` | 없음 | chart가 만든 `<fullname>-worker`. token은 마운트하지 않는다 |
| `EXECUTION_K8S_NAMESPACE` | 없음 | 넣지 않는다. scheduler 자신의 namespace(release namespace)가 된다 |
| `EXECUTION_K8S_STORAGE_CLASS` | `worker.storageClass` | 비면 넣지 않는다 |
| `EXECUTION_K8S_IMAGE_PULL_SECRETS` | `images.pullSecrets` | 제어 영역 Pod에도 같은 Secret을 쓴다 |
| `EXECUTION_K8S_WORKER_NODE_SELECTOR`, `EXECUTION_K8S_WORKER_TOLERATIONS` | `worker.nodeSelector`, `worker.tolerations` | JSON으로 바꿔 넣는다 |
| `WORKER_IMAGE` | `images.registry`, `images.worker.*` | `<registry>/<repository>@<digest>`. digest가 없으면 render가 실패한다 |
| `WORKER_GATEWAY_URL`, `EXECUTION_EGRESS_PROXY_URL`, `EXECUTION_EGRESS_CREDENTIAL_PORT` | 없음 | api Service의 3000, egress-proxy Service의 3128, 3129 |
| `EXECUTION_INSTALLATION_ID` | `installationId` | worker NetworkPolicy의 label 값이기도 하다 |
| `EXECUTION_WORKSPACE_QUOTA_MB`, `EXECUTION_WORKSPACE_GC_MIN_AGE_SEC` | `worker.workspace.*` | quota는 workspace PVC의 크기 |
| `WORKER_CPUS`, `WORKER_MEMORY_MB` | `worker.cpus`, `worker.memoryMb` | |
| `EXECUTION_K8S_WORKER_EPHEMERAL_STORAGE_MB` | `worker.ephemeralStorageMb` | 기본 1024 |
| 설치 상한(`EXECUTION_SLOT_LIMIT` 등) | `config.limits` | api와 scheduler에 같은 값 |
| `SCHEDULER_*` | `scheduler.intervalSec` 등 | `SCHEDULER_PASS_TIMEOUT_SEC`(`scheduler.passTimeoutSec`, 기본 180)는 150보다 커야 한다 |
| `SLACK_ROLE_INTERVAL_SEC`, `SLACK_ROLE_PASS_TIMEOUT_SEC`, `SLACK_ROLE_MAX_CONSECUTIVE_FAILURES`, `SLACK_ROLE_HEALTH_STALE_SEC`, `SLACK_ROLE_BATCH_SIZE`, `SLACK_ROLE_LEASE_SEC` | `slack.intervalSec`, `slack.passTimeoutSec`, `slack.maxConsecutiveFailures`, `slack.healthStaleSec`, `slack.batchSize`, `slack.leaseSec` | 기본 2, 60, 3, 90, 10, 60. `slack.enabled: false`면 slack Deployment를 그리지 않는다 |
| `PLATFORM_ALLOW_UNATTENDED_PERMISSIONS`(slack) | `api.extraEnv` | slack은 api와 같은 카탈로그를 읽으므로 api의 값을 따른다. `slack.extraEnv`에 적으면 그 값이 이긴다 |

어느 Deployment에나 `extraEnv`로 env를 더할 수 있다. Secret에서 오는 값(`DATABASE_URL`, `EGRESS_AUTHORIZER_TOKEN`, AWS key, 카탈로그 credential)은 [Kubernetes 설치 (Helm chart)의 준비 절](/run-server/self-hosting/kubernetes)의 표에 있다.

## probe

| 구성요소 | readiness | liveness | startup |
| --- | --- | --- | --- |
| api | `GET /readyz` | `GET /healthz` | `GET /healthz`(5초 × 24) |
| scheduler | `bun run apps/control-host/src/main.ts scheduler --health` | 같음 | 같음. 실패 허용 횟수는 `(intervalSec + passTimeoutSec + 39) / 10` |
| reconciler | `bun run apps/control-host/src/main.ts reconciler --health` | 같음 | scheduler와 같은 식 |
| slack | `bun run apps/control-host/src/main.ts slack --health` | 같음 | scheduler와 같은 식 |
| egress-proxy | `bun run /app/src/healthcheck.ts` | 같음 | 없음 |

`/healthz`는 HTTP를 받는지만 보고 DB를 보지 않는다. 그래서 liveness에 쓰고, DB·schema·설정을 보는 `/readyz`는 readiness에만 쓴다. DB가 잠시 끊겨도 api Pod는 재시작되지 않고 트래픽에서만 빠진다. `/livez`는 없다. scheduler·reconciler·slack의 `--health`는 loop가 쓰는 status file을 읽고, 직전 pass가 실패했거나 기한을 넘겼거나, `SCHEDULER_HEALTH_STALE_SEC`·`RECONCILER_HEALTH_STALE_SEC`·`SLACK_ROLE_HEALTH_STALE_SEC` 안에 끝난 pass가 없으면 실패한다. startup probe는 첫 pass가 끝날 때까지 기다린다.

## Secret과 AWS values

| 키 | 읽는 곳 |
|---|---|
| `DATABASE_URL` | api, scheduler, reconciler, slack, migrate, checkpoint GC |
| `EGRESS_AUTHORIZER_TOKEN` | api, egress-proxy(같은 값) |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | api, checkpoint GC. `secrets.objectStoreKeys: true`일 때만. `false`면 AWS 기본 credential chain(IRSA)으로 서명한다 |
| `secrets.catalogEnv`의 이름(기본 `ANTHROPIC_API_KEY`) | api만. 설정 문서가 `value_env`로 가리키는 provider·저장소 자격 증명을 환경 변수로 주는 대안이다. 모델 key의 기본 경로는 설치 뒤 콘솔의 **설정 > 워크스페이스 설정 > 모델 연결 > 연결 추가**이고, 그렇게 하면 `secrets.catalogEnv: []`로 비워 Secret에 이 키를 두지 않는다. 기본값을 두면 Secret에 그 키가 없을 때 Pod가 뜨지 않는다. slack은 받지 않는다 |
| `PLATFORM_SECRET_KEY` | api, slack. 필수. 64자 hex master key. 콘솔에서 저장한 자격 증명을 봉인한다. Secret에 없으면 Pod가 뜨지 않는다 |

| 값 | 무엇을 바꾸나 |
|---|---|
| `images.registry`, `images.*.digest` | ECR host와 그 이미지의 digest |
| `secrets.objectStoreKeys: false`, `serviceAccounts.api.annotations` | 정적 AWS key 대신 IRSA. api와 checkpoint GC가 이 role로 S3·Secrets Manager에 서명한다. scheduler와 worker는 S3 권한이 없다 |
| `secrets.externalSecret` | External Secrets Operator가 Secrets Manager의 `remoteKey`(JSON, 위 Secret 키 전부. IRSA면 AWS key 둘은 뺀다)로 Secret을 쓴다. 운영자 CRD가 필요하다 |
| `ingress` | ALB Ingress. `scheme`은 `internal`이다(위). `healthcheck-path: /readyz`, SSE를 위해 idle timeout 300초. 공개 경로(`/v1`·`/docs`·`/healthz`·`/readyz`)만 route하고 `/internal`과 authorizer(3100)는 열지 않는다 |
| `ingress.console.enabled` | 기본 `false`. 켜면 웹 콘솔 `/`와 `/internal` 404 규칙을 더한다. 켜는 조건은 [아래](/run-server/self-hosting/access) |
| `config.egress.credentialAllowlist` | provider host에 checkpoint bucket의 virtual-hosted endpoint를 더한다. worker의 checkpoint upload·restore가 credential route로 나간다 |
| `worker.storageClass`, `worker.nodeSelector`, `worker.tolerations` | worker 전용 node group과 workspace PVC의 StorageClass(gp3) |
| `networkPolicy.enabled` | VPC CNI의 network policy agent가 켜져 있어야 효력이 있다 |

정적 S3 key를 써야 하면 `secrets.objectStoreKeys: true`로 두고 Secret에 AWS key 둘을 넣는다. 둘 다 있으면 정적 key가 IRSA보다 우선한다.

## 지표 역할

| 설정 | 기본값 | 뜻 |
|---|---|---|
| `METRICS_PORT` | `9464` | `/metrics`와 `/healthz`를 받는 포트. chart는 `metrics.port`로 넣는다 |
| `DATABASE_URL` | 없음(필수) | 읽기 전용으로 여는 DB 주소. chart는 다른 역할과 같은 Secret key를 넣는다 |
| `config.limits`의 상한 | [설정 레퍼런스](/run-server/self-hosting/reference/configuration) | launch 대기열을 scheduler와 같은 비용·토큰 상한으로 센다. chart는 scheduler와 같은 값을 넣는다 |
| `LOG_LEVEL` | `info` | 읽기 실패를 남기는 로그 수준 |
