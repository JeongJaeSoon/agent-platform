<Callout type="warn">
아직 공식 릴리스가 없다. `v*` 릴리스가 없다. 릴리스가 생기면 그 GitHub Release에 세 이미지 digest, worker runtime, chart 버전을 담은 `release-manifest.json`이 붙는다([릴리스 manifest 읽기](#릴리스-manifest-읽기)). Helm chart는 `main` 머지마다 그 run의 이미지 digest를 담아 `oci://ghcr.io/jeongjaesoon/werft`로 게시된다([게시 chart로 설치](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/kubernetes-deployment.md#게시-chart로-설치)). 앱 이미지는 `main` 머지마다 `ghcr.io/jeongjaesoon/werft-<app>:main-<12>`로 게시되고, 쓸 때는 digest로 고정한다([이미지와 공급망](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/images-and-supply-chain.md#main-머지마다-게시되는-이미지)). 이 이미지를 받을 수 없으면 저장소를 checkout해 [세 이미지를 직접 빌드](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/test-ops.md#이미지를-직접-빌드한다)하고, checkout의 compose 파일이나 chart로 설치한다. 게시 이미지와 직접 빌드는 모두 x86_64와 arm64를 지원한다.
</Callout>

Werft 서버를 직접 설치해 팀이 함께 쓰는 방법이다. 혼자 시험해 볼 서버라면 [개발용 서버 실행](/run-server/dev-server)으로 충분하다. 설치·운영 문서의 본문은 저장소의 [`docs/operator/`](https://github.com/JeongJaeSoon/werft/tree/main/docs/operator)에 있고, 이 페이지는 어디서부터 읽을지 안내한다.

## 설치 방식 고르기

| 방식 | 실행 기반 | 문서 |
| --- | --- | --- |
| 단일 서버 | Docker Compose, 세션마다 worker 컨테이너 | [단일 서버 배포](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/server-deployment.md) |
| Kubernetes | 게시된 Helm chart, 세션마다 worker Pod | [Kubernetes 설치 (Helm chart)](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/kubernetes-deployment.md) |

어느 방식이든 서버는 API(웹 콘솔 포함), scheduler, reconciler, egress proxy, PostgreSQL, S3 호환 object store로 이뤄진다. 어느 방식에도 Git 서버는 없으므로 세션이 쓸 GitHub 저장소는 콘솔이나 설정 문서로 더한다. 단일 서버 설치에서 HA는 범위 밖이다.

## 릴리스 manifest 읽기

릴리스(`v*` 태그)마다 GitHub Release가 생기고 `release-manifest.json`이 붙는다. 저장소 checkout 없이 `gh`와 `jq`로 읽는다. 아래는 첫 릴리스가 생긴 뒤의 명령이다.

```bash
TAG=v0.1.0   # 읽을 릴리스 태그
gh release download "$TAG" -R JeongJaeSoon/werft -p release-manifest.json
jq -r '.images[] | "\(.image)@\(.digest)"' release-manifest.json   # 배포에 쓰는 세 digest
jq -c .workerRuntime release-manifest.json                          # worker runtime
jq -r '"\(.chart.ref) \(.chart.version)"' release-manifest.json     # chart 위치와 버전
```

digest는 두 아키텍처를 담는 index의 digest이고, 배포는 이 값으로 고정한다. 한번 붙은 manifest는 바뀌지 않는다. 필드와 확인 방법은 [릴리스 manifest 읽기](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/images-and-supply-chain.md#릴리스-manifest-읽기)를 본다.

## 단일 서버 설치 순서

[단일 서버 배포](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/server-deployment.md)의 순서를 요약하면 다음과 같다. 명령과 실패 복구는 그 문서와 거기서 링크하는 runbook을 따른다.

1. 호스트를 준비한다. Linux, Docker Engine 28 이상, Docker Compose 2.24.6 이상, NTP 동기화, 재부팅 뒤 Docker 자동 시작이 필요하다. Docker 데이터 루트는 XFS `prjquota`로 mount돼 있어야 한다. 아니면 scheduler의 quota 검사가 실패해 설치가 멈춘다. 저장소 checkout에서 스크립트를 돌리므로 호스트에 `git`, `jq`, `curl`, Bun 1.3.14도 있어야 한다.
2. 네트워크 경로를 정한다. API는 loopback에 두고 SSH tunnel로 접속하는 것이 기본이다. 내부 DNS로 내보낼 때는 TLS와 VPN 또는 IP allowlist를 갖춘 reverse proxy를 쓰고, 이벤트 스트림(SSE)을 위해 buffering을 끈다. PostgreSQL과 Docker socket은 밖에 열지 않는다.
3. 이 설치 전용 S3 bucket을 준비한다. 같은 호스트의 LocalStack은 재부팅 때 객체를 잃으므로 실서버의 저장소로 쓰지 않는다.
4. 게시된 세 이미지의 digest로 release를 정한다. 게시본을 쓸 수 없으면 checkout에서 빌드해 호스트가 받을 수 있는 registry에 올린다. 설정 문서도 준비하고, 비밀 값은 저장소 밖 env 파일에만 둔다.
5. 설치하고 `/readyz`를 확인한 뒤 웹 콘솔 `/bootstrap`에서 첫 owner와 workspace를 만든다.
6. 사용자마다 API key를 발급한다. key의 owner가 세션의 owner다.
7. 백업, 업그레이드와 롤백, 재부팅 뒤 재개를 미리 연습한다.

## Kubernetes 설치 순서

게시된 chart로 설치하면 저장소 checkout이 필요 없다. 패키지는 로그인 없이 받고, 버전은 정확히 적는다. `main` 머지의 버전은 `<Chart 버전>-main-<12>`이고 `<12>`는 commit SHA의 앞 12자다.

```bash
VERSION=0.1.0-main-<12>
helm show chart oci://ghcr.io/jeongjaesoon/werft --version "$VERSION"
helm show values oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" | sed -n '/^images:/,/^$/p'
```

세 이미지의 digest와 worker runtime은 패키지에 들어 있다. PostgreSQL, S3 bucket, namespace, Secret, 설치별 values 파일을 [Kubernetes 설치](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/kubernetes-deployment.md#게시-chart로-설치)대로 준비한 뒤 설치한다. 게시 이미지는 `linux/amd64`와 `linux/arm64`를 담으므로 노드가 자기 아키텍처를 받는다.

```bash
helm upgrade --install werft oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
  --namespace werft -f values-<installation>.yaml --timeout 10m
```

새 버전으로 올릴 때는 [게시 chart를 올리기](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/kubernetes-deployment.md#게시-chart를-올리기)를 따른다. worker 이미지가 바뀌면 직전 이미지를 함께 넘겨야 하고, `--reuse-values`는 새 chart의 이미지를 적용하지 않는다.

## 서버에 붙기

SDK와 HTTP API는 서버 주소와 API key로 서버에 붙는다. TypeScript SDK는 `baseUrl`(기본값은 환경 변수 `WERFT_BASE_URL`)과 `apiKey`(`WERFT_API_KEY`)를 받는다. 정해진 기본 서버는 없으므로 서버 주소는 꼭 넘긴다. SDK는 [SDK 설치](/getting-started/install)대로 npm에서 설치한다. 자세한 옵션은 [클라이언트 설정과 오류](/getting-started/client#클라이언트-옵션)에 있다.
