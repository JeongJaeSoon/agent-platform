Werft 서버를 직접 설치해 팀이 함께 쓰는 방법이다. 혼자 시험해 볼 서버라면 [개발용 서버 실행](/run-server/dev-server)으로 충분하다. 설치·운영 문서의 본문은 저장소의 [`docs/operator/`](https://github.com/JeongJaeSoon/agent-platform/tree/main/docs/operator)에 있고, 이 페이지는 어디서부터 읽을지 안내한다.

## 설치 방식 고르기

| 방식 | 실행 기반 | 문서 |
| --- | --- | --- |
| 단일 서버 | Docker Compose, 세션마다 worker 컨테이너 | [단일 서버 배포](https://github.com/JeongJaeSoon/agent-platform/blob/main/docs/operator/server-deployment.md) |
| Kubernetes | Helm chart, 세션마다 worker Pod | [Kubernetes 설치 (Helm chart)](https://github.com/JeongJaeSoon/agent-platform/blob/main/docs/operator/kubernetes-deployment.md) |

어느 방식이든 서버는 API(웹 콘솔 포함), scheduler, reconciler, egress proxy, PostgreSQL, S3 호환 object store로 이뤄진다. 단일 서버 설치에는 Git 서버(Gitea)도 들어간다. 단일 서버 설치에서 HA는 범위 밖이다.

## 단일 서버 설치 순서

[단일 서버 배포](https://github.com/JeongJaeSoon/agent-platform/blob/main/docs/operator/server-deployment.md)의 순서를 요약하면 다음과 같다. 명령과 실패 복구는 그 문서와 거기서 링크하는 runbook을 따른다.

1. 호스트를 준비한다. Docker Engine 28 이상, Docker Compose 2.24.6 이상, NTP 동기화, 재부팅 뒤 Docker 자동 시작이 필요하다.
2. 네트워크 경로를 정한다. API는 loopback에 두고 SSH tunnel로 접속하는 것이 기본이다. 내부 DNS로 내보낼 때는 TLS와 VPN 또는 IP allowlist를 갖춘 reverse proxy를 쓰고, 이벤트 스트림(SSE)을 위해 buffering을 끈다. PostgreSQL과 Docker socket은 밖에 열지 않는다.
3. 이 설치 전용 S3 bucket을 준비한다. 같은 호스트의 LocalStack은 재부팅 때 객체를 잃으므로 실서버의 저장소로 쓰지 않는다.
4. release(이미지 digest)와 설정 파일, 카탈로그를 정하고, 비밀 값은 저장소 밖 env 파일에만 둔다.
5. 설치하고 `/readyz`를 확인한 뒤 웹 콘솔 `/bootstrap`에서 첫 owner와 workspace를 만든다.
6. 사용자마다 API key를 발급한다. key의 owner가 세션의 owner다.
7. 백업, 업그레이드와 롤백, 재부팅 뒤 재개를 미리 연습한다.

## 서버에 붙기

SDK와 HTTP API는 서버 주소와 API key로 서버에 붙는다. TypeScript SDK는 `baseUrl`(기본값은 환경 변수 `WERFT_BASE_URL`)과 `apiKey`(`WERFT_API_KEY`)를 받는다. 정해진 기본 서버는 없으므로 서버 주소는 꼭 넘긴다. 자세한 옵션은 [클라이언트 설정과 오류](/getting-started/client#클라이언트-옵션)에 있다.
