title: "GitHub"
description: GitHub リポジトリでセッションを動かし、承認した結果をブランチへ push し、そのブランチで PR を開く
---

GitHub との間でやることは三つある。セッション開始時にリポジトリを clone する。人が承認した commit を `agent/<session-id>` ブランチへ push する。そのブランチで PR を開き、コメントを付ける。clone は worker が API のプロキシ経由で行い、push と PR はプラットフォーム(API)が直接行う。どちらの場合も、リポジトリの認証情報は worker に渡らない。

## 運用者がやること

リポジトリは運用者がカタログ(`config/repositories.yaml`)に登録する。認証情報は次のどちらかである。GitHub App は owner か admin がコンソールの **設定 → ワークスペース → GitHub** で App ID と private key(PEM ファイル)を入れて登録し、同じ画面のリンクからリポジトリにインストールする。画面にはインストールの一覧と、カタログのリポジトリごとに App がインストールされているかが出る。この App を使うリポジトリは、カタログに `auth: { kind: github_app }` だけを書く。鍵は暗号化して保存し、画面にも API の応答にも二度と出ない。ワークスペースの App は一つである。

| 方式 | 必要な権限 |
| --- | --- |
| GitHub App(デフォルト) | Repository permissions: Contents Read and write, Pull requests Read and write |
| fine-grained PAT | 同じ二つの権限 |

`Workflows` 権限は与えない。push される commit はエージェントが書いたものなので、この権限があるとエージェントが書き換えた `.github/workflows/` のファイルも push され、CI で実行される。デフォルトブランチはリポジトリの ruleset でも保護しておく。設定方法は運用ドキュメントにある。

## ユーザーがやること

1. そのリポジトリの `repository_id` でセッションを作る([開始](/sessions/start))。
2. 結果を[リクエスト](/approvals/request)し、[承認](/approvals/approve)する。リクエストが `pushed` になると、リポジトリに `agent/<session-id>` ブランチができる。
3. PR を開く。`sessions:approve` が必要である。

```sh
curl -sS "$API/v1/sessions/$SID/push-requests/$PUSH_ID/pull-request" \
  -H "Authorization: Bearer $KEY" \
  -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{"title": "Add release notes", "body": "Written by the agent, approved by me."}' \
  | jq '{number: .pull_request.number, url: .pull_request.url, created}'
```

head は `agent/<session-id>`、base はカタログに書いたブランチである。リクエスト一つにつき PR は一つである。そのブランチの PR がすでに開いている場合は、新しく開かずにその PR を返す(`created: false`)。プラットフォームは PR を承認・マージせず、レビュアーやラベルも決めない。

4. コメントを付ける。同じ `marker`(デフォルトは `status`)のコメントがすでにある場合は、新しく付けずにそのコメントを書き換える。

```sh
curl -sS "$API/v1/sessions/$SID/push-requests/$PUSH_ID/pull-request/comments" \
  -H "Authorization: Bearer $KEY" \
  -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{"body": "Tests pass on the agent branch."}'
```

タイトル・本文・コメントは GitHub に送る前に整形される。秘密情報に見える行は伏せ、`@メンション` や `Closes #N` のような close キーワードは、通知や自動クローズが起きないように置き換える。

PR 本文の末尾には、プラットフォームが書く末尾ブロックが付く。セッション id とコミット、セッションのアドレス、エージェントとリリース、誰がどの経路で開始したかが入る。そのブランチにもう一度 push して PR をもう一度要求すると、末尾ブロックだけが新しいコミットに変わり、その上に人が書いた本文はそのまま残る。

## 自分の GitHub アカウントを連携する

コミットの作成者は常に GitHub App だ。自分の GitHub アカウントを連携しておくと、自分が開始したセッションのコミットに `Co-authored-by:` トレーラーで自分の名前も入り、GitHub でそのコミットが自分の貢献としても表示される。

1. owner か admin が **設定 → ワークスペース → GitHub** の「ユーザーアカウント連携」で、コールバック URL を App の Callback URL に入れ、App で作った client secret を入力する。この準備がないと連携ボタンは無効になっている。
2. **設定 → 連携アカウント** の GitHub の行で「連携」を押し、GitHub の同意画面で承認する。プラットフォームは GitHub アカウントの id と login だけを読み、GitHub のトークンは保管しない。
3. 連携した行に、コミットに入る行(`Co-authored-by: <login> <<id>+<login>@users.noreply.github.com>`)が表示される。連携を解除すると、それ以降に開始するセッションからは入らない。

Web コンソール、個人 API キー、Slack から開始したセッションは、開始した人の連携に従う。エージェントキーや運用者キーで開始したセッションには開始した人がいないため、共同作成者は入らない。どちらの場合も、運用者がコンソールのアドレスを設定した環境なら、コミットにはセッションのアドレスを入れた `Agent-Session:` トレーラーが付く。セッション詳細の成果物タブの上で、そのセッションがどちらかを確認できる。

GitHub アカウント1つは1人にだけ連携される。他の人がすでに連携したアカウントは連携できない。

## ローカルスタックでは

ローカルの `sample-app` は GitHub ではなくスタック内の Gitea リポジトリで、push 用の認証情報がない。そのため承認した push は `no_push_credential` で `failed` になり、PR のリクエストは push されていないリクエストなので 409 になる。[承認](/approvals/approve)で `failed` として終わったリクエストで確認する。

```bash
FAILED=$(curl -sS "$API/v1/sessions/$SID/push-requests" -H "Authorization: Bearer $KEY" \
  | jq -r '[.items[] | select(.state == "failed")][0].id')
curl -sS "$API/v1/sessions/$SID/push-requests/$FAILED/pull-request" \
  -H "Authorization: Bearer $KEY" \
  -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{"title": "Add release notes"}' | jq '{code: .error.code}'
```

```text
{
  "code": "PUSH_NOT_PUSHED"
}
```

| レスポンス | 意味 |
| --- | --- |
| 409 `PUSH_NOT_PUSHED` | リクエストがまだ `pushed` ではない |
| 409 `PULL_REQUEST_MISSING` | コメントの前に PR を先に開く必要がある |
| 409 `CATALOG_MISMATCH` | リクエストの後に運用者がリポジトリ設定を変更した |
| 403 `FORBIDDEN` | `sessions:approve` がない、セッションを見ているだけで承認する人ではない、または GitHub ではないリポジトリである(`no_forge`) |
| 503 `BACKEND_UNAVAILABLE` | GitHub 呼び出しがリトライの後も失敗した |
