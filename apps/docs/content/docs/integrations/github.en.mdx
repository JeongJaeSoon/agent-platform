---
title: "GitHub"
description: Run sessions on a GitHub repository, push approved results to a branch, and open a PR from that branch
---

Werft does three things with GitHub. It clones the repository when a session starts. It pushes the commits a person approved to the `agent/<session-id>` branch. It opens a PR from that branch and adds comments to it. The worker clones through the API's proxy, while the platform (API) pushes and handles the PR itself. In either case, the repository credentials never reach the worker.

## What the operator does

The credential is one of two kinds. The default is a GitHub App, which an owner or admin handles in the console under **Settings → Workspace → GitHub connection**.

- **Add App**: create a new App on GitHub (the console receives and stores its App ID and key), or connect an existing one with its App ID and private key (the PEM file). A workspace can hold several author Apps and reviewer Apps; a role badge tells them apart in the list. The key is stored encrypted and never shown again on the screen or in an API response. To change a key, use **Register a new key** in the App row's ⋯ menu.
- **Add organization**: install an App on an organization or a personal account. The installation table shows, for each account, its type, repository scope, App, who connected it and its status; **Manage on GitHub** in the row's ⋯ menu opens that installation's settings.
- **Manage repositories**: see the repositories agents picked, by installation, and change their default branch and the App that handles each. A repository appears once it is picked in an agent's GitHub tab; there is nothing to register.
- **Features agents may use**: the workspace's ceiling. A switch saves at once. When an App lacks a permission a feature that is on needs, that App's row says which and offers **Add permissions on GitHub**. Once added, GitHub asks the owner of each account it is installed on to approve; no reinstall is needed.

| Method | Required permissions |
| --- | --- |
| GitHub App (default) | Repository permissions: Contents Read and write, Pull requests Read and write |
| fine-grained PAT | The same two permissions |

Add the `Workflows` permission to the App only when the "Change workflow files" feature is on. The commits that get pushed are written by the agent, so with this permission a `.github/workflows/` file the agent edited would also be pushed and run in CI. Also protect the default branch with a repository ruleset. The operations docs describe how to set this up.

## What the user does

1. Create a session with that repository's `repository_id` ([Start](/sessions/start)).
2. [Request](/approvals/request) and [approve](/approvals/approve) the result. When the request becomes `pushed`, the `agent/<session-id>` branch exists in the repository.
3. Open the PR. This needs `sessions:approve`. The examples below use the `sessionId` and `push` from [Request](/approvals/request) and [Approve](/approvals/approve) (`SID` and `PUSH_ID` in the HTTP API).

<Tabs groupId="client" persist items={["SDK", "HTTP API"]}>
<Tab>

```ts
const opened = await werft.sessions.pushRequests.openPullRequest(sessionId, push.id, {
  title: "Add release notes",
  body: "Written by the agent, approved by me.",
});
console.log(opened.pull_request.number, opened.pull_request.url, opened.created);
```

</Tab>
<Tab>

```bash
curl -sS "$API/v1/sessions/$SID/push-requests/$PUSH_ID/pull-request" \
  -H "Authorization: Bearer $KEY" \
  -H 'Content-Type: application/json' \
  -d '{"title": "Add release notes", "body": "Written by the agent, approved by me."}' \
  | jq '{number: .pull_request.number, url: .pull_request.url, created}'
```

Reference: [`POST …/push-requests/{push_request_id}/pull-request`](/reference/http-api/push-requests/openPullRequest)

</Tab>
</Tabs>

This call has no `Idempotency-Key`, so the SDK does not resend it when it gets no response ([Retries and Idempotency-Key](/getting-started/client#retries-and-idempotency-key)). The head is `agent/<session-id>` and the base is the branch listed in the catalog. Each request gets one PR. If a PR from that branch is already open, no new one is opened and that PR is returned (`created: false`). The platform does not approve or merge PRs, and it does not choose reviewers or labels.

4. Add a comment. If a comment with the same `marker` (default `status`) already exists, it is edited instead of adding a new one.

<Tab>

```ts
await werft.sessions.pushRequests.commentPullRequest(sessionId, push.id, {
  body: "Tests pass on the agent branch.",
});
```

</Tab>
<Tab>

```bash
curl -sS "$API/v1/sessions/$SID/push-requests/$PUSH_ID/pull-request/comments" \
  -H "Authorization: Bearer $KEY" \
  -H 'Content-Type: application/json' \
  -d '{"body": "Tests pass on the agent branch."}'
```

Reference: [`POST …/pull-request/comments`](/reference/http-api/push-requests/commentPullRequest)

Titles, bodies, and comments are sanitized before they are sent to GitHub. Lines that look like secrets are masked, and `@mentions` and closing keywords such as `Closes #N` are rewritten so they trigger no notification or automatic close.

The platform adds a tail to the end of the PR body: the session id and commit, the session's address, the agent and release, and who started the session and how. Push to the branch again and ask for the PR again, and only the tail changes to the new commit; the text a person wrote above it stays.

The agent in a session does the same work with built-in MCP tools: `open_pull_request` opens the PR, `update_pull_request` changes its title and body, and `comment_pull_request` comments on it. `close_pull_request` and `reopen_pull_request` close a PR that a push request of this session opened, without merging it, and reopen it. No person approves these. The agent cannot close a PR from another session, or one in a repository it is not allowed. Closing a closed PR, or reopening an open one, changes nothing and answers `changed: false`. A merged PR is refused with `PULL_REQUEST_MERGED`. Closing does not delete the `agent/<session-id>` branch, so the PR can be reopened.

## Attaching a repository mid-session

While it works, the agent attaches another repository with the built-in MCP tool `attach_repository({ repository_id })`. It can attach only repositories listed in the agent release's GitHub settings (`github.repositories`) that the profile allows. No person approves it; writing to that repository still goes through push request approval, and a person approves pushes to an attached repository even for an agent with push approval off. The agent sees which repositories it can attach with `list_repositories` (its own `primary`, attached ones `attached`, `pending` or `failed`, and attachable ones `available`). A session keeps the release it started with, so a repository added only to a later active release is listed apart as `allowed_in_newer_release`, and `attach_repository` refuses it with `allowed_in_newer_release` instead of `repository_not_allowed`. It does not need to be allowed again: a new session (in Slack, a new thread) can attach it.

A session created without `attached_repository_ids` starts with no repository attached besides its own. Put the repositories it needs from the start in that list; the agent attaches the rest when it needs them.

- The attached repository becomes a git remote named `repository_id` in the workspace, with its default branch fetched to `<repository_id>/<branch>`. The agent never sees a token.
- Attaching the same repository again changes nothing and succeeds. While the fetch is running the tool answers `pending`; call it again to read the outcome.
- The fetch is limited to 300 seconds and 2 GiB. Past either, the attachment fails with the reason in `failure` (`fetch_timeout`, `fetch_too_large`).
- Each attachment leaves an `attach_repository` [receipt](/approvals/receipt): who asked and from which attempt, the repository, the release, the commit fetched, and the refusal reason (`repository_not_allowed` or `allowed_in_newer_release`).
- When the session restarts on another worker (a restore), the attached repositories' remotes are added again. A CLAUDE.md in an attached repository is not read as instructions.

## Link your GitHub account

The GitHub App's bot account (`<App slug>[bot]`) is always the commit author. Link your GitHub account and the commits of sessions you start also carry your name in a `Co-authored-by:` trailer, so GitHub shows the commit as your contribution too.

1. On the "Member GitHub accounts" line under **Settings → Workspace → GitHub connection**, an owner or admin picks the author App to link with (when there are several), puts the callback URL from the ⋯ menu in that App's Callback URL, and enters a client secret made in that App. Until then the link button is off.
2. In the GitHub row of **Settings → Linked accounts**, choose "Link" and approve on GitHub's consent screen. The platform reads only the GitHub account's id and login and keeps no GitHub token.
3. The linked row shows the line commits get (`Co-authored-by: <login> <<id>+<login>@users.noreply.github.com>`). After you unlink, sessions started from then on leave it out.

Sessions started from the web console, a personal API key, or Slack follow the starter's link. A session started with an agent key or an operator key has no person who started it, so no co-author is added. Either way, commits carry an `Agent-Session:` trailer: the session's address where the operator has set the console's address, else the session's id. The line above the Outputs tab in session details shows which case a session is.

A GitHub account links to one person only. Linking an account someone else already linked is refused.

## On the local stack

The local `sample-app` is a repository on the stack's read-only Git server, not GitHub, and it has no push credential. So an approved push ends as `failed` with `no_push_credential`, and a PR request returns 409 because the request was never pushed. Check this with a request that ended as `failed` in [Approve](/approvals/approve).

<Tabs groupId="client" persist items={["SDK", "HTTP API"]}>
<Tab>

```ts
import { isApiError } from "@werft-ai/sdk";

const requests = await werft.sessions.pushRequests.list(sessionId);
const failed = requests.find((request) => request.state === "failed");
if (failed) {
  try {
    await werft.sessions.pushRequests.openPullRequest(sessionId, failed.id, {
      title: "Add release notes",
    });
  } catch (error) {
    if (!isApiError(error)) throw error;
    console.log(error.status, error.code);
  }
}
```

```text
409 PUSH_NOT_PUSHED
```

</Tab>
<Tab>

```bash
FAILED=$(curl -sS "$API/v1/sessions/$SID/push-requests" -H "Authorization: Bearer $KEY" \
  | jq -r '[.items[] | select(.state == "failed")][0].id')
curl -sS "$API/v1/sessions/$SID/push-requests/$FAILED/pull-request" \
  -H "Authorization: Bearer $KEY" \
  -H 'Content-Type: application/json' \
  -d '{"title": "Add release notes"}' | jq '{code: .error.code}'
```

```text
{
  "code": "PUSH_NOT_PUSHED"
}
```

Reference: [`GET /v1/sessions/{id}/push-requests`](/reference/http-api/push-requests/listPushRequests), [`POST …/pull-request`](/reference/http-api/push-requests/openPullRequest)

</Tab>
</Tabs>

| Response | Meaning |
| --- | --- |
| 409 `PUSH_NOT_PUSHED` | The request is not `pushed` yet |
| 409 `PULL_REQUEST_MISSING` | Open the PR before commenting |
| 409 `CATALOG_MISMATCH` | The operator changed the repository settings after the request |
| 403 `FORBIDDEN` | `sessions:approve` is missing, the caller only sees the session and is not one who approves, or the repository is not on GitHub (`no_forge`) |
| 503 `BACKEND_UNAVAILABLE` | The GitHub call still failed after retries |
