GitHub와 하는 일은 셋이다. 세션이 시작할 때 저장소를 clone한다. 사람이 승인한 commit을 `agent/<session-id>` 브랜치로 push한다. 그 브랜치로 PR을 열고 코멘트를 단다. clone은 worker가 API의 프록시를 거쳐 하고, push와 PR은 플랫폼(API)이 직접 한다. 어느 쪽이든 저장소 자격 증명은 worker에 가지 않는다.

## 운영자가 할 일

저장소는 운영자가 카탈로그(`config/repositories.yaml`)에 등록한다. 자격 증명은 둘 중 하나다. GitHub App은 owner나 admin이 콘솔의 **설정 → 워크스페이스 → GitHub**에서 App ID와 private key(PEM 파일)로 등록하고, 같은 화면의 링크로 저장소에 설치한다. 화면은 설치 목록과 카탈로그 저장소마다 App이 설치되어 있는지 보여 준다. 그 App을 쓰는 저장소는 카탈로그에 `auth: { kind: github_app }`만 적는다. 키는 암호화해 저장하고 화면과 API 응답에 다시 나오지 않는다. 워크스페이스에 App은 하나다.

| 방식 | 필요한 권한 |
| --- | --- |
| GitHub App(기본) | Repository permissions: Contents Read and write, Pull requests Read and write |
| fine-grained PAT | 같은 두 권한 |

`Workflows` 권한은 주지 않는다. push되는 commit은 에이전트가 쓴 것이라, 이 권한이 있으면 에이전트가 고친 `.github/workflows/` 파일도 push되고 CI에서 실행된다. 기본 브랜치는 저장소 ruleset으로도 막아 둔다. 설정 방법은 운영 문서에 있다.

## 사용자가 할 일

1. 그 저장소의 `repository_id`로 세션을 만든다([시작](/sessions/start)).
2. 결과를 [요청](/approvals/request)하고 [승인](/approvals/approve)한다. 요청이 `pushed`가 되면 저장소에 `agent/<session-id>` 브랜치가 생긴다.
3. PR을 연다. `sessions:approve`가 필요하다.

```sh
curl -sS "$API/v1/sessions/$SID/push-requests/$PUSH_ID/pull-request" \
  -H "Authorization: Bearer $KEY" \
  -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{"title": "Add release notes", "body": "Written by the agent, approved by me."}' \
  | jq '{number: .pull_request.number, url: .pull_request.url, created}'
```

head는 `agent/<session-id>`, base는 카탈로그에 적은 브랜치다. 요청 하나에 PR은 하나다. 그 브랜치의 PR이 이미 열려 있으면 새로 열지 않고 그 PR을 돌려준다(`created: false`). 플랫폼은 PR을 승인·머지하지 않고, 리뷰어나 라벨도 정하지 않는다.

4. 코멘트를 단다. 같은 `marker`(기본 `status`)의 코멘트가 이미 있으면 새로 달지 않고 그 코멘트를 고친다.

```sh
curl -sS "$API/v1/sessions/$SID/push-requests/$PUSH_ID/pull-request/comments" \
  -H "Authorization: Bearer $KEY" \
  -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{"body": "Tests pass on the agent branch."}'
```

제목·본문·코멘트는 GitHub에 보내기 전에 정리된다. 비밀처럼 보이는 줄은 가리고, `@멘션`과 `Closes #N` 같은 닫기 키워드는 알림이나 자동 닫기가 일어나지 않게 바꾼다.

PR 본문 끝에는 플랫폼이 쓰는 꼬리가 붙는다. 세션 id와 commit, 세션 주소, 에이전트와 release, 누가 어떤 경로로 시작했는지가 들어간다. 그 브랜치에 다시 push하고 PR을 다시 요청하면 꼬리만 새 commit으로 바뀌고, 그 위에 사람이 쓴 본문은 그대로 남는다.

## 내 GitHub 계정 연결

commit 작성자는 늘 GitHub App이다. 내 GitHub 계정을 연결해 두면 내가 시작한 세션의 commit에 `Co-authored-by:` 트레일러로 내 이름이 함께 들어가, GitHub에서 그 commit이 내 기여로도 보인다.

1. owner나 admin이 **설정 → 워크스페이스 → GitHub**의 "사용자 계정 연결"에서 콜백 URL을 App의 Callback URL에 넣고, App에서 만든 client secret을 입력한다. 이 준비가 없으면 연결 버튼이 꺼져 있다.
2. **설정 → 연동 계정**의 GitHub 줄에서 "연결"을 누르고 GitHub의 동의 화면에서 승인한다. 플랫폼은 GitHub 계정의 id와 login만 읽고 GitHub token은 보관하지 않는다.
3. 연결된 줄에 commit에 들어갈 줄(`Co-authored-by: <login> <<id>+<login>@users.noreply.github.com>`)이 보인다. 해제하면 그 뒤에 시작하는 세션부터 들어가지 않는다.

웹 콘솔, 개인 API key, Slack으로 시작한 세션은 시작한 사람의 연결을 따른다. 에이전트 key나 운영자 key로 시작한 세션은 시작한 사람이 없어 공동 작성자를 넣지 않는다. 어느 경우든 운영자가 콘솔 주소를 설정한 설치라면 commit에 세션 주소를 담은 `Agent-Session:` 트레일러가 붙는다. 세션 상세의 결과물 탭 위에서 그 세션이 어느 쪽인지 볼 수 있다.

GitHub 계정 하나는 한 사람에게만 연결된다. 다른 사람이 이미 연결한 계정이면 연결이 거절된다.

## 로컬 스택에서

로컬 `sample-app`은 GitHub가 아니라 스택 안의 Gitea 저장소이고 push 자격 증명이 없다. 그래서 승인한 push는 `no_push_credential`로 `failed`가 되고, PR 요청은 push되지 않은 요청이라 409다. [승인](/approvals/approve)에서 `failed`로 끝난 요청으로 확인한다.

```bash
FAILED=$(curl -sS "$API/v1/sessions/$SID/push-requests" -H "Authorization: Bearer $KEY" \
  | jq -r '[.items[] | select(.state == "failed")][0].id')
curl -sS "$API/v1/sessions/$SID/push-requests/$FAILED/pull-request" \
  -H "Authorization: Bearer $KEY" \
  -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{"title": "Add release notes"}' | jq '{code: .error.code}'
```

```text
{
  "code": "PUSH_NOT_PUSHED"
}
```

| 응답 | 뜻 |
| --- | --- |
| 409 `PUSH_NOT_PUSHED` | 요청이 아직 `pushed`가 아니다 |
| 409 `PULL_REQUEST_MISSING` | 코멘트 전에 PR을 먼저 열어야 한다 |
| 409 `CATALOG_MISMATCH` | 요청 뒤에 운영자가 저장소 설정을 바꿨다 |
| 403 `FORBIDDEN` | `sessions:approve`가 없거나, 세션을 보기만 하고 승인할 사람이 아니거나, GitHub가 아닌 저장소다(`no_forge`) |
| 503 `BACKEND_UNAVAILABLE` | GitHub 호출이 재시도 뒤에도 실패했다 |
