エージェントはワークスペース内の名前付きの定義である。定義はカード (ロール、指示文、モデル、ツール) で、カードを修正するたびに新しいバージョンが積み重なる。バージョン 1 つを実行プロファイルと紐付けたものがリリースであり、エージェントが指しているリリースが有効なリリースである。セッションを作成するときにリリースを指定すると、そのセッションはそのエージェントのものになる。

<Callout type="warn">
現在のセッションは `profile_id` の実行プロファイルで動く。リリースの指示文とツール一覧はセッションに記録されるだけで、モデルにはまだ渡されない。詳しくは [指示文とロール](/agents/instructions-and-roles) と [権限](/agents/permissions) を参照。
</Callout>

## Web コンソールで

ローカルスタックの Web コンソールは `http://127.0.0.1:3000/` である。

1. 初回のみ、`/bootstrap` で最初の owner とワークスペースを作成する。bootstrap token は API が最初に起動したときにログへ一度だけ出力される: `docker compose logs api | grep BOOTSTRAP_TOKEN=`
2. ログイン後、左のサイドバーの「エージェント」を開き、右上の「新規エージェント」を押す。「新規エージェント」画面が 5 つのステップ(名前 → 役割 → リリース → 有効化 → チャンネル接続)で開く。
3. 「名前」ステップで名前を入力する。識別子 (slug) は名前から自動で入力され、変更もできる。「次へ」を押す。
4. 「役割」ステップで役割、指示、回答言語、モデル、使用できるツール、禁止するツールを入力し、「下書きを保存して次へ」を押す。エージェントが下書きとして保存され、バージョン 1 が作成される。
5. 「リリース」ステップで実行プロファイルを選び、「リリースを作成」を押す。カードのモデルがプロファイルで実行できるモデルのひとつでなければリリースは作成できない。
6. 「有効化」ステップで「エージェントを有効化」を押す。以降、新しいセッションはこのリリースで開始する。「あとで設定」を押すと、エージェントは下書きのまま詳細画面に移る。

owner・admin・member のいずれも、エージェントを作成できる。作成した人がそのエージェントの管理者になる。

## API で

エージェント API は、Web コンソールと同じ cookie ログインでのみ呼び出せる。API キーで呼び出すと 403 になる。

### ログイン

```sh
read -rs AP_PASSWORD
AP_COOKIE=$(curl -sS -o /dev/null -D - "$API/v1/auth/login" \
  -H 'Content-Type: application/json' -H 'X-Requested-With: agent-platform-web' \
  -d "$(jq -nc --arg e 'owner@example.test' --arg p "$AP_PASSWORD" '{email: $e, password: $p}')" \
  | sed -n 's/^[Ss]et-[Cc]ookie: \(__Host-ap_session=[^;]*\).*/\1/p')
```

ログイン cookie は名前が `__Host-` で始まり `Secure` なので、http では curl の cookie jar に保存されない。そのため応答ヘッダーから取り出し、`Cookie` ヘッダーで送る。状態を変更するリクエストには `X-Requested-With: agent-platform-web` が必要である。

```bash
WEB=(-H 'Content-Type: application/json' -H 'X-Requested-With: agent-platform-web' -H "Cookie: $AP_COOKIE")
curl -sS "$API/v1/auth/me" "${WEB[@]}" | jq '{role: .principal.role, workspace: .workspace.slug}'
```

### 作成

```bash
agent=$(curl -sS "$API/v1/agents" "${WEB[@]}" -d '{
  "slug": "research-bot",
  "name": "Research Bot",
  "card": {
    "role": "저장소를 읽고 질문에 답한다",
    "instructions": "Answer briefly. Cite file paths.",
    "model": "claude-sonnet-5",
    "capabilities": { "tools": ["Read", "Grep", "Glob"], "mcp": null }
  }
}')
AID=$(echo "$agent" | jq -r .agent.id)
VID=$(echo "$agent" | jq -r '.versions[0].id')
echo "$agent" | jq '{slug: .agent.slug, version: .versions[0].version_no, active_release_id: .agent.active_release_id}'
```

```text
{
  "slug": "research-bot",
  "version": 1,
  "active_release_id": null
}
```

同じワークスペースに同じ slug があると 409 `ALREADY_EXISTS` になる。作成しただけでは何も有効化されない。

### リリースの作成

リリースはバージョン 1 つと実行プロファイル 1 つを紐付ける。カードの `model` がプロファイルで実行できるモデル (`model` と `models`) にない場合や、カードのツールがプロファイルにない場合は 422 になる。リリースで作成したセッションは、`model` を省略するとカードのモデルで動く。

```bash
release=$(curl -sS "$API/v1/agents/$AID/releases" "${WEB[@]}" \
  -d "$(jq -nc --arg v "$VID" '{version_id: $v, runtime_profile_id: "claude-coding-local"}')")
REL=$(echo "$release" | jq -r .release.id)
echo "$release" | jq '{id: .release.id, created, tools: .release.effective_tools.tools}'
```

```text
{
  "id": "sha256:…",
  "created": true,
  "tools": [
    "Read",
    "Glob",
    "Grep"
  ]
}
```

リリース id はカードとプロファイルの内容のハッシュである。同じ内容で再度作成すると、同じリリースが `created: false` で返る。

リクエストに `note`(前後の空白を除いて 1–200 文字)を入れると、リリースにメモとして残る。メモは id に含まれないため、同じ内容で再度作成しても最初のメモのままである。空、または 200 文字を超えると 400 になる。

人がリリースを呼ぶ名前は `label` である。作成した時刻をソウル時間で秒まで書いた `2026-10-30_14:30:28` の形で、同じエージェントで同じ秒にリリースが複数できると、2 つ目から `-2`、`-3` が付く。コンソールのリリース履歴、エージェントの見出しタグ、セッション一覧はこの名前を使う。識別子は引き続きリリース id である。カードの `version_no` はカードを変えたときだけ上がるため、同じカードを別のプロファイルでリリースしてもバージョンは同じである。

### 有効化

`expected_revision` はエージェントの現在の `activation_revision` である。初回は `-1` である。他の場所で先に変更されていた場合は 409 `REVISION_CONFLICT` になる。

```bash
curl -sS "$API/v1/agents/$AID/activate" "${WEB[@]}" \
  -d "$(jq -nc --arg r "$REL" '{release_id: $r, expected_revision: -1}')" \
  | jq '{activation_revision, previous_release_id}'
```

```text
{
  "activation_revision": 0,
  "previous_release_id": null
}
```

リリースの `activated_at` はそのリリースが最後に有効化された時刻、`deactivated_at` は次の有効化がその座を引き継いだ時刻である。いま有効なリリースの `deactivated_at` と、一度も有効化されていないリリースの両方の値は `null` である。どちらも有効化の記録から読むため、これらのフィールドができる前に有効化したリリースにも値がある。

### 一覧と件数

```bash
curl -sS "$API/v1/agents?limit=50" "${WEB[@]}" | jq -c '{n: (.items | length), next_cursor}'
curl -sS "$API/v1/agents/counts" "${WEB[@]}" | jq -c
```

```text
{"n":1,"next_cursor":null}
{"counts":{"all":1,"administered":1}}
```

一覧は古いエージェントから `limit` 件ずつ(既定 50、最大 100)返る。レスポンスの `next_cursor` を `cursor` として送ると次のページになり、最後のページでは `null` である。`cursor` なしで呼ぶと最初のページだけが返る。`GET /v1/agents/counts` は、一覧を最後まで読んだときの件数(`all`)と、そのうち自分が直接またはチームで管理している件数(`administered`)を返す。どちらも一覧と同じ権限が必要で、API キーは拒否される。

## セッションに紐付ける

`POST /v1/sessions` に `agent_release_id` を指定する。`profile_id` はそのリリースのプロファイルでなければならない (そうでなければ 409 `RELEASE_PROFILE_MISMATCH`)。キーはそのエージェントのエージェントキーを使う。Web ログインの cookie で `POST /v1/api-keys` に `kind: "agent"` と `agent_id` を渡して発行する([API キー](/api-keys))。秘密値は変数にだけ入れる。

```bash
AGENT_KEY=$(curl -sS "$API/v1/api-keys" "${WEB[@]}" \
  -d "$(jq -nc --arg a "$AID" '{kind: "agent", agent_id: $a, name: "research-bot", scopes: ["sessions:read", "sessions:write"]}')" \
  | jq -r .secret)
curl -sS "$API/v1/sessions" \
  -H "Authorization: Bearer $AGENT_KEY" \
  -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $(uuidgen)" \
  -d "$(jq -nc --arg r "$REL" --arg m 'GATE-SPEC {"id":"agent","steps":[],"final":"hello from research-bot"}' \
    '{profile_id: "claude-coding-local", repository_id: "sample-app", agent_release_id: $r, message: $m}')" \
  | jq '{status, turn_id}'
```

```text
{
  "status": "queued",
  "turn_id": "1"
}
```

ワークスペースに属さないキー (例: `scripts/local.sh key quickstart …`) で送ると、リリースが見つからず 404 になる。
