エージェントの権限は 3 つの層からなる。実行プロファイルが定めるツールと権限モード、人が答える権限リクエスト、そしてエージェントを管理し認証情報の名前を紐付ける人である。

## ツール: 実行プロファイルが決める

セッションは、実行プロファイルの `tools` に含まれるツールだけを使う。それ以外のツールは権限リクエストなしで拒否され、モデルはエラーの `tool_result` を受け取る。次のスクリプトは、ローカルプロファイルにない `WebFetch` を呼び出す。

```bash
created=$(curl -sS "$API/v1/sessions" \
  -H "Authorization: Bearer $KEY" \
  -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $(uuidgen)" \
  -d "$(jq -nc --arg m 'GATE-SPEC {"id":"outside","steps":[{"tool":"WebFetch","input":{"url":"https://example.com","prompt":"summarize"}}],"final":"done"}' \
    '{profile_id: "claude-coding-local", repository_id: "sample-app", message: $m}')")
SID=$(echo "$created" | jq -r .session_id)
until [ "$(curl -sS "$API/v1/sessions/$SID/turns/1" -H "Authorization: Bearer $KEY" | jq -r .status)" = completed ]; do
  sleep 2
done
curl -sSN --max-time 5 "$API/v1/sessions/$SID/events" -H "Authorization: Bearer $KEY" \
  | awk '/^event: tool_result/ { getline; sub(/^data: /, ""); print }' \
  | jq -c '.data | {is_error, content}' || true
```

```text
curl: (28) Operation timed out after 5006 milliseconds with 4482 bytes received
{"is_error":true,"content":"<tool_use_error>Error: No such tool available: WebFetch. WebFetch is disabled for this session, in subagents as well as here.</tool_use_error>"}
```

`curl: (28)` は `--max-time` がストリームを切断したものである。

リリースから作ったセッションはさらに狭く、そのリリースに固定されたツールだけを使う。カードの `capabilities.tools` (`null` ならリリース作成時のプロファイルのツールすべて) から `forbidden` を除いた一覧で、リリースのレスポンスの `effective_tools.tools` がその一覧である。カードに `Read` だけを書くと、セッションは `Read` だけを使い、ほかの組み込みツールは上と同じく拒否される。リリースなしで作ったセッションは、プロファイルのツールをすべて使う。

<Callout type="warn">
以前は、カードの `tools`・`forbidden` はリリースに固定されるだけで実行には適用されなかった。現在は、それ以前に作ったリリースですでに進行中のセッションも、リリースのツールに絞られる。セッションの実行環境が再び起動したとき (最後のターンが終わってから入力なしで 30 分経ち、実行環境が停止したあとの次のメッセージ、または一時停止からの再開) に適用される。カードの `tool_policy` に書いた組み込みツールの値 (`allow`・`ask`・`deny`) はリリースに固定されるが、まだ実行には適用されない。実行前に確認するかどうかは、下の権限モードが決める。
</Callout>

## 権限モード

プロファイルの `permission_mode` が、ツールを実行する前に人へ尋ねるかどうかを決める。セッション詳細の `runtime.permission_mode` に表示される。

| モード | 動作 |
| --- | --- |
| `default` | ファイルを変更するツール (Write、Edit、ファイルを書く Bash コマンドなど) は、実行前に権限リクエストを作成する。読み取りコマンドは尋ねない。ローカルプロファイルのモードである |
| `acceptEdits`, `dontAsk`, `plan` | Claude Code の同名のモードで動く |
| `auto` | 人の代わりにモデルの分類器が呼び出しごとに許可・拒否を決める。分類器を使えないときは拒否する。インストール設定なしで使える。プラットフォームは分類器に既定のルールを一つ加える: セッション内の commit、組み込み `github` ツールによるセッション自身のブランチ(`agent/<session-id>`)への push 依頼、その PR を開く・タイトルと本文を直す・コメントする、リポジトリ一覧を見る・付けることは尋ねない。既定ブランチへの push、force push、マージ・承認、ほかのリポジトリへの push はこのルールに入らない |
| `bypassPermissions` | 判定なしにすべての呼び出しを実行する。カタログにこのモードのプロファイルがある場合、API は `PLATFORM_ALLOW_UNATTENDED_PERMISSIONS=true` なしでは起動せず、ワークスペースプロファイルでは owner・admin だけが選べる |

モードはカタログにのみ存在し、セッションのリクエストで変更することはできない。

## 承認: 人だけが行う

権限リクエストと質問に答えるには `sessions:approve` scope が必要である。worker 内のエージェントが持つ認証情報は `/v1` で 401 になるため、自分で承認することはできない。エージェントキーも `sessions:approve` を持てるが、そのキーで開始したセッションのリクエストは承認できない。答え方は [承認待ちと再開](/sessions/waiting-and-resume) にある。

セッションを見られるからといって、そのセッションのリクエストに答えられるわけではない。権限リクエストと質問に答え、push・PR を承認するのは次の人だけである。

- セッションを作った人(API キーが作ったセッションならそのキー)
- そのセッションのエージェントの管理者
- ワークスペースの owner・admin

共有でセッションを見ているだけの人が答えると `403 FORBIDDEN`(`reason_code: role`)になり、リクエストは開いたまま残ってセッションは `needs_input` のままである。見られないセッションはこれまでどおり `404` である。`GET /v1/sessions/{id}/pending-requests` の `answerable` が、呼び出した人が答えられるかを示す。コンソールは `false` のとき、許可・拒否を理由とともに無効にして表示する。

## エージェント管理者

エージェントを作成した人が、そのエージェントの管理者になる。管理者は member であっても、そのエージェントのカード修正、リリース、有効化、認証情報の紐付け、管理者の指定、エージェントキーの発行を行える。人やチームを管理者として追加でき、チームの場合はそのチームのメンバー全員が管理者になる。owner・admin でなければ、新しく追加できるのは自分がチーム管理者(`lead`)のチームだけである。

エージェントには担当チームを一つ決められる。担当チームのチーム管理者(`lead`)はそのエージェントの管理者で、メンバー(`member`)は管理しない。owner・admin でなければ、自分が所属するチームだけを担当チームに選べる。担当チームに決まったチームは、そのエージェントをアーカイブするか担当チームを移すまで削除できない。

エージェントを見られる範囲は次のとおり。

| 誰が | 情報(名前・slug・説明・担当チーム・状態・有効なリリース) | 設定(カード・リリース・管理者・認証情報の紐付け・GitHub・Slack)の閲覧 | 設定の変更 |
| --- | --- | --- | --- |
| owner・admin | 読める | 読める | 変えられる |
| エージェント管理者(担当チームの `lead` を含む) | 読める | 読める | 変えられる |
| 担当チームの `member` | 読める | 読める | できない(`403`) |
| それ以外の member | 読める(下の設定が `none` なら見えない) | できない(`403`、設定が `none` なら `404`) | できない(`403`) |

<Callout>
以前は、member は自分が管理しないエージェントを一覧で見られず、担当チームの `member` も設定を読めなかった。今はすべての member が `GET /v1/agents`・`GET /v1/agents/counts` でワークスペースのエージェントを探せ、担当チームの `member` は設定を読める。`include=summary` の要約(管理者・認証情報の紐付け)は、設定を読めるエージェントにだけ付く。エージェントの設定を変えた receipt も、設定を読める人だけが読める。
</Callout>

### エージェントの外の member ができること

owner・admin、エージェント管理者、担当チームのメンバーをそのエージェントの内側と呼び、それ以外の member を外側と呼ぶ。外側の member がエージェントで何をできるかは、ワークスペースの設定二つが決める。変えられるのは owner・admin だけで(`PATCH /v1/workspaces/{id}/agent-access`)、変えるたびに receipt が残る。今の値は `GET /v1/auth/me` の `workspace.settings` にある。

| 設定 | 値 | 外側の member には |
| --- | --- | --- |
| `agent_outsider_access` | `use`(既定値) | 情報を読み、セッションを開始できる |
| | `view` | 情報だけ読める。セッション開始は `403 FORBIDDEN`(`reason_code: role`) |
| | `none` | エージェントが一覧になく、読むと `404`。セッション開始は `403` |
| `agent_outsider_session_visibility` | `managing_team`(既定値) | 担当チームがあるエージェントの `workspace` 共有セッションが、一覧・件数・詳細・イベント・使用量の最近の一覧に出ない |
| | `workspace` | そのセッションもすべての member が見る |

- `agent_outsider_access` は担当チームのないエージェントにも適用される。`agent_outsider_session_visibility` は担当チームがあるエージェントのセッションだけを絞る。
- 外側の member でも、自分が開始したセッションと、自分や自分のチームを指定して共有された(`people`・`team`)セッションは引き続き見える。
- どちらの設定も次のリクエストから、作成済みのセッションにも適用される。開いているイベントストリームは次の確認で切れる。担当チームを変えたときや、メンバーがチームから外れたときも同じである。
- 使用量の合計(セッション数・費用・成果数)は変わらず、最近の成果一覧から見られないセッションの行だけが抜ける。
- 共有範囲が `workspace` でも外側の member に見えないセッションは、`GET /v1/sessions/{id}/share` の `audience_limited` が `true` になる。

```bash
curl -sS -X PATCH "$API/v1/workspaces/$WID/agent-access" "${WEB[@]}" \
  -d '{"agent_outsider_access": "view"}' | jq -c '{agent_outsider_access, agent_outsider_session_visibility, changed: (.receipt_id != null)}'
```

```text
{"agent_outsider_access":"view","agent_outsider_session_visibility":"managing_team","changed":true}
```

`WID` は `GET /v1/auth/me` の `workspace.id` である。

<Callout>
以前は `workspace` 共有セッションをすべての member が見ていた。今は既定値が `managing_team` なので、担当チームを決めたエージェントのセッションはすぐに内側だけが見る。以前のように見せるには `agent_outsider_session_visibility` を `workspace` に変える。
</Callout>

[作成](/agents/create)の `AID` と `WEB` を引き続き使う。

```bash
curl -sS "$API/v1/agents/$AID/admins" "${WEB[@]}" | jq '{users: [.users[].email], teams}'
```

```text
{
  "users": [
    "owner@example.test"
  ],
  "teams": []
}
```

| リクエスト | 内容 |
| --- | --- |
| `POST /v1/agents/{id}/admins` `{"user_id"}` または `{"team_id"}` | 管理者の指定 |
| `DELETE /v1/agents/{id}/admins/users/{user_id}`, `…/teams/{team_id}` | 解除 |
| `PUT /v1/agents/{id}/managing-team` `{"team_id"}` | 担当チームの指定・変更 |
| `GET /v1/administered-agents` | 自分が管理しているエージェント |

## 認証情報の紐付け

カードには、使う認証情報の名前だけを `capabilities.credential_refs` に書く。値は Werft の外 (secret store、remote MCP server の接続) にある。その名前をこのエージェントが使ってよいという紐付けは、管理者が別途作成する。カードに書かれた名前のうち紐付けられていないものがあると、有効化は 409 `CREDENTIAL_UNBOUND` になる。

```bash
curl -sS "$API/v1/agents/$AID/credential-bindings" "${WEB[@]}" -d '{"credential_ref": "notion-token"}' \
  | jq '{credential_ref: .binding.credential_ref, created}'
curl -sS "$API/v1/agents/$AID/credential-bindings" "${WEB[@]}" | jq -c '[.items[].credential_ref]'
```

```text
{
  "credential_ref": "notion-token",
  "created": true
}
["notion-token"]
```

解除 (`DELETE /v1/agents/{id}/credential-bindings/{binding_id}`) は、動作中のセッションを止めない。次のセッションから遮断される。すぐに遮断するには、外部サービスでその認証情報を失効させる。
